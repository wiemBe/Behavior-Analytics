# Behavior Analytics 0.1.10

For the analyst: a world map of events per country (on the SOC Overview dashboard and at
`/geography`), clearer editors for custom rules and property watches, and "Log source volume" in
place of "Phase A" wherever a reader sees it. A page header's "Guide" link now shows once per
account and section, and one fixed "Guide" entry at the bottom of the left navigation reaches the
guide at any time. The interface is English only.

For the operator: a new page, **SIEM load** (`/admin/siem-load`), shows how much load the platform
puts on QRadar and how QRadar itself is doing; the same facts are on the API, in a command, in the
support bundle and in `doctor`. **The map's country now comes from a QRadar custom property, and
you must set that property's exact name** (or keep the old lookup with `GEO_COUNTRY_SOURCE=lookup`);
see the first item below. The schema head moves to `0047`.

## Before you upgrade

- **The map's country comes from a QRadar custom property (GEO-3).** 0.1.9 asked QRadar for the
  country with `GEO::LOOKUP` on the address. From 0.1.10 `GEO_COUNTRY_SOURCE` defaults to
  `property`: the search groups by a custom property that carries the country.
  `GEO_SOURCE_COUNTRY_PROPERTY` defaults to `Source Geographic Location` and
  `GEO_DESTINATION_COUNTRY_PROPERTY` defaults to empty. **Set each to the exact property name on
  your console.** A direction with an empty name is not collected and sends no search, so out of the
  box only the Source direction collects. Destination buckets stored by 0.1.9 stay until retention
  removes them (the map reads them as they are); after that the Destination map says "Not
  collected.". Before its
  first search the collector reads the console's custom-property list. If the named property is not
  there, no search is sent, the direction's watermark records "The country property “<name>” does
  not exist on this console. Set GEO_SOURCE_COUNTRY_PROPERTY to the property's exact name." (or
  `GEO_DESTINATION_COUNTRY_PROPERTY` for Destination), and `doctor` reports it: `watermarks` FAILs
  and the new `geo_country_source` check WARNs with `absent on <console>`. If the list cannot be
  read, no search is sent either, and `geo_country_source` FAILs. A name that is not a valid
  property name makes the settings refuse to load. To keep 0.1.9's behaviour set
  `GEO_COUNTRY_SOURCE=lookup`: both directions are collected with `GEO::LOOKUP` again. A value the
  property returns that is not a country the platform recognises is counted as Unparseable, never
  as a country. A direction switched between the two sources keeps its stored buckets, so a series
  can hold both kinds until retention (`GEO_RETENTION_DAYS`, 35) removes the old ones.
- **The interface is English only (LANG-1, LANG-2, LANG-3; decision D-41).** The language control
  on `/account` is gone. A `ba_locale=tr` cookie or an account with `ui_language = "tr"` still
  loads and is shown English, with no cookie rewrite and no reload. Nothing is deleted:
  `frontend/messages/tr/` and the Turkish tests stay exactly as they were at the git tag
  `checkpoint/bilingual-2026-11-02`, and the operator documents keep their existing Turkish text.
  To turn Turkish back on, set `ENABLED_LOCALES = ["en", "tr"]` in `frontend/src/i18n/locale.ts`
  and translate the keys added since the tag; the contract tests list them.
- **The schema head moves to `0047`.** Three additive migrations, run once in order.
  `0045_rule_match_window_start_index` (FIX-14) creates the btree
  `ix_rule_match_window_window_start` on `rule_match_window.window_start`: the daily
  `rule_match_retention` delete runs `WHERE window_start < :cutoff`, and the primary key
  `(instance_id, window_start)` does not serve that predicate alone, so each batch scanned the
  table. `0046_ariel_search_run` (ARL-1) creates the table `ariel_search_run`, with two indexes and
  no foreign keys. `0047_user_guide_seen` (GUIDE-3) adds the column `app_user.guide_seen` (JSONB,
  not null), which holds the guide sections an account has been shown; every existing account gets
  an empty list. Of the three, only 0047 touches existing rows, and only by filling its new
  column; no existing column or constraint changes. Downgrades drop the index, the table and the
  column. `alembic check` reports no drift.
- **The platform now records every Ariel search it sends (ARL-1).** One row per search: the caller
  (for example `WAF_COLLECTION` or `SCHEDULED_SEARCH`), the outcome, the time the platform waited,
  and the numeric cost fields QRadar's own status reports. A row never holds the query, a result row
  or a raw value. Rows are kept `ARIEL_SEARCH_RUN_RETENTION_DAYS` days (default 30, 1 to 3650) by
  a daily deleter that runs whether or not `RETENTION_ENABLED` is set. No setting is required.
- **A counted refusal carries the rate-limit window (FIX-14).** A request the default limit
  counted now carries `X-RateLimit-Limit`, `X-RateLimit-Remaining` and `X-RateLimit-Reset` even
  when it ends as a 401, 403, 404 or 422. `Retry-After` is written **only** on the 429. What is
  counted did not change: per client key and per path, the same limits, the same exempt health
  routes. 0.1.9's notes said `Retry-After` was on every limited response; that sentence stays as
  shipped and this is the correction.
- **`QRADAR_CONSOLE_FQDN` accepts `host:port` (FIX-13).** A host name with an optional `:port`
  (1 to 65535); a scheme or a path is refused. Omitted, it is the QRadar URL's host with the port
  removed. The MCP client dials the port; certificate verification matches the host.
- **A new or changed console gets its first inventory (FIX-13).** After `python -m app.cli.qradar
  add` commits an enabled console that is new, changed or re-enabled, the log-source and rule
  inventories are queued once for that console instead of waiting for the hourly beat. If the broker
  refuses, the row stays, `first inventory was not queued; the hourly beat will catch up` is printed
  and the exit code is unchanged. The installer summary prints `First inventory    queued` or
  `First inventory    not queued; the hourly beat will catch up`.
- **An 0.1.9 site upgrades directly.** `min_from` is `0.1.9`. A 0.1.8 site upgrades to 0.1.9 first.
  `qradar-dash` reads this file before it edits `.env`, loads a bundle or pulls an image, and
  refuses an older site with `upgrade refused: 0.1.10 requires at least 0.1.9; nothing was
  changed`.

## New for the operator

- **SIEM load page (ARL-2).** `/admin/siem-load`, under Administration in the navigation, needs
  `admin:*`. Its first screen answers "how much are we loading QRadar, and how is QRadar doing":
  our searches in flight (active and stale), permit slots held against the cap, the last 5, 15 and
  60 minutes (submitted, completed, failed, refused, wall time p50 and p95), and a panel per
  console. Below it are the in-flight table and a per-caller summary for 1 h, 24 h, 7 d or 30 d
  (`?range=`). The top bar's Refresh re-reads it; the page has no timer of its own. Each QRadar field
  shows its own state (read, Not collected, Forbidden, Failed) and the reason; a field that was not
  read is never drawn as a zero or as healthy.
- **The same facts without the page (ARL-1, ARL-3).**
  `GET /api/v1/admin/ariel-load?hours=N` (1 to 720, default 24) summarises a window per caller;
  `GET /api/v1/admin/ariel-load/current` is the load now (in flight, permit slots, last 5/15/60
  minutes) plus a `qradar` list with one entry per enabled console. Both need `admin:*`.
  `docker compose exec -T backend python -m app.cli.ariel_load [--hours N | --current] [--json]`
  prints the same as a table or JSON; `--current` always asks QRadar afresh. `./qradar-dash
  support-bundle` adds `ariel-load.json` (or `ariel-load.error.txt` when it cannot be read) to the
  archive. An empty window says so; it is not a row of zeros.
- **QRadar's own health, read-only (ARL-3).** Per console: reachability and API latency, version,
  managed hosts by status, EPS against its allocation, the license pool, and how many Ariel search
  ids QRadar holds. Only GET requests are sent. "Held" is what QRadar keeps for every user,
  finished or active; it is not a count of running searches. QRadar's answers are reused for
  `QRADAR_HEALTH_CACHE_TTL_SECONDS` (default 30, 5 to 600) per API process, and each entry says
  whether it was cached and how old it is. The MCP provider does not support these reads, and the
  fields say so.
- **Two new `doctor` checks.** `qradar_health` (OPS-R67) WARNs when a managed host is not `ACTIVE`,
  when average EPS is over 90 % of the allocation, or when the license pool is over-allocated; it
  SKIPs when the console does not answer or nothing could be read. **A lab CE console has an
  over-allocated license, so `doctor` WARNs there permanently; that is expected.**
  `geo_country_source` (OPS-R30) is described in the first item above.
- **The world map is on the default dashboard.** The "SOC Overview" template places `map.geography`
  across the bottom (12 columns by 18 rows). Its configuration is the address direction (Source, the
  default, or Destination) and the range (1 hour, 24 hours or 7 days); it drills to
  `/geography?direction=…`. `/geography` is under Behavior in the navigation and lists every
  country; the widget lists the top five. Both need `read:geo`; a role without it sees the widget's
  forbidden sentence naming the permission.
- **The map says what it does not know.** "Not collected." means nothing was collected for that
  direction in the range; "Insufficient data." means buckets were collected but no country could be
  assigned; "Partial" means some buckets are missing; "At least" and "≥" mark a lower bound. A
  country with no events is drawn as "No data", never as the lowest class. None of these draws a
  zero. **Stale (GEO-5):** the answer is judged by the `GEO_COLLECTION` cadence like every widget. A
  stale widget keeps the map and adds a warning line ("Stale: the latest data is from <time> UTC,
  <age> old."); `/geography` shows the same age line and the top bar shows "Data to …". The SOC
  Overview template is now version 2: a dashboard created from it records 2, and a saved dashboard
  keeps the version it was created with.
- **"Log source volume" instead of "Phase A" (POL-11).** The family name, the search-cadence page,
  the installer summary and the retention line say so. `doctor`'s `families_off` line names the
  always-on family `LOG_SOURCE_VOLUME`. The API and the database keep `PHASE_A_VOLUME`; nothing
  stored changes.
- **There is no user delete (GUIDE-2).** Removing access is disabling the account (`POST
  /api/v1/users/{id}/disable`): the account row is kept, `disabled_at` is set, its sessions are
  revoked and a `user.disable` audit record names the actor. The last active administrator still
  cannot be disabled.
- **The documents name the right template and page (DOC-5).** The Scheduled searches widget lives
  in the "QRadar Administration" template, and `/admin/search-cadence` shows the same data.
  `docs/FIELD-MAPPING.md` states the threshold rule: thresholds apply to the fields collection
  reads. The manual test's installer check asks which of the address lines appeared.

## For the analyst

- **The world map** (see above). The widget and the page share one body, so every state reads the
  same in both. The page says where the country came from ("From the QRadar property “…”" or "From
  the GeoIP lookup of the address") and what "Unresolved" means for that source.
- **The custom rule editor speaks words (POL-10).** The operator options are "above", "at or above",
  "below", "at or below", "equal to" (and the recovery forms); units are "events/bucket",
  "requests/bucket", "events/s", "share". Metric, Operator, Threshold, Sustain, Recovery, Window and
  Severity each have a "?" that opens on hover, keyboard focus or a click and closes on Escape or
  blur.
- **The metric note is the analyst's (POL-13).** Under Metric, each of the eleven catalog metrics
  has a sentence about what it reads and when it is exact, partial or a lower bound. A metric the
  frontend has no text for shows no note.
- **New combination says why it is off (POL-14).** "Choose the scope first." with no scope; "Needs
  two properties." with a scope and room for a second property, plus an "Add a second property"
  button that moves focus to the new picker; at the catalog ceiling, the existing validation
  sentence.
- **The add-source control is in the page header (POL-12).** On `/admin/ips-sources` and
  `/admin/waf-sources`; a load error shows the notice and no button.
- **A failed session says what the server said (POL-9).** The detail is its own clause: "The server
  said: internal error."; no detail gives no clause. The sign-in-required, rate-limited and error
  notices sit at the top at the sign-in form's width (POL-8).
- **The in-app guide matches this release (GUIDE-2).** Its account section covers the password
  only, and its users section says there is no delete.
- **The "Guide" link in a page header shows once (GUIDE-3).** The first time an account opens a
  page, its header shows the small "Guide" link to that page's guide section; from the next visit
  to a page of the same section it does not. What was shown is stored on the account
  (`guide_seen`), so it follows the analyst to another browser, not just to the next visit. The
  Sources list and a source's detail page share one section, so seeing one hides the other's link.
  One "Guide" entry stays fixed at the bottom of the left navigation on every page: it opens the
  current page's guide section, or the guide's index on a page that has none. The navigation list
  scrolls above it, so it never covers an item. If the session cannot store the choice (a
  development principal with no account), the header link shows on every visit.

**Known limits.** A country the 1:110m outlines do not draw (Singapore, Malta and other
micro-states) is named under the map and kept in the table. Kosovo cannot be collected (`XK` is not
an ISO 3166-1 code). The map's canvas is described to assistive technology by its label only; the
table beside it carries every figure. Out of the box nothing new is collected for Destination
until `GEO_DESTINATION_COUNTRY_PROPERTY` names a property. On the SIEM load page, "Failed" is computed in
the browser from errors, cancellations, timeouts and "Ariel unavailable". A search whose worker died
stays "in flight" in the database until retention removes it; the page lists it as stale after the
longest wait a search may have, plus 30 seconds. A rate-limited refresh on a widget that already
shows data keeps the data and the short note only.

## API

No existing field changes meaning and no request shape changes.

- **New:** `GET /api/v1/admin/ariel-load` and `GET /api/v1/admin/ariel-load/current` (`admin:*`),
  described above.
- **`GET /api/v1/geo/countries`** gains `country_source` (`PROPERTY` or `LOOKUP`),
  `country_property` (null in lookup mode or with no name), `latest_bucket_end` (null while Not
  collected), and the code and params of the unresolved note.
- **A counted response carries the rate-limit window** (FIX-14): `X-RateLimit-Limit`,
  `X-RateLimit-Remaining` and `X-RateLimit-Reset` on a 200 and on a counted 401, 403, 404, 422 or
  429. `Retry-After` is present only on the 429. The exempt health routes carry no window.
- **`GET /api/v1/me`** gains `guide_seen`: the list of guide section ids the account has been
  shown (`null` for a development principal with no account).
- **New:** `POST /api/v1/me/guide-seen` with `{"section": "<guide section id>"}` (a lower-case
  slug, 1 to 64 characters) adds a section to the caller's own list. It needs a session and no
  permission, answers 204, and recording a section already in the list changes nothing. A new
  section past 200 entries is refused with 409 (`account.guide_seen.full`). No route reads or
  writes another account's list, and no audit record is written.
- **`GET /api/v1/version`** reports `migration_head` `0047` after the upgrade.

## Schema

The head is `0047`. 0.1.10 adds three migrations: `0045_rule_match_window_start_index` (the index on
`rule_match_window.window_start`), `0046_ariel_search_run` (the table `ariel_search_run`, indexed
on `(instance_id, submitted_at)` and on `submitted_at`, not a hypertable) and
`0047_user_guide_seen` (the column `app_user.guide_seen`, JSONB, not null, `[]` for every existing
account). All three are additive, need no backfill beyond that empty list and leave `alembic check`
clean. A site coming from 0.1.9 runs them once, in order. A
rollback is a restore of the upgrade's backup, as always; no migration is ever run downward on a
site.

## Upgrade

```bash
git fetch --tags && git checkout v0.1.10
./qradar-dash upgrade 0.1.10
```

The upgrade is allowed from `0.1.9`. A site on 0.1.8 upgrades to 0.1.9 first; the 0.1.9 notes
describe that path. An older release is refused before anything is touched (FIX-12): the refusal
comes from the checkout's own `docs/releases/0.1.10.md`, read before any `.env` edit, bundle load
or pull — `upgrade refused: 0.1.10 requires at least 0.1.9; nothing was changed`. If that file is
missing, unreadable or not for 0.1.10, the refusal names the file and changes nothing either. The
migrations run once (`Running upgrade 0044 -> 0045`, then `0045 -> 0046`, then `0046 -> 0047`), and after the upgrade
`/api/v1/version` reports `migration_head` `0047`. The upgrade takes its own backup before it
migrates, as every upgrade does, and that backup carries the install answers. The collection
families resume on their cadence; the pages show "stale" or "not collected" until the first cadence
after the upgrade has passed, and that is correct.

**After the upgrade, set the geography property names in `.env` (or `GEO_COUNTRY_SOURCE=lookup`),
recreate the backend, worker and beat containers so they read it, and check `./qradar-dash doctor`
for `geo_country_source`.** The map shows "Not collected." until `GEO_COLLECTION` has run for the
chosen direction and range.

On a host with no registry access, make the bundle on a connected host from the same checkout
(`./qradar-dash bundle --output DIR` writes `qradar-dash-0.1.10-bundle.tar` in that directory;
without `--output` the file is written in the current directory, and an existing file is not
overwritten), copy it over, and run, in the installation directory:

```bash
tar -xf /path/to/qradar-dash-0.1.10-bundle.tar --exclude=images.tar
./qradar-dash upgrade 0.1.10 --offline /path/to/qradar-dash-0.1.10-bundle.tar
```

If the upgrade fails and the site must return to 0.1.9, follow `docs/OPERATIONS.md`, "Geri alma
(`rollback`)": it restores the backup the upgrade took — including the install answers and the
`0044` schema — and starts the previous images. Data written since the upgrade is kept only in the
broken copy it leaves. `rollback` runs no `git checkout`; after a successful rollback the operator
returns the checkout to the version that now runs (`git checkout v0.1.9`), as that section says. A
return to 0.1.10 is then `git fetch --tags && git checkout v0.1.10` and
`./qradar-dash upgrade 0.1.10`.
