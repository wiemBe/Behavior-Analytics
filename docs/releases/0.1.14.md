# Behavior Analytics 0.1.14

For the analyst: an active anomaly is listed and counted whatever its age, so the "Active anomalies, now" card and the list can no longer disagree; the `/anomalies` empty state counts and links every active anomaly; the `/` tab title carries the product name; a SIEM load part with no reason no longer prints an empty "Reason:" line; and the QRadar health notifications part says "not collected" when the console has no enabled System Notification log source. The schema head stays `0054`: there is no migration.

For the operator: `GET /anomalies?active_only=true` without `since` has no lower bound (an API behaviour change of 0.1.13's UX-2); the notification part has two new coded reasons, and a console without that source records the QRadar health run as failed; `qradar-dash` no longer accepts a state path that holds a control character; and the cadence and Ariel permit documents now name every family and the real permit bound.

## Before you upgrade

- **No migration; the head stays `0054`.** The newest file in `backend/alembic/versions/` is `0054_ariel_caller_access_check.py`, and this release changes no model and no migration, so `alembic check` reports no drift.
- **A 0.1.13 site upgrades directly.** `min_from` is `0.1.13`. A 0.1.12 site upgrades to 0.1.13 first. `qradar-dash` reads this file before any `.env` edit, bundle load or pull and refuses an older site with `upgrade refused: 0.1.14 requires at least 0.1.13; nothing was changed`.
- **No setting, default or cadence changes.** Nothing in `.env` needs an edit. `API_MAX_RANGE_DAYS` (365 by default) still bounds every explicit time range; it no longer bounds an active-only list that is sent without `since` (see "For the operator").

## For the analyst

- **An active anomaly is listed and counted whatever its age (ANOM-1).** The Dashboard's "Recent anomalies" widget, the search box (TopSearch), the WAF and IPS widgets, and the Behavior pages read the list with `active_only=true` and no start time. That list used to stop at `API_MAX_RANGE_DAYS` (365 days by default), so an active anomaly older than that was in the "Active anomalies, now" card but in neither the list nor its `active_by_family` counts. It now has no lower bound: every active anomaly up to now is listed and counted, whatever its age, so the card and the list hold the same population.
- **The `/anomalies` empty state counts and links every active anomaly (UX-6, ANOM-1).** When the page finds no anomaly in its 24-hour window and active anomalies exist before it, it says how many and offers a link. The count now reads the active list with no start time, so it covers every active anomaly whatever its age, and the link opens `/anomalies?active_only=true` — the same population. The link text is "Show every active anomaly". Both used to stop at 364 days, so the count could be smaller than the list it led to.
- **The `/` tab title reads "Dashboard · Behavior Analytics" (UX-6).** It read only "Dashboard"; every other route already carries the suffix. The title is built from the same catalog key as the other routes, so no new string was added.
- **`/admin/siem-load` no longer prints an empty "Reason:" line (UX-6).** A part of the page that could not be read shows its "Not read" pill and a reason only when the API gave one. Before, a part with no reason printed `Reason:` with nothing after it, and one case printed `Reason: Not read`.
- **The QRadar health notifications part says "not collected" when the console cannot report a notification (HLT-8).** An empty notification answer on `/admin/siem-load` is "none" only when the console has at least one enabled `System Notification` log source. Without one the part is "Not collected" with the sentence "The console has no enabled System Notification log source, so an empty notification answer does not show that nothing happened." If the stored log-source inventory could not be read, it is "Not collected" with its own sentence. A console with an enabled source still shows "none" for an empty answer.

## For the operator

- **`GET /anomalies?active_only=true` without `since` has no lower bound (ANOM-1).** This is an API behaviour change of 0.1.13's UX-2. In 0.1.13 that read reached back to `API_MAX_RANGE_DAYS` (365 days by default); it now reaches back as far as the active set goes, with no lower bound at all, so `API_MAX_RANGE_DAYS` no longer applies to it. An explicit `since` or `until` is used as sent, and both are still validated against the same ceiling (a range beyond it is a 422). `GET /anomalies/summary`'s `active_by_family` counts the same population, so its four totals add up to the `total` of `GET /anomalies?active_only=true`. A script that relied on the 365-day bound will see older rows. The statement's cost is linear in the incident table rather than in the window: ANOM-1 measured about 17 to 19 ms at 250,000 incident rows and about 29 to 32 ms at 500,000, and no index was added.
- **The notification part has two coded reasons, and such a run reads as failed (HLT-8).** The codes are `notification_source_missing` (the console has no enabled `System Notification` log source) and `notification_source_unreadable` (the stored log-source inventory could not be read); both are `qradar_health_detail.reason.*` entries of the backend message catalog, with their English texts. `GET /admin/qradar-health/latest` and the `/admin/siem-load` page show the stored sentence. (`/admin/qradar-health/history` carries no notification part.) The collector counts any `NOT_COLLECTED` part as a partial failure, so `/admin/search-cadence` shows the `QRADAR_HEALTH` run as "Failed" for that window even when nothing is wrong; the `notifications_hours` roll-up counts only `OK` and `PARTIAL` windows, so it skips that window.
- **`qradar-dash` no longer accepts a state path that holds a control character (CI-8).** `valid_state_path` tested for control characters through a `printf | grep -q` pipeline; under `set -o pipefail`, `grep` exiting on the first match could make `printf` take SIGPIPE, and the `!` then turned the failed pipeline into success, so such a path could be accepted instead of refused. The guard now uses bash's own pattern test, with no pipe, so the refusal is certain. A damaged `.qradar-dash/state.json` now gets the refusal the guard was meant to give: `repair-state refused: .qradar-dash/state.json field last_upgrade.backup is invalid or missing. … Nothing was written.`
- **The cadence and Ariel permit documents name every family (DOC-9).** `docs/CONFIGURATION.md` now lists every search family's seeded cadence and switch: six default to five minutes, and WAF collection, IPS collection and QRadar health to fifteen. `docs/ARIEL-PERMIT.md` now names the `QRADAR_HEALTH` and `doctor --aql` searches and states the real bound: the global pool admits `G` = 6 searches and the per-console pool `P` = 3, whatever the process count.

## Manual test

## Schema

No migration; head `0054`. `/api/v1/version` reports `migration_head` `0054` before and after the upgrade.

## Upgrade

```bash
git fetch --tags && git checkout v0.1.14
./qradar-dash upgrade 0.1.14
```

The upgrade is allowed from `0.1.13`. A site on 0.1.12 upgrades to 0.1.13 first; the 0.1.13 notes describe that path. An older release is refused before anything is touched: the refusal comes from the checkout's own `docs/releases/0.1.14.md`, read before any `.env` edit, bundle load or pull — `upgrade refused: 0.1.14 requires at least 0.1.13; nothing was changed`. If that file is missing, unreadable or not for 0.1.14, the refusal names the file and changes nothing either.

No migration runs, so the migrate step prints no `Running upgrade` line. `alembic upgrade head` still opens the database, so Alembic's two start-up lines (`INFO  [alembic.runtime.migration] Context impl PostgresqlImpl.` and `INFO  [alembic.runtime.migration] Will assume transactional DDL.`, shown by `docker compose logs --no-color --no-log-prefix migrate` and in the upgrade's own output) are expected, and the migrate container exits with 0. `upgrade` prints the decision pair twice, both times with `0054`: before the writers stop and after the new stack has started. The upgrade takes its own backup before it migrates, as every upgrade does, and that backup carries the install answers. The restart empties Redis, as in every upgrade. The collection families resume on their cadence; the pages show "stale" or "not collected" until the first cadence after the upgrade has passed, and that is correct.

On a host with no registry access, make the bundle on a connected host from the same checkout (`./qradar-dash bundle --output DIR` writes `qradar-dash-0.1.14-bundle.tar` in that directory; without `--output` the file is written in the current directory, and an existing file is not overwritten), copy it over, and run, in the installation directory:

```bash
tar -xf /path/to/qradar-dash-0.1.14-bundle.tar --exclude=images.tar
./qradar-dash upgrade 0.1.14 --offline /path/to/qradar-dash-0.1.14-bundle.tar
```

If the upgrade fails and the site must return to 0.1.13, follow `docs/OPERATIONS.md`, "Geri alma (`rollback`)": it restores the backup the upgrade took — including the install answers and the `0054` schema, which is the head the site had before the upgrade — and starts the previous images. Data written since the upgrade is kept only in the broken copy it leaves. `rollback` runs no `git checkout`; after a successful rollback the operator returns the checkout to the version that now runs (`git checkout v0.1.13`), as that section says. A return to 0.1.14 is then `git fetch --tags && git checkout v0.1.14` and `./qradar-dash upgrade 0.1.14`.
