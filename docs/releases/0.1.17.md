# Behavior Analytics 0.1.17

A fresh install is the recommended path for this release. A 0.1.16 site can also upgrade directly
(`min_from` is `0.1.16`).

## Install or upgrade (offline)

1. Copy `qradar-dash-0.1.17-bundle.tar`, `qradar-dash-0.1.17-docs.tar` and `SHA256SUMS-transfer.txt` to the host, then check them:
   `sha256sum -c SHA256SUMS-transfer.txt`.
2. Fresh install, in a new directory:
   `mkdir qradar-dash-0.1.17 && tar -xf /path/to/qradar-dash-0.1.17-bundle.tar -C qradar-dash-0.1.17 --exclude=images.tar`,
   then `cd qradar-dash-0.1.17 && ./qradar-dash install --offline /path/to/qradar-dash-0.1.17-bundle.tar`.
3. Upgrade of a 0.1.16 site, from its installation directory (it holds `.env`, `.secrets/`, `.qradar-dash/state.json`):
   `tar -xf /path/to/qradar-dash-0.1.17-bundle.tar --exclude=images.tar`, then
   `./qradar-dash upgrade 0.1.17 --offline /path/to/qradar-dash-0.1.17-bundle.tar`. The upgrade takes its own backup first.
4. Check: `./qradar-dash doctor` (no `FAIL`) and `curl -fsS https://<host>/healthz`.
   Full detail: `docs/INSTALL.md`, "Offline hosts".

## What is new

- **Feature switches at runtime.** Administration → Features turns each family on or off without a restart
  (`python -m app.cli.features` offline). A switch row wins over `.env`.
- **A bad `.env` value no longer stops the application.** A malformed switch is treated as off and a malformed list
  setting falls back to its default. `doctor` reports it as `settings_problems` (WARN). Critical settings still refuse
  startup as before.
- **`/healthz`.** One public URL tells whether the whole application is up: API, database, migrations, Redis, workers,
  walker and beat. It answers `200 ok` or `503 degraded`, with `ok`/`fail`/`unknown` per component only. It is cached for 10 s.
- **JDBC log sources** (Log Sources → JDBC): configuration, connection and flow for JDBC and JDBC-like sources.
- **QRadar source pauses** (switch `qradar_source_pause_enabled`, **off by default**). A source that is disabled in QRadar,
  or missing from two consecutive complete inventory passes, stops raising NO_EVENTS. Its open incidents close without
  a verdict, and its paused time is left out of training. A mass disappearance is held, never applied; see
  `python -m app.cli.inventory absence show|accept`. Enable it in the order described in `docs/INSTALL.md`.
- Also in this release: identity monitoring, notification webhooks, reports, configuration export/import, rule
  silence and storm detection, training exclusions, and the slim QRadar API field lists, which are fixed for real
  consoles (FIX-94).

## Defaults that changed

| Setting | 0.1.16 | 0.1.17 | Turn off with |
|---|---|---|---|
| `JDBC_COLLECTION_ENABLED` | — | `true` | `.env` `false` or Features |
| `RULE_MATCH_COLLECTION_ENABLED` | `false` | `true` | `.env` `false` or Features |
| `RULE_ALERTING_ENABLED` | `false` | `true` | `.env` `false` or Features |
| `QRADAR_SOURCE_PAUSE_ENABLED` | — | `false` | — |

The rule-match search scans every event in its window, so its cost follows event volume. Watch its time on the Search
cadence page after the upgrade. If `.env` lowers `RULE_MATCH_MAX_WINDOWS_PER_RUN` and does not set the repair bound, the
repair bound follows it automatically. An explicit contradictory value still refuses startup.

## Notes

- **Schema head `0077`.** Fourteen additive migrations run once (`0064` to `0077`).
- **Nothing in this release writes to QRadar.**
- **Known issue.** After `absence accept` a held mass absence is accepted once. If no confirming pass follows, the
  acceptance stays armed. Check `absence show` after using it.
