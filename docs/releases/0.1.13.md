# Behavior Analytics 0.1.13

For the analyst: the anomaly views are more honest about what they cover. The `/anomalies` empty state names its window, a list of active anomalies is no longer cut to 24 hours, the "Active anomalies, now" card counts every family, times on another day carry their date, ages keep two units, and the status pill says "Checking" until it has answers.

For the operator: the anomaly list with `active_only=true` and no `since` now reaches back to `API_MAX_RANGE_DAYS` instead of 24 hours (an API behaviour change); `GET /anomalies/summary` has a new, additive `active_by_family` field; and the Ariel search-log warning has new text. The schema head stays `0054`: there is no migration.

## Before you upgrade

- **No migration; the head stays `0054`.** The newest file in `backend/alembic/versions/` is `0054_ariel_caller_access_check.py`. `alembic check` reports no drift.
- **A 0.1.12 site upgrades directly.** `min_from` is `0.1.12`. A 0.1.11 site upgrades to 0.1.12 first. `qradar-dash` reads this file before any `.env` edit, bundle load or pull and refuses an older site with `upgrade refused: 0.1.13 requires at least 0.1.12; nothing was changed`.
- **No setting, default or cadence changes.** Nothing in `.env` needs an edit. One existing setting now bounds more: `API_MAX_RANGE_DAYS` (365 by default) is the reach of the active-only anomaly list (see "For the operator").

## For the analyst

- **The `/anomalies` empty state names its window (UX-1).** With no filter, an empty list used to say only that no anomaly was detected. It now says `No anomalies were detected in the window this page asked for: the last 24 h, <from> to <to>. Set the Start time (UTC) filter to look further back.` (the two times are UTC). When active anomalies exist outside that window, it adds how many (`3 active anomalies were detected before this window.`) and a link, "Show active anomalies from the last year" (active only, from 364 days back). If that count cannot be read, the sentence carries no number: it never shows a zero. The sentence about sources without a baseline follows. The filtered case ("No anomalies match these filters. …") is unchanged.
- **A list of active anomalies is no longer cut to 24 hours (UX-2).** The Dashboard's "Recent anomalies" widget, the search box (TopSearch), the WAF and IPS widgets, and the Behavior pages read the list with `active_only=true` and no start time. They used to see only the active anomalies detected in the last 24 hours, so a widget could say "No active anomalies" while the "Active anomalies, now" card counted some. They now show every active anomaly up to `API_MAX_RANGE_DAYS` (365 days by default).
- **"Active anomalies, now" counts every family, and its parts sum to it (UX-3).** The total is the active anomalies of log sources, WAF endpoints, IPS and property watches. The card has a "Log sources" line (spikes, drops, silent, other), an "Also" line (WAF, IPS, property watches) and a "Lifecycle" line (open, candidates, recovering); each count carries its noun. A family the page could not read is named (`WAF not read`), never drawn as a zero, and the total becomes a lower bound (`≥ 5`) with the note "At least this many: a family could not be read." If no family could be read, the figure is a dash with "not read". When the detector split is not available, "Log sources" shows one part (`3 log sources`). The line "N log sources not judged" now says log sources.
- **Times on another day carry their date (UX-1).** The "Stale: the latest data is from <time>, <age> old." line and the "Data to <time>, <age>." line of a Dashboard widget, and the Geography page's age line, show `2026-11-03 14:02:11 UTC` when the instant is not on the current UTC day, and `14:02:11 UTC` when it is. The "Data to" clock in the top bar is unchanged: it shows the clock only.
- **Ages keep two units (UX-4).** An age shows its largest unit and the one below it, floored: `1 d old`, `3 h 20 min`, not `1 d 7 min 40 s`. Zero parts are dropped (`1 d 0 h` is `1 d`). Configured values (a cadence, an interval, a range) still show every unit, so `1 h 1 s` stays whole.
- **`/login` sends a signed-in account on (UX-1).** An account that already has a session no longer sees the sign-in form: the page shows "Loading the sign-in form…" while it reads the account, then goes to the `next` address, to `/` without one, or to the password page when the password must be changed. An anonymous visitor, or a session that cannot be read, sees the form.
- **The status pill says "Checking" until it has answers (UX-1).** In the top bar, while any of the connection signals is still loading and none has answered with a problem, the control reads "Checking" with no colour. It used to read "Unknown" in that interval. An answered problem still wins.
- **A Dashboard box below the first screens says it is read when scrolled into view (UX-4).** The grid mounts the boxes that are more than about two screens down only when they scroll near. Until then such a box showed "Loading …" although no read had started; it now reads `<Title> is read when this box scrolls into view.` (for the Geography map: "Geography is read when this box scrolls into view."). After scrolling, the box shows its data or its own error state, which names the HTTP status and links to the route that owns the data.
- **"Load by caller" fits at 1024 (UX-5).** On `/admin/siem-load`, a long caller name now wraps inside its cell, so the table no longer scrolls sideways inside its frame at 1024×768 and 1280×800. Type size is unchanged.
- **A Geography box with no map is as tall as its text (UX-5).** In the Dashboard's fixed grid, a Geography box in "Not collected" or "Insufficient data" no longer leaves an empty frame below its sentences. The map state keeps its size, and the drag-and-resize grid is unchanged.

## For the operator

- **`GET /anomalies` with `active_only=true` and no `since` reaches back to `API_MAX_RANGE_DAYS` (UX-2).** This is an API behaviour change. Without `since`, the list still covers the last 24 hours of detections. With `active_only=true` and no `since`, the default start is now `API_MAX_RANGE_DAYS` before the end (365 days by default), because an active anomaly is active whatever its age. An explicit `since` or `until` is used as sent, and both are still validated against the same ceiling (a range beyond it is a 422). `API_MAX_RANGE_DAYS` is the setting that bounds it. A script that read the active list and expected only the last day will see older rows. The query was measured at about 18 ms for 250,000 anomaly rows over 347 days, with no index added (UX-2 report).
- **`GET /anomalies/summary` has a new field, `active_by_family` (UX-3).** It is additive: every existing field keeps its meaning (the Phase A counts such as `open_anomalies`, `spikes`, `drops` still count log-source anomalies of any age). `active_by_family` holds `log_source`, `waf`, `ips` and `property_watch`, each with `open`, `candidate`, `recovering` and `total`. It is read in one statement over the same window as the active list (back to `API_MAX_RANGE_DAYS`), so the four totals add up to the `total` of `GET /anomalies?active_only=true`. `docs/API.md` describes it. An older client ignores it.
- **The Ariel search-log warning has new text (FIX-29).** A failed write while a search is recorded is still counted and never fails the search, but the warning line changes from `ariel search log flush failed rows=<n>` to `ariel search log write failed what=<what> rows=<n>`, where `<what>` is `submit` (the in-flight INSERT), `flush` (the run's write) or `lookup` (no bind or no engine to write on). An alert or a `grep` on the old text must be changed to the new one.

## Upgrade

```bash
git fetch --tags && git checkout v0.1.13
./qradar-dash upgrade 0.1.13
```

The upgrade is allowed from `0.1.12`. A site on 0.1.11 upgrades to 0.1.12 first; the 0.1.12 notes describe that path. An older release is refused before anything is touched: the refusal comes from the checkout's own `docs/releases/0.1.13.md`, read before any `.env` edit, bundle load or pull — `upgrade refused: 0.1.13 requires at least 0.1.12; nothing was changed`. If that file is missing, unreadable or not for 0.1.13, the refusal names the file and changes nothing either.

No migration runs, so the migrate step prints no `Running upgrade` line. `alembic upgrade head` still opens the database, so Alembic's two start-up lines (`INFO  [alembic.runtime.migration] Context impl PostgresqlImpl.` and `INFO  [alembic.runtime.migration] Will assume transactional DDL.`, shown by `docker compose logs --no-color --no-log-prefix migrate` and in the upgrade's own output) are expected, and the migrate container exits with 0. `upgrade` prints the decision pair twice, both times with `0054`: before the writers stop and after the new stack has started. The upgrade takes its own backup before it migrates, as every upgrade does, and that backup carries the install answers. The restart empties Redis, as in every upgrade. The collection families resume on their cadence; the pages show "stale" or "not collected" until the first cadence after the upgrade has passed, and that is correct.

On a host with no registry access, make the bundle on a connected host from the same checkout (`./qradar-dash bundle --output DIR` writes `qradar-dash-0.1.13-bundle.tar` in that directory; without `--output` the file is written in the current directory, and an existing file is not overwritten), copy it over, and run, in the installation directory:

```bash
tar -xf /path/to/qradar-dash-0.1.13-bundle.tar --exclude=images.tar
./qradar-dash upgrade 0.1.13 --offline /path/to/qradar-dash-0.1.13-bundle.tar
```

If the upgrade fails and the site must return to 0.1.12, follow `docs/OPERATIONS.md`, "Geri alma (`rollback`)": it restores the backup the upgrade took — including the install answers and the `0054` schema, which is the head the site had before the upgrade — and starts the previous images. Data written since the upgrade is kept only in the broken copy it leaves. `rollback` runs no `git checkout`; after a successful rollback the operator returns the checkout to the version that now runs (`git checkout v0.1.12`), as that section says. A return to 0.1.13 is then `git fetch --tags && git checkout v0.1.13` and `./qradar-dash upgrade 0.1.13`.
