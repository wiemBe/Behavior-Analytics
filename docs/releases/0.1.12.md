# Behavior Analytics 0.1.12

For the analyst: nothing changes in the interface.

For the operator: two fixes. `./qradar-dash upgrade` no longer refuses a healthy site when the `doctor` report is longer than one pipe write, and the offline bundle's link and path check no longer misses a bad member in a long listing. A failure to look up the database engine while an Ariel search is recorded no longer fails the search. The schema head stays `0054`: there is no migration.

## Before you upgrade

- **No migration; the head stays `0054`.** The newest file in `backend/alembic/versions/` is `0054_ariel_caller_access_check.py`. `alembic check` reports no drift.
- **A 0.1.11 site upgrades directly.** `min_from` is `0.1.11`. A 0.1.10 site upgrades to 0.1.11 first. `qradar-dash` reads this file before any `.env` edit, bundle load or pull and refuses an older site with `upgrade refused: 0.1.12 requires at least 0.1.11; nothing was changed`.
- **No setting, default or cadence changes.** Nothing in `.env` needs an edit.

## Fixes

- **`upgrade` no longer refuses a healthy site on a long `doctor` report (FIX-28).** The wrapper tested the report with `printf … | grep -q` under `set -o pipefail`. `grep -q` leaves at its first match, the writer then gets SIGPIPE and the pipeline reports 141, which an `if` read as "no match". When the report was longer than one pipe write, `upgrade` could print `upgrade refused: doctor did not report db_connect and migration_head as PASS` for a site where both lines were PASS, before the upgrade (the pre-check) or after it (the runtime check, which then started the automatic rollback). Every such test now reads the report from a here-string, so there is no pipe to break.
- **The offline bundle's link and path check could miss a bad member (FIX-28).** 0.1.11 has this second fault. `bundle_precheck` tested the `tar -tv` listing for link members and for absolute or parent-directory paths with the same pipe form, so on a long listing the check could pass a bundle it should have refused. It is fixed in the same way (the path test now lets `grep` read to the end). What still guarded such a bundle in 0.1.11:
  - `bundle_load` extracts with `tar -xf`, and GNU tar's defaults refuse a `..` member (the command fails and `bundle_load` stops with `cannot extract the bundle`) and strip a leading `/`, so nothing lands outside the temporary directory.
  - After extraction, `sha256sum -c` must pass and every extracted regular file must be named in `SHA256SUMS`, or `bundle_load` stops with `nothing was loaded`, before `docker load`.
  - A bundle made by `./qradar-dash bundle` never holds a link, an absolute path or a `..` member: it archives fixed relative names from its own staging directory.
- **A raising engine lookup never fails an Ariel search (FIX-27).** Recording a search asks for the worker's database engine. If that lookup itself raised, the search could fail. The lookup is now guarded: recording a submit counts one failed write, a poll refresh and a terminal close are skipped like a failed statement, and a flush counts its rows as failed. The search itself runs and returns as before. The counter is public as `count_write_failure`; `write_failure_count()` is unchanged. `doctor --aql` keeps its verdicts and its exit code when the lookup raises.

## Manual test

`docs/MANUAL-TEST.md` is now the 0.1.11 → 0.1.12 guide, with its results page. It has six new checks, MT-137 to MT-142, for alert e-mail and the abandoned-search reaper. None of them is core: the core stays 38 checks.

## Schema

No migration; head `0054`. `/api/v1/version` reports `migration_head` `0054` before and after the upgrade.

## Upgrade

```bash
git fetch --tags && git checkout v0.1.12
./qradar-dash upgrade 0.1.12
```

The upgrade is allowed from `0.1.11`. A site on 0.1.10 upgrades to 0.1.11 first; the 0.1.11 notes describe that path. An older release is refused before anything is touched: the refusal comes from the checkout's own `docs/releases/0.1.12.md`, read before any `.env` edit, bundle load or pull — `upgrade refused: 0.1.12 requires at least 0.1.11; nothing was changed`. If that file is missing, unreadable or not for 0.1.12, the refusal names the file and changes nothing either.

No migration runs, so the migrate step prints no `Running upgrade` line. `alembic upgrade head` still opens the database, so Alembic's two start-up lines (`INFO  [alembic.runtime.migration] Context impl PostgresqlImpl.` and `INFO  [alembic.runtime.migration] Will assume transactional DDL.`, shown by `docker compose logs --no-color --no-log-prefix migrate` and in the upgrade's own output) are expected, and the migrate container exits with 0. `upgrade` prints the decision pair twice, both times with `0054`: before the writers stop and after the new stack has started. The upgrade takes its own backup before it migrates, as every upgrade does, and that backup carries the install answers. The restart empties Redis, as in every upgrade. The collection families resume on their cadence; the pages show "stale" or "not collected" until the first cadence after the upgrade has passed, and that is correct.

On a host with no registry access, make the bundle on a connected host from the same checkout (`./qradar-dash bundle --output DIR` writes `qradar-dash-0.1.12-bundle.tar` in that directory; without `--output` the file is written in the current directory, and an existing file is not overwritten), copy it over, and run, in the installation directory:

```bash
tar -xf /path/to/qradar-dash-0.1.12-bundle.tar --exclude=images.tar
./qradar-dash upgrade 0.1.12 --offline /path/to/qradar-dash-0.1.12-bundle.tar
```

If the upgrade fails and the site must return to 0.1.11, follow `docs/OPERATIONS.md`, "Geri alma (`rollback`)": it restores the backup the upgrade took — including the install answers and the `0054` schema, which is the head the site had before the upgrade — and starts the previous images. Data written since the upgrade is kept only in the broken copy it leaves. `rollback` runs no `git checkout`; after a successful rollback the operator returns the checkout to the version that now runs (`git checkout v0.1.11`), as that section says. A return to 0.1.12 is then `git fetch --tags && git checkout v0.1.12` and `./qradar-dash upgrade 0.1.12`.
