# Behavior Analytics 0.1.5

Not released: the release build failed. Use 0.1.6, which carries everything below.

A smaller release than 0.1.4. No migration comes with it; the schema head stays `0032`. A new daily
task deletes old rule-match measurements, the optional MCP profile can now work against a real
console, the analyst pages say why a rule has its verdict and how many offenses could not be
classified, and a few API fields and sentence spellings change in ways an integrator may notice.

## Before you upgrade

- **Rule-match measurements are now deleted after `RULE_MATCH_RETENTION_DAYS`** (default 90, allowed
  30 to 3650). A new daily task removes `rule_match_metric` rows older than that by bucket time and
  `rule_match_window` rows older than that by window start. It runs whether or not `RETENTION_ENABLED`
  is set, in batches of `RULE_MATCH_RETENTION_BATCH_SIZE` (5,000 rows) and at most
  `RULE_MATCH_RETENTION_MAX_BATCHES` (20) per table per run, so a site whose tables never had
  retention clears its backlog over several days, not in the first run. The interval is
  `RULE_MATCH_RETENTION_INTERVAL_SECONDS` (86,400, minimum 3,600). The backend refuses to start when
  the value does not exceed `RULE_HEALTH_WINDOW_DAYS` (default 30). `install` does not write the
  setting; an existing `.env` without it gets 90. To keep the rows longer, set it before the first
  beat run after the upgrade. `doctor`'s `batch_retention` check lists the two tables.
- **The optional MCP profile.** The server now verifies the console certificate with the CA the
  backend uses (`qradar_ca.pem` from the secrets volume), and it receives the QRadar token from the
  backend in an `SEC` header on every request instead of reading it from a file. The container no
  longer reads `deploy/mcp/config.json`, or any other file of the checkout: an operator who created
  that file can delete it, because it may hold a token. With `QRADAR_PROVIDER=mcp`, production now
  refuses to start without `QRADAR_API_TOKEN_FILE` or `QRADAR_SEC_TOKEN`. The image bakes in the
  feature-toggle file that switches the upstream write tools off, and the provider negotiates the
  server's tool list before its first call and refuses a server that offers a write tool. Building
  the image from source is two steps (`docs/INSTALL.md`, "Development and lab hosts"); a production
  host builds nothing and runs the published `qradar-mcp` image. The profile was validated against a
  QRadar 7.6.0 FP1 console on 2026-10-23. To enable it in production, follow `docs/INSTALL.md`,
  "Enable the profile on a production host": check that `QRADAR_CONSOLE_FQDN` matches a subject
  alternative name of the console certificate, that `qradar_ca.pem` holds the full chain, that the
  `internal` network reaches the console, and that the backend already has its token; then add `mcp`
  to `COMPOSE_PROFILES` and run `docker compose up -d qradar-mcp`. Starting the profile does not move
  the application to MCP: `QRADAR_PROVIDER` stays `rest`.
- **Percentages in the sentences the backend writes** now read like the UI: "31.8 %", with a no-break
  space before the sign. Rows written before the upgrade keep their old text. A script that parses
  these sentences must accept both.
- **The overview's critical-offense count uses `OFFENSE_CRITICAL_MAGNITUDE`** (default 7, allowed 1
  to 10). It used a fixed 7, so a site that changed the setting sees the overview number change to
  match the offenses page.
- **Every collector holds its advisory lock on a database connection of its own,** taken from the
  same pool as the rest of the process and kept for the length of the run (the IPS fleet's
  per-source locks likewise). A process's pool is 10 connections plus 5 overflow, so a running
  collector uses one of those 15. Count it if PostgreSQL's `max_connections` is tight.
- **A correction to the 0.1.4 notes about `install`.** It exits 1 when `/api/v1/health/ready` or
  `/api/v1/version` does not answer, or when the published URL check fails, but not when the only
  problem is that the certificate is not trusted (curl exit 60 or 51). In that case it repeats the
  request without certificate verification, and if that answers HTTP 200 it prints a `[warn]` —
  browsers will warn until the site CA is trusted — and exits 0. The URL check runs only with the
  bundled proxy.

## New for the operator

- **`install` keeps an `mcp` profile.** A re-run keeps every profile you added to `COMPOSE_PROFILES`
  and decides only `proxy`; the summary names the profiles it kept. `upgrade` pulls the `qradar-mcp`
  image with the rest and recreates the service in the same `up -d --wait` as the application;
  `rollback`, manual or the automatic one after a failed upgrade, recreates it from the recorded
  digest. Both wait for its healthcheck whenever `mcp` is in `COMPOSE_PROFILES`. Nothing has to be
  done by hand.
- **The install summary** has `rule-match rows` in its `Retention` line.
- **Adding ATT&CK technique mappings** has a runbook section (`docs/OPERATIONS.md`, "Kapsam
  eşlemeleri"): the permission, how to find a rule's UUID, the request, the answers and how to
  compute the result with `sync coverage`.
- **Two runbook additions** from the 0.1.4 release check: the published URL check of `install`
  (above), and the line `docker load` prints when it keeps the secrets helper image only by its ID,
  with what it does to an existing `alpine:3.20` tag.
- **A runbook entry for failing MCP calls** (`docs/OPERATIONS.md`, OPS-R64): the four causes between
  `qradar-mcp` and the console, and the checks that tell them apart.

## For the analyst

- **The rules list says why each rule has its health verdict.** The sentence sits under the rule
  name for every rule that is not HEALTHY or UNKNOWN, and says "No reason recorded" when none is
  stored. The rule page shows the reason of the snapshot that belongs to the verdict beside it, not
  the newest history row.
- **Offense counts say what they could not classify:** "+ N with unknown magnitude" beside the
  critical count and "+ N with unknown age" beside the SLA count.
- **One link and one filter show every active IPS anomaly.** The IPS widget's "View all" opens the
  Anomalies page with entities and sources together, and the subject filter has an "IPS entities
  and sources" choice.
- **The IPS widget no longer cuts the port:** the subject and the line under it wrap.
- **Percent spellings** on the remaining figures (the Dashboard's EPS tiles and class shares, the
  coverage figure, the property-watch coverage and floor) match the backend's sentences.

## API

Additive unless stated.

- `GET /api/v1/rules` and `GET /api/v1/rules/{id}` gain `health_reason`: the reason stored with the
  snapshot written at `health_evaluated_at`, or `null` when that snapshot is gone or recorded none.
- The offense aggregates gain `critical_unknown` and `age_unknown`: open offenses with no magnitude
  and with no age. Both are `null` when no offense snapshot exists.
- `GET /api/v1/anomalies` and `GET /api/v1/anomalies/histogram` accept `subject_kind` more than
  once (`subject_kind=IPS_ENTITY&subject_kind=IPS_SOURCE`). One value behaves as before.
- Changed: the overview's critical count follows `OFFENSE_CRITICAL_MAGNITUDE`, and newly written
  backend sentences use the percent spelling above.

## Schema

No migration. The head stays `0032`.

## Upgrade

```bash
git fetch --tags && git checkout v0.1.5
./qradar-dash upgrade 0.1.5
```

The upgrade is allowed from `0.1.4`. A `0.1.3` site goes through `0.1.4` first, as the notes of that
release describe; the upgrade to `0.1.5` from an older release stops with
`upgrade refused: 0.1.5 requires at least 0.1.4`, after it has moved the image prefix and pulled the
`0.1.5` images. The upgrade takes its own backup before it migrates, as every upgrade does.

On a host with no registry access, make the bundle on a connected host from the same checkout, copy
it over, and run, in the installation directory:

```bash
tar -xf /path/to/qradar-dash-0.1.5-bundle.tar --exclude=images.tar
./qradar-dash upgrade 0.1.5 --offline /path/to/qradar-dash-0.1.5-bundle.tar
```
