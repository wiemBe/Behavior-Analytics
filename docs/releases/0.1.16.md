# Behavior Analytics 0.1.16

For the analyst: a shift handover (`/handover`) leaves a written note and freezes what was open for the next shift; `/entities` shows what the platform has already stored about one IP address, host or user; `j`, `k`, Enter, `o`, Esc, `n`, `a` and `g` work on the anomaly and alert lists; IPS behavior has its own pages (`/behavior/ips`); rule silence and storm incidents can be read in the anomaly list, on Rule statistics and on the rule page; the volume and series charts can draw exponential moving averages (off by default, display only); one alert per console says that log-source volume collection is stale, and one console-wide alert replaces a flood of per-source silence alerts when the whole answer is empty. The alert counter is named for what it counts, and the Dashboard geography widget drops the text under the map.

For the operator: the schema head moves to `0063`. The `postgres` container is recreated by the upgrade, because its image changes, and starts with TimescaleDB telemetry off. A daily job removes handover records older than 90 days, a beat task fills the entity timeline's index from rows stored before it existed, and a second beat task watches log-source volume collection. No permission is added and no role row changes. `./qradar-dash bundle --local-images` makes an offline bundle from images built on the build host. Nothing writes to QRadar.

## Before you upgrade

- **The schema head moves to `0063`.** Three additive migrations run once, in order: `0061_entity_mention`, `0062_entity_mention_backfill`, `0063_shift_handover`. See Schema. Nothing is backfilled by the migrations; the entity timeline's index is filled afterwards by a beat task (below). Round-trip tests that upgrade, downgrade and run `alembic check` exist for `0061` and `0063` (`backend/tests/integration/test_entity_mention_migration.py`, `test_handover_migration.py`), and `test_alembic_check_reports_no_drift` checks the head. They were not run for this note.
- **A 0.1.15 site upgrades directly.** `min_from` is `0.1.15`. A 0.1.14 site upgrades to 0.1.15 first. `qradar-dash` reads this file before any `.env` edit, bundle load or pull and refuses an older site with `upgrade refused: 0.1.16 requires at least 0.1.15; nothing was changed`.
- **The `postgres` container is recreated.** The release's `postgres` image carries `CMD ["postgres", "-c", "timescaledb.telemetry_level=off"]` (`deploy/postgres/Dockerfile`; FIX-47), and the production Compose file tags that image with the release version (`docker-compose.prod.yml`). The upgrade's `up -d` converges the dependency graph, and Compose recreates the container because its image changed. The data volume is kept. The database restarts once more, inside the upgrade's outage window. `SHOW timescaledb.telemetry_level;` answers `off` afterwards (the guide's MT-160 reads it). A rollback restores the previous images, so a rolled-back site runs the 0.1.15 `postgres` image again.
- **A beat task fills the entity timeline's index after the upgrade.** `backfill-entity-mentions` runs every `ENTITY_MENTION_BACKFILL_INTERVAL_SECONDS` (default `300`, at least `60`). It reads rows that were stored before 0.1.16 and writes `entity_mention` rows for them, in bounded keyset batches (`ENTITY_MENTION_BACKFILL_BATCH_SIZE` 500 and `ENTITY_MENTION_BACKFILL_MAX_BATCHES_PER_RUN` 20 by default), one resume row per console and mention source, under its own advisory lock. It is insert-only, reads only stored aggregates and calls no QRadar API. `ENTITY_MENTION_BACKFILL_ENABLED=false` switches it off. Until a source is `COMPLETE`, the entity timeline does not claim absence for it, and `./qradar-dash doctor` shows `WARN entity_mentions` (runbook OPS-R73); the line is never `FAIL`. `docker compose exec -T backend python -m app.cli.entity_mentions status` lists each console and source, and `run` works through the history at once (it ignores the beat task's switch and holds the same lock). The four settings are in `docs/CONFIGURATION.md`, not in `.env.example`. The log-source rows are the exception: they need no backfill (`LOG_SOURCE` is `COMPLETE` from the start) and are written by the log-source inventory sync (every `LOG_SOURCE_SYNC_INTERVAL_SECONDS`, default one hour), so until the first sync after the upgrade the entity timeline's "Log sources" lane reads "Partial: This lane's index is not complete" for the identifier or name of a registered log source, even when `doctor` shows every source indexed. This is intended: the lane never claims absence it cannot prove.
- **A second beat task watches log-source volume collection.** `detect-stale-log-source-collection` runs every `OFFENSE_STALE_CHECK_INTERVAL_SECONDS` (default `300`). A console whose volume collection has not run within `max(900 s, 3 × COLLECTION_INTERVAL_SECONDS)` (900 s with the default), or whose last run failed, gets one alert: severity High, "Log source volume collection is stale for ‹console›". It resolves on the next successful run. A console with no monitored log source is not judged, and an open alert is closed "without a verdict", never as a recovery (FIX-45f); a console registered less than the threshold ago with no run yet is not judged either. So an upgraded site whose collection is already failing gets this alert within about five minutes of beat starting. `docker compose exec -T backend python -m app.cli.sync stale-log-sources --instance <console>` runs one detection by hand.
- **A daily job removes old handover records.** `apply-handover-retention` runs every 86400 s and deletes records older than `HANDOVER_RETENTION_DAYS` (default `90`), at most `HANDOVER_RETENTION_BATCH_SIZE` (500) at a time and `HANDOVER_RETENTION_MAX_BATCHES` (20) batches a run. The interface offers no edit and no delete, so this job is the only way a record leaves. With no handover written, it deletes nothing. The three settings are in `docs/CONFIGURATION.md`, not in `.env.example`.
- **No permission is added and no role row changes.** `backend/app/security/rbac.py` and `backend/app/services/seed.py` are the same as in 0.1.15. Writing a handover needs `anomaly:triage`, which 0.1.15 added (see its notes: an existing `analyst` row does not hold it until an administrator grants it, and `admin:*` already satisfies it). Reading handovers, the entity timeline and IPS behavior needs only a signed-in account; the entity timeline marks a lane "Forbidden" when the account lacks that lane's permission (`read:offenses`, `read:fleet`, `read:property_watches`).
- **Rule silence and storm: nothing changes with the defaults.** `RULE_MATCH_COLLECTION_ENABLED` is still `false`, and rule incidents open no alert unless `RULE_ALERTING_ENABLED=true`. What 0.1.16 adds is the read side: `GET /api/v1/rules/match-anomalies`, `GET /api/v1/rules/{id}/match-anomalies`, the `Rule` subject kind on `/anomalies`, and a rule-match incident's detail. `GET /api/v1/behavior/detectors` now lists `RULE_SILENCE` and `RULE_STORM` as `NOT_ENABLED` while collection is off.
- **Alerting changes a little on a site that had silent sources.** When the volume answer names no monitored source at all for a complete bucket, the engine opens one alert for the console, "No log source sent events in ‹bucket›", and per-source silence is `INSUFFICIENT_DATA` for that bucket (FIX-45c, D-62), instead of one `NO_EVENTS` alert for every source. A silence alert that is raised reads "No events received from ‹source›" with the number of empty buckets and the expected count (FIX-45b), and the silence streak no longer counts across missing buckets (FIX-45a). An anomaly evaluation holds a process-wide advisory lock; a run that finds it held does nothing and returns `skipped_locked` (FIX-45d).
- **No `.env` edit is required.** Every setting above has a default that keeps the behaviour described here.

## For the analyst

- **Shift handover (SOC-14a, SOC-14b).** Behavior → "Handover" (`/handover`) shows the latest record: who wrote it, the window it covers (from the previous record's time, or 24 hours before the first one), the note, the rows marked "Watch", the open items frozen when it was written (severity, item, state, owner, flags "Unassigned", "Over SLA", "New", "Updated", and how long each had waited), what the author did in the window, the sources that were not read cleanly (each with its reason: failed, forbidden, not collected, stale, partial) and the earlier handovers. A frozen list that is empty because a source failed says so instead of reading as an empty queue. "Write handover" needs `anomaly:triage`: the page previews the rows that will be frozen (at most 50), lets the analyst mark up to 20 as "Watch", takes a note of 1 to 4000 characters and saves. **A saved handover is immutable.** There is no edit and no delete in the interface or the API (`GET /api/v1/handover`, `/latest`, `/preview`, `/{id}` and `POST /api/v1/handover`); a correction is a new handover. Building the preview does not move the Queue's "last visit" marker. A "Latest handover" widget (the SOC Overview template; add it from the widget catalog to a dashboard saved earlier) shows the author, the time, the first 240 characters of the note and how many rows are watched.
- **Entity timeline (SOC-16a to SOC-16f).** `/entities` answers, for one IP address, host or user over at most seven days, what the platform has already stored: anomaly contributors, WAF top clients, IPS source contributors and destination entities, QRadar offenses, log sources, catch-all senders and property-watch values. It is read from the database only; it is not a QRadar search and shows no raw event. Each lane has its own status (measured, none stored, not collected, forbidden, partial, stale, truncated, not applicable) and an unmeasured lane is never a zero. A lane that stores only top contributors, or whose index is not yet complete, cannot prove that an entity was absent, and the page says so: "That is not a finding that it was absent." There is no navigation item: the top-bar search offers "Entity timeline for ‹text›", and a contributor value on an anomaly detail links to it. The mentions come from the collectors (each writes in its own savepoint, so a failed mention write never blocks a collection) and, for rows stored before 0.1.16, from the backfill above.
- **Keyboard triage (SOC-15a, SOC-15b).** On `/anomalies` and `/alerts`: `j` and `k` move a row mark, Enter or `o` opens the marked row, Esc clears the mark. On `/anomalies`, `n` opens the marked anomaly with the cursor in its comment field. On `/alerts`, `a` acknowledges the marked alert; the confirmation appears only after the backend answers, only an open alert can be acknowledged, and a refusal names `alert:ack`. `g` then `d`, `q`, `a`, `l` or `o` goes to Dashboard, Queue, Anomalies, Alerts or Offenses (the second key within 1.5 s). The keys do nothing in a form control, with Ctrl, Alt or Meta held, or under a dialog. The top bar's "Refresh" choice is remembered in the browser.
- **IPS behavior (IPS-UI-1, IPS-UI-2, IPS-API-1).** Behavior → "IPS behavior" (`/behavior/ips`) lists the IPS sources that have an enabled profile, attention first: validation, the latest bucket with the measurement of each search dimension, active entities against the ceiling, admission overflow and active anomalies with the worst severity (a source that is not judged says "Not judged", never a count of zero). A source's page (`/behavior/ips/sources/<id>`) draws its series against the expected range, the action mix and its entities. `GET /api/v1/behavior/ips/sources/{id}` returns the list's item for one source, and each list item carries `active_anomaly_count` and `worst_active_severity`.
- **Rule silence and storm on the read side (SOC-6d to SOC-6h).** "Rule" is a subject kind on `/anomalies`; Rule statistics has a "Rule-match anomalies" block; a rule's page has a "Match anomalies" section; a rule incident has its own detail. With collection off, each says "not collected" and never reads as healthy. A rule-match engine failure no longer re-runs the Ariel collection: the engine runs in a savepoint, collected windows commit either way, and a watermark remembers how far windows were judged (SOC-6i).
- **EMA overlays (CHART-1, CHART-2, UIQ-3).** The volume chart, the WAF, IPS and property-watch series charts and the Dashboard's expanded Fleet EPS widget have "EMA" buttons 3, 5, 10 and 20. All are off by default, the choice is remembered in the browser, and the lines are computed in the browser from the observed series. They are never used for detection, and a line stops at a bucket that was not fully observed.
- **Alerts (FIX-45-ui, UIQ-2, FIX-45e).** The list column is "Detections while open" and the detail says "not repeated" or "repeated ‹n›× while open"; the detail also shows the last anomaly bucket and the last evaluation time. A new alert, "Log source volume collection is stale for ‹console›", is described above.
- **Search cadence (FIX-44, FIX-44-ui).** The column is "Bucket width", with a note that it is not how often the family searches. A family whose last run failed says in "Next run (UTC)" that it is not retried before its next slot ("Not retried after the failed run.").
- **Smaller changes.** The Dashboard geography widget drops the text under the map (measured buckets, remainder figures and provenance); `/geography` keeps it (UIQ-1). Top-bar search draws no heading above an empty group (UIQ-2). Traffic's export control says there is nothing to export when no source has a behavior profile, instead of claiming a load failure (FIX-43-ui). An incomplete lane on the entity timeline says why absence cannot be proven (UIQ-4). A QRadar health notification answer whose every row was dropped is `NOT_COLLECTED` with the reason `notification_rows_unreadable`, not an empty "OK" (FIX-41).
- **Known issue (FIX-48).** On the search cadence page (`/admin/search-cadence`), a family that is switched off but still holds an old failed run (for example "Rule matches" while `RULE_MATCH_COLLECTION_ENABLED` is unset) shows a dash in "Next run (UTC)" and, under it, "Not retried after the failed run." The family does not run; the sentence is stale. It changes nothing in collection.

## For the operator

- **The upgrade.** `qradar-dash upgrade 0.1.16` runs the three migrations, recreates `postgres` (see Before you upgrade) and restarts the application. It takes its own backup first, as every upgrade does.
- **`bundle --local-images` (REL-15g).** `./qradar-dash bundle --local-images` builds the offline bundle from the five product images already in the local Docker engine instead of pulling them. It refuses, before writing anything, when the directory is not a git work tree, when a tracked file has uncommitted changes, when an image is missing or when an image's `org.opencontainers.image.version` or `.revision` label does not match the checkout's `VERSION` and `HEAD`. The manifest records `images_source local`. Without the flag the command pulls, as before.
- **New beat entries and tasks:** `detect-stale-log-source-collection` (`detect_stale_log_source_collection`), `apply-handover-retention` (`apply_handover_retention`) and `backfill-entity-mentions` (`backfill_entity_mentions`; `{"status": "disabled"}` when its switch is off, `busy` when the lock is held).
- **New commands:** `python -m app.cli.entity_mentions status [--instance NAME] [--json]` and `run [--instance NAME] [--max-batches N]` (exit 0 done, 1 database failed, 2 console not registered or bad arguments, 3 another run holds the lock, 4 a source failed in this run), and `python -m app.cli.sync stale-log-sources [--instance NAME]`.
- **New `doctor` line:** `entity_mentions`. `PASS` with `‹n› source(s) indexed, ‹m› row(s) written` when every source is `COMPLETE` (or `entity-mention backfill is switched off (ENTITY_MENTION_BACKFILL_ENABLED=false)` with no state row), `WARN` while a source is `PENDING`, `RUNNING` or `FAILED` or the backfill has not run yet, never `FAIL`.
- **New settings,** all optional: `ENTITY_MENTION_BACKFILL_ENABLED` (`true`), `ENTITY_MENTION_BACKFILL_BATCH_SIZE` (`500`), `ENTITY_MENTION_BACKFILL_MAX_BATCHES_PER_RUN` (`20`), `ENTITY_MENTION_BACKFILL_INTERVAL_SECONDS` (`300`), `HANDOVER_RETENTION_DAYS` (`90`), `HANDOVER_RETENTION_BATCH_SIZE` (`500`) and `HANDOVER_RETENTION_MAX_BATCHES` (`20`). `docs/CONFIGURATION.md` lists them.
- **Retention.** An entity mention leaves with the rows it points at: the catch-all, offense-snapshot, property-watch, WAF, IPS and log-source-anomaly retention jobs delete their mentions with their parents, so `entity_mention` does not grow without bound.
- **New API reads,** all `GET` unless noted: `/api/v1/entities/timeline` (database-only, at most seven days, paged by a cursor), `/api/v1/handover`, `/handover/latest`, `/handover/preview`, `/handover/{id}` and `POST /handover` (`anomaly:triage`), `/api/v1/rules/match-anomalies`, `/api/v1/rules/{id}/match-anomalies` and `/api/v1/behavior/ips/sources/{id}`. The anomaly summary carries `active_by_family.rule`, and `GET /anomalies/{id}` answers a rule-match incident.
- **QRadar.** Nothing in this release writes to QRadar. The entity timeline, the handover and the backfill make no QRadar call.

## Schema

The head is `0063`. 0.1.16 adds three migrations. Each is additive.

- `0061_entity_mention` (SOC-16a1): table `entity_mention`, a plain table, not a hypertable. Columns `instance_id` (foreign key to `qradar_instance`, `ON DELETE CASCADE`), `kind` (`IP`, `HOST`, `USER`), `value_norm`, `role` (`SOURCE_IP`, `DESTINATION_IP`, `HOST`, `USER`), `source` (`EXPLANATION`, `WAF_TOP`, `IPS_TOP`, `IPS_ENTITY`, `OFFENSE`, `CATCHALL`, `PW_VALUE`, `LOG_SOURCE`), `ref_table`, `ref_id`, `occurred_at` and `occurred_end`. The kinds, roles and sources are text CHECKs so a later slice can extend them additively. The primary key is `(instance_id, kind, value_norm, source, ref_table, ref_id, occurred_at)`; the index `ix_entity_mention_lookup` is on `(kind, value_norm, occurred_at)`. The migration also creates the index `ix_explanation_contributor_dimension_value` on the existing table `anomaly_explanation_contributor` `(dimension, value)`, built while the writers are stopped; its time grows with that table. The downgrade drops the two indexes and the table.
- `0062_entity_mention_backfill` (SOC-16f2): table `entity_mention_backfill`, one resume row per `(instance_id, source)`: `status` (`PENDING`, `RUNNING`, `COMPLETE`, `FAILED`), `cursor` (JSONB), `rows_written` (non-negative), `started_at`, `completed_at`, `last_error` and `updated_at`. It inserts no row and starts no work; the beat task creates the rows. The downgrade drops the table.
- `0063_shift_handover` (SOC-14a): table `shift_handover`: `id`, `author_subject`, `written_at`, `window_started_at`, `previous_id` (a foreign key to the table itself, `ON DELETE SET NULL`), `note` (1 to 4000 characters, a CHECK) and `body` (JSONB: the frozen open rows, the author's actions in the window and the per-source read lines). The index `ix_shift_handover_written_at` is on `written_at DESC`. Immutability is the API's: it has no update or delete route; the migration adds no trigger. The downgrade drops the index and the table.

No downgrade raises: none of the three tables is referenced by an earlier table or enum. A site rollback is a restore of the upgrade's backup and runs no downgrade. The backup's schema is `0060`.

## Upgrade

```bash
git fetch --tags && git checkout v0.1.16
./qradar-dash upgrade 0.1.16
```

The upgrade is allowed from `0.1.15`. A site on 0.1.14 upgrades to 0.1.15 first; the 0.1.15 notes describe that path. An older release is refused before anything is touched: the refusal comes from the checkout's own `docs/releases/0.1.16.md`, read before any `.env` edit, bundle load or pull — `upgrade refused: 0.1.16 requires at least 0.1.15; nothing was changed`. If that file is missing, unreadable or not for 0.1.16, the refusal names the file and changes nothing either.

`upgrade` prints the deciding pair before the writers stop, while the 0.1.15 backend is still the running image, so that pair says `0060` (`PASS migration_head database and image are at 0060`, and `db_connect`). The migrate container then runs the three revisions once (`Running upgrade 0060 -> 0061`, `0061 -> 0062` and `0062 -> 0063`) and the command prints them in its own output. Alembic's two start-up lines (`INFO  [alembic.runtime.migration] Context impl PostgresqlImpl.` and `INFO  [alembic.runtime.migration] Will assume transactional DDL.`) are expected. After the new stack is up, `upgrade` prints the deciding pair again, both checks `PASS`, and `migration_head` says `0063`. `/api/v1/version` reports `migration_head` `0063`. The `postgres` container is recreated with the new image (see Before you upgrade).

The entity-mention backfill starts with the new beat. `./qradar-dash doctor` shows `WARN entity_mentions` until it has finished; see "Before you upgrade".

On a host with no registry access, make the bundle on a connected host from the same checkout (`./qradar-dash bundle --output DIR` writes `qradar-dash-0.1.16-bundle.tar` in that directory; without `--output` the file is written in the current directory, and an existing file is not overwritten; `--local-images` uses the images built on that host instead of pulling them), copy it over, and run, in the installation directory:

```bash
tar -xf /path/to/qradar-dash-0.1.16-bundle.tar --exclude=images.tar
./qradar-dash upgrade 0.1.16 --offline /path/to/qradar-dash-0.1.16-bundle.tar
```

If the upgrade fails and the site must return to 0.1.15, follow `docs/OPERATIONS.md`, "Geri alma (`rollback`)": it restores the backup the upgrade took — including the install answers and the `0060` schema, which is the head the site had before the upgrade — and starts the previous images. Data written since the upgrade, including every handover record, is kept only in the broken copy it leaves. `rollback` runs no `git checkout`; after a successful rollback the operator returns the checkout to the version that now runs (`git checkout v0.1.15`), as that section says. A return to 0.1.16 is then `git fetch --tags && git checkout v0.1.16` and `./qradar-dash upgrade 0.1.16`.
