# qradar-observability 0.1.1

A patch release on top of 0.1.0. Nothing changes for an analyst; the operator's install,
upgrade and diagnosis get the fixes below.

- **Install records its state even when the QRadar check fails.** A failing QRadar check no
  longer leaves the site without `.qradar-dash/state.json`: as long as the stack came up, the
  state file is written, so `status`, `upgrade` and `rollback` work on such a site. Fix the
  console, token or CA and run `install` again (`qradar add` updates the row).
- **`upgrade` and `rollback` show only the deciding doctor checks.** They print the `db_connect`
  and `migration_head` lines, then `Full report: ./qradar-dash doctor`. The rest of the report
  is hidden because a not-yet-written heartbeat or the QRadar checks would look like a false
  failure. `doctor` itself is unchanged.
- **Install refuses an unusable backup directory at preflight.** When the operator's account
  cannot create or write the backup directory, the install stops before anything is written,
  naming the directory and pointing at `docs/OPERATIONS.md`; a failing `mkdir` of it stops the
  install instead of finishing "healthy" and failing at the first backup.
- **`upgrade` and `install` refuse a checkout of the wrong version.** `upgrade X` stops, before
  anything is pulled or stopped, unless the checkout's `VERSION` is `X`: the target version's
  script and compose files must run the upgrade. When `.qradar-dash/state.json` exists, `install`
  refuses to change the recorded version (it would be an upgrade with no backup and no automatic
  rollback), after a failed upgrade, or on an invalid state file; a re-run at the recorded version
  and an install with no state file work as before.
- **The beat writes its heartbeat at start.** `doctor` no longer reports `celery_beat` FAIL right
  after an install, `upgrade`, `rollback` or a reboot.
- **`bundle` says what to use instead**, in plain text.
- The operator runbook is updated after a fresh-VM install and upgrade run.

**Schema.** No migration; the head stays `0025` (`0025_auth_sessions`).

**Upgrade.** Bring the checkout to the target tag first, then upgrade:

```bash
git fetch --tags && git checkout v0.1.1
./qradar-dash upgrade 0.1.1
```

The 0.1.0 script has no checkout check, so this order is what makes the 0.1.1 script run the
upgrade. A site whose 0.1.0 install failed the QRadar check has no `.qradar-dash/state.json`, and
`upgrade` refuses with `upgrade refused: .qradar-dash/state.json field file is invalid or missing`.
Take `./qradar-dash backup manual` first (it works without a state file), then either:

- fix the QRadar connection and re-run `./qradar-dash install` from the v0.1.0 checkout. That
  writes the state file only when the QRadar check passes. Then upgrade as above; or
- if QRadar cannot be fixed yet, check out v0.1.1 and run `./qradar-dash install`. That brings the
  site to 0.1.1 and writes the state file. This path has no pre-upgrade backup and no automatic
  rollback, which is why the backup comes first.

**Read-only.** The platform never creates, updates or deletes anything in QRadar.
