# Behavior Analytics 0.1.4

A larger release than 0.1.3. Two migrations come with it (the schema head goes from `0030` to
`0032`), several behaviours change in ways an operator should know before upgrading, and the
`qradar-dash` script gains commands for offline sites, state repair and machine-readable
diagnostics. The analyst pages say more about what was not measured, and show a zero only where
something was measured.

## Before you upgrade

- **`GET /api/v1/alerts` returns a page, not an array.** The body is now
  `{"items": [...], "total": N, "limit": N, "offset": N}`. `limit` defaults to 100 and may be up to
  500; `offset` and `status` are accepted; the order is newest first. A script that read the
  response as a list must read `items`.
- **The health score is gone from the API.** The log-source responses no longer carry
  `health_score`, `health_breakdown` and `health_computed_at`, and the overview no longer carries
  `healthy_log_sources` and `average_health_score`. Nothing ever computed them. The offense counts
  in the overview are now `null` when no offense snapshot has been collected (a zero meant
  "measured, none open"), and the overview gains `critical_unknown`, the open offenses whose
  magnitude is not known.
- **`ENVIRONMENT=staging` is now a hardened environment.** It refuses what production refuses
  (`DEBUG`, `QRADAR_VERIFY_SSL=false`, the mock provider, a `SECRET_KEY` shorter than 32
  characters, `AUTH_PROVIDER=oidc`) and it reads the session cookie, with CSRF checks and the API
  docs hidden, instead of the local development principal. Outside development, the placeholder
  `SECRET_KEY` and `ENCRYPTION_KEY` shipped in `.env.example`, an `ENCRYPTION_KEY` that is not a
  Fernet key, and any `ENCRYPTION_KEYS_JSON` entry Fernet cannot build are refused at startup; the
  message names the setting and never prints the value. A site that boots today with such a key
  stops booting, so check the keys before you upgrade.
- **Retention deletes more, on its own switch.** These daily deleters run whether or not
  `RETENTION_ENABLED` is set, in batches of 5,000 rows and at most 20 batches per table per run (a
  large backlog is cleared over several days):
  - closed Phase A incidents (RESOLVED, NORMAL, INSUFFICIENT_DATA) after
    `LOG_SOURCE_ANOMALY_RETENTION_DAYS`, default 365;
  - closed IPS incidents after `IPS_ANOMALY_RETENTION_DAYS`, default 365, even when
    `IPS_RETENTION_ENABLED` is off;
  - rule health snapshots after `RULE_HEALTH_SNAPSHOT_RETENTION_DAYS`, default 90, and detection
    coverage snapshots after `DETECTION_COVERAGE_SNAPSHOT_RETENTION_DAYS`, default 90;
  - closed anomaly evaluation faults after `ANOMALY_FAULT_RETENTION_DAYS`, default 30.

  An incident is kept while a detector state still points at it or any alert lists it, whatever
  the alert's status; open and suppressed incidents are never deleted. The Timescale policies
  (`RETENTION_ENABLED` with the four `RETENTION_*_DAYS` values, 90 days as the installer writes
  them) are unchanged, and so is `RETENTION_OFFENSE_SNAPSHOT_DAYS`. To keep a table longer, raise
  its setting before the first beat run after the upgrade.
  `IPS_METRIC_RETENTION_DAYS` (default 35) must now exceed `IPS_BASELINE_LOOKBACK_DAYS` (default
  28) when IPS collection and IPS retention are both on, or the backend refuses to start.
- **Every Ariel search holds a permit.** Collectors, scheduled searches and manual runs now take a
  PostgreSQL advisory-lock permit for the whole search, so the caps bind across the worker, the
  API and the command line: `ARIEL_MAX_CONCURRENT_SEARCHES` (default 3, per console) and
  `ARIEL_GLOBAL_MAX_CONCURRENT_SEARCHES` (default 6). A search waits up to
  `ARIEL_PERMIT_WAIT_SECONDS` (default 30) and is then refused before anything is sent to QRadar;
  a scheduled search records the refusal as a capacity failure, and a manual run answers
  `503` and keeps its failed run record. `ARIEL_PERMIT_RESERVED_LIVE_SLOTS` (default 2) global
  slots are held for live collection, so history reading, scheduled and manual searches yield to
  it; a history step that finds no permit is deferred and retried, not failed. The reserve must be
  below the global cap, or the backend refuses to start. If a site relied on more than six
  searches at once, raise the global cap deliberately.
- **`/api/v1/health/ready` answers `503` while the database revision is not the image's
  migration head.** The body names both revisions. `backend`, `celery-worker` and `celery-beat`
  now wait for the `migrate` service to finish successfully before they start, so a healthy stack
  is a migrated one.
- **`install` exits 1** when `/api/v1/health/ready` or `/api/v1/version` does not answer, or the
  published URL check fails, as well as when the QRadar check fails. Every `qradar-dash` command
  now refuses an argument it does not know and exits 2; `status`, `doctor` and `support-bundle`
  used to ignore one.
- **The offline bundle holds seven images.** It adds the secrets helper image, which is now pinned
  by digest like the Redis image. There was no `bundle` command in 0.1.3, so there is no 0.1.3
  bundle to reuse; an offline install or upgrade reads only a bundle made by
  `./qradar-dash bundle` from the 0.1.4 checkout, and refuses any other archive before it loads
  anything.
- **Settings the code does not read are now documented as having no effect:**
  `COLLECTION_BATCH_SIZE`, `OFFENSE_PAGE_SIZE`, `RULE_MAX_PAGES`, `EXPLANATION_QUERY_TIMEOUT_SECONDS`,
  `EXPLANATION_COLLECTION_INTERVAL_SECONDS`, `NOTIFY_PER_CHANNEL_RATE` and the `OIDC_*` values.
  They are still accepted. A name that looks like a setting but is not one is ignored, logged at
  startup and reported by `doctor`.
- **`doctor` renames one host check:** `qradar_clock` is now `host_clock`. It checks the host's
  NTP synchronisation, not QRadar's clock. A script that matches the old name must change.

## New for the operator

- **`./qradar-dash bundle`** pulls the release images on a connected host and writes
  `qradar-dash-<version>-bundle.tar`, with checksums, the checkout files and the release notes,
  and never `.env`, `.secrets` or the override file. `install --offline BUNDLE` and
  `upgrade <version> --offline [BUNDLE]` verify it and load it on the air-gapped host.
- **`./qradar-dash repair-state`** records a healthy upgrade or rollback whose state file was not
  written, so the next upgrade is not blocked. It refuses, and writes nothing, unless the API is
  ready and the database revision matches the running image.
- **`./qradar-dash doctor --json`** prints one JSON array: the host checks, then the container's.
- **New doctor checks:** `ariel_permits` (permits held against the caps), `host_clock`,
  `backup_age` (a warning when no backup exists, the newest is older than 26 h, or the backup
  timer is missing), `unknown_settings`, `batch_retention` (every daily deleter with its days) and
  `anomaly_evaluation` (a bucket the engine could not judge). The retention policy check now
  covers every configured table.
- **`GET /api/v1/searches/ariel-budget`** is a read-only view of the permit pool: the caps and the
  permits held now, counts only. It needs both `read:searches` (the searches router) and `admin:waf` (the handler).
- **The install summary** has a `Retention` line with the real day counts and a backup-timer line
  that says whether the timer is installed.
- **A re-run of `install` keeps your `.env`:** answers are rewritten, production invariants are
  enforced with a named warning, and secrets, operator tunables and any other `KEY=VALUE` line
  are carried over. It also uses `docker-compose.override.yml` when one exists, and now writes
  `RETENTION_SEARCH_RESULT_METRIC_DAYS` with the other three. `upgrade` does not rewrite `.env`.
- **Scheduled searches no longer overlap.** One cycle runs at a time, a search is committed before
  it runs, and a run in progress shows as RUNNING. A crash mid-cycle keeps the searches already
  done.
- **An evaluation that keeps failing is recorded.** A bucket the anomaly engine cannot judge is
  retried, given up after `ANOMALY_MAX_BUCKET_ATTEMPTS` failed ticks (default 3), and stored in the
  new fault table with its exception class name only; the source is not given a verdict for it.

## For the analyst

- **Alerts:** the list filters by status, pages, and says "Showing N of M". The bell opens the
  open alerts.
- **Behavior:** the worklist ranks from the active set of up to 200 incidents and says when it was
  capped; a read that failed never shows the all-clear text. A "Resolved, 24 h" count is added.
- **Source page:** open incidents older than the chosen window are shown. A source's own page and
  the inventory show "Judged through ... UTC" and "Not judged" for buckets the engine could not
  judge; the Log sources count says how many sources had such a bucket in 24 h.
- **Business hours follow the source's time zone.** The detector used the UTC hour and ignored the
  weekday list. It now reads the source's time zone and ISO weekdays, a window that ends before it
  starts wraps past midnight, and an unknown zone counts as expected-active. The API refuses an
  invalid zone, weekdays outside 1 to 7, and an empty day list while business hours are on.
- **A rule with an unknown dependency is INSUFFICIENT_DATA, not healthy.** A building block or
  log-source type that is not in the map, or one whose sources were all skipped, now names itself
  in the rule's verdict.
- **Unknown is not zero:** offense counts with no snapshot show "Not collected"; the critical
  count includes only offenses with a known magnitude of 7 or more, and unknown magnitudes are
  counted apart; the oldest offense age and the `sync` command print "unknown" when nothing was
  read.
- **A source that went silent is an open, unsuppressed "no events" finding.** A source with no
  recorded last event is unknown, not silent, so the overview's silent-source count changes.
- **Fleet totals** count only the monitored sources on the current bucket width, and the class
  totals say how much of their window was read from QRadar history.
- **The history page** shows a failed step ("Last step failed at ... UTC (class). The next
  collection retries."), and names the sources a reading is missing. "Read history now" tops up
  a finished reading for the sources that have no floor yet.
- **Dashboard widgets** say "stale" when their data time is older than twice the collection cadence, and
  otherwise "Data to ... UTC". Times show their zone and a relative age after the absolute time,
  and every percentage is written one way.

## Schema

- `0031` adds two nullable columns to `history_backfill_scope`, `last_error_class` and
  `last_error_at`, that keep the last failed history step's exception class name and time.
- `0032` adds the table `anomaly_evaluation_fault`, one row per source and bucket the engine could
  not judge.

The head is `0032`. Both are additive; the upgrade runs them, and existing rows are unchanged.

## Upgrade

```bash
git fetch --tags && git checkout v0.1.4
./qradar-dash upgrade 0.1.4
```

The upgrade is allowed from `0.1.3`. A `0.1.2` site goes through `0.1.3` first, as the notes of
that release describe; the upgrade to `0.1.4` from an older release stops with
`upgrade refused: 0.1.4 requires at least 0.1.3`, after it has moved the image prefix and pulled
the `0.1.4` images. The upgrade takes its own backup before it migrates, as every upgrade does.

On a host with no registry access, make the bundle on a connected host from the same checkout,
copy it over, and run, in the installation directory:

```bash
tar -xf /path/to/qradar-dash-0.1.4-bundle.tar --exclude=images.tar
./qradar-dash upgrade 0.1.4 --offline /path/to/qradar-dash-0.1.4-bundle.tar
```
