# Behavior Analytics 0.1.8

Do not install 0.1.7. Use 0.1.8.

On every session-authenticated site, server-rendered pages failed in 0.1.6 and in 0.1.7. The page
showed "Your session has expired. Sign in again to continue." while the browser held a valid
session. 0.1.8 sends that session's cookie on those reads, and the pages load. A session that
really has expired still shows the same sentence. The pages an analyst opens this way include
alerts, rules, anomalies, behavior, log sources, searches, WAF, IPS, outage policy and
classification.

A sign-in straight after a sign-out could stop on the sentence "Sign-in is required." until the
page was reloaded. That was a stale state, seen in the laboratory and not reproduced outside it.
0.1.8 clears it, so the reload is not required.

`RATE_LIMIT_DEFAULT` is `1200/minute`. It was `120/minute`. Server-rendered pages are counted under
the frontend container's address, which every analyst shares, and one anomaly page calls the API
about 21 times. The login limit stays `300/minute` and the search-execution limit stays
`10/minute`. `install` does not write `RATE_LIMIT_DEFAULT`. Compose passes `.env` into the backend
(`env_file: [.env]` on the backend service; the production overlay does not remove it), so a site
whose `.env` sets the name keeps that value. The code default applies only when the name is unset.
A line copied from an older example, `RATE_LIMIT_DEFAULT=120/minute`, keeps 120. Remove the line,
or raise it.

A site on 0.1.6 that skips 0.1.7 meets everything the 0.1.7 notes say under "Before you upgrade".
That list is repeated below, and then what 0.1.8 adds. The schema head stays `0044`. This release
adds no migration. A site already on 0.1.7 may upgrade: its head is already `0044`.

## Before you upgrade

- **The schema head goes from `0032` to `0044`: eleven migrations, `0033` to `0040` and `0042` to
  `0044` (there is no `0041`).** Every one is additive and `NULL`-able except `0033`, which adds a
  `NOT NULL` column that every existing row reads as `'en'`. Nothing is dropped, rewritten or
  backfilled. Rows written before the upgrade keep their stored English sentence and show it, in
  English, on a Turkish page; only rows written after the upgrade carry a message code. The list is
  under "Schema". Ten of the eleven add nullable columns with no default and no rewrite of the table.
  `0033` adds `app_user.ui_language` with a default that is dropped again in the same step, then a
  check constraint, which scans the `app_user` table once (a table of one row per account). Expect the
  migration step to take seconds, not minutes, and no extra disk beyond the columns' later content.
  The upgrade takes its own backup before it migrates, as every upgrade does. A site already on
  `0044` runs no new migration.
- **A repair of failed rule-match windows, on by default** (RM-2). After each live
  rule-match pass the collector re-reads recent windows that are `FAILED`, oldest first, so a
  never-fired event rule does not stay `INSUFFICIENT_DATA` for the whole health span because of one
  failed search. Four new settings, all optional; an existing `.env` without them gets the defaults:
  - `RULE_MATCH_REPAIR_ENABLED` (default `true`; inert while `RULE_MATCH_COLLECTION_ENABLED` is off);
  - `RULE_MATCH_REPAIR_MAX_AGE_SECONDS` (default 86,400; allowed 60 to 604,800): the oldest window
    start it will re-read. It must stay inside the console's event retention: a window whose events
    QRadar has already rotated out is never re-read, because an empty answer would be false proof of
    silence;
  - `RULE_MATCH_REPAIR_MAX_WINDOWS_PER_RUN` (default 6; allowed 1 to 168);
  - `RULE_MATCH_REPAIR_MAX_ATTEMPTS` (default 3; allowed 1 to 20): repair attempts per window, on top of
    the live ones (`RULE_MATCH_MAX_WINDOW_ATTEMPTS`, default 3), so a window is tried at most six times
    by default and is then left `FAILED`.

  The backend refuses to start, with the setting named, when collection and repair are both on and
  `RULE_MATCH_REPAIR_MAX_AGE_SECONDS` is below `RULE_MATCH_WINDOW_SECONDS` or not below
  `RULE_MATCH_RETENTION_DAYS` in seconds, or when `RULE_MATCH_REPAIR_MAX_WINDOWS_PER_RUN` is above
  `RULE_MATCH_MAX_WINDOWS_PER_RUN` (default 6). The repair sends Ariel searches through the same permit
  pool as the rest (`ARIEL_MAX_CONCURRENT_SEARCHES`, `ARIEL_GLOBAL_MAX_CONCURRENT_SEARCHES`), at most
  the per-run number above, and none in a tick in which a live search failed. If the console's event
  retention is shorter than a day, lower `RULE_MATCH_REPAIR_MAX_AGE_SECONDS` before the first
  collection after the upgrade, or set `RULE_MATCH_REPAIR_ENABLED=false`. Windows that were skipped
  beyond the catch-up horizon and `TRUNCATED` windows are never repaired.
- **`doctor` has one new check and one new status.** `rule_match_coverage` (runbook `OPS-R65`) counts the
  `FAILED` and `TRUNCATED` rule-match windows inside `RULE_HEALTH_WINDOW_DAYS` in one query. It is `PASS`
  with none, `WARN` with some (the line gives the counts, the oldest window, the UTC time the last
  affected window leaves the health span, how many are still repairable and how many were skipped), and
  `FAIL` when it cannot read the table. When `RULE_MATCH_COLLECTION_ENABLED` is off it reports the new
  status `SKIP`, which does not raise the exit code (statuses were `PASS`, `WARN`, `FAIL`). A script that
  reads `doctor --json` must accept `SKIP`. Right after the upgrade a site that has had failed windows
  gets a `WARN` here; it is the measurement, not a new fault. Runbook entry `OPS-R65` is in
  `docs/OPERATIONS.md`. 0.1.8 adds no `doctor` id.
- **`rollback` checks more before it changes anything.** If a service was enabled after the version it
  would return to (the `mcp` profile, for example), the upgrade recorded no image for it. `rollback`
  now uses the old version's tag for that service: it takes the image from the local store, pulls it
  on an online host, and on an offline host refuses, changing nothing, until the old bundle's images
  are loaded or the profile is removed from `COMPOSE_PROFILES`. The refusal names the service and the
  image. A rollback of the 0.1.6 → 0.1.8 path to `0.1.6` does not need this unless you enable such a
  service after the upgrade. See `docs/OPERATIONS.md`, "Geri alma (`rollback`)".
- **The Timescale policy task commits each table on its own** (FIX-5). Retention and compression
  reconciles no longer run in one transaction, so none holds a catalog lock while it waits for the next
  table; a reconcile that loses a deadlock is retried (up to three attempts, pauses of 0.5 s and 1 s).
  Compression is enabled with `ALTER TABLE` only on a hypertable where it is not enabled yet. No setting
  changes and nothing has to be done.
- **Audit rows with an empty client address.** The search-cadence and history-backfill routes now record
  `NULL` in `source_ip` when the client host is empty (they recorded an empty string). The address and
  the user agent of every audited route come from one helper and are cut at 64 and 512 characters, the
  widths of the `audit_log` columns. A script that matches an empty `source_ip` must match `NULL`.
- **Percent-point spelling in the sentences the backend writes.** Newly written WAF and IPS sentences
  write a change as "+29.7 pp" with a no-break space before "pp", as the interface does (the percent
  sign got the same treatment in 0.1.6). Rows written before the upgrade keep their old text.
- **The frontend image includes `next-intl` 4.14.9 (MIT; `NOTICE` names it).** The published image has
  it; a production host builds nothing. A site coming from 0.1.6 meets this dependency on this upgrade.
- **Unchanged for the site, said once so nobody looks for them:** no setting other than
  `RATE_LIMIT_DEFAULT` has a new default or a new meaning. `RATE_LIMIT_DEFAULT` is `1200/minute`, as
  the opening says; a `.env` that sets the name keeps its value, and the login and search-execution
  limits are unchanged. No permission was added or renamed, no retention changed, no scheduled task was
  added or removed, `docker-compose.yml` and `docker-compose.prod.yml` are unchanged, and no `doctor` id
  other than `rule_match_coverage` was added or renamed. `install` writes nothing new to `.env`. The
  release workflow and the CI changes of the 0.1.7 period (REL-2, CI-3, CI-3b, DEBT-6) touch the build,
  not the site.

## New for the operator

- **Server-rendered pages load with the session.** The failure and the fix are in the opening. Nothing
  is configured for it.
- **A sign-in after a sign-out no longer needs a reload.** The stale state is in the opening.
- **`RATE_LIMIT_DEFAULT`.** If `.env` sets it, remove the line or raise it (opening). `docs/OPERATIONS.md`
  OPS-R21 says what a 429 for every analyst means when `FORWARDED_ALLOW_IPS` is already correct: the
  server-rendered pages share the frontend container's address, and the limit is raised.
- **The interface language is a per-account choice**, carried from the 0.1.7 work this release includes
  for a site still on 0.1.6. An analyst picks English or Turkish on the account page (`/account`,
  "Interface language"). The choice is stored on the account (`app_user.ui_language`, `en` or `tr`,
  default `en`) and in the browser in the cookie `ba_locale` (one year, `SameSite=Lax`, `Secure` over
  HTTPS). On the next sign-in the cookie is set from the account. **What does not change with the
  language:** the `qradar-dash` commands and their output, log lines, setting names, permission names,
  `doctor` ids and statuses, runbook ids, HTTP codes, and the API's English text.
- **`docs/MANUAL-TEST.md` and `docs/MANUAL-TEST-RESULTS.md`.** The manual test for this release is the
  0.1.8 section. It upgrades a 0.1.6 site and then tests the upgraded one. The 38 checks marked
  `[çekirdek]` are the production path. The sheet's "Migrasyon başı sonra" field is `0044`.
- **Rule-match repair, the `doctor` status `SKIP`, and the stricter `rollback`** are under "Before you
  upgrade". `docs/OPERATIONS.md` has `OPS-R65` and "Geri alma (`rollback`)".

## For the analyst

- **Server-rendered pages open after sign-in.** Alerts, rules, anomalies, behavior, log sources,
  searches, WAF, IPS, outage policy and classification no longer show "Your session has expired. Sign
  in again to continue." on a valid session. Signing in again after signing out opens the dashboard
  without a reload.
- **The interface is available in Turkish, on every page**, for a site coming from 0.1.6. The account
  page chooses the language. Dates keep UTC and their zone; Turkish numbers use the Turkish grouping.
  The page-by-page list, the terms that stay English, the in-app guide (`/guide`) and the families
  whose new rows read in the reader's language are in `docs/releases/0.1.7.md` under "For the analyst".
  That file is in this checkout. 0.1.8 does not add a page or a language.
- **What still shows English** (expected, not a fault; `docs/MANUAL-TEST.md` MT-59 lists the same, and
  0.1.8 does not close these gaps):
  - every sentence stored before the upgrade, on a Turkish page too: there is no backfill;
  - the titles and descriptions of the alerts that the Phase A, WAF, IPS and property-watch engines raise,
    and their "condition recovered" resolution reason;
  - the catch-all collector's history sentences and the reasons a history reading gives for the catch-all
    scope; the other history families are in Turkish;
  - the text of notifications to Teams, e-mail, Slack, webhook and syslog;
  - free text from QRadar, a provider or a library, and text a person typed, and QRadar's names;
  - readiness details and the WAF and IPS pipeline run reports;
  - the glossary terms, setting names, permission names and HTTP codes;
  - the server's 404 text, capacity 409 reasons and version-conflict messages.

## API

0.1.8 changes no request or response shape. A site coming from 0.1.6 meets the 0.1.7 wire changes on
this upgrade. The field-by-field list is `docs/releases/0.1.7.md` under "API". The shape is:

- **A coded sentence.** Beside a sentence field `X` the response carries `X_code` (a string, or `null`)
  and `X_params` (an object, or `null`). A list of sentences gains a parallel `X_codes`. A sentence
  already inside a structured body gains `code` and `params` inside it. A row written before the
  upgrade, or a sentence with no code, answers `null` for the code and params; read the English field
  then. Every existing sentence field keeps its English text.
- **Refusals.** An HTTP error body keeps `detail` and gains `detail_code` and `detail_params` (and
  `detail_codes` when `detail` is a list). Status codes are unchanged.
- **`PUT /api/v1/me/preferences`** is new. Body `{"ui_language": "en" | "tr"}`. It needs a session and
  no permission. The answer is the same body as `GET /api/v1/me`. `GET /api/v1/me` gains `ui_language`.
- **Changed values, not shapes,** from the same work: newly written WAF and IPS sentences spell a
  percentage-point change "+29.7 pp" with a no-break space, and the search-cadence and history-backfill
  audit rows record `NULL` for an empty client address.

## Schema

The head goes from `0032` to `0044` for a site on 0.1.6. All are additive; the upgrade runs them, and
existing rows are unchanged. 0.1.8 adds no migration. The head stays `0044`. A site already on 0.1.7
is already at `0044`. `0043` and `0044` were renumbered when they were merged (their numbers rise along
the chain, and there is no `0041`); the chain is `0032`, `0033`, ..., `0040`, `0042`, `0043`, `0044`.

- `0033` adds `app_user.ui_language`, `VARCHAR(2) NOT NULL`, with a check that allows `en` and `tr`;
  every existing account reads `en`.
- `0034` adds the nullable JSONB column `anomaly_explanation_dimension.detail_i18n`.
- `0035` adds `reason_i18n` (nullable JSONB) to `detection_coverage` and `detection_coverage_snapshot`.
- `0036` adds `rule_health_snapshot.reason_i18n`.
- `0037` adds `property_watch.last_status_reason_i18n`, `pw_anomaly.explanation_i18n`,
  `pw_anomaly.suppression_reason_i18n` and `pw_anomaly_transition.reason_i18n`.
- `0038` adds `log_source_anomaly.explanation_i18n`, `log_source_anomaly.suppression_reason_i18n`,
  `anomaly_state_transition.reason_i18n`, `waf_anomaly_transition.reason_i18n` and
  `ips_anomaly_transition.reason_i18n`.
- `0039` adds `waf_anomaly.explanation_i18n` and `waf_anomaly.suppression_reason_i18n`.
- `0040` adds `alert.title_i18n`, `alert.description_i18n`, `alert.resolution_reason_i18n` and
  `custom_rule.last_status_reason_i18n`.
- `0042` adds `search_execution.error_message_i18n`.
- `0043` adds `history_backfill_scope.reason_i18n`.
- `0044` adds `ips_anomaly.explanation_i18n` and `ips_anomaly.suppression_reason_i18n`.

Each `_i18n` column holds `{"code": ..., "params": {...}}` beside the English text column it belongs
to. A rollback is a restore of the upgrade's backup, as always; no migration is ever run downward on a
site.

## Upgrade

```bash
git fetch --tags && git checkout v0.1.8
./qradar-dash upgrade 0.1.8
```

The upgrade is allowed from `0.1.6`, and from `0.1.7` (that site is already at head `0044`, and 0.1.8
adds no migration). A `0.1.4` site goes through `0.1.6` first, as the notes of that release describe;
the upgrade to `0.1.8` from an older release stops with
`upgrade refused: 0.1.8 requires at least 0.1.6`, after it has moved the image prefix and pulled the
`0.1.8` images. The upgrade takes its own backup before it migrates, as every upgrade does. After it,
`/api/v1/version` reports `migration_head` `0044`. The collection families resume on their cadence;
the pages show "stale" or "not collected" until the first cadence after the upgrade has passed, and that
is correct.

On a host with no registry access, make the bundle on a connected host from the same checkout
(`./qradar-dash bundle --output DIR` writes `qradar-dash-0.1.8-bundle.tar` in that directory; without
`--output` the file is written in the current directory, and an existing file is not overwritten), copy
it over, and run, in the installation directory:

```bash
tar -xf /path/to/qradar-dash-0.1.8-bundle.tar --exclude=images.tar
./qradar-dash upgrade 0.1.8 --offline /path/to/qradar-dash-0.1.8-bundle.tar
```

After the upgrade, run the `[çekirdek]` checks of `docs/MANUAL-TEST.md` (0.1.8 section) and fill
`docs/MANUAL-TEST-RESULTS.md`. If the upgrade or the checks fail and the site must return to 0.1.6,
follow `docs/OPERATIONS.md`, "Geri alma (`rollback`)": it restores the backup the upgrade took and
starts the previous images. On the 0.1.6 → 0.1.8 path that previous release is 0.1.6. Data written
since the upgrade, including accounts created after it and the language stored on an account, is kept
only in the broken copy it leaves. The browser's `ba_locale` cookie is not in that database; the next
sign-in writes the account's language back into the cookie. After `rollback` the checkout is the old
tag, so a return to 0.1.8 is `git fetch --tags && git checkout v0.1.8` and then
`./qradar-dash upgrade 0.1.8`.
