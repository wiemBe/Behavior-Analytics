# Behavior Analytics 0.1.9

`RATE_LIMIT_DEFAULT` is now enforced. It was never enforced in 0.1.6, 0.1.7 or 0.1.8: with the
shipped FastAPI, Starlette and slowapi versions, the middleware that should have applied the
default found no handler for the included API routes and exempted them all. Only the login limit,
the property-watch preview limit and the account lockout fired. From 0.1.9 the default limit
applies to every API route, and a site may see 429 answers it never saw. A refused request now
carries the `X-RateLimit-*` and `Retry-After` headers on every limited route, and a rate-limited
page says so instead of showing a load error.

Server-rendered pages now count under each analyst's own address. The frontend container is a
second trusted forwarder (`FRONTEND_EDGE_IP`, default `172.28.10.11`), so the pages an analyst
opens no longer share one rate-limit key with everybody. `install` and `upgrade` write the two
trusted addresses into `.env`, and `doctor` warns when the list does not trust the frontend.

The rest of the release is smaller. The offense collector no longer skips offenses behind a full
page. A stalled offense watermark is visible in `doctor`. The pre-upgrade backup carries the
install answers, and `rollback` hands them to the older release. The alert pages, the WAF and IPS
incident details and the history reasons speak the interface language.

The schema head stays `0044`. This release adds no migration.

## Before you upgrade

- **`RATE_LIMIT_DEFAULT` is now enforced (FIX-8).** It was never enforced in 0.1.6, 0.1.7 and
  0.1.8; only the login limit (`RATE_LIMIT_LOGIN`, `300/minute`), the property-watch preview limit
  and the lockout were. From 0.1.9 the default limit (`1200/minute`, unchanged) applies to every
  route under `/api/v1` except `GET /api/v1/health/live` and `GET /api/v1/health/ready`, which
  stay unlimited: they are the container healthcheck and the poll `install`, `upgrade` and
  `doctor` use. `POST /api/v1/searches/{search_id}/run` carries `RATE_LIMIT_SEARCH_EXECUTION`
  (`10/minute`), the same limit the property-watch preview already had. A site may see 429 answers
  it never saw. Limits count per client key **and per path**: one page render of about 21 API
  calls counts once against each path's bucket, not 21 times against one bucket. A refused request
  is answered with `X-RateLimit-*` and `Retry-After` headers and the body
  `{"detail": "rate limit exceeded", "limit": ...}`. `install` still does not write
  `RATE_LIMIT_DEFAULT`; a `.env` that sets the name keeps that value. A site that raised it for
  0.1.8 may lower it again.
- **Server-rendered pages count under each analyst's own address (RL-1).** The frontend is a
  second trusted forwarder. `.env` gains `FRONTEND_EDGE_IP`, default `172.28.10.11` — the address
  after `PROXY_EDGE_IP` (default `172.28.10.10`) on the `edge` network (`EDGE_SUBNET`, default
  `172.28.10.0/24`) — and `FORWARDED_ALLOW_IPS` now holds two addresses. The frontend forwards the
  last hop of `X-Forwarded-For`, so Uvicorn resolves the analyst's own address and the limiter
  keys on it. A forged earlier hop never wins. `install` and `upgrade` write both names: `upgrade`
  appends the frontend to a non-empty list once and writes `FRONTEND_EDGE_IP` when the line is
  missing; a `.env` with no `FORWARDED_ALLOW_IPS` line, an empty value or `*` is not rewritten.
  `doctor` checks the pair as `forwarded_allow_ips`: empty or `*` is FAIL, a list that lacks the
  frontend address is WARN, a list that has it is PASS. Two checks stay with the operator:
  `FRONTEND_EDGE_IP` must sit inside `EDGE_SUBNET` and differ from `PROXY_EDGE_IP`, and the
  installer does not verify either — Compose refuses a bad address when the container is created.
  **What an operator with an external proxy must do:** the proxy must **append** the client
  address to `X-Forwarded-For` (nginx: `$proxy_add_x_forwarded_for`); a proxy that passes the
  header through unchanged or overwrites it lets the client choose its rate-limit key. `install`
  appends the frontend address to the operator's list once; an empty list refuses before the
  backend starts (`external proxy: FORWARDED_ALLOW_IPS in .env is empty. The backend is not
  started.`). Never write `*`. Runbook: `docs/OPERATIONS.md`, OPS-R21.
- **The schema head stays `0044`.** This release adds no migration; the newest migration in the
  tree is `0044`. A site coming from 0.1.8 is already at head `0044` and runs no migration.
- **The pre-upgrade backup carries the install answers, and `rollback` handles them (FIX-9).**
  Every backup now copies `.secrets/install.answers` to `install.answers`, mode `0600`, beside
  `env.bak`. The copy is made only when the live file is a regular file at mode `0600`; a missing
  file, a symlink or any other mode is omitted, the file is not read, and the backup still
  completes. The answers file holds paths and names, never a secret. Without the copy, a rollback
  to an older release left a 0.1.9 answers file in place and the older `install --non-interactive`
  refused it (`unknown key FRONTEND_EDGE_IP`). `rollback` now restores that copy to
  `.secrets/install.answers` (atomically, mode `0600`), or — when the backup has none, as every
  backup made by 0.1.8 or earlier — strips from a private live file every `KEY=` line whose key
  the older release does not know, naming each one: `Removed answer key <name> (unknown to
  <version>).` Comments, blank lines and known keys stay; a file whose keys are all known is left
  untouched. A live file that is missing, a symlink or not mode `0600` is left as it is, and the
  database rollback continues. The refusals happen before the confirmation prompt and before any
  container stops. `restore` does not restore the answers file.
- **A stalled offense watermark warns, and a truncated offense read no longer skips offenses
  (FIX-7, FIX-6).** When offense collection is cut at `OFFENSE_MAX_PAGES` and no timestamp in the
  page is safe to advance past, the watermark row records the stall and `doctor` reports it: the
  `watermarks` check says `<N> watermark(s) stalled at the page ceiling: offense_snapshot` and
  prints runbook `OPS-R66` (OPS-R30 stays the entry for a real failure). A clean run clears the
  signal. Before FIX-6, a read cut at the page ceiling advanced the watermark onto the last row's
  timestamp and the offenses that shared it were never read. The collector now advances only to
  the newest timestamp strictly below the last row, so the boundary offenses are read again on the
  next run; the run is reported as partial and is not counted as a provider failure. A group of
  offenses that shares one timestamp and is larger than one page does not drain until
  `OFFENSE_MAX_PAGES` is raised or the timestamps diverge; the watermark stays and the report says
  so.
- **A rate-limited page says so with the retry time (POL-5).** A 429 on a server-rendered page is
  no longer shown as a load failure. List pages, detail pages and the admin helpers say "Too many
  requests came from this address within a minute. Nothing is wrong with the data or the backend.
  Try again in N s." — or "Try again in a minute." when the answer named no wait. Turkish pages
  say the same in Turkish. A Dashboard widget whose refresh is refused keeps its data and shows
  the short note "too many requests, try again in N s".

## New for the operator

- **`doctor` gains one new check id: `forwarded_allow_ips`** (RL-1). It reports the two trusted
  addresses: empty or `*` is FAIL, a list that lacks the frontend address is WARN, a list that has
  it is PASS. The stall sentence (FIX-7) lives in the existing `watermarks` check, with no new id.
  The status set is unchanged (`PASS`, `WARN`, `FAIL`, `SKIP`).
- **`RATE_LIMIT_DEFAULT` is a real limit now** (opening and "Before you upgrade"). Runbook
  OPS-R21 says what a 429 for every analyst means and what an external-proxy site must check.
- **Backup and rollback carry the install answers** (FIX-9, "Before you upgrade"). The backup
  table in `docs/OPERATIONS.md` names `install.answers`, and §5.1 and §5.4 of
  `docs/OPERATIONS-DESIGN.md` say what `rollback` does with it.
- **A fresh site no longer carries a standing offense-age warning.** A clean empty offense run
  moves the `offense_snapshot` watermark to the run time (POL-3), so the `watermarks` age warning
  does not stay after the first clean collection on an empty console. A failed or truncated run
  still does not move it.
- **The navigation has an "Administration overview" entry** (`/admin`, Turkish "Yönetim özeti"),
  first in the Administration group (POL-4). The pages it links to need no permission of their
  own; the hub filters its cards by what the signed-in analyst may see.

## For the analyst

- **Alert pages speak the interface language (MSG-7b).** The title, description and
  "condition recovered" reason of alerts raised by the Phase A, WAF, IPS and property-watch
  engines, and the failure reason in a failing search's evidence, are stored as message codes. On
  a Turkish page they render in Turkish: the Phase A title is `{log_source} üzerinde
  {anomaly_type}`, and the anomaly type comes from the interface's label set ("Hacim düşüşü",
  "Olay yok" and the rest). Alerts written before the upgrade keep their stored English text.
  Notifications to Teams, e-mail, Slack, webhook and syslog stay English.
- **The history-deferral reason is a message code (MSG-8c).** The sentence
  `deferred: no Ariel permit within N s` on `/admin/history-backfill` and in the property-watch
  history block renders in Turkish as "Ariel izni N sn içinde alınamadı; okuma ertelendi". Rows
  written before the upgrade keep their English text.
- **A suppressed WAF or IPS incident says why (POL-2).** The incident detail shows a
  "Suppression reason" line ("Bastırma nedeni") under the identity row when a reason is stored,
  for example the maintenance window. An incident that was never suppressed shows nothing.
- **Names instead of raw codes (POL-1).** The six Phase A anomaly types are labelled in both
  languages (Parsing degradation / Ayrıştırma bozulması and the rest) wherever they were shown
  raw. Search-execution error pills are labelled (Turkish "Zaman aşımı", "Kapasite"; English keeps
  the codes). On an alert whose evidence repeats the description sentence, the repeated sentence is
  omitted; figures stay. The profile-version-conflict banner gains its full stop, and the WAF
  administration note reads "Çizgi".
- **Honest states instead of zeros (POL-3).** When the log-source inventory sync failed, the two
  Dashboard log-source widgets say the figures are not a count of zero and link to log sources;
  when inventory has never been collected, they say there is no count. The offenses page shows an
  em dash instead of 0 while nothing has been collected. A search-cadence family that is off, or
  has never run and has no future run, shows an em dash in "Next run".
- **Turkish leftovers closed (POL-3).** Disabled collection copy says `kapalı` instead of `false`,
  the silent-source sentences name "(Olay yok anomalisi)", the searches page and guide say
  "kaydedilmemiş, anlık yazılmış AQL", and the run banner and result-trend note say "Hata türü
  Zaman aşımı". English keeps its tokens (`false`, `(NO_EVENTS anomaly)`, "Error type TIMEOUT").
- **A rate-limited page says so** (POL-5, "Before you upgrade").

**Known limits.** A rate-limited refresh on a widget that already shows data keeps the data and
shows the short note only ("too many requests, try again in N s"), not the full sentence. Requests
refused by the CSRF check are answered before the rate limit and are not counted against any
bucket — a cheap refusal, by design.

## API

0.1.9 changes no request shape and no existing field's meaning. Three responses gain fields:

- **WAF and IPS anomaly detail** (`GET /api/v1/anomalies/{id}`) gains `suppression_reason`,
  `suppression_reason_code` and `suppression_reason_params` (POL-2). All three are nullable and
  `null` unless the row carries a suppression reason; a row written before the upgrade answers its
  stored text with a `null` code. The list endpoints carry none of the fields.
- **The log-source overview** (`GET /api/v1/overview`) gains `inventory_state` on the counts
  (POL-3): `NOT_COLLECTED`, `COMPLETE` or `FAILED`. The provider error itself is never exposed.
- **Each search-cadence row** (`GET /api/v1/admin/search-cadence`) gains `enabled` (POL-3).

A 429 answer now carries `X-RateLimit-*` and `Retry-After` headers on every limited route
(FIX-8). The MSG-7b and MSG-8c sentences ride the coded-sentence fields 0.1.8 already defined;
newly written rows fill them, old rows keep answering `null`.

## Schema

The head stays `0044`. 0.1.9 adds no migration, and a site coming from 0.1.8 runs none. A
rollback is a restore of the upgrade's backup, as always; no migration is ever run downward on a
site.

## Upgrade

```bash
git fetch --tags && git checkout v0.1.9
./qradar-dash upgrade 0.1.9
```

The upgrade is allowed from `0.1.8`. A site on 0.1.6 upgrades to 0.1.8 first; the 0.1.8 notes
describe that path. An older release stops with `upgrade refused: 0.1.9 requires at least 0.1.8`,
after it has moved the image prefix, written the frontend addresses into `.env` and pulled the
`0.1.9` images. Nothing is migrated: the head stays `0044`, and after the upgrade
`/api/v1/version` reports `migration_head` `0044`. The upgrade takes its own backup before it
migrates, as every upgrade does, and that backup carries the install answers. The collection
families resume on their cadence; the pages show "stale" or "not collected" until the first
cadence after the upgrade has passed, and that is correct.

On a host with no registry access, make the bundle on a connected host from the same checkout
(`./qradar-dash bundle --output DIR` writes `qradar-dash-0.1.9-bundle.tar` in that directory;
without `--output` the file is written in the current directory, and an existing file is not
overwritten), copy it over, and run, in the installation directory:

```bash
tar -xf /path/to/qradar-dash-0.1.9-bundle.tar --exclude=images.tar
./qradar-dash upgrade 0.1.9 --offline /path/to/qradar-dash-0.1.9-bundle.tar
```

If the upgrade fails and the site must return to 0.1.8, follow `docs/OPERATIONS.md`, "Geri alma
(`rollback`)": it restores the backup the upgrade took — including the install answers — and
starts the previous images. Data written since the upgrade is kept only in the broken copy it
leaves. After `rollback` the checkout is the old tag, so a return to 0.1.9 is
`git fetch --tags && git checkout v0.1.9` and then `./qradar-dash upgrade 0.1.9`.
