# Behavior Analytics 0.1.15

For the analyst: every anomaly family can be triaged beside its detector state; a NEW anomaly nobody took is closed as stale after three days; the detail page shows related activity on the same log source and an Investigate in QRadar block the product does not run; the alert and anomaly lists keep a view in the URL, with relative time chips; Noisy sources ranks log sources and a tuning page previews a threshold change before it is saved; Traffic ranks WAF endpoints and IPS destination addresses; Don't alert this again holds one condition's alert back for 1, 7 or 30 days, with a break-through for extreme evidence; `/admin/alert-policy` sets which sources alert, are only recorded or go into a daily digest, and lists the active quiet periods; Queue shows what changed since your last visit across five kinds of waiting work; the tuning page replays a criticality change and shows a read-only low-volume model. The top bar's "Data to" carries its date when the instant is on another UTC day.

For the operator: the schema head moves to `0059`. Two new permissions, `anomaly:triage` and `alert:suppress`, gate triage and suppression writes. With no `alert_policy` row, no `alert_suppression` row and `ALERT_POLICY_DEFAULT` left at `ALERT`, each anomaly engine opens the same alerts as in 0.1.14. The hourly stale-triage job does run at its default of 3 days, and a `PATCH` of `custom_thresholds` now returns 422 for an unknown key or an out-of-bounds value. A daily digest is scheduled and sends nothing unless a policy says `DIGEST`. One new setting, `LOW_VOLUME_MODEL_PREVIEW_ENABLED`, defaults to `true` and gates a read-only view. Opening `/queue` stores the signed-in account's last-visit marker in this application's own table.

## Before you upgrade

- **The schema head moves to `0059`.** Five additive migrations run once, in order: `0055_anomaly_triage`, `0056_stale_triage_disposition`, `0057_alert_policy_digest`, `0058_alert_suppression`, `0059_user_queue_marker`. See Schema. Nothing is backfilled. `alembic check` on the task databases reported no drift after `0057`, `0058` and `0059`.
- **A 0.1.14 site upgrades directly.** `min_from` is `0.1.14`. A 0.1.13 site upgrades to 0.1.14 first. `qradar-dash` reads this file before any `.env` edit, bundle load or pull and refuses an older site with `upgrade refused: 0.1.15 requires at least 0.1.14; nothing was changed`.
- **No `.env` edit is required for alerting to stay as in 0.1.14.** `ALERT_POLICY_DEFAULT` defaults to `ALERT`. With no `alert_policy` row the resolver returns that default (`backend/app/alerts/policy.py`, `resolve`), and the Phase A, WAF, IPS and property-watch engines pass `settings.alert_policy_default` into the gate. SOC-17c's characterisation tests open the same alerts as the pre-17c engines when the table is empty. `outage_alert_policy` is a separate table and is not replaced. `0058` creates `alert_suppression` empty, so no condition is quiet until an analyst creates a quiet period; with no row the suppression gate finds nothing and the engines take the pre-0058 path.
- **The stale-triage job runs at the default, with no new setting required (SOC-1c).** `TRIAGE_STALE_CLOSE_DAYS` defaults to `3` (`0` disables it). It is documented in `docs/CONFIGURATION.md` and is not in `.env.example`. An hour after the new beat is up, an anomaly that is still `NEW` (no triage row counts as `NEW`) and was detected at least three days ago is closed in triage only: status `CLOSED`, disposition `STALE`, actor `system`, note from `triage.stale_auto_close`. The detector lifecycle and the alert are not written. The job takes at most 500 candidates per family per run (`STALE_TRIAGE_BATCH_SIZE`) and continues on the next hour. A backlog larger than that drains at 500 per family per hour.
- **`DIGEST_HOUR_UTC` defaults to `7` and is in `.env.example`.** `API_MAX_EXPORT_ROWS` defaults to `10000` and is documented in `docs/CONFIGURATION.md` only; it is not in `.env.example`. `LOW_VOLUME_MODEL_PREVIEW_ENABLED` defaults to `true` and is in both `.env.example` and `docs/CONFIGURATION.md`. Leaving `ALERT_POLICY_DEFAULT`, `DIGEST_HOUR_UTC`, `TRIAGE_STALE_CLOSE_DAYS`, `API_MAX_EXPORT_ROWS` and `LOW_VOLUME_MODEL_PREVIEW_ENABLED` unset is the behaviour described below.
- **Existing `analyst` and `detection_engineer` rows do not gain `anomaly:triage` or `alert:suppress` from the upgrade.** Both strings are on the `admin` and `analyst` roles in `backend/app/services/seed.py`, and `detection_engineer` copies the `analyst` list, so a freshly seeded site has them on all three. `admin:*` already satisfies both (`Principal.has`), so an administrator can triage and quiet a condition as soon as the new stack is up: `GET /api/v1/me` expands every `PERM_*` the principal has, and the triage and quiet-period blocks read that list. `read:*` grants neither. The seeded `viewer` role holds only `read:*`. `upgrade` does not call `ensure_default_roles`. That function adds missing strings to the four seeded role rows and is reached by `python -m app.cli.users create-admin` (which also creates or resets that username, sets `must_change_password` and revokes its sessions) and by `python -m app.services.seed` (do not run it on an installed site: it commits only after an inventory sync and can insert a mock console). There is no route that edits a role's permission list. A viewer keeps read-only triage and reads the quiet periods without being able to create or end one.

## For the analyst

- **Triage sits beside the detector state on every anomaly family (SOC-1a, SOC-1b).** Log source, WAF, IPS and property watch. A custom-rule breach is not a triage family: the block says triage is not available for that kind. An anomaly with no triage row reads as `NEW`, unassigned; nothing was backfilled. The block shows status, owner, disposition, note and who updated it, in UTC. Take it sets the owner to the signed-in account and the status to `IN_PROGRESS`. Assign takes the owner string the API stores. Close requires one of `TRUE_POSITIVE`, `BENIGN_TRUE_POSITIVE`, `NOISE`, `COLLECTION_PROBLEM`, `KNOWN_CHANGE`, and an optional note of at most 1000 characters. Reopen sends `IN_PROGRESS` and keeps the history. Comments are activity of kind `COMMENT`, at most 2000 characters, and do not move the version. A stale `expected_version` is a 409: the block names who changed it, turns the controls off and offers "Load their version". Without `anomaly:triage` the block is read-only and names that permission. The detector state and the triage status stay two labels.
- **The anomaly list gains Triage, Owner and Age, and the alert list uses human titles (SOC-1b).** Owner is "Unassigned" when there is none, never a blank cell; a row whose triage block is absent says "not reported". Filters `triage_status`, `owner` (`me`, unassigned, or a name) and `disposition` stay in the URL. Age is whole minutes next to the UTC start, and does not tick until the page is loaded again. The observed-to-expected cell shows the percent beside the multiplier when a ratio exists; a `NO_EVENTS` row says "No events for N min". Alert titles use the catalog label for the detector ("Volume drop on …") when the alert carries `title_code`; an unmapped title stays as sent. The alert list links the first source anomaly, and the detail lists them; the anomaly page links the alert it can see on one bounded alert read.
- **A NEW anomaly nobody took is closed after three days (SOC-1c).** The label is "Auto-closed: stale". The close dialog does not offer `STALE`. The list filter `disposition=STALE` does. Reopen works as for any other closed item. The detector condition can still be open: lifecycle filters still find it. The alert is unchanged.
- **Related activity on the anomaly detail (SOC-3a, SOC-3b).** Heading "Related activity" plus the UTC window and the pad. The pad control is 30 min, 1 h, 2 h (default) and 6 h, kept as `pad` in the URL. Three lists, each with its own state: offenses on this source (newest snapshot, link to the offense page in this product), other anomalies on this source (detector state and triage status as separate columns; the anchor is not in the list), and rules named by those offenses. A rule missing from the catalog reads "Rule not in the catalog (QRadar id N)". A null matched-event count reads "Not measured", never 0; a measured zero is 0; a lower bound reads "≥ N". Each list shows at most 20 rows and the total when there are more ("20 of 34"). An empty OK list means none were found in what was collected. Not collected, stale, partial and truncated each have their own sentence. A property watch with no single log source is not applicable. The product reads stored rows only; it does not call QRadar for this block.
- **Investigate in QRadar (SOC-2).** On the anomaly detail (every family), the alert detail, the offense detail and the log-source detail. The block is titled "Investigate in QRadar" and says "This query is for you to run in the QRadar console. The product does not run it." It shows the AQL, Copy AQL, Copy window (the UTC start and stop) and, when the console host is usable, Open in QRadar (a new tab, `rel="noopener noreferrer"`). No token is put in the link. When the stored console host is missing, empty, invalid or carries credentials, there is no Open control and the block says why. A value the builder will not put in AQL (a quote, a backslash or a control character) is omitted and named in the notes, not escaped. The Open address is built in `backend/app/pivot/aql.py`. SOC-2 recorded those URL forms as unverified on a lab console: a wrong form breaks the open, not the copied AQL.
- **Alert filters, facet counts and a link that reproduces the view (SOC-7a, SOC-7b, FIX-33).** On `/alerts`: status, severity (several), kind (the URL key stays `family`), log source (repeatable), a title search of at most 100 characters, and sort. Counts beside status, severity and kind come from `GET /api/v1/alerts/facets`. Each count ignores that control's own filter, so choosing HIGH still shows how many the other severities have under the rest of the filters. A zero is a measured zero. "All statuses (N)" is the sum of the status counts, not the filtered list total. If the facet read fails, the counts are left out and the list still loads; zeros are not drawn for a failed read. There is no per-detector filter. On `/alerts` and `/anomalies`, chips `1h`, `24h`, `7d` and `30d` stay relative in the URL (`range=24h`), and Custom writes absolute UTC `since` and `until`. The window is printed as absolute UTC next to the chips. Copy link copies the address of the parsed view. An unknown alert-list value is dropped and named ("Ignored an unknown severity value."). With no chip and no Custom range, the alert list is unbounded ("All time"); the anomaly list keeps its default 24-hour window.
- **Noisy sources (SOC-17a, SOC-17a-ui, FIX-34).** Behavior nav, "Noisy sources", `/behavior/noise`, after Sources. Phase A log sources only. The table ranks monitored sources by incidents in the selected window (7 or 28 days), with alerts, a noise share and the worst deviation. The share and the worst deviation always cover 28 days, including when the window is 7 days; the page says so. The share is absent until at least five incidents on that source were closed with a disposition; the cell then shows the noise count over the closed count. A not-judged source says "Not judged" once, then the rest of the reason ("No reliable baseline for this weekday and hour."), and is not shown as quiet. Counts the platform did not measure say "not measured", never 0. Sources with no incident in the window are a collapsed footer ("No incidents on N sources"), not hidden. A partial window says how many of the requested days are stored. Each row links to `/behavior/noise/{id}` ("Tune"). The alerts count links to `/alerts` filtered to that source. The page needs `read:anomalies`.
- **Tuning one source (SOC-17b, SOC-17b-ui).** `/behavior/noise/{id}` answers what would change if this source were tuned this way. Per-detector counts for 7 and 28 days come first. The form is the six knobs plus criticality, pre-filled from the effective values, each marked default, criticality, LAB_MODE or custom. Preview runs the same detectors over the stored window (7 or 28 days) from a clean normal state and shows current M against proposed N. It is not a forecast. The page sends `criticality` only when the form's value differs from the stored one, and a changed criticality is replayed: the result says "Replayed with criticality HIGH (stored: MEDIUM)." Under LAB_MODE it says criticality changes no detection threshold, so the counts do not depend on it. Recorded history is its own line, not M. A detector the chosen direction does not run reads "not run (direction)", never 0. Save stays off until a preview has run for exactly the values in the form; an edit dims the result ("Values changed. Preview again before saving."). Save is the existing log-source `PATCH` and needs `log_source:write`; without it the form is read-only, names that permission, and Preview still runs. Narrowing `direction` from `both` tells the analyst that open incidents of the disabled direction on this source will be closed. The page does not show how many: the `PATCH` response has no count. A custom `open_after` still overrides the criticality matrix in the replay, as it does in the engine, so the line names the criticality the replay used and is not proof that the counts moved. The line is shown for `COMPLETE` and `PARTIAL` results. `INSUFFICIENT_DATA` shows the reason and no counts. `TOO_LARGE` (more than 50,000 buckets) shows no count and offers 7 days. A source in maintenance now is refused rather than replayed.
- **Traffic by destination (TOP-1a, TOP-1b, FIX-34).** Behavior nav, "Traffic", `/behavior/traffic`. WAF endpoints and IPS destination addresses, switched by `view` in the URL, with window, sort, order, page size and source in the URL. Windows are 5 min (the newest complete bucket), 1 hour, 24 hours, 7 days and 28 days. Each row has a trend of events/s for that row (a line, no marker on every point; one bucket has no line). Average and peak are events/s. A null rate is a dash, not a zero. A retired row is marked. A missing or partial bucket is stated on the page. Events not attributed to a listed endpoint are stated, so the host totals are a lower bound. Export CSV downloads the same window and sort, without the page, and says large exports are cut at the server's limit. The file is refused as a formula when a cell starts with `=`, `+`, `-`, `@`, a tab or a carriage return. A forbidden page names `read:anomalies`. A WAF row opens `/behavior/waf/sources/{id}`. An IPS row opens the anomaly list for that entity. No enabled profile links to the admin page that sets it up (`/admin/ips-sources` for IPS).
- **Low-volume model on the tuning page (SOC-17e, SOC-17e-ui).** Below the replay block on `/behavior/noise/{id}`, a section "Low-volume model", shown for a monitored source. It opens with the statement that it is a shadow view: no detector uses it and it opens no alert. It reads the stored weekday × UTC-hour baseline cells over the last 28 days and fits each cell with a Poisson or a negative-binomial model, then counts the buckets whose upper or lower tail is below p = 0.001. A cell's median is pulled toward the source's pooled median with k = 8 (the page shows the weight on the cell). A "new normal" is proposed when the last 7 days' median leaves the cell's own 5th to 95th percentile range with at least 8 samples on both sides; it is a proposal, nothing is written back to a baseline. One grid per metric (event count in events per bucket, average rate in events per second) shows the buckets below p per cell, with a cell detail below it. A calibration table counts, per detector, the replayed flags and how many fall on incidents already closed as `NOISE`; a refused replay shows dashes and the reason, never 0. States: scored, insufficient data, not judged, partial (the covered days are stated; a missing bucket is a gap, not a zero), the switched-off setting (naming `LOW_VOLUME_MODEL_PREVIEW_ENABLED`), an unknown source, forbidden (naming `read:anomalies`), expired session and a failed read with Retry. A cell with too few samples, no variance, a dispersion above 4 or observations that are not whole counts shows no tail count and says why. The stored rate is usually fractional, so its cells are often insufficient and the event-count cells carry the scores.
- **Don't alert this again (SOC-17d, SOC-17d-ui).** On the alert detail and on the anomaly detail of every family (log source, WAF, IPS, property watch). The button opens a form: quiet for 1, 7 or 30 days (no other length, and no "forever"; the page points to a record-only policy for that), a reason of 3 to 1000 characters, an owner that defaults to the signed-in account, "Quiet the whole source (every detector)" for a log source, WAF or IPS condition (not for a property watch), and "This is a planned change" with a required change or ticket reference. The page never sends a detector: the server derives the condition from the alert or anomaly. Incidents are still recorded, with their state and transitions; only the alert and its notification are held back, and one hit is recorded per incident. A banner shows "Quiet until <UTC time> by <owner> (N days)", the incidents recorded while quiet, the reason, the kind (analyst or planned change, with its reference), the scope, the alerts that broke through, and End now (with a confirmation). Saving a quiet period for a condition that already has one moves its end to the chosen number of days from now; past 30 days from its start the server answers 422 and says to end it and create a new one. An alert with no detector condition or no anomaly id has no button. Without `alert:suppress` the page names that permission; reading the banner needs `read:alerts` and `read:anomalies`, and a role with only one sees a forbidden state that names them. A quiet period changes no baseline and sets no maintenance flag.
- **A quiet period lets extreme evidence through (SOC-17d).** The alert opens as it would without the quiet period, and the quiet period stays in force. A volume or count spike breaks through at a ratio of at least 10 times normal (Phase A `VOLUME_SPIKE` also when the baseline is zero and the bucket holds at least 10 times `anomaly_min_bucket_events`); a volume or property-watch drop at a ratio of at most 0.1; a WAF block, error or client-error ratio at an observed share of at least 0.5 and at least 3 times the baseline share; a WAF client or IPS source concentration at a share of at least 0.8 and 3 times the baseline; an IPS block-ratio shift at a rise of at least 0.5 absolute and 3 times; a property-watch value that disappeared always; a Phase A `NO_EVENTS` silence when the source's criticality is `CRITICAL`. The WAF new-endpoint and client-fanout detectors, the IPS new-destination-port detector, the property-watch new-value and new-combination detectors, and the six other Phase A detectors never break through; the rule has no magnitude for them. A WAF, IPS or property-watch spike whose ratio is undefined (a zero baseline) is not evidence and stays quiet.
- **`/admin/alert-policy` (SOC-17c-ui, SOC-17d-ui).** Administration nav "Alert policy". The daily digest block comes first: due hour, last run and its state, sources listed, recipients, and a worded `NOT_CONFIGURED`, `NO_RECIPIENTS` or `FAILED` with a link to where it is fixed; the per-console table sits below the policies and appears only with more than one console. A short explainer says what `ALERT`, `RECORD_ONLY` and `DIGEST` do. The policies table lists each row by source or class, family, detector (or "All detectors"), mode and when it last changed in UTC; a note on `NO_EVENTS` rows says a record-only outage policy wins. Add, Edit and Remove need `admin:outage`; without it the table is read-only and names the permission. A refusal from the server (422) is shown next to the field; removing a row someone else already removed refreshes the list. The three mode labels share one neutral style. A "Quiet periods" section follows the policies: every active quiet period and every active maintenance window, with subject, family, detector, kind, owner, reason, end in UTC, incidents recorded, and End (with a confirmation) for a quiet period when the account holds `alert:suppress`. A maintenance window is read-only there ("Set on the log source") and its incidents column is a dash, not 0. The empty sentence is "Nothing is quiet. Every condition alerts by its policy." Loading, error with retry and forbidden are each worded.
- **Queue (SOC-4a, SOC-4b, SOC-4c).** Behavior nav, "Queue", `/queue`, first in the group. One ordered list of what is waiting, from five kinds: anomalies (the four families; alerts of an anomaly appear as a chip on its row), alerts that no anomaly row accounts for, open offenses, sources awaiting classification review and catch-all senders awaiting review. An anomaly is waiting while its triage is `NEW` (no row counts) or `IN_PROGRESS`, its detector state is `OPEN`, `RECOVERING` or `RESOLVED`, and it is not suppressed. Order is severity, then the longest wait. A row carries a text label New or Updated against the comparison time, and the page says which time that is (your last visit, or the last 24 h on a first visit). Scope (Mine, Unassigned, All), kind, family, severity and "New or updated only" stay in the URL; the comparison chips are 8 h, 24 h and 7 d. A strip names each source's state: failed to load, hidden from this account (naming the permission), not collected, stale (with its age), or partly read. A failed source makes the total a lower bound, and the page and its pager say "at least". The queue stops at 1000 rows and says to narrow it. **Opening the page moves your marker**: after a load with no failed source, no chosen comparison and no scope, filter or page narrowing it, the page posts the load's own time to `POST /api/v1/queue/seen`, and the labels of that visit stay while you filter or page. A narrowed or compared view says that the marker was not moved. A change from another session shows "Another session moved your marker" with Reload. Any signed-in account may open the page; a kind the account may not read shows as hidden, naming its permission, instead of failing the page.
- **The top bar's "Data to" carries its date on another UTC day (UX-7).** Same rule as the Dashboard widgets since 0.1.13: `2026-11-03 21:05:00 UTC` when the instant is not today in UTC, and the clock only when it is. "Refreshed" stays the browser's clock. On `/admin/siem-load`, a stale or partial health sentence with a blank reason no longer keeps an empty tail.

## For the operator

- **`anomaly:triage` is the only new permission (SOC-1a).** It is not implied by `read:*` or by `alert:ack`. Reading triage needs `read:anomalies`, which `read:*` already grants, so a viewer sees the state and cannot change it. Writes are `PATCH /api/v1/anomalies/triage/{family}/{anomaly_id}` and `POST .../comments`. Closing without a disposition is 422. `STALE` on a `PATCH` is 422 ("STALE is set only by the stale triage job"). An unknown family is 422 after the write check, so a caller without `anomaly:triage` gets 403 first. A missing anomaly is 404. A comment is not written to the audit log; a state change is, without the comment text. Who may triage on an existing site is under "Before you upgrade".
- **Triage rows leave with the anomaly (SOC-1a).** There is no foreign key across the four anomaly tables. Each family's retention delete also deletes that family's triage rows, in one bounded batch; the activity rows leave by `ON DELETE CASCADE`. A triage row for an anomaly that is still stored is kept. Audit rows for the state change remain.
- **`GET /api/v1/anomalies` and the detail responses gain `triage` (SOC-1a).** One lookup for the page, not one per row. New list filters: `triage_status`, `owner` (`me` and `none` are reserved and cannot name a real subject), `disposition`. The 0.1.14 rule stands: `active_only=true` with no `since` has no lower bound.
- **The stale job is hourly and race-safe (SOC-1c).** Beat entry `close-stale-triage`, every 3600 s. Per family it reads candidates, then one conditional write (`status` still `NEW`, version and `updated_at` still old enough) plus an insert that does nothing on conflict, then one activity insert. A row an analyst changed between the read and the write is skipped until the next hour. `IN_PROGRESS` and `CLOSED` are never eligible. A `NEW` row whose `updated_at` is newer than the cutoff (a reopen) is not eligible. Detection time is `detected_at` on `log_source_anomaly`, `waf_anomaly`, `ips_anomaly` and `pw_anomaly`. Equal to the cutoff counts as old enough.
- **`PATCH /api/v1/log-sources/{id}` refuses a bad `custom_thresholds` with 422 (SOC-17b).** Unknown keys, wrong types, out-of-bounds values, an unknown `by_type` anomaly type, and a `by_type` value outside the same bounds. The detail names the field as `custom_thresholds.<location>: <message>`. The six bounded keys are `deviation_z` (0.5 to 20), `spike_ratio` (1.01 to 100), `drop_ratio` (0.01 to 0.99), `min_absolute_delta_events` (0 to 1,000,000), `open_after` (1 to 10) and `direction` (`both`, `spike`, `drop`). These keys stay accepted with a type check only: `min_bucket_events`, `silence_grace_buckets`, `min_parsed_ratio`, `max_unknown_ratio`, `delay_interval_multiple`, `cardinality_drop_fraction`, `collection_error_threshold`, `repeated_payload_intervals`, `resolve_after`. A stored row is still read exactly as before, including a key this model would refuse; a stored `direction` other than `spike` or `drop` is treated as `both`. Validation runs on the `PATCH` body only.
- **`direction` skips one volume detector, and narrowing it closes that detector's open incidents (SOC-17b, FIX-35).** The default is `both`, so with nothing configured both detectors run, as in 0.1.14. `spike` skips `VOLUME_DROP`. `drop` skips `VOLUME_SPIKE`. The other detectors ignore it. A `PATCH` that newly excludes a detector resolves that source's `OPEN`, `CANDIDATE` and `RECOVERING` incidents of that detector in the same transaction, writes an `AnomalyStateTransition` to `RESOLVED` with reason `noise.tuning.direction_disabled` ("the direction was disabled by a tuning change"), returns the detector state to `NORMAL`, and resolves the condition's alert through the existing alert service, which enqueues the resolution notification. Switching back to `both` closes nothing. The audit detail can carry the preview the client sent (`at`, `window` as a day count, `current`, `proposed`, `state`); that block is stored and not applied. The closed-incident count is in the audit detail, not in the response.
- **The preview is a read (SOC-17b).** `POST /api/v1/noise/sources/{id}/preview` needs `read:anomalies`, writes nothing and is not audited. Body: `window_days` 7 or 28, `thresholds`, and an optional `criticality` (FIX-37). Omitted or `null`, the proposed fold uses the stored criticality, which is what a 0.1.14 client gets; a value is used for that fold's resolver calls only and is never stored. An unknown value is 422 and nothing is computed. The response gains `effective` with the `criticality` the proposed fold resolved and `lab_mode`; it is present even when the counts are null. Under LAB_MODE criticality has no detection effect, so a proposed value gives the same counts. A client that compares the whole body to a 0.1.14 response must tolerate `effective`. It costs four statements whatever the fleet size, a proposed criticality included. States: `COMPLETE`, `PARTIAL`, `INSUFFICIENT_DATA` (fewer than 7 covered days, more than 10 percent of covered buckets not judged, not monitored, or in maintenance now), `TOO_LARGE`. Counts are null when the preview is not available, never a smaller number standing in for a missing bucket. It judges stored buckets against the baseline stored now, and against the source's current business hours, maintenance flag and outage policy. The noisy-sources list and detail are `GET /api/v1/noise/sources` and `GET /api/v1/noise/sources/{id}` (`window` 7 or 28, else 422). They read Phase A incidents only. `noise_share` is null while the closed-with-disposition denominator is below 5.
- **Alert policy is per source or class, per family, and optionally per detector (SOC-17c).** Tables `alert_policy` and `alert_digest_run`. Modes are `ALERT`, `RECORD_ONLY` and `DIGEST`. Precedence is source+detector, then source, then class+detector, then class, then `ALERT_POLICY_DEFAULT`. Within one step an instance row beats a global row. Property watch has no class scope; its source is the watch. WAF and IPS source scope is the log source. The incident and its transitions are written first. `RECORD_ONLY` and `DIGEST` then skip the alert and its notification. Resolution of an alert that already exists is not gated: a later `RECORD_ONLY` still resolves it when the condition ends. For `NO_EVENTS`, a `RECORD_ONLY` outage policy still wins and is not turned back into an alert. The family switches (`waf_alerting_enabled`, `ips_alerting_enabled`, `pw_alerting_enabled`) stay outside this policy: a family that is off raises nothing. A time-boxed suppression is consulted after this policy returns `ALERT` (next bullet). Custom rules, scheduled searches, inventory and instance alerts are not gated. The policy table is loaded once per engine run.
- **The policy API and its page (SOC-17c, SOC-17c-ui).** `GET /api/v1/alert-policy` and `GET /api/v1/alert-policy/digest` need `read:alerts`. `PUT /api/v1/alert-policy` upserts one row and `DELETE /api/v1/alert-policy/{id}` removes one; both need `admin:outage` and write an audit row with before and after. An unknown detector, an unknown source, a class scope on property watch, or an unknown class is 422 and writes nothing. `/admin/alert-policy` is the page over this API; it has no permission on its navigation entry, reads with `read:alerts` and writes with `admin:outage`. The page keeps its detector lists per family as constants that mirror the backend enums, so a detector added later in the backend needs a line in `frontend/src/lib/alertPolicy.ts` before the page can pick it; the API validates, so a missing line cannot store a wrong row.
- **Suppression is a third layer, after the policy (SOC-17d).** Tables `alert_suppression` and `alert_suppression_hit`. An engine consults it only when the policy decision is `ALERT`; `RECORD_ONLY`, `DIGEST`, a `RECORD_ONLY` outage policy for `NO_EVENTS` and a family switch that is off return before it, so they write no hit. The open rows are loaded once per engine run, on first use: no statement on a run that reaches no alert, one `SELECT` on a run that does, whatever the fleet size. When a quiet period applies and the evidence does not break through, the engine writes one `alert_suppression_hit` per incident (`ON CONFLICT DO NOTHING` on `(suppression_id, anomaly_id)`) and opens no alert; the incident, its state and its transitions are written as before, and the `suppressed` column is not set by it (fleet and overview counts still include the incident). When the evidence breaks through, the alert opens through the existing dedup and the quiet period stays. A row whose `ends_at` has passed never applies, so the next bucket that reaches the alert step opens the alert. Resolution is not gated. The subject is the log source for Phase A, WAF and both IPS kinds, and the watch for property watch. A detector-specific row beats a subject-wide row (`detector_type` null). At most one open row exists per `(family, subject_id, detector_type)`; creating over an expired one closes it first, in the same transaction. The rule table is `BREAKTHROUGH_RULES` in `backend/app/alerts/suppression.py`; a detector with no entry does not break through, and a unit test fails on a missing entry. The WAF open-cost bound in `test_waf_scale.py` moved from 9 to 10 statements for the suppression load, which does not grow with endpoints.
- **Suppression routes (SOC-17d).** All under `/api/v1`, all mounted with `read:alerts`. `POST /alerts/{alert_id}/suppress` and `POST /anomalies/{family}/{anomaly_id}/suppress` need `alert:suppress`; the anomaly route also needs `read:anomalies`, and its family is parsed after both checks. Body: `days` (1, 7 or 30), `reason` (3 to 1000 characters), optional `owner` (defaults to the caller; empty is 422), `whole_source`, `kind` (`ANALYST` or `KNOWN_CHANGE`) and `reference` (required for `KNOWN_CHANGE`, refused otherwise). Unknown keys are refused, so a client cannot name a detector; the server derives the condition. `whole_source` is 422 for property watch. A second POST for an open condition extends that row to now plus `days`, and past 30 days from its start is 422; the database also holds that as a CHECK. `POST /suppressions/{id}/end` needs `alert:suppress`, takes no body, sets `ended_at` (the earlier of now and `ends_at`) and `ended_by`, and returns an already-ended row unchanged. `GET /suppressions` (`active=true` by default) lists the open rows with their hit counts and, in the active list, one read-only `MAINTENANCE` row per source whose maintenance window is on and not past `maintenance_until`; it reads the suppressions in one query, all hit counts in one grouped query, and the maintenance sources in one more when active, whatever the row count. `GET /suppressions/for/{family}/{anomaly_id}` needs `read:anomalies` as well and returns the active row or `null`, its hit count and the alerts of the subject opened inside the window. Rows are ended, never deleted. A create, extend and end each write an audit row (`alert_suppression.create`, `.extend`, `.end`) with the structural before and after; the reason text is on the row only and is not in the audit detail. A planned change (`KNOWN_CHANGE`) writes no maintenance flag and excludes nothing from any baseline.
- **`GET /api/v1/noise/sources/{id}/model` (SOC-17e).** Needs `read:anomalies` (the noise router's guard). A read: it writes nothing, adds no audit row, opens no alert and changes no detector, lifecycle or migration. It returns the 28-day count model for one Phase A log source: per weekday-hour cell and metric (`event_count`, `average_eps`) the fit (Poisson when the dispersion is 0.8 to 1.25, otherwise negative binomial by method of moments), the shrunk median (k = 8), the level-shift proposal, and the count of buckets with a tail below p = 0.001; plus a calibration row per detector against closed `NOISE` incidents. A cell that cannot be fitted carries null tail counts and a reason code (`noise.model.too_few_samples`, `no_variance`, `mean_zero`, `not_counts`, `dispersion`, `nb_parameters`). States are `OK`, `INSUFFICIENT_DATA`, `NOT_JUDGED` and `PARTIAL`. A refused replay (not monitored, in maintenance, fewer than 7 covered days, more than 10 percent of covered buckets not judged, or more than 50,000 buckets) leaves the calibration counts null. For an existing source under the bucket cap the read is four statements, a refused replay included. With `LOW_VOLUME_MODEL_PREVIEW_ENABLED=false` the route answers 404 `low-volume model preview is not enabled`, distinct from 404 `log source not found`, and issues no SELECT.
- **Queue API (SOC-4b, SOC-4a).** `GET /api/v1/queue` needs authentication only; each of its five sources checks its own read permission (`read:anomalies`, `read:alerts`, `read:offenses`, and `read:fleet` for source reviews and catch-all senders) and reports `FORBIDDEN` naming it, with its statement not run. Query: `scope` (`mine`, `unassigned`, `all`), `kind`, `family`, `severity` (repeatable), `new_only`, `since`, `limit` (1 to 100, capped at the page-size setting) and `offset`; `offset + limit` above 1000 is 422, and a `family` without a `kind` narrows the queue to anomalies. `since` is never stored: a future one, one older than `API_MAX_RANGE_DAYS`, or an unreadable one is 422. Every source reports `OK`, `FORBIDDEN`, `FAILED` (its own savepoint; its count is null and `total_exact` is false), `NOT_COLLECTED`, `STALE` or `PARTIAL`, so a failed source is a lower bound and never a zero. The statement count per request does not grow with the number of sources or rows. `POST /api/v1/queue/seen` takes `{as_of, expected, all_sources_ok}` and moves the caller's marker; any signed-in principal may call it, for its own row only. It refuses `all_sources_ok: false` (409 `queue.marker.source_failed`), an `as_of` more than 2 minutes in the future (422 `queue.marker.future`) and an `expected` that is not the stored value (409 `queue.marker.changed`, with the current marker); an `as_of` not after the stored marker is a 200 with `advanced: false`. The stored value is the request's `as_of`, never the server clock. `GET /queue` compares with the stored marker when one exists and no `since` is sent (`marker.kind` `STORED`), with `since` as `OVERRIDE`, and with the last 24 hours as `DEFAULT_WINDOW`. A `GET` writes nothing. The marker row (`user_queue_marker`, keyed by the principal's subject) has no foreign key and no cleanup job: a deleted account leaves its row behind. No audit row is written when the marker moves.
- **Rule silence and rule storm detectors exist as pure code only (SOC-6b).** `backend/app/rules/anomalies.py` and a `RULE` entry in `backend/app/anomaly/capabilities.py`. No engine, task, table, route or page uses them, `RULE_DETECTORS` is not in `all_detectors()`, which the detector list in `backend/app/api/routes/anomalies.py` reads. Nothing about them is visible in 0.1.15.

- **The daily digest sends mail only for incidents whose final mode is `DIGEST` (SOC-17c).** Beat `run-alert-digest`, every 300 s, after `DIGEST_HOUR_UTC` (default 7, range 0–23). For digest date `D` the window is `[D-1 at that hour, D at that hour)` in UTC, not "the 24 hours before the tick". A later tick the same UTC day still covers that date. A date whose tick never ran is not filled in on the next day. One row per instance and date, under the collector advisory lock, so a second tick does not send again. A crash after the mail is handed to the relay and before the row is committed can send that date again on the next tick. Maintenance-suppressed incidents are excluded. The message lists at most 50 sources and then says how many more sources there were. Recipients are the union of `NOTIFY_EMAIL_RECIPIENTS` and every enabled e-mail recipient; a recipient's `alert_types` filter does not apply to the digest, and saving a recipient with `digest` in `alert_types` is 422. `GET /api/v1/admin/email/templates` still lists a `digest` template; the `alert_types` array on that response omits `digest`. Empty `SMTP_HOST` records `NOT_CONFIGURED` and sends nothing. No recipients records `NO_RECIPIENTS`. A configured relay with no `DIGEST` incidents records `EMPTY` and sends nothing. A delivery failure records `FAILED` and a code only, never the relay's text. With no policy row and the default `ALERT`, the job therefore writes a row and does not send mail. That is the sense in which alerting is unchanged.
- **`GET /api/v1/alerts` accepts the filters the page sends (SOC-7a, FIX-33).** Repeatable `severity` and `log_source_id`, `family`, `q` (title only, at most 100 characters, blank refused, `%` and `_` are literals), `since` and `until` on `opened_at`, `sort` (`created_at`, `severity`, `updated_at`) and `order`. Unknown values are 422. Neither bound sent means no time filter, which is the previous list. One bound uses the anomaly routes' one-day rule: no `since` covers the day before the end, no `until` ends now, and a range wider than `API_MAX_RANGE_DAYS` is 422. The body always includes `filters_applied`, `sort` and `order`. A client that compares the whole body to a 0.1.14 response must tolerate those fields. `family` is derived from `source_type`. There is no detector-type filter. `log_source_id` matches an alert whose subject belongs to that source; an alert with no single source (a scheduled search, the offense-collection alert, a fleet-class rule, a type- or group-scoped property watch) is not matched. Facet counts exclude their own dimension; `total` is the list total under every filter. One statement either way.
- **Traffic reads and the CSV (TOP-1a).** `GET /api/v1/behavior/waf/sources/{id}/traffic` and `.../ips/sources/{id}/traffic`, and the same paths with `.csv`, on the behavior router (`read:anomalies`). `limit` is 1 to 1000; above that is 422. The CSV is cut at `API_MAX_EXPORT_ROWS` (default 10000) in sort order, says so with `X-Export-Truncated`, and is not cut silently. `INSUFFICIENT_DATA` and `NOT_COLLECTED` return a header-only file and `X-Export-State`. A source with no usable bucket is `INSUFFICIENT_DATA` and no items, never zeros. Rank is over the whole set. The series is one extra statement for the page. No migration and no new index.
- **`GET /api/v1/anomalies/related/{family}/{anomaly_id}` (SOC-3a).** `pad` is `30m`, `1h`, `2h` or `6h`. Needs `read:anomalies`. It does not call QRadar. Offense freshness is the `offense_snapshot` watermark: no run is not collected; consecutive failures, or an age past `OFFENSE_STALE_AFTER_SECONDS` (900 by default, unchanged), is stale. Rules follow that state. A rule with no measured window has `matched_events` null. The read is a fixed number of statements (13 for a log-source anchor). It scans snapshots for the instance; no index was added.
- **Pivot routes (SOC-2).** `GET /api/v1/anomalies/{id}/pivot`, `GET /api/v1/alerts/{id}/pivot`, `GET /api/v1/offenses/{id}/pivot`, `GET /api/v1/log-sources/{id}/pivot`. Each uses its parent's permission. The console host is the instance's stored `console_host`, not an installer setting named `QRADAR_CONSOLE_FQDN`. An internal API address stored there is the host the Open link uses. The window is clamped from 1 minute to 168 hours. A log source with no other range is the last hour. The product never submits the AQL.
- **A failed notification-source read no longer drops the QRadar health window (FIX-31).** The inventory read runs in a savepoint. A statement PostgreSQL rejects rolls back that savepoint, and the run row is still written with the notification part not collected and reason `notification_source_unreadable`. The metric part is stored as usual. A run that does not hit that error is unchanged from 0.1.14 (HLT-8).
- **The QRadar health page's blank reason (UX-7).** A stale or partial metrics sentence with a null, empty or blank reason uses a catalog sentence that has no reason tail. A present reason is unchanged. English catalog only.

## Manual test

`docs/MANUAL-TEST.md` is still the 0.1.13 → 0.1.14 guide. No 0.1.15 section was written, and no check was added. The core stays 38 checks. DOC-11, inside that 0.1.14 section, corrected three checks so a tester does not score a known case as a Fail:

- **MT-02.** A console that has just booted can fail the lines that reach it for several minutes. The upgrade itself sends nothing to QRadar. The guide says not to start the upgrade while `qradar_tls`, `qradar_auth` or `geo_country_source` is `FAIL` for that reason, to note the lines, and to run `doctor` again once the console answers. A `FAIL` that remains after the console answers is still a Fail.
- **MT-09.** `anomaly_evaluation` can be `WARN` right after the upgrade's restart (runbook OPS-R61) while the engine catches up buckets the stop left unjudged. The check allows the settle margin, one beat and two evaluation ticks — five minutes — before it counts a live bucket. The line clears once a later tick has judged the sources it named.
- **MT-143.** The Network tab shows one `401` on `GET /api/v1/me` before the login `POST`: the sign-in page reads the session on load, and an anonymous window has no `qd_session` cookie. That request is the start of the log, not a Fail. A `401` among the requests after the login `POST` is still a Fail.

The results page was not changed. The checks that would cover triage, related activity, noisy sources, traffic, alert filters, the digest, quiet periods, the alert policy page, the queue and the low-volume model were not added.

## Schema

The head is `0059`. 0.1.15 adds five migrations. Each is additive. No server default outlives the revision except the timestamps on the new tables. `alembic check` stays clean on a database migrated to this head (SOC-1c, SOC-17c, SOC-17d and SOC-4a reports; the round-trip tests for `0057`, `0058` and `0059` run the check at head only, FIX-38).

- `0055_anomaly_triage` (SOC-1a): tables `anomaly_triage` and `anomaly_triage_event`. One triage row per `(family, anomaly_id)`, families `log_source`, `waf`, `ips`, `property_watch`. Status `NEW`, `IN_PROGRESS`, `CLOSED`. Disposition, until `0056`, is `TRUE_POSITIVE`, `BENIGN_TRUE_POSITIVE`, `NOISE`, `COLLECTION_PROBLEM`, `KNOWN_CHANGE`. A `CLOSED` row must have a disposition. No backfill: a missing row reads as `NEW`.
- `0056_stale_triage_disposition` (SOC-1c): the disposition check gains `STALE`. The downgrade raises while any row has `STALE`, and restores the `0055` list once those rows are gone. A site rollback does not run this downgrade.
- `0057_alert_policy_digest` (SOC-17c): tables `alert_policy` and `alert_digest_run`, and the `email_template` alert-type check gains `digest`. `alert_policy` is unique on instance, scope kind, scope value, family and detector, with nulls not distinct, so one global "every detector" row does not collide with another. `alert_digest_run` is unique on instance and digest date. The downgrade raises while an `email_template` row has `alert_type = 'digest'`, then restores the old check and drops the two tables. A site rollback does not run this downgrade.
- `0058_alert_suppression` (SOC-17d): tables `alert_suppression` and `alert_suppression_hit`, with no SQL enum and no foreign key to the subject tables (the family names the table). `alert_suppression` holds one row per quiet period: family (`log_source`, `waf`, `ips`, `property_watch`), subject, detector (null means every detector), kind (`ANALYST` or `KNOWN_CHANGE`), reason, owner, `starts_at`, `ends_at`, `ended_at`, `ended_by`, reference and creator. CHECKs: a reason that is not empty, `ends_at > starts_at`, `ends_at <= starts_at + interval '30 days'`, and a reference when the kind is `KNOWN_CHANGE`. A partial unique index on `(family, subject_id, detector_type)` where `ended_at IS NULL`, nulls not distinct, allows one open row per condition; it cannot test the clock, so the create path closes an expired row first. `alert_suppression_hit` is one row per held-back incident, unique on `(suppression_id, anomaly_id)`, and goes with its suppression by `ON DELETE CASCADE`. The downgrade drops both tables and the index, and raises nothing: it deletes every quiet period. A site rollback does not run this downgrade.
- `0059_user_queue_marker` (SOC-4a): table `user_queue_marker`, one row per principal subject (`owner_subject` primary key, `marked_at`, `previous_marked_at`, `updated_at`), with no foreign key because the subject is a plain string. The downgrade drops the table. A site rollback does not run this downgrade.

A site coming from 0.1.14 runs them once, in order. A rollback is a restore of the upgrade's backup, as always. No migration is ever run downward on a site. The backup's schema is `0054`.

## Upgrade

```bash
git fetch --tags && git checkout v0.1.15
./qradar-dash upgrade 0.1.15
```

The upgrade is allowed from `0.1.14`. A site on 0.1.13 upgrades to 0.1.14 first; the 0.1.14 notes describe that path. An older release is refused before anything is touched: the refusal comes from the checkout's own `docs/releases/0.1.15.md`, read before any `.env` edit, bundle load or pull — `upgrade refused: 0.1.15 requires at least 0.1.14; nothing was changed`. If that file is missing, unreadable or not for 0.1.15, the refusal names the file and changes nothing either.

`upgrade` prints the deciding pair before the writers stop, while the 0.1.14 backend is still the running image, so that pair says `0054` (`PASS migration_head database and image are at 0054`, and `db_connect`). The migrate container then runs the five revisions once (`Running upgrade 0054 -> 0055`, then `0055 -> 0056`, `0056 -> 0057`, `0057 -> 0058` and `0058 -> 0059`). Alembic's two start-up lines (`INFO  [alembic.runtime.migration] Context impl PostgresqlImpl.` and `INFO  [alembic.runtime.migration] Will assume transactional DDL.`) are expected. After the new stack is up, `upgrade` prints the deciding pair again, both checks `PASS`, and `migration_head` says `0059`. `/api/v1/version` reports `migration_head` `0059`. The upgrade takes its own backup before it migrates, as every upgrade does, and that backup carries the install answers. The restart empties Redis, as in every upgrade. The collection families resume on their cadence; the pages show "stale" or "not collected" until the first cadence after the upgrade has passed, and that is correct.

The stale-triage job starts with the new beat. It does not wait for a setting. See "Before you upgrade".

On a host with no registry access, make the bundle on a connected host from the same checkout (`./qradar-dash bundle --output DIR` writes `qradar-dash-0.1.15-bundle.tar` in that directory; without `--output` the file is written in the current directory, and an existing file is not overwritten), copy it over, and run, in the installation directory:

```bash
tar -xf /path/to/qradar-dash-0.1.15-bundle.tar --exclude=images.tar
./qradar-dash upgrade 0.1.15 --offline /path/to/qradar-dash-0.1.15-bundle.tar
```

If the upgrade fails and the site must return to 0.1.14, follow `docs/OPERATIONS.md`, "Geri alma (`rollback`)": it restores the backup the upgrade took — including the install answers and the `0054` schema, which is the head the site had before the upgrade — and starts the previous images. Data written since the upgrade is kept only in the broken copy it leaves. `rollback` runs no `git checkout`; after a successful rollback the operator returns the checkout to the version that now runs (`git checkout v0.1.14`), as that section says. A return to 0.1.15 is then `git fetch --tags && git checkout v0.1.15` and `./qradar-dash upgrade 0.1.15`.
