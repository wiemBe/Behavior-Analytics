# Behavior Analytics 0.1.3

A fix release on top of 0.1.2: no new feature, the same detections and the same data. What changes
is that a large estate keeps collecting, that the watch editor says why a history reading is not
possible, and that `doctor` names the collector it is talking about. No migration comes with it; the
schema head stays `0030`.

- **Collection holds on a large estate.** The live multi-row writes — the IPS entities, entity
  metrics, source buckets and watermarks, the Phase A metrics, the rule metrics, the WAF endpoint
  ledger, the fleet classifications and the inventory types and groups — are now written in
  batches the database accepts at any size. Before, a tick with enough sources, rules or endpoints
  in it failed the write, and none of that tick's rows was stored.
- **The watch editor says what a history reading costs.** The option that asks a watch to read
  its own past is disabled, with the reason, when the server cannot pay for one history step: the
  per-tick history search budget (`PW_BOOTSTRAP_SEARCHES_PER_TICK`) is named when it is the limit
  that binds. Before, the editor allowed the option and the save was refused afterwards.
- **`doctor` names the collector it is talking about.** A known collector name such as
  `geo_countries_destination` is no longer printed as `***redacted***`; these names are constants
  of the code, and the secrets beside them are still masked.
- **The operator runbook matches what an upgrade does.** The upgrade section of
  `docs/OPERATIONS.md` now lists the pre-checks in the order the script runs them, says how often
  `upgrade` and `rollback` print the two deciding doctor lines, and says that a refused upgrade
  has already moved the image prefix and pulled the target images.
- **The code runs on the versions its images already ship.** The code no longer uses the APIs that
  SQLAlchemy 2.1 and pydantic 2.14 deprecate; what the API answers is unchanged.
  `backend/pyproject.toml` now requires SQLAlchemy 2.1 or later, and the images already ship
  2.1.4.
- **The synthetic telemetry lab generator** accepts `newuser.demo` as a fixed username, so a
  property watch can be shown a new value on purpose, and its `--stdout` and `--dry-run` help now
  says that `--stdout` prints the events and still sends them.

**A correction to the 0.1.2 notes.** The 0.1.2 notes said that on a `0.1.0` site `upgrade 0.1.2`
is refused and changes nothing. It is refused, but it first moves the image prefix in `.env` and
pulls the `0.1.2` images; the step through `0.1.1` then pulls `0.1.1` from the new name, which
is published for every release. No container is stopped and the state file is not written. The
0.1.2 notes are left as they are.

**Schema.** No migration; the head stays `0030`.

**Upgrade.**

```bash
git fetch --tags && git checkout v0.1.3
./qradar-dash upgrade 0.1.3
```

The upgrade is allowed from `0.1.2`. An older site is brought up one release at a time, through
`0.1.1` and then `0.1.2`, as the notes of those releases describe; the upgrade to `0.1.3` from
an older release stops with `upgrade refused: 0.1.3 requires at least 0.1.2`, after it has moved
the image prefix and pulled the `0.1.3` images. The upgrade takes its own backup before it
migrates, as every upgrade does; there is nothing to do before or after it.
