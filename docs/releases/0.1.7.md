# Behavior Analytics 0.1.7

This release adds a Turkish interface. Every page, the account's language choice and an in-app guide
(`/guide`) come with it, and most of the sentences the backend writes now carry a message code beside
their English text, so the interface shows them in the reader's language. Eleven migrations come with
it (the schema head goes from `0032` to `0044`); all of them add columns only. A repair pass for
failed rule-match windows, a new `doctor` check and a stricter `rollback` are the changes an operator
meets besides the language.

## Before you upgrade

- **The schema head goes from `0032` to `0044`: eleven migrations, `0033` to `0040` and `0042` to
  `0044` (there is no `0041`).** Every one is additive and `NULL`-able except `0033`, which adds a
  `NOT NULL` column that every existing row reads as `'en'`. Nothing is dropped, rewritten or
  backfilled. Rows written before the upgrade keep their stored English sentence and show it, in
  English, on a Turkish page; only rows written after the upgrade carry a message code. The list is
  under "Schema". Ten of the eleven add nullable columns with no default and no rewrite of the table.
  `0033` adds `app_user.ui_language` with a default that is dropped again in the same step, then a
  check constraint, which scans the `app_user` table once (a table of one row per account). Expect the
  migration step to take seconds, not minutes, and no extra disk beyond the columns' later content.
  The upgrade takes its own backup before it migrates, as every upgrade does.
- **A repair of failed rule-match windows, on by default** (RM-2). After each live
  rule-match pass the collector re-reads recent windows that are `FAILED`, oldest first, so a
  never-fired event rule does not stay `INSUFFICIENT_DATA` for the whole health span because of one
  failed search. Four new settings, all optional; an existing `.env` without them gets the defaults:
  - `RULE_MATCH_REPAIR_ENABLED` (default `true`; inert while `RULE_MATCH_COLLECTION_ENABLED` is off);
  - `RULE_MATCH_REPAIR_MAX_AGE_SECONDS` (default 86,400; allowed 60 to 604,800): the oldest window
    start it will re-read. It must stay inside the console's event retention: a window whose events
    QRadar has already rotated out is never re-read, because an empty answer would be false proof of
    silence;
  - `RULE_MATCH_REPAIR_MAX_WINDOWS_PER_RUN` (default 6; allowed 1 to 168);
  - `RULE_MATCH_REPAIR_MAX_ATTEMPTS` (default 3; allowed 1 to 20): repair attempts per window, on top of
    the live ones (`RULE_MATCH_MAX_WINDOW_ATTEMPTS`, default 3), so a window is tried at most six times
    by default and is then left `FAILED`.

  The backend refuses to start, with the setting named, when collection and repair are both on and
  `RULE_MATCH_REPAIR_MAX_AGE_SECONDS` is below `RULE_MATCH_WINDOW_SECONDS` or not below
  `RULE_MATCH_RETENTION_DAYS` in seconds, or when `RULE_MATCH_REPAIR_MAX_WINDOWS_PER_RUN` is above
  `RULE_MATCH_MAX_WINDOWS_PER_RUN` (default 6). The repair sends Ariel searches through the same permit
  pool as the rest (`ARIEL_MAX_CONCURRENT_SEARCHES`, `ARIEL_GLOBAL_MAX_CONCURRENT_SEARCHES`), at most
  the per-run number above, and none in a tick in which a live search failed. If the console's event
  retention is shorter than a day, lower `RULE_MATCH_REPAIR_MAX_AGE_SECONDS` before the first
  collection after the upgrade, or set `RULE_MATCH_REPAIR_ENABLED=false`. Windows that were skipped
  beyond the catch-up horizon and `TRUNCATED` windows are never repaired.
- **`doctor` has one new check and one new status.** `rule_match_coverage` (runbook `OPS-R65`) counts the
  `FAILED` and `TRUNCATED` rule-match windows inside `RULE_HEALTH_WINDOW_DAYS` in one query. It is `PASS`
  with none, `WARN` with some (the line gives the counts, the oldest window, the UTC time the last
  affected window leaves the health span, how many are still repairable and how many were skipped), and
  `FAIL` when it cannot read the table. When `RULE_MATCH_COLLECTION_ENABLED` is off it reports the new
  status `SKIP`, which does not raise the exit code (statuses were `PASS`, `WARN`, `FAIL`). A script that
  reads `doctor --json` must accept `SKIP`. Right after the upgrade a site that has had failed windows
  gets a `WARN` here; it is the measurement, not a new fault. Runbook entry `OPS-R65` is in
  `docs/OPERATIONS.md`.
- **`rollback` checks more before it changes anything.** If a service was enabled after the version it
  would return to (the `mcp` profile, for example), the upgrade recorded no image for it. `rollback`
  now uses the old version's tag for that service: it takes the image from the local store, pulls it
  on an online host, and on an offline host refuses, changing nothing, until the old bundle's images
  are loaded or the profile is removed from `COMPOSE_PROFILES`. The refusal names the service and the
  image. A rollback of this upgrade to `0.1.6` does not need this unless you enable such a service
  after the upgrade. See `docs/OPERATIONS.md`, "Geri alma (`rollback`)".
- **The Timescale policy task commits each table on its own** (FIX-5). Retention and compression
  reconciles no longer run in one transaction, so none holds a catalog lock while it waits for the next
  table; a reconcile that loses a deadlock is retried (up to three attempts, pauses of 0.5 s and 1 s).
  Compression is enabled with `ALTER TABLE` only on a hypertable where it is not enabled yet. No setting
  changes and nothing has to be done.
- **Audit rows with an empty client address.** The search-cadence and history-backfill routes now record
  `NULL` in `source_ip` when the client host is empty (they recorded an empty string). The address and
  the user agent of every audited route come from one helper and are cut at 64 and 512 characters, the
  widths of the `audit_log` columns. A script that matches an empty `source_ip` must match `NULL`.
- **Percent-point spelling in the sentences the backend writes.** Newly written WAF and IPS sentences
  write a change as "+29.7 pp" with a no-break space before "pp", as the interface does (the percent
  sign got the same treatment in 0.1.6). Rows written before the upgrade keep their old text.
- **The frontend image gained one dependency, `next-intl` 4.4.0 (MIT; `NOTICE` names it).** The published
  image has it; a production host builds nothing.
- **Unchanged for the site, said once so nobody looks for them:** no other setting has a new default or
  a new meaning, no permission was added or renamed, no retention changed, no scheduled task was added or
  removed, `docker-compose.yml` and `docker-compose.prod.yml` are unchanged, and no `doctor` id other
  than `rule_match_coverage` was added or renamed. `install` writes nothing new to `.env`. The release
  workflow and the CI changes of this period (REL-2, CI-3, CI-3b, DEBT-6) touch the build, not the site.

## New for the operator

- **The interface language is a per-account choice.** An analyst picks English or Turkish on the
  account page (`/account`, "Interface language"). The choice is stored on the account
  (`app_user.ui_language`, `en` or `tr`, default `en`) and in the browser in the cookie `ba_locale`
  (one year, `SameSite=Lax`, `Secure` over HTTPS). On the next sign-in or page load on another browser the
  cookie is set from the account, so the choice follows the account. A session with no account (the
  development principal) keeps the choice in that browser only. The change is one audit record,
  `account.preferences.update`, with the old and the new value. No permission is needed: a user changes
  only their own. **What does not change with the language:** the `qradar-dash` commands and their
  output, log lines, setting names, permission names, `doctor` ids and statuses, runbook ids, HTTP
  codes, and the API's English text.
- **`docs/MANUAL-TEST.md` and `docs/MANUAL-TEST-RESULTS.md`.** A step-by-step manual test for this
  release, in Turkish, and the sheet to write the results on. The guide is divided by release, with
  the 0.1.7 section first: it upgrades a 0.1.6 site and then tests the upgraded one. Every check has a
  precondition, an action, an expected result and what to record (`Geçti`, `Kaldı` or `Koşulmadı`). The
  38 checks marked `[çekirdek]` are the production path and are the ones to run on the production
  site; the rest are for a laboratory and, on production, only when the operator has the time. A check
  marked `yalnızca lab` changes what analysts see or leaves a trace that cannot be removed, and is
  written `Koşulmadı` on production. The sheet's "Migrasyon başı sonra" field is `0044`.
- **Rule-match repair and its `doctor` check** (above). The runbook has the entry `OPS-R65`, and
  `docs/CONFIGURATION.md` the four settings.
- **A stricter `rollback`** (above). `docs/OPERATIONS.md`, "Geri alma (`rollback`)", lists the
  refusals.
- **A short runbook change for the `doctor` statuses:** they are now `PASS`, `SKIP`, `WARN`, `FAIL`.

## For the analyst

- **The interface is available in Turkish, on every page.** The top bar, the navigation, the Dashboard
  and its widgets, Behavior and the anomaly list and detail, the WAF, IPS and property-watch pages,
  offenses, alerts, rules, rule statistics and custom rules, the catalog, coverage, the catch-all pages
  and log sources, saved searches, search cadence and history backfill, administration, outage policy,
  classification rules and field mapping, and sign-in and the account page. Dates keep UTC and their zone;
  Turkish numbers use the Turkish grouping (`1.204`, `1.260,0`). The top-bar search shows its results in
  the chosen language and finds a Turkish IPS subject by its Turkish words.
- **A few English terms stay English on purpose,** so an analyst finds the same word in QRadar and in
  the product: `coverage`, `scope`, `baseline`, `offense`, `log source`, `instance`, `custom property`,
  `cron`, `EPS`.
- **The in-app guide, `/guide`.** It is open to every signed-in user, last in the navigation, and exists
  in both languages: 38 sections (how the product works, the honesty states, the expected range, the
  anomaly lifecycle, times and cadence, roles, and one section per page family) and a route map. Each
  page's header links to its section.
- **The backend's sentences read in the reader's language** for these families, from now on in new rows:
  - refusals and validation messages of the API (403, 409, 422, sign-in and CSRF refusals, password
    rules), and the reasons a draft custom rule, a saved search or a profile is refused;
  - rule statistics and detection coverage reasons;
  - the reason beside a rule's health badge;
  - WAF and IPS profile validation and collection-eligibility sentences;
  - property-watch sentences (status, scope, draft validation, the history check, detector and engine
    explanations);
  - Phase A detector explanations and the reasons of lifecycle transitions (Phase A, WAF and IPS);
  - WAF anomaly explanations and suppression reasons, and the IPS ones;
  - the alerts that search runs, custom rules, inventory sync (a new log source), the catch-all review
    (a new sender) and offense-collection freshness raise, with their resolution reasons; the status
    reason of a custom rule;
  - search scheduling and run results (the fixed sentences: the Ariel search failed, the timeout, the
    refused permit, the cron floor, the Ariel budget) and the history backfill's sentences (why a
    source is not read, how far it reached, what the estimate assumes).
- **The rule page and list say why more exactly** when a rule's rule-match windows failed: how many
  windows are complete of those expected, how many failed and how many were never searched, the first
  and last affected window (UTC), and when the rolling span stops holding the last one. The badge and
  its reason now always belong to the same evaluation: a verdict held back by flap damping keeps its
  reason too.
- **What still shows English in 0.1.7** (expected, not a fault; `docs/MANUAL-TEST.md` MT-59 lists the
  same):
  - every sentence stored before the upgrade, on a Turkish page too: there is no backfill;
  - the titles and descriptions of the alerts that the Phase A, WAF, IPS and property-watch engines raise,
    and their "condition recovered" resolution reason (MSG-7b, not in this release);
  - the catch-all collector's history sentences, the reasons a history reading gives for the catch-all
    scope (MSG-8c, not in this release); the other history families are in Turkish;
  - the text of notifications to Teams, e-mail, Slack, webhook and syslog: it is English whatever the
    interface language;
  - free text from QRadar, a provider or a library (`anomaly.error`, Ariel's own error messages, a
    watermark's `last_error`), and text a person typed (a resolution reason, search and rule names,
    descriptions, a classification pattern), and QRadar's names (offense descriptions, log source and rule
    names, tactic and technique names);
  - readiness details and the WAF and IPS pipeline run reports;
  - the glossary terms above, setting names, permission names (`read:anomalies`) and HTTP codes;
  - the server's 404 "not found" text (the interface shows its own sentence), capacity 409 reasons and
    version-conflict messages.

## API

Additive unless stated. Every existing sentence field keeps its English text, byte for byte.

- **The wire shape of a coded sentence.** Beside a sentence field `X` the response carries `X_code`
  (a string, or `null`) and `X_params` (an object, or `null`). A list of sentences gains a parallel
  `X_codes` (a list of `{code, params}` objects, or `null` for an item with no code). A sentence that is
  already inside a structured body (`{message, ...}`) gains `code` and `params` inside it. A param value
  is a string, number, boolean or `null`; or `{"kind": "duration", "seconds": N}`;
  `{"kind": "percent", "ratio": N, "precision": N}`; `{"kind": "points", "points": N, "precision": N,
  "signed": bool}`; `{"kind": "list", "items": [...]}`; or a nested `{code, params}`. A row written before
  the upgrade, or a sentence with no code, answers `null` for the code and params; read the English
  field then. A code is a name, not a promise of its wording: render the English field if you do not
  translate.
- **Fields that gained a pair** (the pair is `<name>_code` and `<name>_params`):
  - alerts (`/alerts`, `/alerts/{id}`): `title`, `description`, `resolution_reason`;
  - anomalies: `explanation` on the unified list, the Phase A, WAF, IPS and property-watch anomaly
    responses, and the log-source response; the lifecycle transition `reason`; the explanation
    dimension `detail`; `reason` and `caveat` or `claim` inside the WAF, IPS and property-watch
    detection detail;
  - rules: `health_reason` (on `GET /api/v1/rules` and `GET /api/v1/rules/{id}`), and `reason` on each
    health-history row; the rule-statistics `reason`, `excluded_reason`, `label`, `unit`, `silent_reason`
    and `top_reason`;
  - coverage: `reason`, on the technique and on a rule entry;
  - custom rules: `last_status_reason`;
  - property watches: `reason`, `status_reason`, `scope_reason`, `current_unavailable` and the
    transition and anomaly `reason`;
  - WAF and IPS profiles and sources: `detail` on a validation field, `ineligible_reason`, and the
    list `reason_codes` and `validation_reason_codes`;
  - history backfill: `reason`, `later_yes`, `collection_reason`, `message`, `detail`, and the list
    `assumption_codes`;
  - searches: `error_message` on a run, and `reason_codes` beside the authoring `reasons`.
- **Refusals.** An HTTP error body keeps `detail` exactly as before and gains top-level `detail_code`
  and `detail_params`. A list-valued `detail` (password and directory rules) gains `detail_codes`. A
  `detail` that is an object keeps its `message` and gains `code` and `params` inside it; the authoring
  body (`message`, `reasons`) gains `reason_codes`. This covers the 403 of a missing permission
  (`auth.permission.missing`, with the permission as a param), the CSRF refusals, the sign-in
  refusals and the history-backfill conflict body (`detail_code`, `detail_params`). Status codes are
  unchanged.
- **New endpoint: `PUT /api/v1/me/preferences`.** Body `{"ui_language": "en" | "tr"}` (any other key or
  value is `422`); the answer is the same body as `GET /api/v1/me`. It needs a session and no
  permission. `401` for a session whose account is gone or disabled, `409` for a principal with no
  account, `403` for a cross-site request (as for every mutating route). A re-send of the stored value
  changes nothing and writes no audit row.
- **`GET /api/v1/me` gains `ui_language`** (`en` or `tr`; `en` for a principal with no account).
- **Changed values, not shapes:** newly written WAF and IPS sentences spell a percentage-point change
  "+29.7 pp" with a no-break space; the search-cadence and history-backfill audit rows record
  `NULL` for an empty client address. No endpoint was removed and no request body changed.

## Schema

The head goes from `0032` to `0044`. All are additive; the upgrade runs them, and existing rows are
unchanged. `0043` and `0044` were renumbered when they were merged (their numbers rise along the chain,
and there is no `0041`); the chain is `0032`, `0033`, ..., `0040`, `0042`, `0043`, `0044`.

- `0033` adds `app_user.ui_language`, `VARCHAR(2) NOT NULL`, with a check that allows `en` and `tr`;
  every existing account reads `en`.
- `0034` adds the nullable JSONB column `anomaly_explanation_dimension.detail_i18n`.
- `0035` adds `reason_i18n` (nullable JSONB) to `detection_coverage` and `detection_coverage_snapshot`.
- `0036` adds `rule_health_snapshot.reason_i18n`.
- `0037` adds `property_watch.last_status_reason_i18n`, `pw_anomaly.explanation_i18n`,
  `pw_anomaly.suppression_reason_i18n` and `pw_anomaly_transition.reason_i18n`.
- `0038` adds `log_source_anomaly.explanation_i18n`, `log_source_anomaly.suppression_reason_i18n`,
  `anomaly_state_transition.reason_i18n`, `waf_anomaly_transition.reason_i18n` and
  `ips_anomaly_transition.reason_i18n`.
- `0039` adds `waf_anomaly.explanation_i18n` and `waf_anomaly.suppression_reason_i18n`.
- `0040` adds `alert.title_i18n`, `alert.description_i18n`, `alert.resolution_reason_i18n` and
  `custom_rule.last_status_reason_i18n`.
- `0042` adds `search_execution.error_message_i18n`.
- `0043` adds `history_backfill_scope.reason_i18n`.
- `0044` adds `ips_anomaly.explanation_i18n` and `ips_anomaly.suppression_reason_i18n`.

Each `_i18n` column holds `{"code": ..., "params": {...}}` beside the English text column it belongs
to. A rollback is a restore of the upgrade's backup, as always; no migration is ever run downward on a
site.

## Upgrade

```bash
git fetch --tags && git checkout v0.1.7
./qradar-dash upgrade 0.1.7
```

The upgrade is allowed from `0.1.6`. A `0.1.4` site goes through `0.1.6` first, as the notes of that
release describe; the upgrade to `0.1.7` from an older release stops with
`upgrade refused: 0.1.7 requires at least 0.1.6`, after it has moved the image prefix and pulled the
`0.1.7` images. The upgrade takes its own backup before it migrates, as every upgrade does. After it,
`/api/v1/version` reports `migration_head` `0044`. The collection families resume on their cadence;
the pages show "stale" or "not collected" until the first cadence after the upgrade has passed, and that
is correct.

On a host with no registry access, make the bundle on a connected host from the same checkout, copy
it over, and run, in the installation directory:

```bash
tar -xf /path/to/qradar-dash-0.1.7-bundle.tar --exclude=images.tar
./qradar-dash upgrade 0.1.7 --offline /path/to/qradar-dash-0.1.7-bundle.tar
```

After the upgrade, run the `[çekirdek]` checks of `docs/MANUAL-TEST.md` (0.1.7 section) and fill
`docs/MANUAL-TEST-RESULTS.md`. If the upgrade or the checks fail and the site must return to 0.1.6,
follow `docs/OPERATIONS.md`, "Geri alma (`rollback`)": it restores the backup the upgrade took and
starts the previous images; data written since the upgrade is kept only in the broken copy it leaves.
