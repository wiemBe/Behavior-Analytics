# API and interface reference

The backend serves a versioned REST API under `/api/v1`. The browser talks only to this API; it
never receives a QRadar credential and never connects to QRadar or the optional MCP service.

OpenAPI documentation generated by FastAPI is the endpoint-level contract. This document groups
the public surfaces and records the authorization and data-honesty rules that apply across them.

## Authentication and authorization

Health and build-version endpoints are public. Login is public; logout and password change require
an authenticated principal. `/me` returns only that principal's identity and effective grants.

All product routers are guarded when mounted. Adding a handler to a guarded router therefore cannot
make it anonymous accidentally. Read-only roles commonly use `read:*`; writes require the specific
capability or `admin:*`.

| API group | Read requirement | Additional write requirement |
|---|---|---|
| `/overview` | `read:overview` | none |
| `/log-sources` | `read:log_sources` | `log_source:write` or administrative inventory access |
| `/searches` | `read:searches` | `search:write`; execution also needs `search:execute` |
| `/alerts` | `read:alerts` | `alert:ack` or `alert:resolve` |
| `/admin/search-cadence` | `read:search_cadence` | `admin:search_cadence` |
| `/offenses` | `read:offenses` | none |
| `/rules` | `read:rules` | `rule:write` |
| `/coverage` | `read:coverage` | `coverage:write` |
| `/providers` | `read:providers` | none |
| `/anomalies`, `/behavior`, `/noise` | `read:anomalies` | none |
| `/waf` | `admin:waf` | same administrative capability |
| `/ips` | `admin:ips` | same administrative capability |
| `/fleet`, `/classification-rules`, `/fleet/catchall` | `read:fleet` | `admin:classification` or `log_source:write`, depending on action |
| `/geo` | `read:geo` | none |
| `/outage-policy` | `admin:outage` | same administrative capability |
| `/dashboards` | `read:dashboards` | `dashboard:write`; sharing needs `admin:dashboards` |
| `/custom-rules` | `read:custom_rules` | `custom_rule:write` |
| `/property-watches` | `read:property_watches` | `property_watch:write` |
| `/admin/history-backfill` | `read:history_backfill` | `admin:history_backfill` |
| `/auth/admin` | `admin:auth` | same administrative capability |
| `/users` | `admin:users` | same administrative capability |
| `/admin/email` | `admin:notifications` | same administrative capability; `read:*` does not grant it |
| `/admin/qradar-health` | `admin:*` | none (reads only) |

`read:*` does not grant any write capability. `admin:*` grants every administrative, read and write
capability.

A write is committed before its response is sent: once a client has a `2xx` (and the login
cookie), the row is visible to the next request, and a commit that fails answers a `5xx`.

A rate-limited request answers `429` with `{"detail": "rate limit exceeded", "limit": "<rate>"}`,
where `<rate>` is the limit as text (for example `2 per 1 minute`), plus the `Retry-After` and
`X-RateLimit-*` headers.

## Behavioral incidents

`GET /anomalies` is the unified incident list. A detail read returns the subject, lifecycle,
detector observation, expected range and evidence metadata. Source-volume, WAF, IPS and
property-watch incidents share the analyst surface while retaining their own anomaly taxonomies.

Without `since` the list covers the last 24 hours of detections. With `active_only=true` and no
`since`, it has no lower bound: it lists every active anomaly up to `until` (or now), however old
its `detected_at`, because an active anomaly is active whatever its age. An explicit `since` or
`until` is used as sent and is validated against the same ceiling. `GET /anomalies/summary` keeps
its Phase A fields (`open_anomalies`, `spikes`, ...), which count log-source active anomalies of
any age. It also returns `active_by_family`: the active anomalies of log sources, WAF, IPS and
property watches (`log_source`, `waf`, `ips`, `property_watch`), each with its `open`, `candidate`,
`recovering` and `total` counts. These come from one statement over the same population as the
active list, so their sum equals the `total` of `GET /anomalies?active_only=true`.

The investigation page exposes every expected evidence dimension even when it is unavailable. An
unavailable dimension includes a reason and is never hidden as though it were checked and clean.
Evidence states are explicit: `NOT_REQUESTED`, `PENDING`, `COMPLETE`, `PARTIAL`, `UNAVAILABLE` and
`FAILED`.

Null means unmeasured. A measured zero remains `0`. Partial or missing chart buckets are gaps and
are not connected across an outage. Expected ranges are returned and drawn as bands.

### Related activity for an anomaly

`GET /anomalies/related/{family}/{anomaly_id}` answers "what else happened on this source at
this time": the QRadar offenses, the other anomalies of every family, and the rules they name.
It reads stored data only and never asks QRadar.

| Parameter | Values | Meaning |
|---|---|---|
| `family` | `log_source`, `waf`, `ips`, `property_watch` | The anomaly table `anomaly_id` names. Any other value is `422`. |
| `anomaly_id` | UUID | An unknown id in that family is `404`. |
| `pad` | `30m`, `1h`, `2h` (default), `6h` | Padding added on both sides of the anomaly's own interval. |

The route requires `read:anomalies`, like the rest of `/anomalies`. Its anchor is the anomaly's
log source: an internal id, its QRadar id and its name. An IPS incident whose subject is an entity
and a WAF incident whose subject is an endpoint both anchor on the source behind that subject. A
property watch scoped to a source type or a group has no single source; that read answers
`state = NOT_APPLICABLE` with a reason code and empty sections.

The window is `[anomaly start - pad, anomaly end + pad]` from the anomaly's stored interval. An
incident that is still open ends at the end of its newest evaluated bucket, not at the wall clock,
so the same incident does not grow a new window on every request.

The response has the `anchor` and three sections. Each section carries its own `state`, a
`reason_code` when the state is not `OK`, the full `total`, and at most 20 `items`:

| Section state | Meaning |
|---|---|
| `OK` | The input was collected (or the local table is current) and is complete. An empty `items` is then a measured "none". |
| `NOT_COLLECTED` | The input for this window was never collected. It is never an empty `OK` list. |
| `STALE` | The input exists but is older than its collection cadence allows. |
| `PARTIAL` | Some input was collected and some was not; per-item fields say which. |
| `TRUNCATED` | More rows matched than are shown; `total` is the full count. |
| `NOT_APPLICABLE` | The anchor has no log source. |

**`offenses`** — each offense's newest snapshot, where `log_source_ids` contains the anchor's
QRadar source id and the offense span (`start_time` … `close_time`, or `last_updated_time` while
open) overlaps the window. Ordered by magnitude descending, then start descending, then id. Each
item carries `qradar_offense_id`, `description`, `status`, `magnitude`, `severity`, `start_time`,
`last_updated_time`, `close_time`, `offense_type_name`, `rule_count` and `captured_at`. The state is
`NOT_COLLECTED` when the offense collector has never run for the console, and `STALE` when its last
run is older than `OFFENSE_STALE_AFTER_SECONDS` or its last run is failing. The freshness signal is
the `collection_watermark` row for the `offense_snapshot` collector.

**`anomalies`** — other anomalies of every family on the same log source whose own interval
overlaps the window, excluding the anchor. Custom-rule breaches are included as `custom_rule` items
when their rule is tied to a log source. Ordered by start descending, then family, then id. Each
item carries `family`, `id`, `type`, `lifecycle_state`, `severity`, `start`, `end` and the analyst
`triage_status` (`NEW` when no triage row exists).

**`rules`** — the union of `rule_ids` over *all* matching offenses, not only the 20 shown. Each
item carries the catalog `id`, `qradar_id`, `name`, `type`, how many matching offenses name it, and
`matched_events` with its `measurement`. A rule id QRadar named but the catalog lacks is listed with
a null `id`, `name` and `type` and is still counted. `matched_events` is `null` with
`measurement = NOT_COLLECTED` when no measured rule-match window covers it (and for a rule type an
event search cannot measure); it is never a zero for "not measured". Ordered by offense count
descending, then matched events descending with nulls last, then QRadar id.

Reason codes are English sentences in the backend message catalog:

| Reason code | English sentence |
|---|---|
| `related_activity.reason.no_log_source` | This anomaly has no log source, so related activity cannot be resolved. |
| `related_activity.reason.offense_not_collected` | QRadar offense collection has not run for this console, so no offense in this window was collected. |
| `related_activity.reason.offense_stale` | QRadar offense collection is stale, so the offenses in this window may be incomplete. |
| `related_activity.reason.rules_not_collected` | Offenses were not collected for this window, so the rules that fired cannot be resolved. |
| `related_activity.reason.rules_stale` | Offense collection is stale, so the rules that fired in this window may be incomplete. |
| `related_activity.reason.rules_partial` | Rule-match collection did not measure this window for every rule; a missing measurement is null, never zero. |
| `related_activity.reason.items_truncated` | More rows match this window than are shown; the list holds the first 20 and the total is the full count. |

## Noisy sources

Two read-only routes answer which Phase A log sources keep firing and how much of that is noise.
They write nothing, scan only stored aggregates, and use three statements whatever the fleet size.

| Method and path | Question |
|---|---|
| `GET /noise/sources` | Which monitored sources fired in the window, ranked, and how much of that was closed as noise? |
| `GET /noise/sources/{log_source_id}` | What are one source's per-detector counts, current settings and coverage? |

The list takes `window` (`7` or `28`, default `28`), `order` (`incidents`, `alerts` or
`noise_share`; default `incidents`), `limit` (1–200, default 50) and `offset` (at least 0).
Anything else is 422. `window` selects the incident and alert counts the ranking and the fired/
quiet split use; every row still carries both windows. `order=noise_share` puts rows whose share
is null last. Ties fall back to the other real count, then name and id, so a page is a stable slice
of the whole list; `total` counts the fired sources and the quiet ones are counted, never listed.

Each row carries `incidents_7d`/`28d` (detected incidents), `opened_7d`/`28d` (incidents that
reached OPEN), `alerts_7d`/`28d` (alert rows linked through `source_anomaly_ids`; inventory alerts
carry none and are not counted), `noise_closed` out of `noise_closed_total` (closed triage items
with a disposition), `noise_share`, `worst_ratio`, `worst_z`, `top_detector` and `judged`.
`noise_share` is null, not zero, while fewer than five items are closed with a disposition; the
row then shows the two counts instead of a percentage. An unclosed item is not a negative
judgement and is excluded from the denominator.

The honesty states are explicit and a number never stands in for a missing measurement:

| State | Meaning |
|---|---|
| `NOT_COLLECTED` | `monitoring_enabled=false`; every count is `null`, never `0`. The detail route returns it; the list is the monitored fleet only. |
| `INSUFFICIENT_DATA` | no reliable baseline cell for the current weekday and hour. Counts are the real recorded counts, but a zero is not evidence of calm. |
| `PARTIAL` | the configured `log_source_anomaly_retention_days` is shorter than the requested window; `covered_days` names the covered span. |
| `COMPLETE` | the stored window covers the requested one. |

Every state but `COMPLETE` carries `reason` (an object with `code`, for example
`noise.reason.no_reliable_baseline`, plus `params` and the English `text`). An empty window carries
`empty_reason` and the last evaluation watermark in `last_collection`, so "nothing fired" is
distinguishable from "nothing was collected".

The detail response adds `detectors` (the same counts per `anomaly_type` for both windows),
`current` (criticality, `custom_thresholds`, maintenance and business-hours settings), and the
same `coverage` block. `suppression` and `replay` are null in this slice; the suppression table
and the 28-day replay arrive with later steps, and null says so rather than inventing an empty
object.

## Log-source fleet summary

`GET /fleet/summary` returns one class summary for each non-internal source class. Its `buckets`
object carries the completeness of the selected window:

| Field | Meaning |
|---|---|
| `expected` | Complete collection buckets expected from the class's enabled, monitored sources |
| `complete` | Buckets collected completely; these are the only buckets used in events and mean EPS |
| `complete_from_history` | Of `complete`, the buckets read from QRadar history rather than collected by the cadence |
| `partial` | Buckets collected incompletely and excluded from events and mean EPS |
| `missing` | Expected buckets that are neither complete nor partial |

`complete_from_history` is always between `0` and `complete`. History buckets remain COMPLETE data
and stay in the class totals; the field states how much of that measured total came from the past.

## Ariel load rows

`GET /admin/ariel-load` (`admin:*`) counts every closed search by `outcome`, per caller: `COMPLETED`,
`ERROR`, `CANCELED`, `TIMEOUT`, `REFUSED`, `PROVIDER_UNAVAILABLE` and `ABANDONED`. A search that is
still running is `IN_FLIGHT` and only `/admin/ariel-load/current` lists it. A row becomes
`ABANDONED` when it has been `IN_FLIGHT` for longer than the longest wait the application allows a
search plus `ARIEL_SEARCH_ABANDON_SCAN_SECONDS` (default 600): its worker stopped before it recorded
an end, and the beat task `reap_abandoned_ariel_searches` closes it with one UPDATE. An abandoned
search is counted in `searches` and `outcomes` and adds nothing to the percentiles; its wall time,
execution time and record count stay null and are counted in the `*_unknown` fields, never 0. A
worker that ends late still records its real outcome over `ABANDONED`.

## QRadar health

`GET /admin/ariel-load/current` carries `qradar`: one entry per enabled console. Every field of an
entry is `{state, value, reason_code, reason}` with `state` one of `OK`, `NOT_COLLECTED`,
`FORBIDDEN`, `FAILED`; only an `OK` field carries a value, and a field that was not read is never
a zero and never "healthy". The QRadar reads are reused for `QRADAR_HEALTH_CACHE_TTL_SECONDS`.

**`hosts`** is the per-host table, from `GET /config/deployment/hosts` joined with
`GET /system/servers`. `value` holds `hosts` (managed hosts read), `truncated`, `ha_pairs`,
`ha_problem` and `items`, one per **managed host**:

| Field | Meaning |
|---|---|
| `host_id`, `hostname`, `private_ip`, `public_ip`, `appliance_id`, `appliance_description`, `version`, `status` | The deployment record, as QRadar writes it; a field QRadar did not give is `null`. `status` is the deployment status ("Active"), not the server status. |
| `cpus`, `total_memory_kb` | Hardware as QRadar reports it; `null` when absent. |
| `role` | `console` when the host's component list holds `magistrate` (the Magistrate runs only on the console: IBM QRadar 7.1 MR2 Installation Guide, "You can add one Magistrate component for each deployment"; IBM support note 6558024), `managed` when the list is non-empty and does not, `null` when QRadar gave no list or an empty one. Never a guess. The component list itself is not returned. |
| `eps`, `fpm` | A field each: `value` is `{allocation, hardware_limit, average, peak}` (average and peak are QRadar's previous month). They are the managed host's own figures, once per host: an HA pair is never counted twice. `NOT_COLLECTED` (`field_missing`) when QRadar gave none of the four. |
| `pair_state` | `single`, `ha_healthy`, `ha_degraded`, `ha_failed_over`, `ha_failed` or `unknown`. |
| `unclassified` | For `unknown` only: the status strings that were read, as QRadar wrote them (upper case). |
| `members` | One entry for a single host, two for an HA pair: `server_id`, `hostname`, `private_ip`, `role` (`primary` or `secondary`, `null` when the host record does not name it) and `status`, a field of its own (`FAILED` / `NOT_COLLECTED` when `/system/servers` was not read or lacks the member). |

Pair states follow IBM's HA host statuses (High Availability Guide, "Status of HA hosts": Active,
Standby, Failed, Synchronizing, Online, Offline, Restoring, Needs License, Setting Offline,
Setting Online, Needs Upgrade, Upgrading):

| `pair_state` | When |
|---|---|
| `single` | The host names no secondary server. |
| `ha_healthy` | The primary is `ACTIVE` and the secondary is `STANDBY`. |
| `ha_degraded` | The primary is `ACTIVE` and the secondary is any other documented status: no failover is possible. |
| `ha_failed_over` | The secondary is `ACTIVE` and the primary is any other documented status. |
| `ha_failed` | No member is `ACTIVE`. |
| `unknown` | A status outside the list above, a member that was not read (including a secondary that `/system/servers` did not return), two `ACTIVE` members, or roles that are not known because the deployment hosts were not read. Never read as healthy. |

`hosts.value.truncated` is `true` when the deployment lists more than 100 managed hosts: `hosts`
is the count kept, the host part is partial, and the sums in `eps` are lower bounds.

**`servers`** is the managed-host summary, redefined on managed hosts with the pair rule. `total`
and `active` count managed hosts: a host is active when exactly one of its members is `ACTIVE`,
so the standby of a healthy pair is never counted as not active and never listed in `not_active`.
`not_active` (at most 20) holds the hosts without exactly one `ACTIVE` member; its `status` is the
member status for a single host, and both statuses, primary first ("FAILED / OFFLINE"), for a
pair, with `ha_state` set. `all_active` is false when the read was cut at its bound (`truncated`).
`members_total` is the number of members behind `total`: one per single host, two per HA pair
(a member whose `/system/servers` record was not returned counts, with an unread status).
`by_status` and `unreported` count members, never hosts. Example, an HA site with a console, one
managed host and one HA pair (`ep-ha`, primary `ACTIVE`, secondary `STANDBY`):
`total: 3`, `active: 3`, `members_total: 4`, `by_status: {"ACTIVE": 3, "STANDBY": 1}`,
`unreported: 0`, `ha_pairs: 1`, `ha_problem: 0`. A reader compares hosts with hosts (`total`,
`active`) and members with members (`members_total`, `by_status`, `unreported`), and never has to
infer the count. Added fields: `ha_pairs`, `members_total`, `ha_problem` (pairs not `ha_healthy`), `ha_issues` (those
pairs, at most 20) and `truncated`. No field was renamed or removed.

**`eps`** is unchanged in meaning: the sum over managed hosts, one record per host (so an HA pair
counts once); `truncated` was added.

## WAF profiles

Each WAF source has a versioned mapping from logical URL, method, virtual-host, action,
response-code, rule and user-agent fields to QRadar properties. The profile also defines which
action values mean blocked or allowed.

The property catalog contains names and types only. Any property name that passes the syntax guard
may be entered, but a profile must validate against read-only bounded Ariel probes before it can
collect. A mapping change increments the profile version and pauses collection until that version
is valid. Stale concurrent edits return `409`. Every mutation and validation result is audited.

## IPS profiles and analyst reads

The `/ips` administration API supplies the mapping schema, candidates, profiles, validation,
history and property catalog. Mapping changes are versioned and stale writes return `409`. There is
no IPS profile CLI.

Analyst reads live under `/behavior/ips`: sources, entities, metrics and seasonal baselines. IPS
incidents also appear in `/anomalies`. An unmeasured bucket is `null`; source IP values are not
served outside a bounded stored contributor list, and these routes do not expose that list.

## Traffic ranking

Two read-only routes rank the stored traffic of one source. They read aggregates only and return
counts and rates, never a raw path, action value or address outside the entity's own key.

| Method and path | Question |
|---|---|
| `GET /behavior/waf/sources/{log_source_id}/traffic` | Which of this WAF source's endpoints take the most events per second? |
| `GET /behavior/ips/sources/{log_source_id}/traffic` | Which of this IPS source's destination IPs take the most events per second? |
| `GET /behavior/waf/sources/{log_source_id}/traffic.csv` | The whole WAF ranking as one CSV file |
| `GET /behavior/ips/sources/{log_source_id}/traffic.csv` | The whole IPS ranking as one CSV file |

`window` is `5m`, `1h`, `24h`, `7d` or `28d` (default `1h`). Collection runs on a cadence, so
`5m` is the newest **complete** stored bucket, not the last five minutes of the clock; the other
windows end at that bucket's end and cover whole buckets. `sort` is `rate`, `peak`, `host` or
`endpoint` for WAF and `rate`, `peak` or `ip` for IPS (default `rate`), with `order` `desc` or
`asc` (default `desc` for counts, `asc` for text). `limit` is 1–1000 (default 10) and `offset` is
at least 0. Anything else is 422. The sort runs over the whole set with the entity id as a stable
tie-break, so a page is a slice of the whole list; `total` counts the whole set.

Every number is over the measured buckets of the window only. `buckets_measured` and
`buckets_expected` say how much of it was measured, and `state` is `OK`, `PARTIAL`, `TRUNCATED`,
`INSUFFICIENT_DATA` or `NOT_COLLECTED`. `TRUNCATED` outranks `PARTIAL`, because a bucket that lost
groups or entities makes even the measured rows lower bounds. A `reason_code` of the form
`waf_traffic_detail.reason.*` or `ips_traffic_detail.reason.*` accompanies every state but `OK`;
its English sentence is in the message registry and the generated frontend catalog.

A missing bucket is never a zero. With no complete bucket, or with no measured bucket in the
window, the response is `INSUFFICIENT_DATA` with no items and `null` measurements. An entity with
no metric row in any measured bucket is not listed, and an entity retired since is still listed
(`active: false`) while it has data in the range. A source without an enabled, validated profile
is `NOT_COLLECTED` with a reason code and status 200; an id that is not a log source is 404.

`rate_per_second` divides by the measured seconds of the window, not by its wall-clock width, and
`peak_rate_per_second` is the largest single bucket's count over that bucket's own width.

**New entities.** Because the contract uses one denominator for the whole window, an entity
admitted part-way through it is diluted by the measured buckets before its first row: its
`rate_per_second` is its events over the whole measured window, not an average since it appeared.

`series_start`, `series_step_seconds` and `series_points` describe a shared trend grid, and each
item carries `series`, one rate per point, with `null` where no source bucket in that step was
measured. The step is a whole number of source buckets and the grid covers the window exactly: at
300 s buckets it is 1 point of 300 s for `5m`, 12 of 300 s for `1h`, 48 of 1800 s for `24h`, and
56 of 10 800 s / 43 200 s for `7d` / `28d`. The series is read for the returned page only, in one
statement, so a page of 1 000 rows costs no more queries than a page of 1.

### Traffic CSV export

The two `traffic.csv` routes take the same `window`, `sort` and `order` and no `limit`/`offset`:
the file is the whole sorted set. The response is `text/csv; charset=utf-8`, RFC 4180, UTF-8,
`\r\n` line ends and one header row, as an attachment named
`traffic-waf-<source>-<window>-<YYYYMMDDTHHMMZ>.csv` (IPS likewise; the stamp is `range_end`, or
`no-range` when no bucket defined it).

Columns, in order. WAF: `rank`, `host`, `method`, `path`, `avg_events_per_s`,
`peak_events_per_s`, `peak_bucket_start_utc`, `events`, `buckets_with_data`, `partial_buckets`,
`active`, `window`, `range_start_utc`, `range_end_utc`, `buckets_measured`, `buckets_expected`,
`state`, `source`, `truncated`. IPS puts `destination_ip` and `display_name` in place of `host`,
`method` and `path`. Numbers are plain, with `.` as the decimal point and rates to three decimals;
times are ISO 8601 UTC with `Z`; a `null` is an empty cell, never `0`. A text cell that starts with
`=`, `+`, `-`, `@`, a tab or a CR is prefixed with `'`, so a spreadsheet opens it as text.

The export holds at most `API_MAX_EXPORT_ROWS` rows (default 10 000). Past it, the response is
still 200 with the first rows in sort order, `X-Export-Truncated: true` and `truncated` set to
`true` on every row: a cut export is never silent. In `INSUFFICIENT_DATA` or `NOT_COLLECTED` the
body is the header row only, and `X-Export-State` always names the state the file was built from.

### The history block of a watch

Every watch read carries a `history` object:

| Field | Meaning |
|---|---|
| `state` | `NOT_REQUESTED`, `READING`, `COMPLETE`, `PARTIAL` or `UNAVAILABLE` |
| `days_requested` | the days asked for; `null` when no history was requested |
| `target_start`, `floor`, `through`, `end` | the start of the window, the proved floor, the resume point and the boundary at hand-off |
| `days_read` | whole buckets read, one decimal; `null` when nothing was measured |
| `searches`, `buckets_read` | the counters of the reading; `null` when nothing was measured |
| `gaps` | the spans that could not be read, with their reason |
| `reason` | words, never a value |
| `progress_unreadable` | true when the stored progress did not read back; the counters are then `null`, never zero |
| `started_at`, `finished_at` | wall clock |
| `estimate` | the cost of the request, on a single-watch read of a watch that asked and has not finished |

There is no ETA: the estimate is the planner's arithmetic on the stored pins, not a promise.

`history_days` is an optional field of the create and patch bodies. Omitted on a create, it is
`PW_BOOTSTRAP_DAYS` while history reading is on and none while it is off; `0` asks for none and an
explicit `null` is refused. `POST /property-watches/{id}/history` takes `{"history_days": n}` and
asks for a read of that many days; `0` means no history. The value must be `0` or between
`PW_NEW_VALUE_HISTORY_DAYS` and `PW_BOOTSTRAP_DAYS`; anything else is a 422 with the reason. The
request is allowed only on a watch that has never read, holds no bucket of its current version and
has no watermark; otherwise it is a 409 naming the reason. The route writes the request and nothing
else of the bootstrap: the collector starts the reading at its next tick and owns every other
history column. The same value as stored is a 200 with no audit row. The request is audited as
`property_watch.history_request` with the day count, never a value.

A capacity refusal is a 409 whose body is `{"detail": "...", "codes": ["..."]}`: `detail` is the
reason text, every reason joined into one sentence, and `codes` carries one stable code per reason,
in the same order. The codes are `ENABLED_CAP`, `GROUP_TOO_LARGE`, `WATCH_SEARCH_LIMIT`,
`TICK_BUDGET` and `HISTORY_BUDGET`. A client branches on the code, never on the wording; a body
that carries no code carries none.

## History backfill

All paths below are under `/admin/history-backfill`. The router requires `read:history_backfill`;
the three writes require `admin:history_backfill` as well. `read:*` does not grant the write.

| Method and path | Purpose |
|---|---|
| `GET /admin/history-backfill` | One entry per enabled console: the decision, the mode and every family's scopes |
| `GET /admin/history-backfill/estimate` | The cost model per console and family |
| `PUT /admin/history-backfill/{instance_id}` | Record the answer (`{"answer": "YES" \| "NO"}`) |
| `POST /admin/history-backfill/{instance_id}/start` | Ask every family to read history now |
| `POST /admin/history-backfill/{instance_id}/stop` | Ask every family that is reading to stop |

The body of the decision takes `answer` and nothing else: `days` is always the stored setting, and
no route takes an AQL, a window or a number of days from the browser. The answer is written once
per direction. A `NO` may become a `YES` later; a `YES` is never reversed. The writes are audited
as `history_backfill.decide`, `history_backfill.start` and `history_backfill.stop`.

The decision returns the console entry again, with `201` when the row was created and `200` when
it already existed or was upgraded. The two requests return the console entry with a `message`
that says what was recorded; they change no scope row, because each family applies the request at
its next collection.

An unknown or disabled console is a 404 (`console not found`). A refused write is a 409 whose body
carries the reason and the console's current state:

| Refusal | Reason |
|---|---|
| A `NO` on a console that already answered `YES` | "a Yes is never reversed; stop the reading instead" |
| A decision recorded in the meantime | "a decision was recorded in the meantime; it is shown here" |
| "Read history now" or "Stop reading" on a console with no `YES` | "record Yes first: the console has no Yes answer to start or stop" |

The console entry holds the decision (`answer`, `days`, who recorded it and when, and the two
requests), the mode (`UNDECIDED`, `NO`, `ACTIVE` or `STOPPED`) and one family per reading family:
the family's collection switch and the reason for it, the fitted window (`days_requested`,
`days`, `available`, `limited_by`, `reason`) and its scopes. A scope carries its state, the days
asked for and the days that fit, the start of the window, the floor (`floor_proved` is true only
when the family proves a scope-wide floor **and** the row carries one: a row with no floor at all —
a `NOT_ELIGIBLE` one, or one whose floor was never proved — says false; for source volume and
catch-all the floor is only where the read started), the resume point, the anchor,
the counters (`searches`, `buckets_read`, `days_read`), the gaps and the reason. A counter that
was not measured is `null`, never a zero, and `progress_unreadable` says that a stored progress
did not read back. `last_error_class` is the class of the last failed history step, cleared by the
next step that succeeds; never a message. `last_error_at` is that failure's UTC time.

A scope of a console-wide family (source volume, catch-all) also names the sources the reading
was short of, because the reason gives counts only:

| Field | Meaning |
|---|---|
| `sources_cut` | the monitored sources whose floor is later than `T0 + one bucket`: QRadar holds less than asked for them |
| `sources_silent` | the monitored sources with no event at all in the window |
| `sources_cut_count` | the whole number of cut sources; the list above holds at most 25 names |
| `sources_silent_count` | the whole number of silent sources; the list above holds at most 25 names |

Each name is a `{"key": "<QRadar log-source id>", "name": "<the source's name or null>"}`. The
lists are sorted by name and then by key, and a source whose name is not known sorts last. They
are judged against the sources monitored **now**, so a source added or removed since the reading
finished can differ from the counts in `reason`. All four are `null` — never an empty list and
never a zero — for every other family, for a scope that has not searched yet and for a stored
progress that did not read back.

The estimate is a model of the cost, not a measurement: searches, ticks and hours per family,
with the assumptions it rests on. A family whose count the model needs is missing answers with no
figure and a reason.

### Which bucket came from the past

Every family that stores buckets says, per bucket, whether it was read from QRadar's past or
collected by the cadence. The field is `origin`, with the values `LIVE` and `HISTORY`. A bucket
that was read from the past is used for learning and is never judged.

| Response | Where `origin` is |
|---|---|
| `GET /behavior/sources/{log_source_id}/metrics` | every bucket |
| `GET /behavior/waf/sources`, `GET /behavior/waf/sources/{log_source_id}` | the source's latest bucket |
| `GET /behavior/waf/endpoints/{endpoint_id}/metrics` | every bucket |
| `GET /behavior/ips/sources` | the source's latest bucket |
| `GET /behavior/ips/sources/{log_source_id}/metrics` | every bucket |
| `GET /behavior/ips/entities/{entity_id}/metrics` | every bucket |
| `GET /fleet/catchall/buckets` | every bucket |
| `GET /property-watches/{id}/buckets`, `GET /property-watches/{id}/series` | every bucket and every point |
| `GET /rules/statistics` | `history_windows`: how many of the complete windows came from the past |

The endpoint and entity metric rows of a WAF or IPS bucket carry the marker of their source
bucket, so a metric row without a source bucket has no origin at all.

## Custom threshold rules

Custom rules evaluate stored aggregates only. The metric catalog defines the subject, unit and
whether a lower bound can prove an increase. A rule names a stored subject, operator, threshold,
sustain period, recovery period and severity; it never contains free-form subject text.

The API supports list, create, detail, patch, delete, draft preview, stored-rule preview, catalog
and breach history. New rules are safe to preview without persisting, alerting or running Ariel.
Writes use optimistic concurrency. Domain validation returns all reasons together; duplicate names
and enabled-cap conflicts return `409`.

Rule status is explicit: disabled, subject retired, not collected, stale, open, recovering, OK or
no verdict. A never-evaluated null is not OK. Unmeasured and maintenance buckets pause hysteresis;
they are not treated as zeros.

## Scheduled searches

Only stored, validated and versioned AQL executes. A new search is disabled. The API validates time
range, timeout, row and concurrency bounds, and requires new or changed cron expressions to leave at
least five minutes between runs.

`GET /searches/{search_id}/results` returns stored aggregates oldest first. It accepts:

| Parameter | Default | Notes |
|---|---|---|
| `metric_key` | `total` | Total or one stored grouped dimension |
| `start`, `end` | unbounded | Inclusive; naive timestamps are interpreted as UTC |
| `limit` | `500` | Maximum `5000`; the most recent matching points win |

Each point carries execution state, duration, result count, threshold state and query version. A
failed execution creates a chart gap, not a zero. Query-version boundaries are marked because data
on either side may not be comparable.

The dispatcher seeds a new search without running it immediately, runs one catch-up after downtime,
deduplicates repeated delivery by run key, skips a still-running execution, preserves schedule state
for malformed cron text, and caps the number dispatched per cycle.

## Geography

`GET /geo/countries` requires timezone-aware `since` and `until`, an ordered interval within the API
range cap, and `direction=SOURCE` or `DESTINATION`. It returns countries, unresolved/over-cap/
unparseable remainder counts, exact or lower-bound measurement, expected and measured bucket counts,
and one of `NOT_COLLECTED`, `INSUFFICIENT_DATA`, `PARTIAL` or `OK`.

`country_source` and `country_property` are the **current setting** (`GEO_COUNTRY_SOURCE` and the
direction's property name), not what the plotted buckets used. `collected_with` says how the buckets
in the range were collected: `ways` lists each distinct `{country_source, country_property, buckets}`
present (`PROPERTY` or `LOOKUP`; `country_property` is null in lookup mode; most buckets first, never
a per-bucket list), and `unknown_buckets` counts buckets stored before 0.1.11, which did not record
it. Those buckets are never given a guessed source. `collected_with` is `null` while the status is
`NOT_COLLECTED`. It rides in the existing second statement, so the request still costs two
statements whatever the range.

Private, internal and unknown addresses all produce the same unresolved lookup result in QRadar and
cannot be distinguished. No address is selected or stored by this collector.

## QRadar health in detail

Disk, system, pipeline and QRadar's own system notifications, stored by the `QRADAR_HEALTH`
search family (see `docs/SEARCH-CADENCE.md`). Both reads need `admin:*`, read the database only
and ask QRadar nothing; each costs a fixed number of statements however many consoles and hosts
there are.

`GET /api/v1/admin/qradar-health/latest` returns `{generated_at, collection_enabled, consoles[]}`, one entry
per enabled console. `collection_enabled` is `false` when `QRADAR_HEALTH_COLLECTION_ENABLED` is off:
the windows are then the last ones collected, returned with their own times, not hidden or zeroed.


- `window` (`start`, `end`, `collected_at`, `cadence_seconds`): the newest window any run stored,
  or `null` when the console has none.
- `metrics` and `notifications`: `{state, reason_code, reason}` for the newest run's part. `state`
  is `OK`, `PARTIAL` (a search hit its row cap), `STALE` (the window is older than
  `QRADAR_HEALTH_STALE_CADENCES` cadences plus the settle time), `NOT_COLLECTED` (no window yet, the
  console lacks the `Metric ID`, `Value` or `Element` custom property, or an empty notification
  answer on a console that cannot report notifications) or `FAILED` (the search failed or was
  rejected). Anything but `OK` carries a stable `reason_code` and an English `reason`. A part that
  was not measured has no values below: never a zero. `last_metrics_window_end` is the end of the
  newest window whose metrics were collected, even when a later run failed.
- `hosts[]`, per host (the hostname parsed from the `Health Metrics-<n> :: <hostname>` log-source
  name): `disk` (`fullest` mount and all allowlisted `mounts`, each with `used_fraction` 0 to 1,
  `used_percent`, `used_bytes`, `total_bytes`, `free_bytes` when both were read, `total_from` and `level`
  `OK`/`WARN`/`FAIL` against the disk thresholds; QRadar sends the total once an hour, so when
  the window holds none, `total_bytes` is the newest stored total of that console, host and mount
  from an earlier window at most 2 h old and `total_from` is that window's end in UTC, otherwise
  `null` with `total_bytes` and `free_bytes` null too, never a zero), `system` (`cpu_percent`, `memory_percent`,
  `load_avg_5`, `swap_percent`, `io_wait`, `running_queries`, `host_running_queries`) and `pipeline`
  (`cre_queue`, `throttle_spill_bytes`, `throttle_spilling`, `ect_tcp_to_ep_disk_bytes`,
  `flow_governor_queue_disk_bytes`, `busiest_stage`). Every figure is a cell `{state, value,
  average, samples, reason_code, reason}` holding the window's maximum and average; a metric the
  host did not report is `NOT_COLLECTED`, and in a `STALE` window the cells are `STALE` with their
  values. `throttle_spilling` is true when events spilled to disk because the host is over its EPS
  allocation.
  `busiest_stage.busy_percent` is the share of the stage's threads in the RUNNABLE state
  (`RunnableRatio`); a window collected before query version 2 has `busiest_stage: null`.
- `notification_list`: `entries[]` (`host`, `qid_name`, `events`, `max_severity`, `last_seen`), the
  50 busiest groups of the window with `Information Message` excluded, and `remainder`
  (`events`, `groups`) for the groups below them, so the window's events still add up.
  An empty answer is `OK` with no entries only when the console has an enabled
  `System Notification` log source in our synced log-source inventory; a console without one has
  the notification part `NOT_COLLECTED` with `notification_source_missing` (or
  `notification_source_unreadable` when that inventory could not be read), so a search that found
  nothing on a console that could not send anything is never reported as "no notifications".
  A search that returned rows without hitting its row cap is `OK` when the fold kept at
  least one group from them and `NOT_COLLECTED` with `notification_rows_unreadable` when it
  kept none, so returned rows that folded to nothing are never reported as "no notifications".
  With the query parameter `notifications_hours` (1 to 168; anything else is `422`) the list is
  instead the roll-up of every stored window of that many hours whose notification search was
  measured (`OK` or `PARTIAL`): the groups are summed per host and QID name (`events` summed,
  `max_severity` and `last_seen` the largest), the 50 busiest are listed, and `remainder` holds
  the stored remainders plus the groups cut here, so the range's events still add up (`groups`
  there is an upper bound on distinct groups: a group can fall below the cut in several windows).
  The list then also carries `hours`, `windows` (the measured windows rolled up) and
  `covered_from` / `covered_until` (the start of the first and the end of the last), so a reader
  can tell a range that was looked at from one that was only partly looked at. With no measured
  window in the range `notification_list` is `null`, never an empty list: "nothing happened" is
  only said of a range that was looked at. `notifications` stays the newest run's state, so a
  failed newest run is still reported beside the earlier windows' list. Without the parameter
  the list is the newest window alone, as before (`hours`, `windows` and the `covered_*` fields
  are `null`). The statement count is fixed whatever the range, the consoles or the groups.
- Counted, never shown: `unparseable_hosts` (log-source names with no hostname), `dropped_mounts`
  (mounts outside `QRADAR_HEALTH_DISK_MOUNTS`), `dropped_metrics`, `null_values`, `invalid_values`
  (negative or out-of-range), `dropped_events`.
- `rest_sample`: the newest REST sample (`sampled_at`, `reachable`, `api_latency_ms`,
  `hosts_active`, `hosts_total`, `ha_problem_count`, `license_overallocated`); a figure that was
  not read is `null`.

`GET /api/v1/admin/qradar-health/history?hours=24|168` (`400` for any other value) returns
`{generated_at, hours, since, until, expected_interval_seconds, consoles[]}`. Per console:
`metrics` (`NOT_COLLECTED` with `no_window_in_range` when no window was stored in the range),
`hosts[]` with three series each (`disk_fullest_fraction`, the `DiskUsage` of the fullest
allowlisted mount per window with the `mount` behind each point; `cre_queue`;
`throttle_spill_bytes`) and `reachability` (`points[]` of `reachable` and `api_latency_ms` from the
REST samples). A series with no point is `NOT_COLLECTED`. A gap longer than
`expected_interval_seconds` between two points means windows are missing, not that the value held.
A series longer than 400 points is folded into equal time slices, each keeping its maximum
(`windows` says how many windows a point stands for); a reachability slice keeps an unreachable
sample over a reachable one.

## Dashboards

Dashboard records store widget identity, geometry and bounded configuration, never executable
content. Layout version and size are validated. Owners can see their private dashboards; every
reader can see shared dashboards. Updates carry an expected revision and return `409` with the

## Alerts and operator actions

The shared alert lifecycle is `OPEN → ACKNOWLEDGED → RESOLVED`. A partial unique index on the active
deduplication key prevents two unresolved alerts with the same fingerprint.

Alerts can originate from behavioral incidents, stored-search thresholds, repeated search failure,
custom-rule breaches, new inventory, new catch-all senders and stale offense collection. Each
condition has its own fingerprint. Recovery and operator actions enqueue notifications through the
same transition pipeline.

Acknowledge, resolve and manual-search actions are authorized by the backend. The browser receives
identifiers and ordinary display values, never credentials. Notification enqueueing is separate
from delivery; the worker retries and dead-letters failures without delaying the HTTP response.

### Alert list filters

`GET /api/v1/alerts` takes optional, combinable filters (SOC-7a). With no filter it answers exactly
as it did before: the same rows, total, limit and offset, in `opened_at DESC, id DESC` order.

| Parameter | Meaning |
|---|---|
| `status` | `OPEN`, `ACKNOWLEDGED` or `RESOLVED` |
| `severity` | Repeatable: `CRITICAL`, `HIGH`, `MEDIUM`, `LOW`, `INFO`. Rows are returned when the severity is any of the values sent |
| `log_source_id` | Repeatable: a log-source UUID. See the scope note below |
| `family` | One of `log_source`, `waf`, `ips`, `property_watch`, `catchall_sender`, `custom_rule`, `scheduled_search`, `qradar_instance` |
| `q` | A case-insensitive substring of the alert title, at most 100 characters. `%`, `_` and `\` are literal characters, not wildcards |
| `since`, `until` | The alert's creation time (`opened_at`): `since` inclusive, `until` exclusive. Without `since` the window is the day before `until`; without `until` it ends now; without either, no time filter is applied. A window wider than `API_MAX_RANGE_DAYS` (365 by default) is refused |
| `sort` | `created_at` (the alert's `opened_at`), `severity` or `updated_at`. Default `created_at` |
| `order` | `asc` or `desc`. Default `desc`. For `sort=severity`, `desc` lists the most severe first and `asc` lists `INFO` first |
| `limit`, `offset` | The existing paging contract: 1–500, default 100, default offset 0 |

`family` groups the eight alert producers that raise alerts: `log_source` (Phase A incidents and new
inventory), `waf` (WAF endpoint incidents), `ips` (IPS source and entity incidents),
`property_watch` (pinned-value incidents), and the alert-only families `catchall_sender`,
`custom_rule`, `scheduled_search` and `qradar_instance`. The first four are the anomaly families,
named exactly as `GET /api/v1/anomalies/summary` names them. It is not `AnomalyType`: that enum is
persisted in Phase A rows and fingerprints and keeps its values. A specific detector or anomaly type
(for example `VOLUME_DROP`) is not a column on `alert` and is not a list filter.

`log_source_id` matches an alert whose subject belongs to that log source. A `log_source` or
`ips_source` alert stores the log-source id directly; a WAF, IPS-entity, catch-all-sender or
pinned-value alert stores its own subject's id, which is resolved to the log source. A
custom-rule alert follows its rule's subject. An alert with no single log source — a type- or
group-scoped property watch, a fleet-class custom rule, a scheduled search, the offense collection —
is not matched by a source filter. The filter is therefore narrower than "every alert that mentions
the source", and never wider: it never returns an alert from another source.

Every response carries `filters_applied` with the filters the server applied: `status`, `severity`,
`log_source_id`, `family`, `q` (the stripped search), `since` and `until` (the resolved window, or
null when no window was applied). The page also echoes `sort` and `order`.

```json
{
  "items": [],
  "total": 0,
  "limit": 100,
  "offset": 0,
  "filters_applied": {
    "status": null,
    "severity": [],
    "log_source_id": [],
    "family": null,
    "q": null,
    "since": null,
    "until": null
  },
  "sort": "created_at",
  "order": "desc"
}
```

An unknown `status`, `severity`, `family`, `sort`, `order` or `log_source_id`, a `q` longer than
100 characters or blank, and an inverted or over-wide time window answer `422`.

`GET /api/v1/alerts/facets` takes the same filters (without paging and ordering) and returns the
counts a filter bar draws its chips from:

```json
{
  "severity": [
    {"value": "CRITICAL", "count": 0},
    {"value": "HIGH", "count": 2},
    {"value": "MEDIUM", "count": 0},
    {"value": "LOW", "count": 0},
    {"value": "INFO", "count": 0}
  ],
  "family": [
    {"value": "log_source", "count": 2},
    {"value": "waf", "count": 0},
    {"value": "ips", "count": 0},
    {"value": "property_watch", "count": 0},
    {"value": "catchall_sender", "count": 0},
    {"value": "custom_rule", "count": 0},
    {"value": "scheduled_search", "count": 0},
    {"value": "qradar_instance", "count": 0}
  ],
  "status": [
    {"value": "OPEN", "count": 1},
    {"value": "ACKNOWLEDGED", "count": 1},
    {"value": "RESOLVED", "count": 0}
  ],
  "total": 2,
  "filters_applied": {
    "status": null,
    "severity": [],
    "log_source_id": [],
    "family": "log_source",
    "q": null,
    "since": null,
    "until": null
  }

```

Every closed value is present in a stable order, even at zero: zero is a measured count under the
same filters. The facets are counted with every filter applied — including the family filter itself —
so each column adds up to `total`, and `total` equals the same filter's `GET /alerts` `total`. The
counts cost one grouped statement, never one read per alert.

## QRadar access check

The application is read-only against QRadar and does not know in advance which of the APIs it uses
the token may reach. A check sends one minimal read to each API (a `GET` with `Range: items=0-0`,
or the endpoint's own minimal form; the license pool takes no `Range`) and, for Ariel, one tiny
stored search that is cancelled unread. It keeps the status code of each answer and nothing from
the body. The catalog of APIs is code (`backend/app/providers/access_catalog.py`); `docs/INSTALL.md`
lists it for the QRadar administrator. Both routes need `admin:*` (`read:*` does not satisfy it).

| Route | What it does |
|---|---|
| `GET /api/v1/admin/qradar-access` | The latest stored result per enabled console and catalog entry, and the state of its check. Sends nothing to QRadar. `{consoles: [{instance_id, instance_name, applicable, last_checked_at, check_running, last_check_started_at, last_check_finished_at, entries, syncs_started}], check_interval_seconds}`. `applicable` is false for a console that is not on the direct REST provider: nothing is checked on it. `syncs_started` names the syncs the latest check started. `check_running` is true while a check of that console runs, whoever started it (beat, worker start-up or the POST below); `last_check_started_at` and `last_check_finished_at` are UTC, null when no check ever started or finished (while a check runs, the finished time is the previous run's). **A run that started more than 10 minutes ago and never finished counts as not running**, so a worker that died mid-check cannot leave `check_running` true; the next check then starts normally |
| `POST /api/v1/admin/qradar-access/check` | Queues the check for every enabled REST console and answers `202` at once with the same shape as `GET` plus `started` (consoles queued by this request), `already_running` (consoles that had a check running: nothing was queued for them, the answer shows the running one) and `failed` (consoles whose task the queue refused; their run is released). It never probes inside the request, because a check takes about a minute and the proxy waits 60 seconds. Poll `GET` until `check_running` is false. Rate limited by `RATE_LIMIT_ACCESS_CHECK` (`2/minute`; `429` beyond it); a request answered with `already_running` still counts. Audited as `qradar_access.check`, with `started`, `already_running` and `failed` in the detail |

An entry: `id`, `title`, `method`, `path`, `feeds` (what it feeds in this application), `used_by`
(collectors and pages), `status`, `http_status`, `checked_at`, `previous_status`, `syncs_started`,
`required_capability`, `capability_verified`, `capability_hint`, `sources` and `covers`.

`status` is `ok`, `forbidden` (403), `unauthorized` (401: the token itself), `not_found` (404: the
API is missing on this version), `unreachable` (network, TLS or timeout) or `error` (5xx or any other
code); it is `null` before the first check of that entry, never a zero. `http_status` is null when
QRadar did not answer. **`required_capability` is the capability IBM documents for that API; IBM's
per-endpoint reference documents none, so it is `null` with `capability_verified: false` for every
entry.** `capability_hint` is the closest role permission IBM documents for the same data (a hint
to confirm with the QRadar administrator, never a fact), and `sources` are the IBM pages read.
`covers` lists calls that are not probed on their own, each with the reason.

When an entry goes from anything but `ok` to `ok`, the check starts the syncs that depend on it
once per console: `log_source_inventory`, `rule_inventory`, `offense_snapshot`,
`log_source_metrics` (volume collection) and `health_cache` (the QRadar health reads are fetched
again). Nothing is started for an entry that stays refused, on its first check, or for one that
was not answered. A sync the queue refused is not reported as started. The checks run at start-up,
every `QRADAR_ACCESS_CHECK_INTERVAL_SECONDS` (six hours) and on demand.

## Alert e-mail administration

Alerts go out by e-mail through the site's SMTP relay. The relay, its security mode and the password
stay in the server environment (`.env`) and never reach the browser; the application administers
only what an analyst may change: the message templates and the recipients. Every route below
needs `admin:notifications` (`admin:*` includes it, `read:*` does not), is audited on write, and
answers `403` with the usual coded permission message otherwise. All texts are English.

| Route | What it does |
|---|---|
| `GET /api/v1/admin/email/settings` | The transport as configured. Fields: `configured` (is `SMTP_HOST` set; when false, no mail can leave), `host`, `port`, `security` (`starttls`, `ssl` or `none`), `security_source` (`SMTP_SECURITY` or `SMTP_USE_TLS`), `from_address`, `from_name`, `username_set`, `ca_file_set`, `site_name`, `test_rate_limit`. **Never the password.** |
| `GET /api/v1/admin/email/placeholders` | `{syntax, placeholders: [{name, description}]}`, the fixed allowlist of `{{ name }}` placeholders |
| `GET /api/v1/admin/email/templates` | `{templates: [{key, alert_type, label, customised, enabled, updated_at, updated_by}], alert_types: [{key, label}]}`: the default plus one entry per alert type, `customised` meaning a stored row exists |
| `GET /api/v1/admin/email/templates/{key}` | One template. `key` is `default` or an alert type. Fields: `key`, `alert_type`, `label`, `customised`, `enabled`, `effective_source` (`own`, `default` or `shipped`: what this key sends today), `subject`, `html_body`, `text_body` (empty means derived from the HTML), `updated_at`, `updated_by`. A key with no stored row returns the template it falls back to, so an editor can start from it |
| `PUT /api/v1/admin/email/templates/{key}` | Create or replace. Body `{subject, html_body, text_body?, enabled?}`; unknown fields are refused. Returns the stored template, so the editor shows the **sanitised** HTML that will be sent |
| `DELETE /api/v1/admin/email/templates/{key}` | Remove the stored row: the default key returns to the shipped template, a type key returns to the default. `404` when no row exists |
| `POST /api/v1/admin/email/preview` | Body as `PUT` plus `alert_type` (null for the generic sample). Renders against a **fixed sample alert** of that type, never a real one. Returns `{subject, html, text, sanitized_html_body, sample_alert_type}` |
| `POST /api/v1/admin/email/test` | Body as `preview` plus `to`, one mailbox typed by the administrator. Sends the rendered sample, subject prefixed `[Test] `, through the configured relay. Rate limited by `RATE_LIMIT_EMAIL_TEST` (`5/minute` by default; `429` beyond it). Returns `{ok, outcome: {code, params, message}}` with `200` for any SMTP outcome: `email.test.sent`, `email.test.not_configured`, `insecure_login` (a username with `SMTP_SECURITY=none`: refused, nothing connects), `connection_refused`, `timeout`, `connection_failed`, `tls_failed`, `auth_failed`, `recipient_refused`, `sender_refused`, `server_error`. The relay's own reply text is never returned |
| `GET /api/v1/admin/email/recipients` | `{recipients: [{id, address, min_severity, alert_types, enabled, created_at, updated_at, updated_by}], from_env: [address]}`. `from_env` lists `NOTIFY_EMAIL_RECIPIENTS`, read-only: they receive every alert at LOW and above |
| `POST /api/v1/admin/email/recipients` | Body `{address, min_severity?, alert_types?, enabled?}`. `min_severity` is `INFO`, `LOW` (default), `MEDIUM`, `HIGH` or `CRITICAL`. `alert_types` null (default) means every type, otherwise a non-empty list of alert types. The address is validated (one plain mailbox, no display name or list) and stored in lower case. `201`; `409` for a duplicate; `422` with a coded message otherwise |
| `PUT /api/v1/admin/email/recipients/{id}` | Replace the recipient's fields |
| `DELETE /api/v1/admin/email/recipients/{id}` | Remove it. `204` |

**Alert types** are the alert's own `source_type`: `log_source`, `waf_endpoint`, `ips_entity`,
`custom_rule`, `pw_value`, `catchall_sender`, `qradar_instance`, `scheduled_search`.

**Templates.** One default template (`default`) and an optional template per alert type. An alert
uses the enabled template of its type, else the enabled default, else the shipped default that
lives in the code. A disabled row is skipped, never an error. A template has a one-line `subject`,
an `html_body` and an optional `text_body`; without a text body the plain-text part is derived
from the HTML.

**Placeholders** are written `{{ name }}`; there is no logic and no template engine. Allowed names:
`alert.title`, `alert.description`, `alert.severity`, `alert.transition`, `alert.type` (the label),
`alert.occurrences`, `alert.first_seen`, `alert.opened_at` (UTC), `alert.url`, `evidence.observed`,
`evidence.expected`, `evidence.deviation`, `evidence.reason`, `instance.name`, `site.name`. Saving
or previewing a template that names anything else is refused with `422`: `detail` lists one
English sentence per unknown name, and `detail_codes` carries `email.template.unknown_placeholder`
with the `name` for each. Values are HTML-escaped in the HTML part, plain in the text part and
stripped of line breaks in the subject; a value that is missing renders as an em dash.

**Sanitising.** The HTML body is cleaned on save and again returned in the response: only e-mail
layout tags (tables, headings, paragraphs, lists, links, `img`), `https:` image sources, `https:`
or `mailto:` links, and an allowlist of inline style properties survive. Scripts, `<style>`
blocks, event handlers, forms, frames and `url(...)` values are removed. A link target may be a
placeholder only when it is `{{ alert.url }}`. An HTML body with nothing left after cleaning is
refused with `422`.

The e-mail is a `multipart/alternative` message (text, then HTML), UTF-8, with `Date`,
`Message-ID`, `From` (`SMTP_FROM`, optional display name `SMTP_FROM_NAME`) and the recipient in
`To`.
