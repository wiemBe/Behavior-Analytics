# Task T-051a — IPS detectors, part 1: the pure layer (Phase D, G2)

Read `AGENTS.md` at the repository root first and follow it exactly. These rules matter most here:
- rule 3: raw values never leave the pure functions, except the bounded contributor lists;
- rule 6: `AnomalyType` and `WafAnomalyType` stay as they are. IPS types go in a new
  `IpsAnomalyType`;
- rule 8: fail closed. A detector never grants itself lower-bound reasoning; its verdict scope
  comes from the requirements it declares in `app/anomaly/capabilities.py`;
- §4: never weaken a test; stop and report a conflicting test, except where this spec rules on it
  in advance (see "Pinned tests").

**This task is pure: no database, no migration, no engine, no Celery task, no API route, no UI.**
T-051b, which comes after it, adds the migration, the baselines, the bulk loaders, the engine and
the lifecycle, and feeds your types from the database. Design what you build so T-051b can fill it
from plain values without reshaping it.

## Build

### 1. `IpsAnomalyType` (`app/models/enums.py`)

Exactly the seven names of §D.6, in that order:
`IPS_PORT_RATE_SPIKE`, `IPS_DESTINATION_RATE_SPIKE`, `IPS_SIGNATURE_BURST`,
`IPS_NEW_DESTINATION_PORT`, `IPS_SOURCE_CONCENTRATION_SPIKE`, `IPS_PORT_FANOUT_SPIKE`,
`IPS_BLOCK_RATIO_SHIFT`.

### 2. Inputs and observations (`app/ips/inputs.py`, new)

- `IpsInput` (StrEnum): one member per measured input the detectors read, for example entity
  events, dimension events, source-IP top-1 events, source-IP events, max distinct ports, blocked
  events, action events, port history. Name them after what they are.
- Frozen dataclasses for one entity's bucket and one source's bucket, built from plain values
  (the columns of `IpsSourceBucket`, the entity's `IpsEntity` fields, and the entity's
  `IpsEntityMetric.events` or `None` when it has no row).
- **The absence rule, as a pure function, with tests.** An admitted, active entity with no metric
  row in a bucket is a **measured zero only when** that dimension's measurement is `EXACT`, its
  coverage is at or above the floor, and `admission_truncated` for that dimension is false.
  Otherwise its count in that bucket is **unknown** (`None`), never 0. An entity with a row in a
  `LOWER_BOUND` dimension has a lower-bound count.
- `input_measurement(...)` for IPS, mirroring `app/waf/inputs.py`: what each input is for one
  observation (`EXACT`, `LOWER_BOUND` or unknown). A ratio numerator is a lower bound when some of
  the denominator's events were unmapped (`unmapped_events > 0`), as in WAF.

### 3. Detectors (`app/ips/detector.py`, new; split into two modules if it grows past ~700 lines)

Pure functions, one per `IpsAnomalyType`, each returning a verdict carrying
`AnomalyEvidence[IpsAnomalyType]` exactly as WAF does, with `EVIDENCE_VERSION` and readable
reasons. An `IpsThresholds` dataclass holds every guard with a default; T-051b maps settings onto
it. The verdicts:

- **`IPS_PORT_RATE_SPIKE`, `IPS_DESTINATION_RATE_SPIKE`, `IPS_SIGNATURE_BURST`.** Entity events
  above the entity's seasonal band. Use the WAF spike math and guards (deviation, ratio, minimum
  absolute delta, minimum bucket events, MAD floor), with IPS thresholds. A lower-bound count may
  prove an increase only (`INCREASE_ONLY` scope); it never proves normal.
  - `IPS_SIGNATURE_BURST`: when the entity's display name starts with `GENERIC_NAME_PREFIX`,
    `INSUFFICIENT_DATA` (§D.8: a claim about a specific signature is not safe).
  - A port entity whose key is port `0`, or protocol `255`, is `INSUFFICIENT_DATA`. The fold
    already excludes them; guard anyway.
- **`IPS_NEW_DESTINATION_PORT`** (subject: the source). The claim must be stated honestly as:
  **a destination port that stayed below the admission threshold in every bucket of a complete
  history window now carries traffic above a floor.** Absence of an entity row in history proves
  only "below the threshold", and only when that history bucket's discovery and admission were
  complete. Mirror `app/waf/novelty.py` with a `verify_port_history(...)` that requires, per
  history bucket: present, same width, `DESTINATION_PORT` measurement `EXACT`, coverage at or
  above the floor, `admission_truncated` false, the same profile version and normalizer version,
  and not in maintenance. Then:
  - a re-admitted (retired, then seen again) entity is not new: `NORMAL`, with the reason;
  - a flood at appearance is `INSUFFICIENT_DATA`, as WAF §30.5 decides it;
  - anything the history cannot prove is `INSUFFICIENT_DATA` with the failing bucket in the
    reason.
- **`IPS_SOURCE_CONCENTRATION_SPIKE`.** The top-1 source IP's share of source-IP events above its
  pooled baseline, with a volume floor. Mirror `detect_client_concentration_spike`: the largest
  contributor and the total must both be exact.
- **`IPS_PORT_FANOUT_SPIKE`.** One source IP reached more distinct destination ports in a bucket
  than the source's baseline cell of the per-bucket maximum allows (scan shape, §D.7). A
  lower-bound `max_distinct_ports` may prove an increase only. The evidence may name the top
  fan-out contributors from the bucket's bounded `PORT_FANOUT` list. It makes no intent claim:
  "port sweep" is a shape, not an attack verdict (§D.2).
- **`IPS_BLOCK_RATIO_SHIFT`.** Blocked share of action events above its pooled baseline, mirroring
  `detect_ratio` with `BLOCK_RATIO`. When the source's action dimension is `NOT_COLLECTED`
  (no action property mapped), `INSUFFICIENT_DATA` with the reason "no action property mapped".

Every detector, before any comparison: `INSUFFICIENT_DATA` when the bucket is in maintenance, when
an input it needs is unknown, when the dimension's coverage is below the floor, when its baseline
cell is missing, unreliable or below `baseline_min_samples`, or when the cell was built under a
different profile or normalizer version. Never `NORMAL` from a missing input, and never a zero.

### 4. Capability specs (`app/anomaly/capabilities.py`)

- Add `BehaviorDomain.IPS_ENTITY` and `BehaviorDomain.IPS_SOURCE`. Each detector takes the domain
  of its subject in the §D.6 table.
- `IPS_BASELINE_METRICS` (the metric names §D.7 needs) and
  `IPS_DETECTORS: dict[IpsAnomalyType, DetectorSpec]`, declaring each detector's inputs with
  `InputRequirement`, each with its rationale. Widen `InputRequirement.input` to
  `WafInput | IpsInput`.
- `ips_input_scope(...)`, mirroring `waf_input_scope`: the narrowest declared input decides.
- **`scheduled_task=None` for every IPS spec.** Nothing runs them until T-051b wires the engine,
  so `detector_status` must report `NOT_SCHEDULED`, never `OPERATIONAL`. Each IPS spec carries a
  `limitation` an operator can read, such as "IPS detection does not run on a schedule yet": the
  API test `test_a_non_operational_detector_says_why` requires one. Extend `detector_status`
  for the two IPS domains: `UNSUPPORTED` when the spec's baselines are not a subset of
  `IPS_BASELINE_METRICS` or it is not implemented, `NOT_SCHEDULED` when it has no task.
- `IPS_BLOCK_RATIO_SHIFT`: `activation` says it needs an `ACTION` mapping with a value map in the
  source's IPS profile.
- `all_detectors()` includes the IPS specs, after the WAF ones.

## Pinned tests (ruled in advance)

Adding seven detectors is a deliberate contract change. If an existing test enumerates
`all_detectors()`, `BehaviorDomain` or the `/behavior/detectors` response and pins the full set,
**add** the IPS entries (with status `NOT_SCHEDULED`) and nothing else. One is known:
`tests/integration/test_phase_a_api.py::TestDetectorCapabilities::test_every_named_detector_is_published_with_its_status`
pins `set(status) == AnomalyType | WafAnomalyType`. Add `| IpsAnomalyType` to that set, and add an
assertion that every IPS type is `NOT_SCHEDULED`; keep every other assertion as it is. Change no existing entry,
remove nothing, loosen no assertion. List every such edit in your report. Any other conflicting
test: stop and report it.

## Tests

- Unit tests for every guard and exit path of every detector: `INSUFFICIENT_DATA`, `NORMAL` and
  anomalous, including `INCREASE_ONLY` from a lower bound, and a lower bound that never yields
  `NORMAL`.
- The absence rule: each of its conditions on its own turns a missing row into unknown.
- `verify_port_history`: one test per failing condition, plus the complete case.
- Capability tests: every `IpsAnomalyType` has a spec; every IPS spec is `NOT_SCHEDULED`; the
  scope of each declared input; `UNSUPPORTED` for an unknown baseline metric.
- A guard test that no `IpsAnomalyType` value collides with an `AnomalyType` or `WafAnomalyType`
  value.
- Break the code on purpose for at least five guards and confirm the tests fail (AGENTS.md §4).
  List them.
