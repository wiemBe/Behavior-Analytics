## What was built, and what you are checking

Read [`docs/SEARCH-CADENCE.md`](../SEARCH-CADENCE.md) in full. In short: every search family has a
cadence (5 min to 8 h, default 1 h). At each tick a family runs **one** Ariel search keyed by
`starttime / bucket_ms` that returns **every** 5-minute bucket of the window; it splits on
truncation. The unit and integration suites prove the keyed path equals the per-bucket path on the
mock. Nobody has run it against a real console yet.

Answer, with measured evidence:

1. **One search per kind per tick.** For Phase A volume and for rule matches, run one tick at a
   1 h cadence and one at an 8 h cadence through the **application's own collectors**
   (`MetricCollector` keyed path; the rule-match collector keyed path). Count the Ariel searches
   each tick creates (wrap or log the provider in your probe script; do not edit `app/`). Expected:
   1 per tick unless the result was truncated and split; report any split and why.
2. **Equivalence with the per-bucket path.** For each of those ticks, pick at least 3 buckets
   (first, middle, last) and run the old per-bucket query for them (the single-bucket provider
   method, e.g. `get_log_source_metrics` / `get_rule_matches`). Compare per source (per rule) per
   bucket: `SUM(eventcount)` volume, event count, the zero-filled sources, and the rule-match
   counts. Report every mismatch with its size. Small differences in the very last bucket may be
   late arrival; say so only if a re-run of that one bucket a few minutes later converges.
3. **Wide-search timing (the §SC.6 asymmetry).** Report the wall time and row count of every keyed
   search, especially at 8 h. Did any wide search fail or time out? If one did, Phase A would hold
   its watermark (it does not split on failure); say whether the evidence says Phase A needs
   split-on-failure.
4. **WAF, if a WAF source can be made live.** The lab WAF source is `lab-waf-behavior-01`
   (QRadar id 312), fed by the lab generator. See `docs/LAB-SYNTHETIC-TELEMETRY.md` (its safety
   contract is binding) and `docs/PHASE-B-WAF-BEHAVIOR.md` §26 for the verified property names.
   - If 312 has no events in the last 8 h, you may run the generator's WAF stream **within the
     safety contract** (its documented rate limits; RFC 5737 addresses; the operator-configured lab
     destination only) for at most 20 minutes.
   - Create the WAF profile **in your own task database only** with `python -m app.cli.waf set`,
     validate it with `python -m app.cli.waf validate` (read-only against QRadar), and run one WAF
     tick at a 1 h cadence through `run_waf_source` or the collector.
   - Answer: does `GROUP BY "<custom property>", starttime / bucket_ms` work live? How many
     searches did the tick create (expected: endpoints + totals + one per enabled breakdown)? Do
     3 buckets equal the per-bucket path?
   - If the WAF source cannot be made live within the contract, say so and skip this part.
5. **Optional, only if budget remains:** the alert path. A fresh database has no trained Phase A
   baselines, so a real spike alert needs history. Do not backfill weeks of data. If you can show
   the evaluation watermark (0014) walking every new bucket in order on live data, report that; an
   alert is not required.
