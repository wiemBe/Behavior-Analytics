# Task T-074 — live smoke: the T-050a keyed IPS searches against the lab IPS sources

Read `AGENTS.md` at the repository root first. Follow it exactly.

This is a **live, read-only check**. Write no application code, and change no repository file
except your report. Throwaway scripts go only in your scratch directory (below).

## Why

T-050a added `QRadarRestProvider.get_ips_keyed`, one fleet-wide keyed search per dimension. Some of
its AQL forms have **never run on a live QRadar**:
- `QIDNAME("qid") AS "qname"` selected while only `"qid"` is in the `GROUP BY` (SIGNATURE);
- `ORDER BY UNIQUECOUNT("destinationport") DESC` (PORT_FANOUT);
- `ORDER BY SUM(eventcount) DESC` with several group keys plus `starttime / <bucket_ms>`;
- `logsourceid IN (412, 413)` together with the population filters (`INCIDR`, `> 0`).

T-065 showed that an unverified form (`LIKE` on an IP field) can sink a whole feature. Find out
before T-050b's collector depends on these.

## Method

1. Work from the T-050a code. Use the integration branch's main checkout,
   `/home/efe/Documents/QRadar-Dash/backend`, once T-050a is merged, with `PYTHONPATH=.` and
   `.venv/bin/python -I`. Assert at the start that `app.providers.qradar_rest` has

2. Send IPS traffic with the repository generator, as T-065 did: `pan_threat`, then `ftd_ips`,

   a time. Stop each by its PID and confirm none is left.
3. Build the provider with the application's factory and the process-environment overrides below.
   Call `get_ips_keyed` **once per dimension**:
   - `TOTALS`, `DESTINATION_PORT`, `DESTINATION_IP`, `SIGNATURE`, `SOURCE_IP` and `PORT_FANOUT`;
   - with **both sources in one call**, `qradar_log_source_ids = [412, 413]`;
   - with the `CISCO_FTD` preset mapping's references (the two presets have the same normalized
     references);
   - over one window of whole 5-minute buckets that covers both sends (at most 30 minutes);
   - with `bucket_seconds = 300` and `max_rows = 5000`.

   Skip ACTION, which no lab source has mapped. Then fold each result with `app/ips/fold.py`
   through `app/ips/keyed_search.run_dimension` with a fresh budget, so the real driver runs.
   **No database writes.**
4. For any rejected form, run **one** alternative per construct directly, and report whether
   QRadar accepts it. For example: `QIDNAME(qid)` added to `GROUP BY`, or `ORDER BY` a column
   alias or position.

## Questions

1. For each dimension:
   - was the search accepted or rejected, and how long did it take;
   - how many rows came back, and was it truncated;
   - what are the per-source, per-bucket totals for TOTALS;
   - what are the top three entities per source for the entity dimensions;
   - what is the largest distinct-port count for fan-out;

2. Does the sum of the dimension's events per (source, bucket) relate sensibly to TOTALS? The
   port, IP and signature filters exclude some events, so less is expected. Is coverage above 1.0
   ever seen?
3. For anything rejected: the accepted alternative and its exact AQL.
