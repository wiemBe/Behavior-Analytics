## 2. `PW_ANOMALY_RETENTION_DAYS` is applied (`backend/app/services/pw_retention.py`)

**Facts (verify them):**
- `PwRetention` deletes `pw_value_metric`, `pw_bucket` and retired `pw_value` rows. No code reads
  `pw_anomaly_retention_days` (`grep -rn pw_anomaly_retention_days backend/app` finds only
  `config.py`).
- Resolved incidents therefore stay for ever, although §G.14.3 promises 180 days.
- The pattern to follow is `backend/app/services/waf_retention.py`: the `waf_anomaly` step ~L85–94
  and the module docstring. It deletes only terminal incidents older than the cutoff, and never
  one a detector state points at.
- `pw_detector_state` has `active_anomaly_id` and `open_anomaly_id`
  (`backend/app/models/property_watch.py` ~L369–370).
- `pw_anomaly_transition` cascades from `pw_anomaly` (~L440).

**Build:**
- A `pw_anomaly` step in `_STATEMENTS`, batched like the others and placed **before** the
  `pw_value` step, with its own cutoff `now - pw_anomaly_retention_days`. It deletes only
  incidents in a terminal state. **Read the PW engine** (`backend/app/property_watch/engine.py`)
  for which `AnomalyState` values a PW incident can end in, and use exactly those. Do not copy
  WAF's list unread.
  - The age is `COALESCE(resolved_at, anomaly_end, detected_at)`, as WAF does. Check that this
    is right for PW's columns.
  - Never delete an incident a `pw_detector_state` row points at.
  - Never delete one an alert still depends on. Check how a `pw_anomaly` alert finds its incident
    (`backend/app/services/pw_pipeline.py` and the alert enqueuer, PW-4) and whether a resolved
    incident can still have an unresolved alert. If it can, keep that incident and count it in
    `blocked`.
- The transitions go by cascade, and the module docstring states the new rule.
- The step's statement count is bounded by the batches, as every other step's is. The design's
  §G.14.3 says nothing more, so add no new setting.
