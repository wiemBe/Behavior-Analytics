## What I did

- Used distinct PostgreSQL transaction advisory-lock keys so each cap serializes its count and
  write without coupling unrelated custom-rule and scheduled-search requests. Disabling, deleting,
  and disabled creates do not acquire these locks.
- Kept the existing validators/services responsible for the one count and the existing 409 text,
  422 shapes, writes, and audit actions.
- Exercised POST and PATCH races with independent real sessions. The first transaction is held
  after its count until the second enters the cap check.
- Removed all four lock call sites temporarily and confirmed every new test failed because both
  concurrent writes succeeded; then restored the lock calls and confirmed all four tests passed.
