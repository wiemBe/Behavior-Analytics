## 2. What I did

**Provider check first (task item 1).** Every implementation of `QRadarProvider.get_ariel_search_results` was inspected before touching the executor:

- `mock.py:1104` — `truncated = len(rows) > max_rows`, `total_count = min(len(rows), max_rows)`: capped, truncated only past the cap. ✓
- `qradar_rest.py:1687` — requests `Range: items=0-{max_rows}` (max_rows+1 rows), `truncated = len(rows) > max_rows` before slicing, `total_count = len(rows[:max_rows])`: capped, truncated only past the cap. ✓
- `base.py:509` — abstract (raises `NotImplementedError`). ✓
- `qradar_mcp.py` — does not implement it (AQL is MCP-forbidden anyway); inherits the abstract stub. ✓

All providers agree, so the `+1` is valid and no provider code was changed.

**Executor.** `_apply_threshold` on a truncated run now compares the proven lower bound `value + 1`: `GT t=max` is recorded breached (true ≥ max+1 > max), `GT t=max+1` is not, `GE t=max+1` is breached; `LT`/`LE`/`EQ`/unknown keep "no verdict" (recorded `False`), and untruncated behavior is byte-for-byte the old mapping.

**Create.** `ScheduledSearchCreate` refuses with a pydantic 422 (`model_validator(mode="after")`): `GT` with `threshold_value >= max_result_rows + 1`, `GE` with `threshold_value > max_result_rows + 1`. `None`, `LT`, `LE`, `EQ` unaffected. Message matches the task example: `threshold GT 20000 can never be reached: a run counts at most max_result_rows (10000) rows; raise max_result_rows above the threshold or lower the threshold`.

**Update.** `ScheduledSearchService.update` merges the partial patch with the stored search and runs the *same* pure helper on the effective values before mutating; refusal raises `ThresholdUnreachableError`, the route returns 422, and nothing (row or audit) is written.

**Shared helper.** `unreachable_threshold_reason` is one pure function used by create, update and (via its `max_result_rows + 1` boundary, the same constant the executor's `value + 1` lower bound derives from) the executor's reasoning.

**Existing fixtures/tests (task item 3).** Zero. Grep of `backend/tests` for `threshold_value`/`max_result_rows` shows only `None`, 0, 10, 50, 100 and 1000-with-`LT` thresholds against caps of 1000/20/default — none is an unreachable GT/GE threshold, so no stored search or test needs migration. `ScheduledSearchCreate` was not previously exercised with a threshold above its cap anywhere in the suite.
