# Task T-047 — Scheduled searches: a threshold that can never fire is refused; the truncation lower bound is exact

Read `AGENTS.md` at the repository root first and follow it.

## Background (T-033 open point)

`QRadarRestProvider.get_ariel_search_results` asks for `max_rows + 1` rows and reports
`truncated = len(rows) > max_rows`, then returns `rows[:max_rows]` and `total_count = len(rows)`.
So on a truncated run `total_count == max_rows` and the **true count is at least `max_rows + 1`**.

`SearchExecutor._apply_threshold` (`backend/app/services/search_executor.py`) treats a truncated
`value` as a lower bound, but compares the bound `value` itself, not `value + 1`:
- `GT` with `threshold_value == max_result_rows` is provably breached on a truncated run
  (true ≥ max+1 > max), yet it is recorded as not breached.
- A `GT` threshold `t >= max_result_rows + 1`, or a `GE` threshold `t > max_result_rows + 1`, can
  **never** be breached: an untruncated run counts at most `max_result_rows`, and a truncated run
  proves only `>= max_result_rows + 1`. Such a search is accepted today and silently never alerts.

## What to do

1. **Exact lower bound.** In `_apply_threshold`, when `truncated` is true, compare using the proven
   lower bound `value + 1` for `GT` and `GE`. Keep "no verdict" (recorded `False`) for `LT`, `LE`,
   `EQ` and unknown operators, exactly as today. First check `backend/app/providers/mock.py`'s
   `get_ariel_search_results` (around line 451–465) and every other implementation of that method:
   the `+1` is valid only if every provider caps `total_count` at `max_rows` and sets `truncated`
   only when more than `max_rows` rows exist. If any provider differs, **stop and report**; do not
   change provider code.
2. **Refuse unreachable thresholds** with a 422 whose message says why and what to change, e.g.
   `"threshold GT 20000 can never be reached: a run counts at most max_result_rows (10000) rows;
   raise max_result_rows above the threshold or lower the threshold"`:
   - `GT` with `threshold_value >= max_result_rows + 1`;
   - `GE` with `threshold_value > max_result_rows + 1`.
   - `threshold_value is None`, and `LT`/`LE`/`EQ`, are unaffected.
   - On **create** (`ScheduledSearchCreate`): a pydantic `model_validator` is the natural place.
   - On **update** (`ScheduledSearchUpdate` is partial): the check must use the *effective* values
     after the patch (a patch that lowers `max_result_rows` below an existing threshold, or raises
     the threshold above the existing `max_result_rows`, or changes only the operator, is refused).
     Do it in `ScheduledSearchService.update` or the route, wherever the merged values are known,
     and return 422 with the same message. Nothing is written on refusal.
   - Use one shared pure helper for the rule so create, update and the executor's reasoning agree.
3. Existing stored searches are not migrated or altered. Mention in your report how many existing
   tests or fixtures (if any) create such a search.
