## The gap (found in the T-129 review, 2026-10-17)

The production host runs whatever the operator's git checkout holds: the script, the compose
files and `deploy/`. Nothing ties that checkout to the version the site runs.

1. `./qradar-dash upgrade X` from a checkout of another version runs that version's script and
   compose files against X's images. It works for 0.1.0 → 0.1.1 (only `qradar-dash` changed), but
   a release that changes `docker-compose*.yml` or `deploy/` would start new images on an old
   compose file. The design's own offline bundle (§ bundle) carries the script, the compose files
   and the images of one version together.
2. `./qradar-dash install` from a checkout of a newer version, on a site that already records an
   older version, rewrites `.env` with the newer `QRADAR_DASH_VERSION` and brings the stack up on
   it: an upgrade with **no pre-upgrade backup and no automatic rollback**. The runbook tells the
   operator to re-run `install` after fixing QRadar, so this is one `git pull` away.

## What to build

1. **`upgrade` refuses a checkout of another version.** Right after the SemVer check and before
   the state file is read: read `VERSION` (strip whitespace). If it cannot be read, or differs
   from the target:
   `upgrade refused: this checkout is version <checkout>, not <target>; run git fetch --tags && git checkout v<target> first (see docs/OPERATIONS.md, Yükseltme)`
   (for an unreadable file, `<checkout>` is `unknown`). Exit 1. Nothing is pulled or stopped.
   The release notes are still read from the target image (design §1.3 is unchanged).
2. **`install` refuses to change the recorded version.** Before anything is written (so also
   under `--dry-run`), when `.qradar-dash/state.json` exists:
   - `state_read` fails →
     `install refused: .qradar-dash/state.json field <field> is invalid; see ./qradar-dash status`;
   - the last upgrade is recorded as failed without `restored_from` (the same condition
     `cmd_upgrade` uses) →
     `install refused: the last upgrade failed; run rollback or restore first`;
   - `installed_version` differs from the checkout's `VERSION` →
     `install refused: this site runs <installed> and this checkout is <checkout>; use ./qradar-dash upgrade <checkout> to change versions, or check out v<installed> to re-run install (see docs/OPERATIONS.md, Yükseltme)`.
   - With **no** state file, `install` behaves as today. That is the path a 0.1.0 site whose
     QRadar check failed (it has no state file) uses to reach a state file; do not break it.
   - A re-run at the **same** version (the documented "fix QRadar and run install again") still
     works.
3. **Runbook** (`docs/OPERATIONS.md`; Turkish prose, English commands and messages copied from the
   script):
   - "Yükseltme": before the command, the operator brings the checkout to the target tag
     (`git fetch --tags`, `git checkout v<version>`; a registry install needs no submodule), and
     why: the target version's script and compose files run the upgrade. Quote the refusal.
   - "Geri alma (`rollback`)" and "Otomatik geri alma": after a rollback (manual or automatic), return the checkout to the version that
     now runs (`git checkout v<previous>`), so `install` and the compose files match it.
   - "Yeniden çalıştırma": a re-run uses the checkout of the version the site runs; quote the
     install refusal.
   - Keep every symptom id and its order; if you add one, add it after OPS-R45 and list it.
4. **Release notes** `docs/releases/0.1.1.md`:
   - add a bullet for the two refusals above;
   - rewrite the **Upgrade** paragraph: (a) normal path: `git fetch --tags && git checkout v0.1.1`,
     then `./qradar-dash upgrade 0.1.1` (the 0.1.0 script has no checkout check, so this order is
     what makes the 0.1.1 script run the upgrade); (b) a 0.1.0 site with no state file (its
     QRadar check failed at install): take `./qradar-dash backup manual` first (it works without a
     state file: read `cmd_backup_create` to confirm), then either fix QRadar and re-run
     `./qradar-dash install` from the v0.1.0 checkout (that writes the state file only when the
     QRadar check passes), then upgrade as in (a); or, if QRadar cannot be fixed yet, check out
     v0.1.1 and run `./qradar-dash install`, which brings the site to 0.1.1 and writes the state
     file — say plainly that this path has no automatic rollback, which is why the backup comes
     first;
   - in the beat bullet, replace "for the first two minutes after …" with "right after an
     install, `upgrade`, `rollback` or a reboot" (the heartbeat is written at beat start).
   - Keep the front matter exactly as it is.
5. **Design note:** in `docs/OPERATIONS-DESIGN.md`, add a short `**[as built, T-131]**` paragraph
   to the upgrade section saying that `upgrade` requires the checkout at the target version and

## Tests (through the commands themselves)

- `upgrade` with `VERSION` ≠ target: exit 1, the message, and the stub saw **no** `pull`, `stop`
  or `up` (use the existing docker stub's call log). With `VERSION` missing: same, `unknown`.
- `upgrade` with `VERSION` = target still runs as before. The existing upgrade fixtures need a
  `VERSION` file equal to their target: **add it to the fixture**; never weaken, skip or delete a
  test. List each fixture you changed in the report.
- `install` (`_install_flow` / `flow_path` in the installer tests): a state file recording another
  version → exit 1, the message, `.env` unchanged byte for byte; a state file whose last upgrade
  failed → exit 1, the message; an invalid state file → exit 1, the message; the same version →
  install completes; no state file → install completes (as today). One `--dry-run` case refuses
  too.
