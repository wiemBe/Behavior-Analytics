## 2. Property -> log-source type

Join (no single endpoint does it; two collections joined client side):

`property_expressions.regex_property_identifier == regex_properties.identifier`, then
`property_expressions.log_source_type_id` == the log source's `type_id`
(`GET /config/event_sources/log_source_management/log_sources/{id}?fields=id,name,type_id,enabled`).
Match `log_source_id in (-1, <source id>)` and `enabled == true`. Identifiers are GUIDs for
user-made properties and `DEFAULTCUSTOMEVENT10`-style keys for built-ins; the join key is always
`identifier`, never `id`.

- `lab-waf-behavior-01` (id 312, type 212): **HTTP_Method, URL, WAF_Action, WAF_ResponseCode,
  WAF_USERAGENT** (5 properties; `filter=log_source_type_id=212` returns exactly these 5 rows).
  Finding: **`WAF_URL` has its only expression on type 232, not 212**, so it does not apply to the
  WAF source's type; the type-212 URL-like property is `URL` (built-in, 16 expressions over many
  types). A type-aware editor would flag a mapping of `WAF_URL` for this source.
- IPS, `McAfee Network Security Platform @ edge-ips-01` (id 118, type 25): **no** property
  (`filter=log_source_type_id=25` returns 0 rows).
- IPS, `ips-gw-01@IPS` (id 212, type 2, Snort): **IPS_Action** (1 property).
- Properties with no expression anywhere: 8 of 119 (never apply to any source).

## 3. Request shape

All verified on `property_expressions` / `property_aql_expressions` / `regex_properties`:
- `fields=` honoured (response keys are exactly the list). `fields=id,regex_property_identifier,
  log_source_type_id,log_source_id,enabled` shrinks 474 rows from 663,980 bytes to 66,200.
- `filter=log_source_type_id=212` honoured (5 rows; type 25 gives 0; AQL endpoint with `=64` gives 4).
  `filter=name="WAF_URL"` on regex_properties gives 1 row;
  `filter=identifier in ("<guid>","<guid>")` gives 2 rows.
- `Range: items=0-4` honoured (5 rows). Provider `_paginate` works unchanged.
- Payload, full catalog: unfiltered regex 47 KB + expressions 664 KB (bodies included) is wasteful;
  with `fields=` it is **13.4 KB (regex_properties, id/identifier/name/property_type) + 66.2 KB
  (property_expressions slim)** = about 80 KB, two requests. Per type: one filtered call of < 1 KB.
- One cached fetch per instance per 10-30 minutes is realistic (two calls, ~80 KB). Properties
  change by hand-editing on the console. Cache both collections slim, join in memory, and key the
  result by (instance, type id). Include an explicit refresh button; do not call per keystroke.

## 4. Ariel: normalized vs custom (3 of 3 searches, each START/STOP = last 1 h, LIMIT 10)

Source 312 had **no events in the window**, so every search returned 0 rows. What this proves:
QRadar parsed and accepted each statement (status COMPLETED, no rejection at create; T-027 saw
invalid statements rejected at create). It does **not** show row values.

- S1 `SELECT "destinationport", "sourceip" FROM events WHERE logsourceid = 312 LIMIT 10 START .. STOP ..`
  accepted: **double-quoted normalized fields are accepted.**
- S2 `SELECT QIDNAME(qid) AS qn, "WAF_Action", SUM(eventcount) AS ec ... GROUP BY qid, "WAF_Action"
  ORDER BY ec DESC LIMIT 10 ...` accepted: **QIDNAME(qid) beside a quoted custom property in one
  GROUP BY works.**
- S3 `SELECT "destinationport", QIDNAME(qid) AS qn, "WAF_Action", SUM(eventcount) AS ec ... GROUP BY
  "destinationport", qid, "WAF_Action" ORDER BY ec DESC` accepted: quoted normalized field in
  GROUP BY next to qid and a quoted custom property.

Conclusion: one code path that double-quotes every name (normalized or custom) is syntactically
safe. Unverified (no rows): that returned column keys are the unquoted name for normalized fields
and that values are non-NULL; check with T-040's live events before relying on it.

## 5. Name rules

Against `^[A-Za-z0-9_][A-Za-z0-9_ -]{0,63}$`: **0 of 119** lab property names fall outside it
(no `.`, `/`, parentheses; there are spaces and hyphens, e.g. `Events per Second Coalesced - Peak 1
Sec`; no duplicates; none starts with a space or exceeds 64). Normalized Ariel field names
(`sourceip`, `destinationport`, `qid`) also match. Console-side names can in principle contain
other characters, so keep the allowlist as a hard validation and show a rejected catalog entry as
"not selectable: name not allowed" instead of dropping it silently.

## Recommended provider method

Read-only, REST only, no AQL; add to `QRadarProvider` (base.py) and `QRadarRestProvider`; mock
returns a fixed list.

```python
async def list_custom_properties(
    self, *, log_source_type_id: int | None = None
) -> list[CustomPropertyDTO]: ...
```

Implementation: two paginated GETs with `fields=` (regex_properties; property_expressions slim),
optional `filter=log_source_type_id=<n>` on the second, join on identifier, enabled expressions
with `log_source_id == -1` only (every lab row; a non-`-1` row would need the source id, so also
accept `log_source_id: int | None` later). Aggregate expressions per property so the DTO has one
row per property.

```python
@dataclass(frozen=True)
class CustomPropertyDTO:
    qradar_id: int                       # regex_properties.id
    identifier: str                      # join key
    name: str                            # as shown in Ariel, double-quoted
    property_type: str                   # "string" | "numeric"
    use_for_rule_engine: bool
    auto_discovered: bool
    log_source_type_ids: tuple[int, ...] # enabled expressions, sorted; empty = no expression
    name_allowed: bool                   # matches PROPERTY_NAME_PATTERN
```

No regex, payload, format_string or capture_group in the DTO. Normalized fields are a static list in
the app, not fetched.
