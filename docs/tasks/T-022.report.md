## What I did

Implemented the §C.2 schema and migration, provider enrichment, bulk inventory persistence,
classification, reviewed/new lifecycle, and low-severity inventory alert. Inventory now performs
one existing-source query instead of one query per DTO. Types, groups, sources, classifications,
and seed rules use bulk operations; a group-capability refusal or provider failure leaves the
source sync successful and classifies without a group hierarchy for that pass.

Classification follows the binding order: override, internal, group, type/type-name, name/
identifier, then unclassified. Same-level highest priority wins; an equal-priority class tie is
recorded and falls through. Lower-level disagreements are retained in `conflicts`. The group walk
includes a source explicitly assigned to group 0 but treats parent 0 on a non-zero group as the
root sentinel, avoiding the live-observed 0↔root ambiguity.

The first successful non-empty inventory for an instance bootstraps all seen sources as
`REVIEWED`. Later non-internal additions are `NEW`; a re-sync does not create another alert.
Internal additions are always `REVIEWED`. The alert context includes `class`/`source_class`, basis,
type, auto-discovery, identifier, owner, and instance, and the fingerprint is keyed by instance id
plus QRadar id.

### Internal-flag decision

Both upstream facts are recorded:

- `log_source.is_internal` stores the 7.6 log-source row's own `internal` value.
- `log_source_type.internal` stores the type-table value joined by `type_id` during classification.

Classification uses `log_source_type.internal`, or the explicit identifier `127.0.0.1`, exactly as
§C.3 specifies. The type table is authoritative because internality is a DSM/type property; the
row-level flag is retained as independently observable inventory evidence and is not allowed to
silently change the classification rule.

### Seed-insertion decision

The seed list lives in `app/fleet/seed_rules.py` and is inserted during inventory sync before rule
loading. Each rule has a fixed UUID, and one PostgreSQL `ON CONFLICT (id) DO NOTHING` statement
makes insertion idempotent while preserving an operator's enabled/disabled state and other edits.
I chose sync-time insertion instead of migration insertion so revision 0011 remains a self-contained
historical DDL snapshot rather than importing mutable application data. It also guarantees the
rules exist immediately before every classification pass.

## What I did

I chose disjoint patterns for the Azure overlap: the CLOUD rule now names the real
`Microsoft Azure Platform` DSM explicitly, while `Microsoft Azure Active Directory` remains in
IDENTITY. This avoids creating a conflict at all, rather than merely hiding the overlap with a
priority difference. The 62-name unit matrix asserts each DSM produces exactly its expected class
or no type match, and independently rejects equal-priority cross-class matches. It includes all
types observed in T-015 section 7, representative DSMs for every built-in class, and all five
catch-alls. The matrix also exposed two missing common DSMs, which are now covered: Cisco Firepower
Threat Defense is FIREWALL and Infoblox NIOS is DNS.

`ensure_seed_rules()` now uses `ON CONFLICT (id) DO UPDATE` for definition fields only: `kind`,
`pattern`, `target_class`, `priority`, and `description`. The update has a
`classification_rule.built_in IS TRUE` predicate. It deliberately omits `enabled`, so an existing
built-in rule whose operator disabled it receives the shipped definition update but stays disabled.
The integration test starts with a synced built-in rule, makes its pattern stale and disables it,
runs one more inventory sync, and verifies the full shipped definition is restored while
`enabled = false` remains.

The upgrade-path test creates two existing `log_source` rows with no classification rows, then
syncs those two sources together with one genuinely new source. It pins the non-bootstrap result:
both legacy sources become `REVIEWED`, the new source becomes `NEW`, and the only inventory alert
belongs to the new source. For the required mutation check I temporarily removed the
`source.id in new_source_ids` guard from `classify_sources()`. The test failed because both legacy
sources became `NEW`; after restoring the guard, it passed.
