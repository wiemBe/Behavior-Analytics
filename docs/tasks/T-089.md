# Task T-089 — WAF incidents show percentage points 100 times too large

Read `AGENTS.md` at the repository root first and follow it exactly, §3a included. Then read
`docs/PRODUCT-UX-GUIDELINES.md` §4 (numbers and units).

## The defect (on `main`)

The WAF ratio detectors (block ratio, error ratio, and any other share detector) write
`percentage_point_change` **in percentage points**:
- `backend/app/waf/behavior.py` sets `"absolute_deviation": round(rise, 6)` (a fraction) and
  `"percentage_point_change": round(rise * 100, 2)` (points), at lines ~430 and ~574;
- so a rise from 0.10 to 0.397 is sent as `29.7`.

`frontend/src/components/waf/wafFormat.ts` `formatPoints` multiplies by 100 again, and
`WafIncidentMetrics.tsx` feeds it that field. A real WAF ratio incident therefore reads
"+2970.0 pp" in the Deviation card.

The tests never caught it because they feed `0.297`, a fraction, not what the backend sends:
- `wafFormat.test.ts` (`formatPoints(0.297)` → "+29.7 pp");
- `WafInvestigation.test.tsx` (`percentage_point_change: 0.297`).

T-087 found the same convention on the IPS side and fixed it there with its own formatter.

## Build

1. `formatPoints` takes **points**: 29.7 → "+29.7 pp", −5 → "-5.0 pp", null → the em dash. It no
   longer multiplies. Keep its name and its other behaviour.
2. Check every caller of `formatPoints`, and every reader of `percentage_point_change` and
   `absolute_deviation` in `frontend/src/`, against the backend's convention. Fix any other place
   that treats points as a fraction or a fraction as points. List them all in the report, even if
   correct.
3. Backend, **comment only**: in `backend/app/schemas/anomaly.py`, document the unit on both
   `percentage_point_change` fields (the WAF and the IPS detection projections), for example
   `#: The observed minus the expected share, in percentage points (29.7 means +29.7 pp).` No
   field, type or behaviour change.
