# Task T-052 — IPS alerting, behind `ips_alerting_enabled` (default false)

Read `AGENTS.md` at the repository root first and follow it exactly. These rules matter most here:
- rule 3: raw values stay inside the pure functions, except what the design allows as evidence;
  an alert carries the entity's **stored** identity (an admitted `IpsEntity`), never raw event
  values;
- rule 5: no secret and no exception text in an alert;
- rule 6: Phase A and WAF alerting behaviour stays exactly as it is;
- rule 8: fail closed;
- rule 9: a constant number of statements per (source, bucket), whatever the number of alerts;
- §4: never weaken a test; stop and report a conflicting test.

## Binding design

- [`docs/PHASE-D-IPS-BEHAVIOR.md`](../PHASE-D-IPS-BEHAVIOR.md) **§D.10**: alerts go through
  `AlertService` with the `ips_anomaly` fingerprint, which is fixed at creation and never changed;
  behind `ips_alerting_enabled`, **default false** (shadow mode first, as WAF did); the context
  carries `source_class` (T-023 routing), `owner`, `instance`, the entity and the measured facts.
- **Mirror WAF exactly**, reusing by import where possible: `backend/app/waf/engine.py`:
  - `_apply_transition` collects `_AlertOpenOrUpdate` and `_AlertResolve` actions **only** behind
    `waf_alerting_enabled`, and never opens or updates while the source is in maintenance;
  - `_apply_alert_actions` applies them in **one** `AlertService.apply_bulk` call, with one
    round trip for the instance name and the source class, and enqueues notifications through the
    enqueuer;
  - `_alert_input` builds the context and title; `source_class` is added only when known and is
    never part of the fingerprint.
- The fingerprint helper exists: `ips_anomaly_fingerprint` in `backend/app/alerts/fingerprint.py`
  (T-051b). Entity incidents pass `dimension` and the entity's stable `value_key`; source
  incidents pass neither. Read how T-051b defined `value_key` on `IpsEntity` and use it as stored.
- The hook point: `backend/app/ips/engine.py`, the comment "T-052 raises or resolves alerts here,
  behind ips_alerting_enabled" (and the hysteresis code that decides OPEN, RESOLVED and the
  update of an OPEN incident). Read `docs/tasks/T-051c.report.md` and `T-051d.report.md`.

## Build

1. **Setting**: `ips_alerting_enabled: bool = False` in `config.py`, with a one-line comment in the
   file's voice (shadow mode: incidents are recorded, nothing pages).
2. **Engine**: collect alert actions during the hysteresis fold exactly where WAF does (open, an
   OPEN incident that is still anomalous, resolve), behind the setting and the maintenance rule;
   apply them once per evaluated bucket in one bulk call. With the setting false, **no alert row
   is written and no statement is added** (pin both).
3. **Alert content**:
   - title: the detector and the subject in words, for example
     "IPS_PORT_RATE_SPIKE on {source}: destination port 3389". Use the entity's stored display
     value; for a source-level detector, the source only;
   - severity from the evidence; `source_type` `"ips_entity"` or `"ips_source"`; `source_id` the
     entity or source id;
   - context: `log_source`, `owner`, `criticality`, `instance`, `detector_type`, `dimension` and
     the entity's display value for entity incidents, the measured facts the evidence carries
     (observed, expected, ratio), and `source_class` when known;
   - the description is the evidence's reason text, which is already built from plain values.
     Never include an exception message.
4. **Resolve**: a RESOLVED transition resolves the alert by the same fingerprint, actor
   `"ips-anomaly-engine"`, reason "condition recovered", as WAF does.
5. **Capability and docs surfaces** that state whether IPS alerts: if
   `backend/app/anomaly/capabilities.py` or an API reports alerting per detector family, make it
   report IPS alerting from the setting. Look; if nothing reports it, change nothing there and say
   so.

## Tests

Integration (`tests/integration/test_ips_alerting.py`, new), mirroring the WAF alerting tests
(find them with `grep -l waf_alerting_enabled tests/`):
- setting false (default): an incident opens and resolves; **no alert row**; statement count equal
  to a run without alerting code paths (pin it);
- setting true: OPEN opens one alert with the fixed fingerprint; a further anomalous bucket updates
  the same alert (no second row); RESOLVED resolves it; a recurrence after resolution opens a
  **new** alert lifecycle as `AlertService` defines it (check WAF's test for the exact rule);
- maintenance: no open or update while in maintenance;
- entity vs source fingerprints differ, and two entities of one source differ;
- the context carries `source_class` when classified and omits it when not; routing by class
  matches (reuse the T-023 routing test pattern);
- notifications are enqueued once per transition (use the enqueuer test double WAF uses);
- **statement count per (source, bucket) is constant** at two numbers of alerting subjects
  (extend `tests/integration/test_ips_scale.py` or add beside it);
- no alert text contains raw event values beyond the stored entity display value (assert on the
  fields).
Break the code on purpose for at least five guards (the setting, maintenance, the fingerprint
inputs, the resolve path, the bulk call) and confirm a test fails; list them.
