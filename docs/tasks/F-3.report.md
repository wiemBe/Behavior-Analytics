## 2. What I did

The API is read-only against QRadar. Preview and the rule responses read stored aggregates. Raw paths stay inside the fold (`subject_label=""` on the preview fold). A breach history row returns the stored `subject_label`.

**Permissions.** `read:*` satisfies `read:custom_rules` and does not satisfy `custom_rule:write`. `custom_rule:write` does not imply the read. `admin:*` satisfies the write, so the admin role does not list the string. `detection_engineer` holds every analyst permission plus `search:write` and `custom_rule:write`, and holds no `admin:*`, `admin:outage`, `admin:waf`, `admin:dashboards`, `admin:users` or `admin:auth`. The router requires the read. Create, patch and delete call `_guard` after the body has parsed, so a writer still receives every domain reason. A missing token is 401 with detail `missing bearer token` (OIDC, no principal override). A principal without the read is 403 naming `read:custom_rules`. A reader who lacks the write is 403 naming `custom_rule:write`.

**Roles on the routes and on searches.** Admin and detection engineer may create, patch and delete rules and may `POST`/`PATCH /searches`. Analyst and viewer may list, read, list breaches and run both previews, and they receive 403 on rule writes and on search writes. A detection engineer receives 403 on `GET /outage-policy`; admin receives 200.

**Validation.** One call to `validate_rule_draft` with the real enabled count and `custom_rules_max_enabled`. A missing subject row is one more reason after those: `log source {id} does not exist` (log source and IPS source), `waf endpoint {id} does not exist`, or `ips entity {id} does not exist`. A null id is already a pairing reason, so it is not repeated. A retired subject is still a legal rule. If any reason is not the cap sentence, the response is 422 `{"message": "; ".join(reasons), "reasons": reasons}`, including a cap sentence when it is mixed with other reasons. If the only reason is the cap (`at most ` … `rules may be enabled at once`), the response is 409 and the detail is that sentence. A second enabled rule at `max_enabled=1` is 409; a disabled create is 201; enabling that disabled rule is 409. A value outside the `subject_kind` or `severity` enum stays FastAPI's list 422. A duplicate name is 409 `a custom rule named '{name}' already exists`, with an `IntegrityError` savepoint backstop.

**Version.** Patch requires `expected_updated_at`. A mismatch is 409 `{"message": "rule version conflict; current version is {isoformat}", "current_version", "updated_by"}`. `isoformat()` is `+00:00`. JSON responses serialize datetimes with `Z`. The test compares instants. An empty patch, including one that sends the current values, does not audit and does not move the token. A real change assigns `updated_at` in Python. If that instant is not later than the previous token, it moves by one microsecond. Create stamps `created_at` and `updated_at` in Python. Patch and delete take the row `with_for_update`.

**Delete.** `resolve_deleted_rule_alert` runs with the principal as actor and a `NotificationDispatcher` built like the beat (`notifiers={}`, `default_policy()`), then the row is deleted (breaches cascade), then `custom_rule.delete` is audited, then 204. A following GET is 404. The open alert is `RESOLVED`, `resolved_by` is the principal, and `resolution_reason` is `the rule was deleted`.

**Response.** Each rule carries `last_status`, `last_status_reason`, `last_evaluated_at`, the hysteresis counters, `active_breach`, `alerting_mode` and `threshold_unit`. `alerting_mode` is `alerting_mode(settings.custom_rules_alerting_enabled)` (`shadow` or `alerting`). It is not a column. A rule that has never been evaluated has `last_status` null. A dangling `active_breach_id` returns `active_breach` null and still 200. List is ordered by name, then id. `limit` defaults to 200 and is clamped to `api_max_page_size`. Breaches are `opened_at` descending, id ascending, default limit 50, same clamp.

**Preview.** Both previews call `replay`, which calls `fold_rule` over stored buckets. No Ariel search, nothing persisted, nothing audited, nothing alerted. `hours` is 1–168; outside that is 422. The window is every epoch-aligned bucket start in `(now - hours, latest_closed_bucket]`. One loader call covers that window. Maintenance is applied the way the engine applies it. Operational halts are not: the fold is told the platform is on, the rule is enabled, the subject is not retired, the family is collected, and `collection_stale_reason` is none, so a draft or a disabled rule still answers the historical question. `STALE` stays on the rule's `last_status`. A draft preview validates with `previously_enabled=True` and `enabled_count=0`, so it does not take an enabled slot, and it still checks that the subject exists. Each bucket has value, measurement (`EXACT`, `LOWER_BOUND` or `NOT_MEASURED`), completeness and `in_maintenance`. The body also has breach intervals, `fired_count`, measured and unmeasured counts, and the threshold with its unit and operator. Measured is `EXACT` or `LOWER_BOUND`. An absent row is `NOT_MEASURED` with null completeness, never zero.

Agreement with the evaluator, one hand-built case each, watermark seeded before the first data bucket, at most one breach outcome per tick (the engine persists `resolved` or the new breach, not both):

- `EXACT` event count, sustain 2 recovery 2: opens on the second high, resolves on the second low. Sink open/resolve and the persisted resolved row match. The high bucket is `EXACT`, value 400, completeness `COMPLETE`.
- Fleet EPS `LOWER_BOUND`: a partial fleet above a `GT` line opens; a later lower bound under the line does not resolve. A disabled sibling with a large event count does not enter the expected-source count.
- `NOT_MEASURED`: a `PARTIAL` bucket and a missing bucket pause the counters. The open is the second complete high. The resolve is the second complete under after the gap. Preview inserts no breach row.

The statement count for `hours=1` equals `hours=168`: one `log_source_metric` statement, no `INSERT`, `UPDATE` or `DELETE`.

**Audit.** `custom_rule.create`, `update`, `delete`, `enable`, `disable`, with actor and before/after snapshots (name, description, subject, metric, operator, threshold, sustain, recovery, severity, enabled). Enable and disable are used only when `enabled` is the only snapshot key that changed. Create stays `custom_rule.create` when the rule is born enabled. Previews add no audit row. UUID strings in the detail are redacted by `app/security/redaction.py`; the tests assert the non-UUID fields.

**Editing a live rule** does not reset hysteresis and does not close the open breach. That matches the task's open point.

## 4. Open points

- `updated_at` is the optimistic token. There is no integer version. Two writes in the same microsecond move the token by one microsecond.
- A 409 `current_version` is `datetime.isoformat()` (`+00:00`). A successful response's `updated_at` is JSON with `Z`. They are the same instant. Clients have to compare instants.
- Preview ignores `DISABLED`, `SUBJECT_RETIRED`, family off, platform off and `STALE`, so a draft still answers the historical question. `STALE` remains the rule's last status. Maintenance is applied.
- The engine persists only `output.resolved` or the new breach on a tick that does both. Agreement tests use one breach outcome per run. Preview's full window counts leading unmeasured slots the engine's walk does not; the tests compare intervals and the persisted row, not those totals.
- The enabled-count query is one unlocked read. Two creates can pass it together.
- Changing the subject, metric or threshold does not reset hysteresis and does not close the live breach.
- UUID subject ids inside an audit snapshot are redacted. Tests assert the other fields.
- The cap count and the subject-existence check are API concerns. `validate_rule_draft` cannot see the database.
- AUTH-1 is editing `rbac.py` and `seed.py` on another branch. The additions here are the two constants and the `detection_engineer` entry built from the analyst list. `admin` was not given a new string.
- Breach retention and an Ariel preview of a rule that has not been collected are outside this task. No UI.
