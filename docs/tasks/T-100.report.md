### 2.2 The change

`frontend/vitest.config.ts` only:

```diff

+    // Shared, loaded machine (load avg 32 on 24 CPUs): the slowest test measured 5.5 s under load.
+    testTimeout: 15000,
   },
```

15 s is ~2.7× the slowest measured test, so load spikes are absorbed while a genuinely hung test
still fails. No per-test timeout, no skip, no test file edited.

## 4. Open points

1. **Slowest tests are slow for a reason worth its own task.** Three families dominate the table and
   each renders a large list in jsdom: `PropertyInput` (500 properties, 2.3–4.8 s),
   `rules/statistics/page` (500 rows, 3.8–5.5 s), and the `ProfileEditor`/`IpsProfileEditor`
   saving-change suites (1.5–2.7 s per test, repeatedly re-rendering the whole editor). A follow-up
   could cut their fixtures or assert on a smaller slice; this task intentionally only raises the
   ceiling.
2. **`testTimeout` is a global ceiling, not isolation.** If anything ever genuinely hangs, the suite
   now takes 15 s to say so instead of 5 s. That is the intended trade for a shared machine, but it
   is worth remembering when reading a timed-out run.
3. **The suite's wall time tracks machine load, not the code.** 52 s to 97 s across three runs of an
   identical tree. Per-test durations from a single run are therefore only indicative; the ranking
   above is from one run at load ~10–23.
4. **Out of scope, noticed:** `npx vitest run` on `src/app/rules/statistics/page.test.tsx` alone
   executes 18 tests, but the file's truncation test is the only one near the limit — no other test
   in the measured run came within 2 s of the old 5 s default beyond the four named above.
