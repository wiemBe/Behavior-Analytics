## Build (§F.8.1 validation feedback, §F.8.2, the F.2 rows of §F.11)

1. **Enabled-search cap.**
   - Add a new setting, `scheduled_searches_max_enabled`, default 25.
   - `POST /searches` with `enabled=true`, or `PATCH` that enables, beyond the cap returns
     `409` with the limit named (the dashboards limit pattern).
   - Count enabled searches with one query.
2. **Cron floor.** A new or changed `schedule_cron` must fire at least 300 s apart.
   - Check it by computing successive fire times with the scheduler's `CronTrigger`
     (`app/services/search_scheduler.py`) over a bounded horizon, and say how many fires you
     check and why.
   - Refuse with `422` and a clear reason.
   - An existing cron that is not changed is **kept verbatim**, even if it would fail the floor
     (`docs/SEARCH-CADENCE.md`, "Custom").
3. **422 reasons as a list.** `AQLValidationError.reasons` is folded into one string today
   (`app/schemas/search.py`).
   - Return the reasons as a **list** in the 422 detail, plus the threshold-reachability reason
     when it applies.
   - Keep the existing string field for compatibility.
   - Document the shape in the route docstring.
   - No reason is paraphrased.
4. **Audit split.** A `PATCH` that only flips `enabled` writes `search.enable` or
   `search.disable`, with actor and before/after values. Other updates keep `search.update`, as
   today.
5. **Result retention.**
   - Add `search_result_metric_retention_days` (default 90) and the batch settings, following
     the WAF/catch-all retention pattern (`app/core/config.py`; find the existing retention
     services).
   - Add a bounded daily Celery task that deletes `search_result_metric` rows older than the
     retention by `bucket_start`, in batches.
   - Register it in the beat schedule the way the other retention tasks are.
   - The table is a Timescale hypertable. If chunk-based dropping is the project's pattern
     elsewhere, follow it and say so.

Rule 4 stands. Nothing here runs AQL that came from a request body. "Run now" stays the stored
query by id.

  irregular cron with one short gap fails; the horizon bound holds.
- Unit tests for the 422 shape: the reasons list, the string kept, and reachability.
- Integration tests:
  - the 409 cap on create and on enable;

  - the cron floor on create and on change, while an unchanged legacy cron is kept;
  - the audit actions (`search.enable`, `search.disable`, `search.update`);
