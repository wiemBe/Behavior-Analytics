## 2. What I did

The platform stays read-only against QRadar. The evaluator still reads stored buckets only. Raw paths, action values, response codes, and addresses stay inside the fold. An alert carries the seven evidence fields §F.6 names and nothing else: `observed_value`, `measurement`, `threshold`, `operator`, `first_bucket_start`, `last_bucket_start`, `unmeasured_buckets`. Context is `rule`, `subject_kind`, `subject_label`, and `metric` as one string `"metric (unit)"`. Title is `"{rule name} crossed its threshold"`. `source_type` is `custom_rule`. Severity is the rule's severity.

**Shadow mode (D-17).** `custom_rules_alerting_enabled` defaults to false. With it false the fold still writes breach rows and rule state. The engine keeps `NoOpCustomRuleAlertSink`, adds no extra resolve, flushes no alert batch, and enqueues nothing. An injected sink still receives the fold's own events, so F-1's recording-sink tests keep seeing `open` and `resolve` while the alert table stays empty. With the flag true, and no injected sink, the engine uses `AlertingCustomRuleSink`.

**The field F-3 should expose.** `alerting_mode`, values `shadow` and `alerting`, from `app.custom_rules.alerts.alerting_mode`. The constant `ALERTING_MODE_FIELD` is `"alerting_mode"`. It is computed from the platform setting, the same value for every rule. It is not a column. It is not written into `last_status_reason` (that sentence stays the evaluation honesty: `STALE`, maintenance, `DISABLED`). `EvaluationReport.as_dict()` carries the same key, so the beat payload does too. The task's early disabled return does not: that dict stays `{"status": "disabled"}`. F-3 should put `alerting_mode` on `GET /custom-rules` and `GET /custom-rules/{id}`.

**Fingerprint.** `compute_fingerprint(source_type="custom_rule", source_id=rule_id, condition="custom_rule_breach")`. The pinned value for rule `00000000-0000-0000-0000-0000000000f2` is `custom_rule_breach:b77528a0664e5d8f55bd631f47eab7df`. The same digest comes from the string and the UUID. A test holds it apart from `anomaly_fingerprint`, `inventory_fingerprint`, `catchall_sender_fingerprint`, `waf_anomaly_fingerprint`, both `ips_anomaly_fingerprint` shapes (entity and source), `search_threshold_fingerprint`, and `search_failure_fingerprint`.

**Open, refresh, resolve.** After `sustain_buckets` the sink opens through `apply_bulk` (`open_or_update`). A later breaching bucket refreshes: `occurrence_count` goes up, `transition` is none, and nothing is enqueued. After `recovery_buckets` exact unders, `resolve_by_fingerprint` runs with actor `custom-rule-evaluator` and reason `condition recovered`. A notification is enqueued only when `result.transition` is set, the same rule as `SearchAlertEvaluator._notify`. A tick that both opens and resolves goes through one `apply_bulk`: opens are applied first, then resolves, so one alert is created and resolved and both `OPENED` and `RESOLVED` are enqueued. A `LOWER_BOUND` above a `GT` line opens, and the description says `at least {value} {unit}`. A later lower bound below the line does not resolve: the measurement stays `LOWER_BOUND`. An unknown event action is dropped.

**What closes a page, and what is kept.** `extra_resolve_reason` returns none while shadow mode is on, so a page opened earlier stays open until alerting is turned back on. That includes a rule disabled during shadow. With alerting on:

| Situation | Alert | Breach row | Reason |
|---|---|---|---|
| `DISABLED` | resolved | kept | `the rule is disabled` |
| `SUBJECT_RETIRED` | resolved | kept | the fold's `status_reason` (it names the timestamp), or `the subject is retired` when that sentence is missing |
| `STALE`, `NOT_COLLECTED`, or maintenance, with a live breach | kept | kept | none. Absence is not recovery. |
| No live breach (`OK`, idle, a recovery that happened in shadow) | resolve attempt | as the fold left it | `condition recovered` |

The no-breach close is idempotent when no page is open. It is one bulk lookup per tick, so a page left open because recovery happened in shadow converges the next time alerting is on. Re-enabling a disabled rule while the breach is still open calls `open_or_update`, finds no active alert, and opens a new one. The partial unique index allows that once the previous row is `RESOLVED`. A second resolve for the same rule in one tick keeps the first reason, so `the rule is disabled` is not overwritten by `condition recovered`.

**Deleted rules.** There is no soft-delete. A log-source delete cascades the rule, and the evaluator then cannot see it. Two paths, both reason `the rule was deleted`:

- `resolve_deleted_rule_alert(session, rule_id, *, actor, enqueuer=None, clock=None)` is for F-3. The actor is the deleting principal. A blank actor raises `ValueError` before the session is used. A notification is enqueued when the transition is set. A second call finds nothing and enqueues nothing.
- Each alerting flush runs one orphan `SELECT`: active alerts with `source_type="custom_rule"` whose `source_id` is not one of the loaded rules. Those resolve with actor `custom-rule-evaluator`. An empty loaded set omits the `NOT IN` clause, so a tick with no rules still closes leftover custom-rule pages. Other source types are left alone. If F-3 already resolved the page, the sweep finds nothing. No new index: one scan a minute is the cost.

Live rules are watched before that scan, so a rule that still exists is not treated as deleted. The sink drops its buffer after compiling it, so a second flush cannot page the same transitions again.

**Maintenance.** F-1's fold already emits no open, refresh, or resolve, and it does not count the bucket as unmeasured. This task builds on that. A live breach during maintenance is not resolved. The check is the engine's live maintenance window plus the stored bucket flag `interpret` already copies.

**Retention.** `apply_custom_rule_retention` (180 days, batches of 5000, at most 20) is already in F-1, including its beat. Design §F.15 lists it under F-2; `docs/tasks/F-1.md` put §F.10 in F-1, and that is the copy that shipped. This task leaves `backend/app/custom_rules/retention.py` alone. `search_result_metric` retention is F-4.

**SQL cost.** One orphan select plus one `apply_bulk` per tick, whatever the rule count. Refreshes of already-open alerts flush as one batched update. Inserts of new alerts stay inside per-alert savepoints; that cost is the §F.4.2 exception and is outside the counted window. The pin compares a non-opening tick at 10 rules with one at 100, alerting on, and a refresh tick at the same two sizes. Both pairs have equal statement counts, one `log_source_metric` statement on the non-opening tick, and a small equal alert-statement count.

## 5. Open points

- Breach retention is F-1's. This task did not rebuild it.
- `alerting_mode` is computed. F-3 exposes that key. It is not a column, so there is nothing to migrate.
- While the flag is false, a disabled rule, a retired subject, and a recovery do not close a page. The next alerting-on tick does.
- `STALE`, `NOT_COLLECTED`, and maintenance keep a live page. A tick with no live breach still attempts `condition recovered`, which is how a shadow recovery converges.
- F-3's delete path should call `resolve_deleted_rule_alert` with the deleting principal before the row goes away. The minute sweep is the backstop and attributes the close to `custom-rule-evaluator`. A cascade from `log_source` never reaches F-3, so the sweep is what closes that page.
- New-alert inserts are per alert. The constant-count window is the non-opening tick and the refresh tick. There is no new index on `(source_type, status)`.
- No advisory lock around the tick. That is unchanged from F-1.
- No API and no UI in this task.
