# T-015 report — what the lab QRadar exposes for fleet classification and rule analytics

Measured on 2026-10-12 against the lab console. The catalog (`GET /api/help/endpoints`) tops out at
API version 29.0, so "7.6" in the task title refers to a console that serves a v29 catalog.
Everything below is measured unless marked "not measured". The lab is small and mostly stale:
51 log sources, of which only 4 delivered events in the last hour.

## Method and budget

- Provider built with `build_provider` (REST). Token and CA bundle were supplied by process
  environment on the command line only; no file was edited. The token was never printed.
- Catalog, inventory, rule and detail reads: `GET` through `provider._request("GET", ...)`.
- Ariel: only `create_ariel_search`, `get_ariel_search_status`, `get_ariel_search_results`.
  **7 of 12 searches used**, one at a time, each `LAST 60 MINUTES` and `LIMIT 200`. Search
  handles were not cancelled or deleted (that would be a `DELETE`).
- **Side effect to disclose.** `GET /analytics/rules/{id}/dependents` is a `GET` that starts a
  server-side task (response: a task object, `status: PROCESSING`, `name: "Finding dependents."`).
  I called it once for one rule (id 100003) while looking for rule logic. It changes no
  configuration, but it is not a pure read. Phase E must not call it.
- The provider sanitizes upstream error text by design (`_sanitize_upstream_error`, and the Ariel
  status DTO replaces error messages with a fixed string). Every search I ran was accepted, so no
  rejection text exists to report. If a later probe needs the real rejection text, the provider
  hides it.

## 6. EPS

- `average_eps` is present on every row, an integer. The API help says it is "the average events
  per second (EPS) rate of the log source over the last 60 seconds". It is therefore a 60-second
  figure, not an hourly mean.
- **AQL 3 (accepted, 1.1 s, 4 rows):**
  `SELECT logsourceid, LOGSOURCENAME(logsourceid) AS lsname, COUNT(*) AS c, SUM(eventcount) AS ec FROM events GROUP BY logsourceid ORDER BY ec DESC LIMIT 200 LAST 60 MINUTES`
- Only 4 sources had events. Comparison (hourly mean = `ec / 3600`; `average_eps` read from
  REST at four moments within about 12 minutes of the search):

| id | name | `ec` (1 h) | `ec/3600` | `average_eps` (4 reads) |
|---|---|---|---|---|
| 69 | Health Metrics-2 | 44,037 | 12.2 | 35, 102, 113, 111 |
| 65 | System Notification-2 | 7,307 | 2.03 | 2, 2, 2, 2 |
| 64 | SIM Audit-2 | 1,421 | 0.39 | 0, 1, 0, 0 |
| 67 | Asset Profiler-2 | 13 | 0.004 | 0, 0, 0, 0 |

- `average_eps` agrees with the hourly mean only for a steady source (id 65). For the bursty
  Health Metrics source it varied 35 to 113 against an hourly mean of 12.2. Small sources round
  to 0. It cannot stand in for volume: use AQL `SUM(eventcount)` over a window for that. Three
  sources were requested; I compared four because the search returned four.
- All 47 sources that sent no events in the hour show `average_eps = 0`, which is consistent
  but cannot tell "silent" from "not reporting" (use `last_event_time` for that).

## 11. Firing counts

`creEventList` is an event property that holds the ids of the rules and building blocks that an
event matched. All four attempts below were accepted; all four were `LAST 60 MINUTES`,
`LIMIT 200`. Six was the cap for this question; four were enough.

Total events in the hour (from question 6): 44,037 + 7,307 + 1,421 + 13 = 52,778.

**Attempt 1 (accepted, 1.1 s, 11 rows)**
`SELECT creEventList, COUNT(*) AS c FROM events GROUP BY creEventList ORDER BY c DESC LIMIT 200 LAST 60 MINUTES`
- Output: one row per rule id, `creEventList` as a bare integer id (not a name, not a list). The
  counts sum to 315,994, six times the 52,778 events. **So an event that matches several rules
  is counted once per rule** (the list is expanded to one row per entry).
- Joined against the REST lists by id: all 11 ids resolve. 6 are rules (for example 100221
  "Destination Asset Weight is Low", 100272 "Load Basic Building Blocks", 100216 "Context is
  Local to Remote"), 3 are building blocks (100277, 100101, 100352), and 100271 "System:
  Notification" is a rule. **Building blocks appear among the rules.** Ids alone do not tell
  which list they came from, but rule and building-block ids do not collide in the lab
  (rules list and BB list are disjoint here).

**Attempt 2 (accepted, 1.1 s, 11 rows)**
`SELECT RULENAME(creEventList) AS rule, COUNT(*) AS c FROM events GROUP BY creEventList ORDER BY c DESC LIMIT 200 LAST 60 MINUTES`
- Same 11 rows and counts. `RULENAME()` returned the literal string `"null"` for 6 of 11 ids,
  including ones that exist in the REST rule list (100216 "Context is Local to Remote",
  100223, 100217, 100215) and both building blocks 100277 and 100101, while it resolved
  100352 (a BB) and 100271. So `RULENAME` is **not reliable**; join by id against
  `/analytics/rules` and `/analytics/building_blocks`.

**Attempt 3 (accepted, 2.1 s, 6 rows)**
`SELECT RULENAME(creEventList) AS rule, COUNT(*) AS c FROM events GROUP BY RULENAME(creEventList) ORDER BY c DESC LIMIT 200 LAST 60 MINUTES`
- Grouping on the function collapses the unresolved ids into one `"null"` row of 52,778 (equal
  to the event total, not to the sum of the 6 unresolved ids), so it merges information and
  loses per-rule counts. Do not group on `RULENAME(...)`.

**Attempt 4 (accepted, 1.1 s, 27 rows)**
`SELECT creEventList, logsourceid, COUNT(*) AS c FROM events GROUP BY creEventList, logsourceid ORDER BY c DESC LIMIT 200 LAST 60 MINUTES`
- Two-key grouping works: counts per (rule id, log source id). Example: every event from
  Health Metrics (id 69, 44,037 events) matches the same 6 ids, each with c = 44,037. This gives
  per-rule, per-source firing at one bounded query cost, within the 200-row limit (27 rows here).

Summary of what was measured:

- Counts are matches of an event against a rule or building block, not offenses or alerts.
  Most matches here are the always-on system building blocks, and none of the 7 user rules
  matched in this hour.
- The 60-minute window in a lab with 4 live sources produced 11 distinct ids, so the 200-row cap
  was never tested. With hundreds of active rules and many log sources the cap will truncate;
  a truncated result must be treated as incomplete.
- Not measured: `creEventList` on a busy console, `LAST` windows shorter than 60 minutes, and
  whether an event that matches the same rule twice is counted twice.

## Design implications

1. Phase C.1 can rely on `log_sources` (51 rows, all 31 keys on every row), `log_source_types`
   (419 rows) and the group list. They are plain `GET`s that fit in one page at lab scale
   (still paginate with `Range` in code).
2. The type table has no category or vendor field. Classification into WAF, IPS, Linux and so on
   must come from a platform-owned mapping of `type_id`/type name to class, not from QRadar.
3. Log-source names are not a reliable class key: hostnames drive them (11 IPS-typed rows are
   named after hosts, 7 FirePass rows are named `*-waf-*`). A name regex hit 33/51; use it only
   as a fallback or hint, and keep a manual override.
4. Log-source groups carry nothing in this lab: every source is in group 0 under one
   non-assignable parent. Phase C.1 must not depend on `group_ids` for classification, and a
   tree walk must handle the `0` id/`parent_id` ambiguity.
5. Internal QRadar sources (`internal: true` on the type, or the `<Type>-<n> :: <host>` name) are
   seven rows of the fleet. They need their own bucket so they never count as devices.
6. Use `last_event_time` (epoch ms, `0` = never) for freshness. `status.status` is `ERROR` for 42
   of 51 sources in the lab because of the 720 minute rule, so it is a coarse input. `status`
   is an object, not a string.
7. `average_eps` is a rounded 60-second value (0 for 47 sources, 35 to 113 for a bursty one). It
   must not be used for volume. Use bounded AQL `SUM(eventcount)` per source.
8. SIM Generic and Universal DSM types are catch-alls (ids 67, 39, 212, 367, 4000). Only the
   SIM Generic source was found, and it is QRadar-internal. Sender identification for these
   types is not measured (the SIM Generic source was silent), so Phase C.1 cannot assume a
   per-sender breakdown for catch-alls. User-created Universal sources carry the sender in
   `log_source_identifiers`.
9. Phase E cannot read rule logic, tests or XML from QRadar: no `GET` returns them. Anything
   that needs rule semantics must come from the platform's own metadata.
10. There is no rule-statistics endpoint. `rules_offense_contributions` and
    `health_data/top_rules` describe offenses, not matches; they undercount silent rules.
11. `average_capacity` and friends are static benchmark figures in "EPS" (millions here). They
    did not change in 11 minutes and carry a two-day-old timestamp. They are not a firing rate
    and must not be shown as one. Zero means "no benchmark" (all disabled rules, 8 enabled
    rules, 54 BBs).
12. Per-rule firing counts come from `GROUP BY creEventList` over `events`. It is accepted,
    about 1 to 2 s for 60 minutes in the lab, and an event is counted once per rule it
    matches. Building blocks and rules share one id space in the output, so join the ids to
    both REST lists.
13. Do not use `RULENAME(creEventList)`: it returned `"null"` for 6 of 11 ids, and grouping on
    it merges them. Resolve names by id from the REST rule and building-block lists.
14. The `creEventList` query is one more Ariel search per window; it fits the "constant SQL cost"
    rule only if the platform runs it once per window for all rules, grouped by rule id (and
    optionally `logsourceid`), never once per rule. Cap rows at 200 and treat a full page as
    truncated.
15. Do not call `/analytics/rules/{id}/dependents` (or any `*_tasks` endpoint): it is a `GET` with a
    server-side task as a side effect. Treat any `GET` outside the lists above as unaudited until
    checked.
