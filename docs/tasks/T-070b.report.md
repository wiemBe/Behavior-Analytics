## 2. What I did

- Queue first: API order is kept (no client sort). Columns: Sender (monospace, wraps, full value in `title`), Catch-all source, Seen (UTC; first and last in one column), 24 h events (right-aligned, tabular; `unknown` for null, lower-bound note in tooltip and under the table), Review (status pill plus who and when UTC), Actions. First and last seen share one column, and status and reviewer share one, so that six columns fit 1024 px with no local scroller.
- Filters: status (default New, shows "New (n)" from the sources endpoint), source, search `q` (300 ms debounce), "Reload list", "Show more senders" (offset paging). Rows stay in place after an action; they leave the list on reload.
- Actions: pessimistic (no optimistic UI): "Saving…", one request per click (ref guard plus disabled), the API's row replaces the old one. A failure leaves the row as it was and says "Not changed. <reason>". After a 403 all actions are disabled with the reason on `title`, `aria-describedby` and a visible note naming `log_source:write`.
- One sentence says what a sender is (page description). Times are UTC with the zone.
- Volume by source: source and range (6 h, 24 h, 7 d, never above the API's 7 days). Bars per bucket on a category axis ("Bucket start (UTC)", y title `Events (events / 5 min)` from `bucket_seconds`), distinct senders as a plain line on a right axis, not joined across gaps. A bucket with no row is a null (no bar) and runs before the latest measured bucket are shaded "Not measured". Nothing after the latest measured bucket is drawn or shaded: the text says "Collected up to <time> UTC" and the selected-bucket panel says "not collected yet". LOWER_BOUND buckets take the warn fill and are "at least" in legend, tooltip and panel. A key lists only marks that are drawn.
- Selected bucket: by click, or by "Earlier / Later measured bucket" buttons (keyboard route). Panel shows measurement, events, records, distinct senders, the admission counts in words, the "refused senders are never stored by name" note and up to 20 top senders. Selecting a gap says it was not measured, with no figures.
- Honest text alternative: named `img` plus an `sr-only` summary.
- States designed and tested: loading, error with retry, empty (never collected vs queue clear vs filtered vs none in status), no catch-all source (lists `catchall_type_ids` from the API), 403 read, not-measured gaps, LOWER_BOUND, unknown events, action in flight, action failure, action without permission.

## 5. Open points and contract questions

1. **No way to know write permission up front.** There is no principal or permissions endpoint, so Review and Dismiss are enabled until the first 403, then all are disabled with the reason. Spec asks for disabled-with-reason without permission; a `GET /me` (or a `can_write` flag on the senders page) would make it exact.
2. **No per-status counts.** The senders page gives only `total` for the current filter. The "New (n)" figure is the sum of `new_sender_count` from the new sources endpoint; Reviewed and Dismissed have no count.
3. **Bucket grid is inferred.** `/buckets` returns rows only, so the grid is anchored on the first returned row's `bucket_start` and `bucket_seconds`. With no row in the range the width is unknown and no gap can be drawn (the page says so).
4. A `LOWER_BOUND` bucket's `events` is stored as a lower bound, so it is labelled "at least"; its `distinct_senders` is flagged only if `distinct_senders_lower_bound` is true.
5. `FAILED` and `NOT_COLLECTED` rows are treated as not measured (a gap), though the collector never writes them.
6. Leading buckets of a range that start before the first measured bucket count as gaps, per the spec's rule. A 7-day view of a source with 3 days of data therefore shades 4 days as "not measured".
7. The queue shows the API's first 50 (and "Show more" pages by offset); there is no total-page control. `api.ts` was touched only by the allowed block.
8. Existing test conflicts: none.
