# T-032 report: one Ariel search per cadence tick, many buckets per search

Measured on 2026-10-12 (about 15:00 to 16:30 UTC) against the lab console, with the REST provider
(`build_provider`) and its three Ariel methods only. Token and CA bundle came from the process
environment on the command line; nothing secret was printed or written. Scripts are in the
scratchpad `t032/`. No banned endpoint was called, no search was cancelled or deleted, and no
repository file other than this report changed. One `GET` read of the log-source inventory
(`list_log_sources`) located the WAF source.

**Budget: 12 of 12 searches used.** Searches 3, 7 and 11 were rejected at create (HTTP-level
"invalid"; the provider hides the reason). Search 11 was a mistake of mine: a script edit did not
apply, so it re-sent the rejected search 7 unchanged. Both count against the budget.

**Lab state that limits what can be said.** Only four sources delivered events in the 8-hour
window: SIM Audit (64), System Notification (65), Health Metrics (69) and Asset Profiler (67, 4
buckets only). Every WAF and IPS source is stale (`lab-waf-behavior-01`, id 312, status ERROR), so
questions 5 to 7 use internal sources as stand-ins, and say so. Console history in the 8-hour
window covers only about 5 hours (60 five-minute buckets per active source; data starts near
10:25 UTC).

## Q1. A timezone-free 5-minute bucket key

Accepted: **`starttime / 300000`**, in `SELECT` and in `GROUP BY`, with `logsourceid`,
`SUM(eventcount)` and `MAX(starttime)`; `ORDER BY "k"` on the alias also works.
Rejected: **`FLOOR(starttime / 300000)`** (search 3; the same query with `FLOOR` removed was
accepted, so `FLOOR` is the cause). No other integer form was tried (budget).

```sql
SELECT logsourceid AS "id", starttime/300000 AS "k", SUM(eventcount) AS "ec", MAX(starttime) AS "mx"
FROM events WHERE starttime >= 1791813600000 AND starttime < 1791817200000
GROUP BY logsourceid, starttime/300000 ORDER BY "k" LIMIT 5000
START 1791813600000 STOP 1791817200000
```

The division is **integer** (the value is truncated, not rounded): the raw rows were

```
{'id': 64, 'k': 5972712, 'ec': 62.0,    'mx': 1791813891154.0}
{'id': 65, 'k': 5972712, 'ec': 565.0,   'mx': 1791813896611.0}
{'id': 69, 'k': 5972712, 'ec': 33263.0, 'mx': 1791813895447.0}
{'id': 64, 'k': 5972713, 'ec': 60.0,    'mx': 1791814199408.0}
```

`k` comes back as a JSON integer; `1791813891154 / 300000 = 5972712.97`, shown as 5972712.
`5972712 * 300000 = 1791813600000`, exactly the window start. `ec` and `mx` come back as floats
(`62.0`, `1791813891154.0`); the existing `as_int` / `parse_qradar_time` handling already copes.
The bucket start is `k * 300000` ms (epoch UTC), with no timezone involved.

## Q2. The `DATEFORMAT` fallback

Accepted: `DATEFORMAT(starttime, 'yyyy-MM-dd HH:mm')` in `SELECT` and `GROUP BY` (search 2, 181
rows against 37 for the 5-minute key; one row per source per minute because Health Metrics emits
one record per minute).

```sql
SELECT logsourceid AS "id", DATEFORMAT(starttime, 'yyyy-MM-dd HH:mm') AS "d",
       SUM(eventcount) AS "ec", MAX(starttime) AS "mx" FROM events
WHERE starttime >= 1791813600000 AND starttime < 1791817200000
GROUP BY logsourceid, DATEFORMAT(starttime, 'yyyy-MM-dd HH:mm') LIMIT 5000
START 1791813600000 STOP 1791817200000
```

Proof against known epochs, from the same rows:

| `mx` epoch (ms) | `mx` in UTC | `d` returned |
|---:|---|---|
| 1791817195904 | 2026-10-12 14:59:55.904 | `2026-10-12 14:59` |
| 1791813655156 | 2026-10-12 14:00:55.156 | `2026-10-12 14:00` |
| 1791813644942 | 2026-10-12 14:00:44.944 | `2026-10-12 14:00` |

So **this console renders `DATEFORMAT` in UTC.** What this cannot show is *whose* timezone it is:
the console's, the API user's, or a UTC default. The lab console and its user both appear to be
UTC, so the test cannot tell them apart (the client host is UTC+03 and is clearly not the source).
I did not read the console timezone from configuration. The risk is therefore real but untested:
if `DATEFORMAT` follows a non-UTC console or user timezone, the string repeats for one hour at the
autumn DST change (two distinct instants map to the same `HH:mm`, so two distinct buckets would
merge in `GROUP BY`) and skips an hour in spring. The string also needs parsing with a known
zone. It is not a safe key. Use the integer key.

## Q3. Equivalence of one multi-bucket search and the per-bucket query

Best form: `starttime / 300000`. Search 1 (closed 1-hour window 14:00 to 15:00) against search 4
(bucket 5972712, `[14:00:00, 14:05:00)`) and search 5 (bucket 5972718, `[14:30:00, 14:35:00)`),
the latter being the exact `get_log_source_metrics` AQL with `START/STOP` equal to the bounds:

| bucket | source | per-bucket `SUM(eventcount)` | multi-bucket | per-bucket `MAX(starttime)` | multi-bucket |
|--:|--:|--:|--:|--:|--:|
| 5972712 | 64 | 62 | 62 | 1791813891154 | 1791813891154 |
| 5972712 | 65 | 565 | 565 | 1791813896611 | 1791813896611 |
| 5972712 | 69 | 33263 | 33263 | 1791813895447 | 1791813895447 |
| 5972718 | 64 | 54 | 54 | 1791815676564 | 1791815676564 |
| 5972718 | 65 | 548 | 548 | 1791815696674 | 1791815696674 |
| 5972718 | 69 | 33230 | 33230 | 1791815695865 | 1791815695865 |

All 12 comparisons are equal (`SUM` and `MAX`). The 3 sources per bucket match one for one.

Edge behaviour: `k = starttime / 300000` for a positive integer `starttime` is
`floor(starttime / 300000)`, so `k = n` holds exactly for `n*300000 <= starttime < (n+1)*300000`,
the same half-open interval as `starttime >= a AND starttime < b`. An event at exactly
`(n+1)*300000` lands in bucket `n+1` in both forms. I could not test it on a real event: no
record in these windows sits on a bucket edge (sub-second timestamps), so the edge claim rests on
the integer division result above (`k * 300000` equals the window start) and not on an observed
edge event. The multi-bucket search must keep the explicit `WHERE starttime >= a AND starttime < b`
for the whole window as well as `START/STOP`, as today.

## Q4. Cost and shape of the multi-bucket Phase A search

| | 1 hour (search 1) | 8 hours (search 6) |
|---|--:|--:|
| rows | 37 (3 sources x 12 buckets, plus source 67) | 184 (60 buckets x 3 sources, plus 4 for source 67) |
| time to `COMPLETED` | 0.37 s | 0.61 s |
| status `record_count` | 37 | 184 |
| status `data_file_count` | 120 | 590 |
| `processed_record_count` | 406,336 | 1,976,366 |
| `query_execution_time` | 152 ms | 523 ms |
| results payload (compact JSON) | 2,009 B | 9,995 B |

About 54 bytes per row. The 8-hour window held only about 5 hours of console history (60
buckets), so the full 96 buckets per source are extrapolated, not measured. `data_file_count`
scales roughly with the window (120 files per hour). With 4 active sources the 8-hour search would
return `4 x 96 = 384` rows; the lab never produced more than 184. The 5,000-row cap holds for up to
`5000 / 96 = 52` sources reporting in every bucket. The inventory has 51 log sources, so a fully
active fleet would sit just under the cap; the margin is thin and must be checked per run.

Paging: **not needed at these sizes.** The provider does not page Ariel results. It sends one
request with `Range: items=0-{max_rows-1}` (`get_ariel_search_results`), where
`max_rows = page_size * max_pages = 500 * 200 = 100,000` in `get_log_source_metrics`; all 184 rows
came back in that one request (my probe used `max_rows=5000`). The `_paginate` helper, which walks
`Range: items=start-end` in 500-row pages, is used only for list endpoints. I did not test whether
the console honours a Range above 5000. Note for the design: `truncated=len(rows) > max_rows` in
`get_ariel_search_results` can never be true, because the Range already limits the response to
`max_rows`. Truncation has to be detected by the caller: `row_count == LIMIT`, or the status
`record_count` reaching the `LIMIT`. The status DTO carries `record_count` but not
`data_file_count`; I read the raw status through `_request` for the table above.

## Q5. `LIMIT` across buckets

Stand-in: the WAF source is stale, so search 8 and 9 use sources 64, 65 and 69 with an
endpoint-style, multi-key grouping (`QIDNAME(qid)`, `category`) plus the time key, 1 hour:

```sql
SELECT QIDNAME(qid) AS "raw_url", category AS "raw_method", starttime/300000 AS "k",
       SUM(eventcount) AS "request_count", COUNT(*) AS "record_count",
       UNIQUECOUNT(sourceip) AS "dc"
FROM events WHERE logsourceid IN (64, 65, 69)
AND starttime >= 1791813600000 AND starttime < 1791817200000
GROUP BY qid, category, starttime/300000 ORDER BY SUM(eventcount) DESC LIMIT 5000
START 1791813600000 STOP 1791817200000
```

- `LIMIT 5000` returned **56 rows** (12 buckets, 4 to 7 groups per bucket, 6,242 B). Status
  `record_count` 56.
- The same search with **`LIMIT 10`** returned exactly 10 rows. Per bucket, one row in each of 10
  buckets; buckets 5972719 and 5972721 got **none**. So `LIMIT` caps the **whole** result, not each
  bucket, and `ORDER BY SUM(eventcount) DESC` competes across buckets: a quiet bucket's groups are
  dropped first. Under a `LIMIT` that bites, some buckets can be missing entirely, and a missing
  bucket looks the same as an empty one.
- **Per-bucket top-N: I found no Ariel form for it.** I tested none (the search budget was spent
  on measuring), and I read no documentation. Treat it as unavailable. The only safe patterns are
  (a) `LIMIT` high enough that it cannot bite, then take top-N per bucket in the fold function, or
  (b) a `LIMIT` and treating `row_count == LIMIT` as truncation of every bucket in the window.
- Row-count estimate for a real endpoint search: groups per bucket x buckets. At 4 to 7 groups per
  bucket here it is 56 rows per hour. A real WAF source with `max_groups = 500` per bucket
  (today's default) would need `500 x 12 = 6,000` rows per hour, **over the 5,000 limit** for a
  single 1-hour search. Not measured on WAF data; this is arithmetic on the configured cap.

## Q6. `creEventList` by bucket

Accepted (search 10, 1-hour window, 104 rows, 0.32 s, 5,209 B):

```sql
SELECT creEventList AS "cre", starttime/300000 AS "k", SUM(eventcount) AS "ec", COUNT(*) AS "n"
FROM events WHERE starttime >= 1791813600000 AND starttime < 1791817200000
GROUP BY creEventList, starttime/300000 ORDER BY SUM(eventcount) DESC LIMIT 5000
START 1791813600000 STOP 1791817200000
```

Rows per bucket: 8 to 10 (12 buckets). `cre` comes back as a single integer rule id per row (for
example `100272`, `100227`, `100221`), and several rule ids carried the same `ec` in one bucket
(34,014 for three of them). That suggests the list is split so an event counts once under each
rule it matched, but I did not verify it (one search). **Do not sum `ec` across `cre` rows for a
total volume**, since one event may appear under several rule ids. 104 rows per hour is small;
at 8 hours it is about 800.

## Q7. Late events

Measured on the internal sources only (every external source is stale). Searches 6 and 12:

- **Lag of `MAX(starttime)` behind the clock.** Search 6's window ended at 15:25:00 UTC and it was
  fetched 171 s later. In each active source's last bucket, `MAX(starttime)` was **3.2 s (source
  65), 4.1 s (69) and 7.1 s (64) before the window end**, and sources 64, 65 and 69 had a record in
  every one of the 60 buckets they covered. So when the search ran 171 s after the edge, no record
  was missing near the edge. Source 67 (Asset Profiler) is sporadic: 4 buckets in 8 hours, last
  event 2,280 s before the window end.
- **Wall-clock lag.** In search 12 the last `MAX(starttime)` was 233 s (65), 234 s (69) and 237 s
  (64) behind the wall clock at the moment the script ran, about 233 s after its window end. That
  is consistent with "no data after the window end was requested", not with ingest lag.
- **`devicetime` against `starttime`** (search 12, per source per bucket, seconds):
  `MAX(devicetime) - MAX(starttime)` was -1.0 to -0.3 (65), -1.9 to -0.2 (64), -1.1 to -0.1
  (69); the device clock sits **0.1 to 1.9 s behind** `starttime`, never ahead.
  `MAX(starttime) - MIN(devicetime)` was 192.9 to 348.3 s (65), 179.7 to 326.5 (64) and 160.2 to
  296.1 (69). A value above 300 s means some event in the bucket has a `devicetime` before the
  bucket start: the largest was 348.3 s, i.e. **up to about 48 s before the bucket** for those
  internal sources.
- **Not measurable:** how long after a bucket closes events can still be stored. `storagetime`
  was needed for that, and Ariel rejected it (searches 7 and 11, same query; the reason is hidden,
  and I did not isolate whether `storagetime` or `MIN` caused it). The 5-minute buckets here use
  `starttime`, which for these internal sources tracks the device clock to under 2 s, so they show
  no reordering. A remote or batch-forwarded source (a WAF behind a forwarder, an IPS with a clock
  skew or a queue) can deliver events with an old `starttime`; this lab has none to test.

## Design implications for search cadence

1. **Bucket key: `starttime / 300000`** (integer division, accepted, searches 1 and 6 to 12). It is
   the bucket index in epoch UTC, equal to `starttime >= a AND starttime < b` bucketing (12 of 12
   comparisons match), with no timezone. Do not use `FLOOR` (rejected) and do not use
   `DATEFORMAT` (UTC here, but console/user-timezone dependence and DST merging are unproven
   against).
2. **Phase A: one search per tick is safe.** An 8-hour, 5-minute-keyed search cost 0.61 s, 184
   rows and 10 KB with 4 active sources; the 8-hour search for all 51 sources would be near
   `51 x 96 = 4,896` rows, just under the 5,000 cap. Keep the existing `WHERE` bounds plus
   `START/STOP`, and add `ORDER BY` only if the fold needs it.
3. **A bucket with no row is "no events", not zero, and not necessarily silence.** Source 67 had 4
   of 96 buckets. Phase A must tell "source silent" (stale `last_event_time`, already tracked)
   from "no record in this bucket"; a missing bucket row for a source that is otherwise live is the
   zero-volume reading the existing per-bucket query also produced.
4. **Truncation per bucket, fail closed.** `LIMIT` caps the whole result and drops the smallest
   groups across all buckets (search 9: two of twelve buckets lost every row). Since no per-bucket
   top-N exists, a search with `row_count == LIMIT` (or status `record_count` at the `LIMIT`) must
   mark **every bucket in the window** `INSUFFICIENT_DATA` for that search, never keep the
   buckets that happen to look complete. `get_ariel_search_results.truncated` is always false (the
   Range caps rows first), so detect truncation from the row count against the `LIMIT` sent.
5. **WAF: one search per tick only with a raised cap.** Today's `max_groups = 500` per bucket
   times 12 buckets per hour is 6,000 rows, over the 5,000 `LIMIT` (and per-bucket top-N does not
   exist). At an 8-hour cadence it is `500 x 96 = 48,000`. Either keep WAF per-bucket searches, or
   do one search per tick with the `LIMIT` chosen so it cannot bite and top-N cut in the fold, or
   one search per sub-window sized to `max_groups x buckets <= 5000`. WAF volumes were not
   measured (source stale), so no WAF row count is claimed.
6. **Rule matches (`creEventList`):** the grouping works and is small (8 to 10 rows per bucket,
   104 per hour). One search per tick is safe on rows. A single event may appear under several
   rule ids, so totals must not be summed across rule ids.
7. **Row bound at an 8-hour cadence:** 96 buckets x active sources, capped at 5,000 (fits up to 52
   sources for Phase A at one row each). Time scales sub-linearly in this lab (0.37 s for 1 h,
   0.61 s for the 8-hour window with 5 hours of data); the full 8 hours was not measured. A
   larger fleet or a wider key (WAF, rule matches) hits the row cap before the time.
8. **No paging at these sizes.** One `Range: items=0-{n-1}` response held 184 rows. Do not add
   paging for Phase A; keep the provider's single-range read, and fail closed when the row count
   reaches the `LIMIT`. A Range above 5,000 was not tested.
9. **Settle delay before a bucket counts as complete:** the lab shows events from internal
   sources present within seconds of the window end (3 to 7 s before the edge, search fetched 171
   s later), and `devicetime` within 2 s of `starttime`. That supports a settle delay on the order
   of the current practice (a few minutes), but **this is a lower bound from internal sources
   only**: `storagetime` could not be queried and no forwarded or batched source was live. Make
   the settle delay a configurable setting and default it to at least one `source_delay` value
   from the fleet (the platform already tracks `event_delay_seconds`); do not hard-code a number
   from these measurements.
10. **Equal key across detectors and migrations:** persist the bucket start as
    `k * 300000 ms` UTC, derived from the integer key, so a search of any width produces
    bucket-aligned rows that match the per-bucket collector row for row.
11. **Keep `SUM(eventcount)`, `MAX(starttime)` and the half-open `WHERE`.** They were proven
    identical to the per-bucket query for every compared row.
12. **Open items for the next round of live work:** (a) a Range above 5,000; (b) a live
    forwarded/WAF source to measure real group counts and late arrival; (c) whether `storagetime`
    is queryable on its own (searches 7 and 11 failed together); (d) the console timezone setting,
    if `DATEFORMAT` is ever considered.
