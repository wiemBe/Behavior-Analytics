## How the override was checked (what the task asked to say)

Both, as offered by the task: (a) the local `docker buildx build --label …` + `docker image
inspect` above, which shows `maintainer` no longer the IBM value in the built image; and (b)
the mechanism: the workflow's `labels:` input on `docker/build-push-action@v7.4.0` is forwarded
to buildkit's image export as build-time OCI labels, applied at image-config generation after
the Dockerfile's own `LABEL`s of the same key, so the build-time value replaces the
Dockerfile's, while labels the Dockerfile alone sets (IBM's `description`) survive — which is
why `description` is deliberately overridden too.

## Round 1 (review defect, 2026-10-18)

**What was wrong.** In `.github/workflows/release.yml`, the `Labels` step wrote the maintainer
override under the key `org.opencontainers.image.maintainer=...`, but the spec (item 4) asks for
the key `maintainer=...`. Docker labels are a flat map, so those are two different keys: the fix
as written would have *added* `org.opencontainers.image.maintainer` to the qradar-mcp image
instead of overriding the Dockerfile's label, leaving IBM's `LABEL maintainer="IBM QRadar
Investigation Assistant Team"` (`qradar-mcp/Dockerfile`, key `maintainer`) intact on the
published image — the exact outcome the override exists to prevent. The round 0 local check
passed because it used the correct key (`docker buildx build --label maintainer=...`), so the
defect existed only in the workflow file.

and the comment above it was corrected to describe the actual mechanism — the step writes

and a `--label` value wins over the image's own `LABEL` of the same key. Nothing else changed in
