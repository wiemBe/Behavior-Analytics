## Build (§C.5)

1. **Permissions** (`app/security/rbac.py`, following T-031's comments and pattern):
   `PERM_FLEET_READ = "read:fleet"` (satisfied by `read:*`) guards a new `/fleet` router at the
   router level (`app/api/router.py`, like the others), and `PERM_CLASSIFICATION_ADMIN =
   "admin:classification"` for classification-rule writes. The override and review endpoints use the
   existing `log_source:write` (handler-level check first, 403 before 404, as
   `update_log_source` does). Seed: admin gets `admin:classification`; no other role changes.
2. **`GET /api/v1/fleet/summary?window=1h|24h|7d`** exactly as §C.5: per class — source counts
   (enabled / disabled / internal), events and mean EPS over the window from `log_source_metric`,
   expected EPS from reliable baselines with the share of sources that have one, open Phase A
   incidents by type, the top 5 sources by events; plus NEW, conflict and UNCLASSIFIED counts.
   - **Completeness is reported, never hidden:** per class, the expected and present bucket counts.
     Missing buckets are not zeros; a class with no complete measurement reports `null` events and
     EPS, not `0`.
   - **Constant SQL:** a fixed number of grouped queries regardless of the number of sources or
     classes. Pin it with a statement-count test at two fleet sizes (e.g. 10 and 400 sources).
3. **`GET /api/v1/fleet/sources`** with filters `class`, `review_status`, `has_conflict`, `basis`,
   paginated like the existing list routes; returns the classification fields (class, basis, rule
   id, override, conflicts, review status and times, `first_seen_at`, `auto_discovered`).
4. **`PATCH /api/v1/log-sources/{id}/classification`**: set or clear (`null`) the override class;
   audited with `{from, to}`; re-classifies **that source** through `classify()`; returns the new
   classification.
5. **`POST /api/v1/log-sources/{id}/review`**: mark reviewed (`reviewed_at`, `reviewed_by`),
   audited, and **resolves the source's new-source alert** through `AlertService` (the T-016
   path). Idempotent. Classifying never resolves it (§C.4).
6. **`GET/POST/PATCH/DELETE /api/v1/classification-rules`**: list (read:fleet); create, update,
   delete (admin:classification). Built-in rules: only `enabled` may change; any other change or a
   DELETE → 409. Patterns ≤ 256 characters, compiled at save (`re.compile`), invalid → 422; the
   `(instance_id, kind, pattern)` uniqueness → 409. Every change audited and **re-classifies the
   affected instance** (all instances for a global rule) in bulk, with constant SQL.
7. **Routing by class:** `app/alerts/routing.py::RoutingRule` gains
   `source_classes: frozenset[str] | None = None`, matched against `alert.context["source_class"]`
   (None = match any; a rule with classes never matches an alert without one). Phase A anomaly
   alerts and inventory (new-source) alerts carry `source_class` in their context. Find where their
   contexts are built; add the key without changing any fingerprint (fingerprints are persisted).

## Tests

- Every route: 401, 403 (`read:*` on writes; a principal without `read:fleet` on reads), 404, 422,
  409 as above; success bodies.
- Summary: completeness with missing buckets (null, not zero); a class with sources but no
  metrics; internal sources counted apart; the statement-count test at two sizes.
- Override: set, clear, re-classification result, audit.
- Review: resolves exactly the new-source alert of that source; a second call changes nothing.
- Rules: built-in edit refused except `enabled`; invalid regex 422; duplicate 409; a rule change
  re-classifies (a source's class changes after a new NAME_REGEX rule).
- Routing: a `source_classes` rule matches only alerts of those classes; an alert without
  `source_class` matches only rules without the condition; existing routing tests unchanged.
- Fingerprints unchanged: an existing test or a new one proving the anomaly alert fingerprint is
  identical before and after the context change.

and confirm tests fail; restore.
