### The state-file question (Upgrade bullet)

`upgrade` reads `.qradar-dash/state.json` first and refuses without it
(`qradar-dash:2039-2042`). A 0.1.0 install whose QRadar check failed never wrote that file: in the
`v0.1.0` tag, `cmd_install` runs `write_install_state` only inside `if [ "$qr_rc" -eq 0 ]`
(`v0.1.0:774-777`); T-127 (for 0.1.1) is what makes it unconditional. OPS-10 hit exactly this
("DEFECT D2", `docs/tasks/OPS-10.report.md` §Part B) and used an **undocumented** workaround,
`QRADAR_DASH_SOURCE_ONLY=1 bash -c 'source ./qradar-dash; write_install_state'`, which is not a
supported operator command (`QRADAR_DASH_SOURCE_ONLY` appears only at `qradar-dash:2689`).

The supported way, from the runbook, is a second `./qradar-dash install` — the install summary
says it (`qradar-dash:797-798`), and OPS-9 r3's runbook text says it for the failing-QRadar case:
"QRadar'ı düzelt ve `install` komutunu yeniden çalıştır" (`docs/OPERATIONS.md:235-239`),
supported by the `Yeniden çalıştırma` section (`docs/OPERATIONS.md:252-265`: a second install with
the existing `.env` keeps `SECRET_KEY`/`ENCRYPTION_KEY`/`POSTGRES_PASSWORD` and re-runs `qradar
add`, migrate and `up -d`). `install` is the only command that writes the state file outside
`upgrade`/`restore`. So the notes say: fix the QRadar connection and run `./qradar-dash install`
again — from the 0.1.0 checkout so it records `installed_version` 0.1.0, then `upgrade 0.1.1`;
run from the 0.1.1 checkout it writes the state file at 0.1.1 itself, so nothing is left to
upgrade. The exact refusal text (`upgrade refused: .qradar-dash/state.json field file is invalid
or missing`) was confirmed against the script's `state_read` (see §3).
