### Where the code and a document disagreed

The design sentences were left in place. The README and the as-built notes follow the code.

1. **Fleet class.** A log source, IPS source, WAF endpoint or IPS entity is a pinned row
   id. A fleet class is a `SourceClass` string (`custom_rule.source_class`). The draft
   treated every subject as a pinned row id.
2. **Lower bound.** `event_count`, `average_eps` and `total_events` are `EXACT_ONLY`
   (`backend/app/custom_rules/catalog.py`): a lower bound proves nothing, including
   `GT`/`GE`. The other seven are `LOWER_BOUND_PROVES_INCREASE` and prove `GT`/`GE` only.
   Design §F.5 rule 2 says a lower bound proves "above" without that split. Rule 5 and the
   catalog are what the fold implements. Recovery always needs consecutive `EXACT` unders.
3. **`NOT_ENABLED`.** It is the fold's answer when the platform switch is off. The beat
   returns `{"status": "disabled"}` and opens no session while `custom_rules_enabled` is
   false, and the engine folds with the platform on, so the beat does not persist
   `NOT_ENABLED`. Design §F.4.1 says every rule then reports `NOT_ENABLED`.
4. **Disabled family.** Design §F.5 rule 7 names `NOT_ENABLED`. The code uses
   `NOT_COLLECTED`, and only for WAF and IPS, with the reasons
   `waf_collection_enabled is off` and `ips_collection_enabled is off`. A log-source or
   fleet-class rule is never `NOT_COLLECTED`.
5. **`SUBJECT_RETIRED`.** A missing log source or IPS source is retired
   (`the subject no longer exists`). An inactive endpoint or entity names
   `retired_at` when one is stored. A fleet class is never retired.
6. **`STALE`.** An empty grid beyond `cadence + bucket + settle + 60`
   (`COLLECTION_LATE_TOLERANCE_SECONDS = 60`) sets `last_status` to `STALE` on every
   evaluable rule of that kind, including one whose breach row stays `OPEN`. Counters and
   the watermark do not move. A disabled, retired or family-off rule keeps its own status.
   A gap still inside the bound keeps the previous status.
7. **`OK` and `NO_VERDICT`.** `OK` means no live breach and the last judged bucket was
   measured. A streak that has not reached `sustain_buckets` is still `OK`. `NO_VERDICT`
   means no live breach and the last bucket proved nothing (unmeasured or maintenance).
   The draft's "OK (judged and under)" was false. One exact under enters `RECOVERING`
   until `recovery_buckets` is met; when that count is 1, the same bucket resolves.
8. **Unmeasured and maintenance.** `INSUFFICIENT_DATA` is a bucket outcome, not a rule
   status (`String(16)` would not hold it). It pauses both counters. `unmeasured_buckets`
   increments only while a breach is already open. Maintenance pauses the same way, emits
   no open, refresh or resolve, and is not counted as unmeasured. Fleet class has no
   maintenance window. A rule never evaluated has a null status, which is not `OK`.
9. **Seed and SQL cost.** A kind is seeded only when it has an evaluable rule (enabled,
   not retired, family collected). That first run writes the watermark at the latest
   closed bucket and judges nothing. The metric read is one statement per such kind. The
   evaluation tick and the non-opening and refresh alerting ticks are pinned equal at 10
   and at 100 rules. A tick that opens alerts inserts one row per new alert; that cost is
   outside the pin. Design §F.13's "≤ ~20 statements, constant in rule count" is the
   design's estimate. The pins do not establish 20.
10. **Watermarks.** One row per subject kind that has been seeded. There are five kinds.
    Design §F.13 says "3 watermark rows".
11. **Latency arithmetic.** §F.4.4 and the §F.13 latency cell say "about 1 h 13 min". The
    terms they add (1 h cadence + 5 min bucket + 2 min settle + ≤ 1 min) sum to 68
    minutes. The README cadence line is that sum without the evaluation beat, about
    1 h 7 min. §F.12's plain "about an hour" is quoted once in the README, as the task
    requires. It is the sentence the design gives the custom-rules pages. Those pages are
    not built, so the sentence is not rendered. The search editor uses a different
    sentence (`SEARCH_LATENCY_STATEMENT` in `frontend/src/components/searches/authoring.ts`).
12. **API errors.** Domain validation is FastAPI-wrapped
    `{"detail": {"message", "reasons"}}`. The enabled-cap alone is 409 and the detail is
    that sentence. A duplicate name is 409 (`a custom rule named '{name}' already exists`).
    A patch requires `expected_updated_at`; a mismatch is 409 with `message`,
    `current_version` and `updated_by` inside `detail`. `current_version` is
    `datetime.isoformat()` (`+00:00`). A value outside an enum stays FastAPI's list 422.
    The enabled-count read is one unlocked `SELECT count(*)`.
13. **Search guards.** `check_cron_floor` (`CRON_FLOOR_SECONDS = 300`) uses a fast UTC
    derivation and falls back to walking `CronTrigger` fires, off the event loop. Design
    §F.8.2 describes the walk only. An unchanged cron, including one faster than the floor,
    is kept verbatim. A cron-floor 422 has a string detail, not the reasons object. The
    enable/disable audit split ignores `change_note`.
14. **Alert families.** Fingerprints also include `waf_anomaly`, `ips_anomaly`, `inventory`
    (new log source or new catch-all sender) and `offense_collection_stale`. A closed
    count of three or four conditions is false. `custom_rule_breach` stays out of
    `/anomalies`.
15. **Shadow, delete, orphan sweep.** While evaluation is on and
    `custom_rules_alerting_enabled` is false, breaches and rule state are written and the
    evaluator opens, refreshes, resolves and enqueues nothing. Disable, subject-retired
    and recovery do not close an already-open page until a later alerting-on tick.
    `STALE`, `NOT_COLLECTED` and maintenance leave a live page open. `AlertingCustomRuleSink.flush`
    runs only when paging is on (`engine.py`), so the orphan sweep runs on an alerting
    tick and is attributed to `custom-rule-evaluator`. `resolve_deleted_rule_alert` is the
    exception: the delete path resolves either way, actor the deleting principal, reason
    `the rule was deleted`.
16. **Retention.** `custom_rule_breach_retention_days` is not a `custom_rules_*` name.
    The delete skips a `RESOLVED` row still referenced by `custom_rule.active_breach_id`
    (`backend/app/custom_rules/retention.py`). Breach retention shipped in F-1. Design
    §F.15 assigns it to F-2. Search-result retention is F-4 (90 days by `bucket_start`).
    The optional Timescale chunk policy stays off unless `RETENTION_ENABLED` is set.
17. **Table count.** The committed README said 64 tables. AUTH-1 added `auth_session` and
    `ldap_config`, and Phase F added the three custom-rule tables. With `user_role`, the
    count is 69. Hypertables stay 13.
18. **`search:write`.** Design §F.8.2 says "admin only today". `detection_engineer` holds
    it too (D-17). The admin role does not list `custom_rule:write` because `admin:*`
    already satisfies it.
19. **Preview agreement.** Design §F.7 and §F.14 ask for a property test over randomized
    streams. The pin is the hand-built cases in
    `backend/tests/integration/test_custom_rules_api.py`. Preview tells the fold the
    platform is on, the rule is enabled, the subject is not retired, the family is
    collected, and there is no stale reason, so `STALE` is ignored. Maintenance is applied.
    Draft preview validates with `previously_enabled=True` and `enabled_count=0`.
20. **Migration head.** Design §F.10 chains `0024` after head `0023`. `0024` revises
    `0023`, and `0025_auth_sessions` (AUTH-1) revises `0024`. The chain head on this
    branch is `0025`.
21. **F-6 and F-6a.** `docs/tasks/F-8.md` "Why" lists F-6a among what is built on this
    branch. The route is not in `custom_rules.py`, and `frontend/src/app/custom-rules`
    does not exist. Both are documented as `(F-6a, in progress)` / `(F-6, in progress)`
    and `[BUILDING]`. Catalog response fields from `docs/tasks/F-6a.md` were not copied
    into the README or the design.
22. **§F.15 "ran as written".** Review changed the cron floor (§F.8) and replaced the
    search editor's latency sentence (§F.12). The task table was not rewritten.
