## The problem

WAF incidents (`WafAnomaly`) have a full lifecycle in `app/waf/engine.py`, but they raise no
alerts: nothing in `app/waf` calls `AlertService`. So an analyst is never notified of a WAF
anomaly.

Phase A shows the pattern to mirror. In `app/anomaly/engine.py`, read `_alert_input`, `_refresh`
and `_resolve`, and see how `app/workers/tasks.py` passes a `NotificationDispatcher` as the
`enqueuer`.

The design decision is fixed by `docs/PHASE-B-WAF-BEHAVIOR.md` §14:
- reuse `AlertService.open_or_update()` and `resolve_by_fingerprint()`;
- an incident's fingerprint is `(qradar instance, WAF log source, normalized endpoint, detector
  type)`;
- the detector type is part of the fingerprint, so two detectors on one endpoint are two alerts,
  each recovering on its own.

## What to build

1. **Fingerprint.** In `app/alerts/fingerprint.py`, add `waf_anomaly_fingerprint(...)`, built
   with `compute_fingerprint`.
   - Use the condition family `"waf_anomaly"`, distinct from Phase A's `"anomaly"`. A routing rule
     with `alert_types={"anomaly"}` therefore does not pick up WAF alerts by accident.
   - Build the identity from the endpoint's natural key (the columns of `WafEndpoint`'s unique
     constraint) plus the detector type, never from the surrogate `id`.
2. **Setting.** In `app/core/config.py`, add `waf_alerting_enabled: bool = False`, with a comment
   in the style of the neighboring WAF settings.
   - It exists so that operators can collect and baseline a WAF source silently ("shadow mode")
     before it can page anyone.
   - When it is False, the engine behaves exactly as it does today.
3. **Engine.** `WafAnomalyEngine` takes an optional `enqueuer`, as `AnomalyEngine` does. When
   `waf_alerting_enabled` is on:
   - **OPEN transition:** call `open_or_update` with a WAF-shaped `AlertInput`.
     - title: `"<detector type> on <source name>: <method> <normalized endpoint>"`;
     - `source_type="waf_endpoint"`;
     - `description` = the evidence reason;
     - evidence = `evidence.to_dict()`;
     - `source_anomaly_ids` = the incident id;
     - `context`: `log_source`, `owner`, `criticality`, `instance`, `virtual_host`, `endpoint`,
       `method` and `detector_type`. The routing rules in `app/alerts/routing.py` read `owner` and
       `instance`.

     Enqueue a notification when the result carries a transition.
   - **Still OPEN, still anomalous:** refresh the alert, as Phase A's `_refresh` does, but
     never in maintenance and never with a notification.
   - **RESOLVED transition:** call `resolve_by_fingerprint`, and enqueue a notification when the
     result carries a transition.
   - **Any other transition** (CANDIDATE, RECOVERING, SUPPRESSED, NORMAL, INSUFFICIENT_DATA):
     raises no alert and resolves none.
   - `_apply_transition` is synchronous. Collect the alert actions while the bucket is folded,
     then apply them in one async step after the detector loop.
4. **Cost** (AGENTS.md rule 9; design §29.5 and §29.11). This is the hard part.
   - With alerting on and no endpoint changing alert state, the statement count per evaluated
     bucket must not grow with the number of endpoints. That includes the refresh of
     still-open alerts: load the active alerts for every fingerprint that needs one in **one**
     query per bucket evaluation, not through a `_find_active` per endpoint.
   - Add whatever bulk helper `AlertService` needs for this. Keep the existing methods'
     behavior unchanged.
   - An OPEN or RESOLVED transition may cost a bounded number of statements each, since the
     notification enqueue uses a savepoint per route. Measure and report that number.
5. **Wiring.** `run_waf_source` / `WafPipeline` in `app/services/waf_pipeline.py` accept the
   enqueuer and pass it to the engine. The WAF Celery task in `app/workers/tasks.py` builds a
   `NotificationDispatcher(session, notifiers={}, policy=default_policy())`, as the Phase A task
   does. Change only that wiring in `tasks.py`.

## Tests

Put integration tests in a new file, `tests/integration/test_waf_alerting.py`. Reuse the helpers
the existing WAF integration tests use (`tests/integration/test_waf_b2_engine.py` and
`tests/integration/factories.py`).

1. A request-rate incident that opens raises exactly one open alert with the WAF fingerprint,
   the title and the context, and enqueues one notification per matching route.
2. Further anomalous buckets refresh it: `occurrence_count` rises, and no second notification is
   sent.
3. Recovery to RESOLVED resolves the alert and enqueues a recovery notification.
4. A recurrence after RESOLVED opens a new alert.
5. Two detectors on one endpoint give two alerts with different fingerprints, and resolving one
   leaves the other open.
6. With `waf_alerting_enabled=False`, nothing happens: no alert rows, no notifications.
7. An anomalous bucket in maintenance neither opens nor refreshes an alert.
8. CANDIDATE and INSUFFICIENT_DATA raise nothing.
9. The scheduled path (`run_waf_source`) opens an alert end to end. Follow
   `tests/integration/test_waf_scheduled_breakdowns.py`.

Unit-test the fingerprint: it is stable for the same natural key, and differs for each part of
the key.

Extend `tests/integration/test_waf_scale.py` (add tests; do not change existing assertions):
- with alerting on and no transitions, statements at 40 endpoints = statements at 800 endpoints,
  and at most 1 more than with alerting off;
- with every endpoint holding an already-open incident and alert, refreshing costs the same
  number of statements at 40 and at 800 endpoints.

After writing the tests, break the code on purpose (for example, drop the maintenance guard, or
build the fingerprint from the surrogate id), confirm a test fails, then restore it.
