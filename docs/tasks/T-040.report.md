The 16:00 mismatches, all keyed minus per-bucket = +5 in records and in events: rule 100101
(405,610 vs 405,605), 100216 (405,608 vs 405,603), 100221 (406,342 vs 406,337), 100227 (406,342 vs
406,337), 100272 (406,340 vs 406,335), 100277 (405,644 vs 405,639). The windows were 4 h old, so
this is not late arrival. Search 18 re-ran the per-bucket query for that window about 5 min later
and returned 406,337 / 406,335 / 405,605 again: it did not converge on the keyed value.

Searches 19 and 20 found the cause. The same `WHERE starttime >= a AND starttime < b` on one rule
gave 405,605 with `STOP b` and 405,610 with `STOP b + 10 min`. The latest event in the window had
`starttime` 16:59:59.952. So `START`/`STOP` filter on a time slightly later than `starttime` (the
time QRadar stored the event), and events whose `starttime` is just before the window end but that
were stored just after it are dropped by a query whose `STOP` equals the window end. The keyed
search sees them in every bucket except the last one of its span. Interior buckets are therefore
complete, and the per-bucket path is the one that undercounts by a few events at its edge.

## Findings

1. **The `STOP` edge effect (low, not blocking).** A bucket's count depends on whether the bucket
   is at the end of a search span: the last bucket of a span can miss events stored just after the
   span's `STOP`. This differs between the keyed and the per-bucket path by a handful of events
   (5 in 2.4 million here). It affects both paths and the keyed one is closer to the truth, but it
   breaks the "persisted rows equal per-bucket rows, column for column" bar in rare cases. The
   unit and mock tests cannot show this. If exact equality matters, pad the Ariel `STOP` (not the
   `WHERE` bound) by the settle time. Otherwise document it.
2. **Late arrival was not isolated.** The last bucket of each tick was settled by about 1 min or
   more and matched; no separate late-arrival run was needed because no last-bucket mismatch
   appeared.
3. **First-search latency.** The first keyed search of a process took 3.5 s against 1-2 s later.
   Immaterial.

## Recommendation

**Merge `feat/phase-ce` to `main` as is.** One search per kind per tick held for Phase A volume,
rule matches and WAF; the keyed values equal the per-bucket path in every bucket compared except
for a 5-event edge effect that is a QRadar property and favours the keyed path; no wide search
failed; the evaluation watermark walks every bucket in order. Follow-ups, not blockers: decide on
Finding 1; run the truncation/split and failure paths on a busier console before relying on
Phase A's no-split-on-failure behaviour; repeat the WAF run with action and response-code
breakdowns when budget allows.
