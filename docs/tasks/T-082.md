# Task T-082 — docs: production needs one origin for the browser's API reads

Read `AGENTS.md` at the repository root first and follow it exactly. **Documentation only**: change
no code, no configuration file and no test. Check every claim against the code and say where the
code and a document disagree.

## The problem to document

- `backend/app/main.py` configures `CORSMiddleware` with `allow_origins=["http://localhost:3000"]`
  outside production and **`[]` in production**, with the comment "The SPA is same-origin behind the
  reverse proxy in production".
- The frontend calls the API **from the browser** through `NEXT_PUBLIC_API_BASE_URL`
  (`frontend/src/lib/api.ts`: `PUBLIC_BASE`, `baseUrl()`); server components use
  `INTERNAL_API_BASE_URL`. `docker-compose.yml` publishes the frontend on `127.0.0.1:3000` and the
  backend on `127.0.0.1:8000` ("front with a TLS reverse proxy"), and `.env.example` sets
  `NEXT_PUBLIC_API_BASE_URL=http://localhost:8000/api/v1`.
- Since UI-1.5 (the top bar) and UI-2.x (the Home at `/`), much of the UI reads the API from the
  browser. With the production CORS list empty, **those reads fail unless the browser sees the UI
  and the API on one origin**. Nothing in the README says so today.
- The rate limiter keys on the client address (`backend/app/core/rate_limit.py`,
  `get_remote_address`). Uvicorn runs with `--proxy-headers` (`docker-compose.yml`). Find out from
  uvicorn's documented behaviour which proxy addresses it trusts by default
  (`--forwarded-allow-ips` / `FORWARDED_ALLOW_IPS`), and state what that means behind a reverse
  proxy: whether the limiter sees the real client or the proxy's address, and what the operator must
  set. Cite the uvicorn documentation you relied on (name and section); do not guess.

## Write

In `README.md`, in the section where deployment or "Connecting a real QRadar" / the compose stack is
documented (find the right place; match its voice), add a short **"Production: one origin for UI
and API"** subsection that says:
1. why: the browser reads the API directly, and production CORS allows no cross origin;
2. what: a TLS reverse proxy serves the UI at `/` and the API at `/api/` on one origin, and
   `NEXT_PUBLIC_API_BASE_URL` is set to the relative path `/api/v1` at **build time** (check
   whether Next inlines `NEXT_PUBLIC_*` at build time and say so precisely, because that decides
   whether the image must be rebuilt per deployment);
3. a minimal example of the two proxy routes, for one common proxy (nginx or Caddy), clearly
   marked as an example, with TLS left to the operator, and nothing that weakens a security header
   the backend sets (`main.py` sets `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`,
   `Cache-Control`);
4. the proxy-headers and rate-limit point above;
5. that development keeps working as today (`localhost:3000` is allowed outside production).

Also correct `.env.example`'s comment next to `NEXT_PUBLIC_API_BASE_URL` **only if** it is wrong;
if it is right, leave it. (`.env.example` is documentation, so a comment edit is allowed; never
change a value.)
