## The problem

T-028 guarded every router. Two handlers still mutate state behind a **read** permission only, and
`tests/unit/test_route_auth_guard.py` allowlists them in `_READONLY_MAY_MUTATE`:

- `PATCH /api/v1/rules/{rule_id}` (`app/api/routes/rules.py::update_rule_metadata`), guarded only by
  the router's `read:rules`;
- `POST /api/v1/coverage/mappings` (`app/api/routes/coverage.py::create_mapping`), guarded only by
  the router's `read:coverage`.

So a `read:*` viewer can change SOC rule metadata and coverage mappings.

## Build

Follow the existing pattern exactly: `PERM_LOG_SOURCE_WRITE` in `app/security/rbac.py`, and its
handler-level check in `app/api/routes/log_sources.py` (`PrincipalDep` + `_guard`).

1. `app/security/rbac.py`: add `PERM_RULE_WRITE = "rule:write"` and
   `PERM_COVERAGE_WRITE = "coverage:write"`, with a comment in the voice of the neighbouring
   comments (why it is a write and why `read:*` must not grant it).
2. Both handlers take the principal and check the write permission **first**, before any lookup,
   so a forbidden caller learns nothing (403 before 404).
3. Both mutations are recorded with `record_audit` with the principal as actor, if they are not
   already. Look at how `update_log_source` does it. If one is already audited, keep it and only make
   sure the actor is the principal's subject.
4. `app/services/seed.py`: the `admin` and `analyst` roles gain both permissions (the analyst
   already edits SOC metadata today, and the frontend calls `PATCH /rules/{id}`); `viewer` does not.
   The seed is additive for existing roles; keep that.
5. `tests/unit/test_route_auth_guard.py`: remove both entries from `_READONLY_MAY_MUTATE`, so the
   guard test now proves 403 for a read-only principal on both routes. Add bodies to `_BODIES` if
   the test reports 422. Do not change anything else in that file. If `_READONLY_MAY_MUTATE` ends up
   empty, keep the (now empty) set and its skip; do not restructure the test.
6. New tests, in the existing test modules for rules and coverage (find them under `tests/`):
   - a `read:*` principal gets 403 on each route and the row is unchanged;
   - a principal with exactly `read:*` + the write permission succeeds (200 / 201);
   - 403 comes before 404 for an unknown rule id;
   - the audit row carries the principal as actor.

Check the frontend: `frontend/src/lib/api.ts` calls `PATCH /rules/{id}`. Do not change frontend
code; just confirm in your report that the default analyst role keeps working.
