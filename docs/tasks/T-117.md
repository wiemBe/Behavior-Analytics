# Task T-117 — the frontend's npm advisories: reachability first, then the smallest safe fix

Read `AGENTS.md` at the repository root first and follow it exactly.

## Why

`npm audit` in `frontend/` reports 8 advisories (2 moderate, 6 high), and every fix it offers is
a **major** version change:

| Package | Severity | Path | `npm audit`'s fix |
|---|---|---|---|
| `echarts` 5.5.1 | moderate | direct, **runtime** | `echarts` 6.x (major): "Apache ECharts has a cross-site scripting (XSS) vulnerability" |
| `next` 15.5.28 → `postcss` | moderate / high | direct → transitive | `next` 16.x (major): PostCSS XSS via unescaped `</style>` in stringify; arbitrary `.map` file read via `sourceMappingURL` |
| `eslint-config-next` 15.1.3 → `@next/eslint-plugin-next` → `fast-glob` → `micromatch` → `braces` | high | dev only | a different `eslint-config-next` major |

`npm audit fix --force` would cross three majors at once. That is not acceptable for this
product. The orchestrator needs to know which advisories are reachable before deciding.

## Do

1. **Reachability, per advisory** (read each GHSA advisory text; `npm audit --json` and
   `npm explain <pkg>` show the paths):
   - **`echarts` XSS.** Which API or option is vulnerable (for example tooltip or label
     formatters rendering HTML, `richText`, `title`)? Does this frontend use it with a string the
     analyst does not control? WAF paths, log-source names, signatures and IPS values come from
     QRadar, and an attacker can shape some of them. Grep every `echarts` use under
     `frontend/src/`. Is there a patched **5.x** release (`npm view echarts versions`)? If a 6.x
     upgrade is the only fix, list what breaks: the API changes that affect our chart code.
   - **`postcss` under `next`.** Is it reached at runtime in the production `next start` server,
     or only at build time on CSS this repository authors? Is a patched `next` **15.x** or a
     patched `postcss` reachable through an `overrides` entry, without a `next` major?
   - **The eslint chain.** Confirm that it is dev-only (`npm ls --omit=dev`). Is a non-major
     path available (an `overrides` pin of `braces` / `micromatch` / `fast-glob`)?
2. **Apply only fixes that cross no major version** of a direct dependency: a patch or minor
   bump, or an `overrides` entry for a transitive package. Each fix must keep every gate green.
   Do **not** upgrade `next`, `echarts` or `eslint-config-next` across a major.
3. **If our echarts use is reachable with attacker-shaped strings and no 5.x fix exists**, show
   where (file and line). Do not change chart code in this task. Propose the smallest mitigation,
   for example escaping in our formatter, as a follow-up.
