## The problem (found by T-007, reproduced by the orchestrator)

`WafSourcePipeline.run` (`app/services/waf_pipeline.py`, around line 204) builds
`WafEndpointCollector(...)` without its `breakdowns=` argument. Nothing on the scheduled path
(`collect_waf_source` → `run_waf_source` → `WafSourcePipeline.run`) passes a `BreakdownPlan`
to the collector.

So in production every bucket records every breakdown as `NOT_COLLECTED`, and none of the
Phase B.2 detectors can ever produce a verdict. Only tests that drive the collector directly with
`breakdown_plan(profile, settings)` exercise breakdown collection.

The training step already computes the plan: `_train` receives breakdown identities built from
`breakdown_plan(profile, self.settings).collect` (task T-005). Collection must use the same plan.

## What to build

1. In `WafSourcePipeline.run`, compute `breakdown_plan(profile, self.settings)` **once per run**.
   - Pass it to `WafEndpointCollector(..., breakdowns=plan)`.
   - Derive the training identities from the same `plan` object, so collection and training can
     never disagree within one run.
2. **Observability.** The plan's skipped breakdowns and their reasons (`BreakdownPlan.skipped`, or
   whatever the dataclass calls it) must be visible to an operator.
   - Look at `WafPipelineReport` and at the admin status service (`app/services/waf_status.py`,
     `GET /api/v1/waf/sources`).
   - Add the planned and skipped breakdowns to the pipeline report.
   - If the status service already summarizes per-source state from persisted data, it is enough
     for the report to carry the plan. Do not add a database column.
3. **Ariel budget.** Each breakdown is one more bounded Ariel search under the same permit
   (`app/services/waf_ariel_budget.py`). Read how the collector acquires the permit, and confirm
   the breakdown searches run inside it. If they do not, report that; do not restructure the
   budget.
