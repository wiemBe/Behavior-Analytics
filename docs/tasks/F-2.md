## Build

1. **Shadow mode (D-17, question 1).** A new setting `custom_rules_alerting_enabled`, default
   **false**, beside `custom_rules_enabled`.
   - With it false, the evaluator still writes breach rows and rule state exactly as F-1 does,
     and **opens, refreshes and resolves no alert and enqueues no notification**.
   - With it true, the alert seam described below is used.
   - The rule's API state must be able to say which mode applies (a field or a status reason
     that F-3 will expose; name it in the report).
2. **Fingerprint.** `custom_rule_breach_fingerprint(rule_id)` in `app/alerts/fingerprint.py`
   (§F.6): `source_type="custom_rule"`, `condition="custom_rule_breach"`. It must never collide
   with Phase A, WAF, IPS or search fingerprints; pin that with a test over the existing
   fingerprint kinds.
3. **The seam.** Implement F-1's alert seam with `AlertService`: open after `sustain_buckets`
   (`open_or_update`, the rule's severity, the context and evidence §F.6 lists), refresh while
   still breaching (occurrence count), resolve after `recovery_buckets`
   (`resolve_by_fingerprint`, actor `custom-rule-evaluator`, reason `condition recovered`), and
   enqueue notifications per transition exactly as `app/alerts/search_alerts.py` does.
4. **Maintenance.** A subject whose log source is in maintenance neither opens, refreshes nor
   resolves (the IPS rule, §F.6). Check what F-1 already does for maintenance and build on it.
5. **Rule disabled or deleted.** A disabled rule's open alert is resolved with a reason that
   says so; check what F-1's statuses give you (`DISABLED`, `SUBJECT_RETIRED`) and resolve or
   keep accordingly, with the reason in the report.
6. **Breach retention** (§F.10): if F-1 did not build the bounded daily retention of resolved
   breaches (180 days), build it here; otherwise leave it.
