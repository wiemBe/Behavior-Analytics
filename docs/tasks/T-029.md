## Why

Production IPS is **Cisco Firepower Threat Defense** and **Palo Alto Networks (THREAT logs)**. The
lab has no live IPS telemetry (T-027). Phase D (IPS port and IP behavior, goal G2) needs real
QRadar-parsed IPS events.

The platform is read-only, and the lab guide forbids creating log sources over the API. So the
lab IPS sources are to be created by **QRadar auto-discovery**: QRadar recognizes a vendor's native
syslog format and creates the log source itself. That requires payloads close enough to the real
products that QRadar's **Palo Alto PA Series** and **Cisco Firepower Threat Defense** DSMs both
auto-discover and parse them.

## Build, in `tools/qradar_lab_loggen.py`

1. **Two new profiles, each with one default identity, documented in the identity table:**
   - `pan_threat`: identity `pa-fw-01`. PAN-OS **THREAT** log in the default syslog CSV format.
     The subtypes are `vulnerability`, `spyware` and `url`.
     - The fields QRadar's DSM maps must carry realistic values: receive time, serial, type,
       subtype, generated time, source and destination IP, rule, application, zones, interfaces,
       session id, source and destination port, protocol, **action** (`alert`, `allow`, `drop`,
       `reset-client`, `reset-server`, `reset-both`, `block-ip`), threat name with id (for example
       `Apache Struts Remote Code Execution Vulnerability(33435)`), category, severity and
       direction.
   - `ftd_ips`: identity `ftd-01`. Cisco FTD **intrusion event** syslog, message `%FTD-1-430001`
     (and `430002`/`430003` for connection events where useful).
     - Key-value body, with realistic `EventPriority`, `DeviceUUID`, `InstanceID`,
       `FirstPacketSecond`, `ConnectionID`, `AccessControlRuleAction`, `SrcIP`, `DstIP`,
       `SrcPort`, `DstPort`, `Protocol`, `IngressInterface`, `EgressInterface`, `IngressZone`,
       `EgressZone`, `IntrusionPolicy`, `GID`, `SID`, `Revision`, `Message`, `Classification`,
       `Client`, `ApplicationProtocol`, `InlineResult` (`Blocked`, `Would block`, `Allowed` …),
       and so on.
   - **Ground every field order and value set in the vendor's published log format**: the PAN-OS
     syslog field descriptions for THREAT, and Cisco's FTD syslog message guide for 430001.
     Use IBM's QRadar DSM guide for the Palo Alto PA Series and Cisco Firepower Threat Defense
     DSMs to confirm which format and transport QRadar expects for auto-discovery. Cite the
     source document, title and version, in a comment above each renderer. If you cannot reach a
     document, say so in the report and mark the renderer `UNVERIFIED`. **Do not guess silently.**
   - The syslog header carries the identity as hostname, because that is what auto-discovery keys
     on. Follow how the existing renderers build the header.
2. **Payload safety:**
   - external addresses come from the RFC 5737 networks only (`198.51.100.0/24`,
     `203.0.113.0/24`, `192.0.2.0/24`);
   - protected internal assets use `10.10.20.0/24`;
   - no real signatures beyond public names and ids;
   - usernames, if any, only from the synthetic list.
3. **IPS scenarios** that work for both profiles. Phase D's detectors need them:
   - `ips-baseline`: a stable mix over 8–15 destination service ports (22, 25, 53, 80, 443,
     445, 3389, 8080 …), 20–40 source IPs, about 10 signatures, and a stable action share.
   - `ips-port-sweep`: one source IP hits many sequential destination ports on one host.
   - `ips-new-port`: after baseline, sustained traffic to a destination port never used in
     baseline.
   - `ips-source-concentration`: one source IP rises to more than 60% of events.
   - `ips-signature-burst`: one signature's rate multiplies by 10 or more.
   - `ips-block-shift`: the share of blocking actions rises from about 10% to about 60%.

   Reuse the Phase A plan, schedule and rate machinery where it fits. Rates, bounds and the
   `--allow-high-rate` rule are unchanged.
4. **Determinism:** `--seed` reproduces the stream, as elsewhere.
