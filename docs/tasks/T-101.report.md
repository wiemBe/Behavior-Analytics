# T-101 report — lab generator: IPS scenarios never reach their change phase with two profiles

## 1. Files changed

- `tools/qradar_lab_loggen.py` — fix for defect D-1. `_scenario_event` now derives the change
  phase from the profile's own round-robin share and passes it into `_ips_event`; the whole-run
  count moved into a new `_planned_events()` helper.
- `backend/tests/unit/test_qradar_lab_loggen_phase_d.py` — 29 new test cases (new tests only; no
  existing test was edited, skipped or weakened).
- `docs/tasks/T-101.report.md` — this report (new).

## 2. What I did

Defect D-1: with `--types pan_threat ftd_ips --count 9000`, `_scenario_event` round-robins the two
profiles and hands each `local_index` 0…4499, while `_ips_event` computed
`transition = max(1, planned // 2)` from the **total** run (4500). `anomaly = index >= transition`
was therefore never true and every phase-gated scenario stayed baseline-shaped.

Fix (kept minimal, no new option, no change to event content, rate, bounds or output):

- Added `EventGenerator._planned_events()`, which returns the whole-run planned count
  (`--count`, else `int(--duration × --eps)`) — the arithmetic previously inlined in `_ips_event`.
- `_scenario_event` computes `per_profile_planned = self._planned_events() // len(profiles)` and
  passes it to `_ips_event(..., planned=per_profile_planned)`. Floor division is the **smallest**
  share, so the transition always falls inside every profile's own run even when the total leaves a
  remainder (e.g. 9001 → shares 4501/4500, transition 2250).
- `_ips_event` takes an optional keyword-only `planned`; `None` (the `_normal_event` /
  `ips-baseline` path) keeps the previous whole-run behaviour, so nothing else changed.

Single-profile behaviour is byte-for-byte identical: with one profile `planned = total // 1`, so
the transition is unchanged. The `planned == 0` fallback (`transition = 1_000`) is unchanged.

New tests (`test_qradar_lab_loggen_phase_d.py`), all built in memory (no socket, no network):

- Two profiles `--count 9000`, all four gated scenarios, both profiles: baseline half
  (`local_index` 0…2249) has change-share < 0.2, second half (2250…4499) ≥ 0.6. Pins that each
  profile reaches its own change phase.
- `ips-new-port`: port 8443 appears in **no** baseline-half event and in **every** second-half
  event, for both profiles.
- `ips-signature-burst`: second half is exactly signature `IPS_SIGNATURES[0]` for both profiles;
  baseline half carries it exactly `2250 // 10 = 225` times.
- `ips-source-concentration`: the single top source in the second half is `IPS_EXTERNAL_IPS[0]`
  and holds exactly 70 % of it, for both profiles.
- Odd total `--count 9001`: profile shares 4501/4500, transition 2250, both profiles reach their
  change phase (parametrized over all four gated scenarios and both profiles).
- `--duration 9000 --eps 1` with two profiles: same change phase as the `--count` path.
- One profile: the change still begins at index 4500 for count 9000 and at 2000 for count 4000
  (the shape the existing tests pin), i.e. the transition is unchanged from today.
- `planned == 0` fallback: a single profile with `--count 0` still begins port 8443 at index 1000.

**Break-it:** I reverted the fix on purpose (`per_profile_planned = self._planned_events()`),
re-ran the new file, and confirmed the two-profile tests fail — **27 failed, 34 passed**; the 7
failures were exactly the new two-profile cases while the two single-profile/fallback tests stayed
green. I then restored the fix and re-ran everything clean.

`ips-port-sweep` is intentionally untouched: it is not gated on `anomaly`.
