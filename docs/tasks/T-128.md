# Task T-128 — the beat heartbeat is written at beat start

Read `AGENTS.md` at the repository root first and follow it exactly. Then read
`docs/tasks/OPS-10.report.md` (the `celery_beat` observation), `backend/app/workers/celery_app.py`
(the beat schedule, `BEAT_HEARTBEAT_KEY`, `BEAT_HEARTBEAT_TTL_SECONDS`, and the existing
`@beat_init.connect` handler `_apply_policies_at_beat_start`), the `beat_heartbeat` task in
`backend/app/workers/tasks.py`, and `check_celery_beat` in `backend/app/cli/doctor.py`.

## The problem

The heartbeat task runs every 60 s, and beat's first run of an interval task comes one interval
after beat starts. After every restart (install, upgrade, rollback, a reboot), and after
`upgrade`'s Redis `FLUSHALL`, the key is missing for up to a minute, so `doctor` reports
`FAIL celery_beat … heartbeat is missing` on a healthy stack. OPS-10 saw it after every upgrade and
rollback.

## The fix

- At beat start, also send `beat_heartbeat` once, in the same handler pattern as the policy task:
  through `send_task`, and a broker that is down must not stop beat (log a warning, carry on).
  Keep one `beat_init` handler or add a second; either way, each task is sent exactly once per
  beat start.
- Change nothing in `check_celery_beat`: a missing heartbeat is still a FAIL, because a running
  beat now writes it within seconds.

## Tests

- Extend the existing beat-start tests (find them with
  `grep -rn "beat_init\|apply_policies_at_beat_start\|beat_start" backend/tests`): a beat start sends
  `beat_heartbeat` exactly once and `apply_timescale_policies` exactly once; a dead broker is
  survived for both, and the second send is still attempted when the first one raises.
- Break the fix once (stop sending the heartbeat) and confirm a test fails.
