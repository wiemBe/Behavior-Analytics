# Task T-066 — defuse the clock time bomb in two profile-admin tests (setup only)

Read `AGENTS.md` at the repository root first. Follow §4: **no assertion changes.**

## The defect (found by the orchestrator, 2026-10-13)

Two integration tests seed a *pending* validation request with the fixed constant
`NOW = datetime(2026, 10, 13, 9, 0, tzinfo=UTC)`. The API they then call builds its service with
the **real clock**, and treats a request older than the pending timeout (900 s) as expired. So
from 2026-10-13 09:15 UTC on, the request is no longer pending:
- the WAF test gets `202` where it expects `409`;
- the IPS test enqueues a real Celery task and fails on Redis.

These tests are:
- `tests/integration/test_waf_profile_admin.py::test_validate_pending_timeout_and_enable_disable`.
  The seed is `profile.validation_requested_at = NOW`, around line 355. This test is already on
  `main`.
- `tests/integration/test_ips_profile_admin.py::test_pending_enable_disable_report_history_and_candidates`.
  The seed is `validation_requested_at=NOW`, around line 309, in the `IpsSourceProfile(...)`
  constructor.

## The fix (a setup change only)

In **those two seeds only**, replace `NOW` with `datetime.now(UTC)`. That makes the request
pending relative to the clock the API uses. Both files already import `datetime` and `UTC`.
Change nothing else:
- no assertion;
- no other use of `NOW` (the worker tests pass their own clocks or timestamps on purpose);
- no other file.

Add a one-line comment above each changed line, for example: `# Pending relative to the API's
real clock: a fixed timestamp expires after the 900 s pending timeout.`
