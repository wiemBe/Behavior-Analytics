# Task T-079 — `/admin/search-cadence`: report the IPS collection's bucket width

Read `AGENTS.md` at the repository root first and follow it exactly. In particular §4: never weaken
a test.

This task is small and mechanical. Change only what is listed here.

## Why

`GET /api/v1/admin/search-cadence` returns `bucket_seconds` per search family. The UI uses it to
show the bucket width and the worst-case delay (`SearchCadenceTable.tsx`, `worstCaseDelay`).
`_bucket_seconds` in `backend/app/api/routes/search_cadence.py` returns
`settings.collection_interval_seconds` for `PHASE_A_VOLUME`, `WAF_COLLECTION` and
`CATCHALL_SENDERS`, but **not** for `IPS_COLLECTION`. IPS collection also writes buckets of
`collection_interval_seconds`: see `self.settings.collection_interval_seconds` in
`backend/app/collectors/ips_collector.py`. The API therefore reports `null` for IPS, and the page
says "This family has no buckets" for it and computes the worst-case delay without a bucket. The
gap came in with T-050b.

## Build

1. `backend/app/api/routes/search_cadence.py`, `_bucket_seconds`: add
   `SearchFamily.IPS_COLLECTION` to the set that returns `settings.collection_interval_seconds`.
   Change nothing else in the file.
2. `backend/tests/integration/test_search_cadence_api.py`: add a new test, or new assertions in
   `test_readonly_can_get_but_cannot_put_and_last_run_is_null` **after** the existing ones. Look
   rows up by `family`, not by position, and assert:
   - `IPS_COLLECTION` and `CATCHALL_SENDERS` have `bucket_seconds == 300`, the test settings'
     `collection_interval_seconds`. If the test settings use another value, assert that value
     instead and say so in the report;
   - `ANOMALY_EXPLANATION` stays `None`.

   Keep the three existing positional assertions unchanged.

Break the fix on purpose (remove `IPS_COLLECTION` from the set), confirm that the new assertion
fails, and restore it (AGENTS.md §4).
