## The question the view answers

**`/rules/statistics`** answers: "How is the rule set made up, which rules carry the matching load,
which enabled rules are provably silent, and which are the most expensive to evaluate?" The first
screen must show the measurement window's honesty line and the composition. The other sections
follow in this order:

1. **Measurement window** (one line, not a card). For example: "Matches measured over 6 d 23 h of
   the last 7 days: 167 of 168 windows complete, 1 truncated. Times are UTC." When `complete` is
   false it is a designed PARTIAL state that carries `window.reason` verbatim. When no window was
   collected it is a designed INSUFFICIENT_DATA state. A days selector offers 1, 7 and 30 days
   (`days`), and the selection lives in the URL query.
2. **Composition**, from `counts`: a compact pivot table, not KPI cards. Rows are rule type ×
   building block (rules, then building blocks); columns are enabled, disabled and total; origin
   (SYSTEM / USER / OVERRIDE) is a filter or a secondary breakdown. Use readable labels. A `null`
   type or origin shows as "Unknown type" / "Unknown origin", never blank.
3. **Most matched**, from `top_by_events` (default) and `top_by_matches` (toggle). Columns: rule
   (link to `/rules/<id>`), type, building block, matched events, match records, and **match rate
   in events/s**. `lower_bound` renders "≥ n" with the meaning available, for example "flow
   matches are not searched, so this may undercount". `null` lists render `top_reason`.
4. **Silent enabled rules**, from `silent`: a measured zero over a complete span. Show the rule,
   its type, `first_seen_at` (so a young rule is visible) and `last_fired_at`. Show `total` and
   `items_truncated` honestly ("showing 500 of 1,204"). Render `excluded` as a short sentence, or
   a table by type, with `excluded_reason`: "N enabled rules were not judged, because …". A `null`
   section renders `silent_reason`. **Never** render a null section as "0 silent rules".
5. **Costliest by benchmark**, from `costliest_by_benchmark`. Use the API's `label` and `unit`.
   It must say plainly that this is QRadar's capacity benchmark, that **lower means costlier**,
   and that it is **not a firing rate**. Add `no_benchmark_count` as "N enabled rules have no
   benchmark".
6. **`/rules/[id]`** gains a **Capacity history** section from `/rules/{id}/capacity-history`:
   newest first, a sample only when QRadar re-benchmarked. Use a compact table (timestamp UTC,
   average and base capacity with the unit, host id). A chart is allowed only when there are
   enough samples for one to say something, and it must follow the T-038 chart rules. Empty means
   "QRadar has not re-benchmarked this rule since collection began". This is not an error.

Add **one nav entry**, "Rule statistics", next to "Rules", and update the pinned nav test for

## Honesty (§3a, guidelines §4/§6)

- Every `null` with a reason renders the reason; every measured zero renders `0`.
- Numbers are right-aligned, tabular and carry their unit: events, records, events/s, and the
  benchmark's unit from the API.
- Times are in UTC, with the zone shown.
- A 404 from `/rules/statistics` ("no instance registered") is a designed empty state. It says
  that no QRadar instance is registered and what the analyst can do about it. It is not an error
  page.
- No placeholder or invented data anywhere.
