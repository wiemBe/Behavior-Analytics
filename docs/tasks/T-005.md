## The problem

`app/anomaly/capabilities.py` declares `WAF_BASELINE_METRICS` as "every baseline metric the WAF
builder trains". It lists `block_ratio`, `server_error_ratio`, `client_error_ratio` and
`top1_client_share`. **`app/waf/baseline.py` trains none of them.** It only writes `request_count`
cells.

The docstring at `baseline.py:78` points to a `RATIO_METRICS` table that does not exist. The
columns `waf_endpoint_baseline.numerator_sum` / `denominator_sum` (migration 0010) are read by the
detectors in `app/waf/behavior.py`, but nothing ever writes them.

## What to build

Make `WafBaselineBuilder` train those four metrics. The cells must match exactly what the
detectors read, in `app/waf/behavior.py` (`detect_ratio`, `detect_client_concentration_spike`,
`_Guard.baseline`, `_surprise`).

The cells are compared in two ways:
- **Expected proportion:** `cell.numerator_sum / cell.denominator_sum`, pooled over the cell's
  training buckets.
- **Seasonal score:** `robust_z(observed_proportion, cell.median, cell.mad)`, with `cell.p95` as
  the fallback when MAD is zero.

So:
- `median`, `mad`, `p05`, `p95`, `sample_count` and `is_reliable` come from
  `app.anomaly.seasonal.summarize_cell` over the per-bucket proportions.
- `numerator_sum` and `denominator_sum` are the sums over those same buckets.

**Metric table.** Define it once as `RATIO_METRICS` in `baseline.py`. Do not import
`app.waf.behavior`; it imports `baseline.py`, so that would be a cycle.

| metric | numerator | denominator | breakdown status / semantics on the bucket | uncertain values |
|---|---|---|---|---|
| `block_ratio` | `blocked` | `action_events` | `action` / `action_semantics` | `unmapped_actions` |
| `server_error_ratio` | `server_errors` | `response_code_events` | `response_code` / `response_code_semantics` | `unclassified_responses` |
| `client_error_ratio` | `client_errors` | `response_code_events` | `response_code` / `response_code_semantics` | `unclassified_responses` |
| `top1_client_share` | `top1_client_requests` | `client_events` | `client` / `client_semantics` | — |

The counts live in `EndpointObservation.counts` (`BreakdownCounts`). The statuses and semantics
live in `EndpointObservation.breakdowns` (`BreakdownStatus`). Both are in
`app/waf/observations.py`.

**Training eligibility for a ratio sample.** Keep the existing shared checks and their order:
unfinished, incompatible semantics, maintenance, … The incompatible-semantics check here compares
the bucket's breakdown semantics against the identity being trained for this metric. After the
shared checks, a bucket trains a ratio cell only when all of these hold:

1. The breakdown status is `EXACT`. `LOWER_BOUND` counts as incomplete. `NOT_COLLECTED` and
   `FAILED` are unavailable; count them under a new tally key.
2. The uncertain-value count is 0. Otherwise the numerator is only a lower bound, and training on
   it would drag the expected proportion down and make the detector over-fire.
3. The request count is exact, and `denominator / request_count >= waf_min_endpoint_coverage`.
   This is the same coverage floor the detector applies.
4. The bucket is material:
   - ratio metrics: `denominator >= waf_ratio_min_denominator`;
   - `top1_client_share`: `denominator >= waf_concentration_min_endpoint_requests`.

   A proportion over a handful of requests is noise, and the detector only judges buckets above
   the same floor.
5. The bucket is not inside a known-anomaly span (existing rule).

**Exclusion tally.** Record each exclusion in the ratio cell's tally (`exclusion_counts`). The
tally is an operator-facing contract. Add new keys only for ratio cells. A `request_count` cell's
`exclusion_counts` must stay byte-for-byte as it is today.

**Semantics.**
- A ratio cell's `metric_semantics` is the breakdown's identity, from
  `app.waf.semantics.breakdown_semantics`. It is never the request-count identity.
- The caller in `app/services/waf_pipeline.py` must pass the identities for the source's current
  profile.
- A breakdown the profile does not collect has no identity. Its metric is then not trained, and
  no cell is written for it.

**Sparse buckets.** A tracked endpoint with no row in an exact breakdown bucket has numerator 0
and denominator 0. That is immaterial, not a zero-proportion sample.

**Cost.** This must not change (design §29.5, AGENTS.md rule 9).
- Ratio cells go into the same bulk upsert as the `request_count` cells.
- Breakdown columns are selected in the same `_rows` / `source_bucket_facts` queries. Check that
  `BucketFacts.of` and `RowFacts.of` get every column they read.
- The statements per rebuild must not grow with endpoints, cells or metrics.
  `tests/integration/test_waf_scale.py` pins the per-run statement count. It must still pass with
  the same number.

## Tests to add

**Unit tests** for the pure eligibility logic. One test per exclusion reason. Also test:
- the pooled sums against hand-computed values;
- that the cell statistics are over proportions, not counts.

**Integration tests**, in a new file:
- a source with exact breakdowns trains all four metrics with the right pooled sums;
- `LOWER_BOUND`, `NOT_COLLECTED` and `FAILED` buckets are excluded and tallied;
- buckets with uncertain values are excluded;
- a semantics change is excluded;
- `request_count` cells are unchanged;
- extend `test_waf_scale.py`: the statement count is unchanged with breakdowns present.

**A guard test** that every metric in `WAF_BASELINE_METRICS` is one the builder writes
(`RATIO_METRICS` plus `request_count`). This keeps the registry from claiming an untrained metric
again.
