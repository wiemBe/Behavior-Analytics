## 1. The PW pipeline takes the per-instance collector lock

**Facts (verify them):**
- Every other collector holds `CollectorAdvisoryLock(session, settings, instance.id, <name>)`
  (`backend/app/services/locks.py`) for its run. It is non-blocking: a second worker that finds
  the lock held skips the run. Examples: `backend/app/collectors/geo_collector.py:280-285`
  (`report.skipped_locked`), and the WAF, IPS, catch-all and rule-match collectors.
- The property-watch path takes none. That path is `dispatch_property_watch_collection`
  (`backend/app/workers/tasks.py` ~L1393) → `PwInstancePipeline.run`
  (`backend/app/services/pw_pipeline.py` ~L82) → collect, evaluate, train.
- `claim_slot` stops two dispatches from claiming the *same* slot. It does not stop a tick that
  is longer than the cadence from overlapping the next slot's tick. Under D-28 (a 5-minute
  default) a tick can last that long: up to 40 searches, each allowed 120 s. Two runs would then
  collect, evaluate and train the same watches at once.

**Build:**
- `PwInstancePipeline.run` holds one `CollectorAdvisoryLock` for the instance (collector name
  `property_watch`) around the **whole** pipeline (collect → evaluate → train).
- A run that does not get the lock sends no search and writes nothing. It reports
  `skipped_locked`, which the dispatch's per-instance result carries, as the geo collector's
  does.
- The dispatch's `record_run` must not count a skipped run as `failed`. Read how the other
  families record a lock skip, and do the same.

## 2. A re-enabled watch starts fresh

**Facts (verify them):**
- The `PATCH` route (`backend/app/api/routes/property_watches.py` ~L780–863) sets
  `watch.enabled = wants_enabled` (~L825) and resets neither `collected_through` nor
  `evaluated_through`.
- The collector plans from `collected_through + step`, at most `cadence / interval +
  collection_max_backfill_intervals` buckets per tick (`backend/app/collectors/pw_collector.py`
  ~L340–365).
- So a watch disabled for a week and then re-enabled collects the disabled week from Ariel,
  bucket by bucket, and evaluates it. That takes about 14 h of ticks at a 5-minute cadence and
  about 7 days at 1 h. With alerting on, it means alerts on events days old.
- The disable already resolves the open incidents (PW-3c).
- Note `pending_buckets` (`backend/app/repositories/property_watch.py` ~L195–205): a NULL
  `evaluated_through` makes **every** stored bucket up to `collected_through` pending. So simply
  nulling both watermarks would re-evaluate the old buckets. Do not do that.

**Decision (orchestrator, 2026-10-18).** Re-enabling starts fresh, exactly as a first enable
does:
- The first tick after `enabled` turns false → true seeds at the latest closed bucket.
- The disabled period is never collected or evaluated.
- No bucket stored before the disable is evaluated again.
- New-value claims whose history window crosses the gap are `INSUFFICIENT_DATA` (incomplete
  history), which is the honest consequence (fail closed).
- Catching the gap up as learning-only history belongs to the bootstrap build (PW-13), not here.

**Build:** in the transition `enabled` false → true only:
- set `collected_through` so that the collector's existing first-run rule seeds at the latest
  closed bucket;
- set `evaluated_through` so that no stored bucket is pending.

Choose the values from the code and explain the choice in a comment. The watch version, values,
pins, baselines and detector states stay as they are. A `PATCH` that leaves `enabled` alone, or
that disables, changes no watermark. The audit row of the enable stays as it is.
