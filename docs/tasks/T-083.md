# Task T-083 — diagnose the intermittent setup ERROR in `test_migrations.py`

Read `AGENTS.md` at the repository root first and follow it exactly. This is a **diagnosis** task.
Do not change any test assertion, and do not skip, `xfail` or retry-wrap a test.

## The symptom

`backend/tests/integration/test_migrations.py::test_timescale_extension_and_hypertables` has
errored **at setup** twice, each time inside a long integration run while other pytest processes
used other databases on the same Postgres server (`localhost:5433`, image
`timescale/timescaledb:2.17.2-pg16`). It passed every time it ran alone or in a small group.
Nobody captured the error text (see `docs/tasks/G-2.report.md`, "One transient error").

A setup error means the `clean_db` fixture failed. The fixture runs
`DROP SCHEMA public CASCADE; CREATE SCHEMA public` in one transaction on a database that the
previous test upgraded to `head` (TimescaleDB hypertables and their chunks included).

Candidate causes to test. These are hypotheses, not findings; prove or rule out each with evidence:
1. **Lock-table exhaustion.** Dropping a schema with hypertables takes a lock per table and chunk,
   and Postgres's lock table is shared by every database on the server. Concurrent runs elsewhere
   could push the drop over `max_locks_per_transaction × max_connections` ("out of shared memory").
2. **A TimescaleDB background worker** (job scheduler or policy job) on the same database holding
   a conflicting lock, ending in "deadlock detected".
3. **A leaked connection** from an earlier test (an engine not disposed, or an async pool) holding a
   lock on a `public` table, ending in a lock or statement timeout.

## What to do

1. Read the fixture and the tests that run before this one in the file. Record the server's
   `max_locks_per_transaction`, `max_connections`, `lock_timeout` and `statement_timeout`
   (`SHOW ...`), and the timescaledb background-worker settings, read-only.
2. Run the file alone, 5 times, on `qradar_obs_t083`. Record the results.
3. Reproduce under load. Run the file in a loop on `qradar_obs_t083` (at least 30 iterations, or
   until the error appears) **while** a second process loads the server through
   `qradar_obs_t083b`: run the migration and hypertable-heavy integration files there in a loop
   (for example `tests/integration/test_migration_00*.py`). Capture the **full** text of every
   setup error: the exception, the SQL state, and the Postgres server log lines around it
   (`docker logs qradar-observability-test-test-db-1 --since <time>`, read-only).
4. Decide the cause from the evidence. If it is cause 1, show the lock count the drop needs
   (count the chunks and tables under the schemas the drop cascades into, just before a drop).
5. **Fix only if the cause is proven** by a captured error. The fix may change only the `clean_db`
   fixture (or a shared helper it calls) in `backend/tests/integration/test_migrations.py`, and
   only so that it cleans the database reliably; every test body and assertion stays byte-for-byte
   unchanged. Examples of acceptable fixes: drop the hypertables first in a bounded number of
   transactions; terminate other sessions on *this test database only* before the drop. Never
   change the server's configuration, the compose file, or another test file. Then re-run step 3
   with the fix (at least 30 iterations under the same load) and report the counts before and after.
   If you cannot reproduce the error, **do not fix anything**: report what you ran and what you
   ruled out.
