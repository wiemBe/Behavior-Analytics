> "ayrıca şunuda ekleyelin custom aql yazma seçeneği buna bağlı grafik oluşturması etc. ve custom

In English, the user wants three things:
1. an option to write custom AQL;
2. charts built from it;
3. custom incident logic, meaning user-written rules. Examples: "alert when this log source goes
   above this EPS", "alert when this URI gets this many requests".

The user left the "how" to the orchestrator.

## The orchestrator's decision (D-15): two tools, one alert pipeline

**F.1 — Threshold rules on data that is already collected. No AQL.** The user's two examples
read values the platform already measures in every 5-minute bucket:
- Phase A: a log source's events and EPS;
- the fleet: EPS by source class;
- Phase B: a WAF endpoint's requests and its 4xx, 5xx and block ratios;
- Phase D: IPS counts per port, destination and signature.

A rule therefore names a subject, a metric, an operator, a threshold with its unit, a sustain
(N consecutive buckets) and a recovery (M buckets back under, hysteresis), plus a severity. The
rule is evaluated in the existing pipeline tick, after collection.
- It costs **no extra Ariel search**.
- It fails closed the way the detectors do. An unmeasured bucket is INSUFFICIENT_DATA, never
  "below". A LOWER_BOUND count can prove "above" but never "below".
- Its alerts go through `AlertService`, with a new fingerprint kind and its own enum. It does
  not extend `AnomalyType` (rule 6).

**F.2 — Custom AQL, for conditions the platform does not collect** (a QID, a user, a custom
property). The backend already supports this as scheduled searches:
- stored, validated and versioned queries (`app/models/search.py`, `app/services/aql_validator.py`);
- a threshold, with the `search_threshold` alert (a truncated run never resolves it) and the
  `search_failure` alert (`app/alerts/search_alerts.py`);
- result metrics (`SearchResultMetric`);
- a POST and PATCH API behind permissions.

What is missing is the UI and the charts:
- **today `/searches` is read-only;**
- there is no editor;
- no widget plots a search's results.

Rule 4 stands. The browser never runs AQL. It submits text to be **validated and stored as a
new version**. Only stored versions run, on their cadence or through "Run now" on a stored
version. A preview is a run of a stored, disabled draft version, never of unsaved text.

## Questions the design must answer (with evidence from the code)

1. **F.1 subjects and metrics.**
   - List each one, its source table and column, its unit and its measurement.
   - State which are EXACT and which LOWER_BOUND, and what a sustained breach needs in each case.
2. **WAF admission.** Only admitted endpoints are collected (bounded per source and per bucket).
   - What does a rule on a URI that is not admitted do? Say "not collected"? Pin the endpoint
     inside the existing bounds? Reject the rule with a reason?
   - Choose, and keep rule 9: constant SQL per run, bulk loaders only.
3. **Latency.** Collection runs at the D-7 cadence (default 1 h) plus the settle delay.
   - State the worst-case alert delay per cadence.
   - Say plainly in the UI that this is not a real-time correlation engine: QRadar's own rules are
     the tool for alerting within seconds.
4. **Evaluation cost.** Rules are evaluated in bulk (one query per subject kind per tick), with a
   cap on the number of rules. Give the numbers.
5. **Lifecycle.** Does an F.1 breach reuse the incident lifecycle
   (CANDIDATE → OPEN → RECOVERING → RESOLVED) or only the alert lifecycle? Justify the choice
   against what an analyst needs.
6. **The rule preview.** "Would have fired N times in the last 24 h", drawn as the metric with the
   threshold as a line and the breaches shaded. It must come from data already collected, with
   unmeasured buckets shown as unmeasured.
7. **F.2 cost guards.**
   - a cap on enabled custom searches;
   - the minimum cadence (D-7 range);
   - `max_time_range_hours` and `max_result_rows`;
   - the existing Ariel concurrency budget;
   - who may write AQL (a permission such as `search:write`, admin by default);
   - audit of every version.
8. **The F.2 result chart.**
   - Which result shapes chart: a time series per `metric_key`, or a top-N table.
   - How `visualization_type` maps to the widget catalog, as a new configurable widget type
     with honest states: never run, failed, truncated (lower bound), stale.
   - The same chart on `/searches/[id]`.
9. **Persistence.** New tables and the migration after head `0023`, additive only. Retention.
10. **Permissions, audit and API** for both tools, matching the existing patterns.
11. **UI.**
    - Where the rule editor and the AQL editor live (navigation group, routes).
    - The validation feedback: the validator's reasons, shown inline.
    - The states each view must design (AGENTS.md §3a).
12. **Task split**, in the PLANNER's style: backend and UI tasks, each narrow, with the agent
    kind and its dependencies.
