# Task PW-10 — Phase G live validation on the lab console: collection, preview, an F.1 threshold on a pinned value, the honesty states, the real costs

Read `AGENTS.md` at the repository root first. Follow it exactly.

This is a **live validation** of Phase G (property watches) on the lab console, in **shadow mode**
(`PW_ALERTING_ENABLED=false`; the user decides separately whether alerting is turned on).
**Write no application code and change no repository file** except your report. Throwaway
scripts go only in your scratch directory. If a defect blocks a step, stop that step, document it
precisely (input, expected, observed, the code path), and move on; the orchestrator turns it into
a fix task.

**What a live run can and cannot show.** The volume detectors need reliable seasonal cells (one
sample per hour of the week per week; `pw_baseline_lookback_days` 28) and the new-value detectors
need `pw_new_value_history_days` (≥ 1 day) of complete history. A run of a few hours cannot fire
them, and seeding fabricated history would prove nothing the integration tests do not. So this
task shows the **collection, preview and F.1 path live**, and shows that every detector reports
learning / `INSUFFICIENT_DATA` honestly in that window, never `NORMAL`. A 24-hour new-value run is
a separate task if the user wants it.

## Scenario (plan in UTC, written in the report before sending anything)

- **A. The editor path through the API** (an `admin` or `detection_engineer` principal):
  `GET /property-watches/catalog`, `scope-options`, `property-options` for the chosen scope;
  create the watch (one pinned value, automatic tracking on, every detector selected); `GET
  /{id}/scope`; `POST /{id}/preview` against the real Ariel (record the generated AQL, the
  outcome, coverage, the unparsed remainder, the rows); `GET /{id}/aql`. Then enable it
  (record the enable caps and the search budget the response states).
- **B. Collection ticks, at least 6** (≈ 30 minutes of buckets at the minimum cadence): the
  generator sends a steady mix of values for the chosen scope, then raises one **pinned** value
  for ≥ 3 buckets, then lowers it. Per tick record: the buckets written, `values_measurement`,
  coverage, the unparsed remainder, admission (new values admitted / refused), the statements the
  tick issued (wrap the session with the application's statement recorder used by the scale
  tests), the Ariel time of each search, the watch status. Read the series, values and buckets
  routes after each tick.
- **C. F.1 on the pinned value:** after the pin has a `pw_value` row, create a custom rule of the
  "Property watch value" kind through the API (`GT`, a threshold between the steady and the raised
  rate, `sustain_buckets` 2, `recovery_buckets` 2). Expected: the rule reads OK during the steady
  phase, a breach opens after the second raised bucket and resolves after two recovered buckets,
  **no alert exists** (shadow), and the stored-rule preview over the same window shows the same
  interval. The watch's `threshold_rules` lists the rule; deleting the watch is refused with the
  409 naming it.
- **D. The detectors in a learning window:** every selected detector's state after each tick, and
  `/behavior/detectors`: they must read learning / `INSUFFICIENT_DATA`, never `NORMAL`, and no
  incident may open on a value without a reliable cell or a complete history. Record the
  training statement count and the rows it read per chunk (PW-3b open point).
- **E. Fail-closed checks:** (1) skip one tick and show the gap is `NOT_COLLECTED`, not zero
  (series, values, F.1); (2) one tick with `pw_max_rows_per_search` lowered in the environment so
  a search truncates: the bucket is a lower bound, values read "at least n", and no verdict reads
  the cut bucket as an absence; restore the setting.
- **F. Disable and delete:** disable the watch through `PATCH` (PW-3c: incidents and alerts
  resolve; there are none in shadow, so show the path ran and changed nothing it should not);
  detach the rule, then delete the watch; show the values went with it.
