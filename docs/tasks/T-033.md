# Task T-033 — defect: Ariel results can never report truncation

Read `AGENTS.md` at the repository root first. Follow it exactly. Background:
[`docs/SEARCH-CADENCE.md`](../SEARCH-CADENCE.md) §SC.2, and
[`docs/tasks/T-032.report.md`](T-032.report.md) Q4.

## The defect

`QRadarRestProvider.get_ariel_search_results` (`backend/app/providers/qradar_rest.py`) does the
following:
- it requests `Range: items=0-{max_rows - 1}`;
- it then sets `truncated=len(rows) > max_rows`.

The server honours the range, so `len(rows) <= max_rows` always holds, and `truncated` is **always
false**. `total_count=len(rows)` then presents a capped count as the total.

Consequences found so far:
1. **Scheduled searches** (`app/services/search_executor.py`).
   - A search capped at `max_result_rows` is recorded with `truncated = False`.
   - Its threshold is applied to the capped `total_count`.
   - The `"total"` `SearchResultMetric` stores the cap as if it were measured.
   - This breaks AGENTS.md rule 8 (fail closed).
2. **Phase A** (`get_log_source_metrics`, `max_rows = page_size * max_pages`).
   - A capped result would silently drop sources.
   - `MetricCollector` would then zero-fill them as COMPLETE silence, which means false
     `NO_EVENTS`.
3. **The mock disagrees with REST.** `MockQRadarProvider.get_ariel_search_results` reports
   `total_count=len(all rows)` and a working `truncated` flag. That is why no test caught this.

## What to do

1. **Reproduce first.** Write tests that fail on the current code:
   - a REST-provider unit test with a fake transport that honours `Range` and has more rows than
     `max_rows`; it expects `truncated is True`;
   - a test proving that a truncated scheduled-search result is currently recorded as complete.

   Run them and keep the failing output for your report.
2. **Fix the provider.**
   - Request `max_rows + 1` rows (`items=0-{max_rows}`).
   - Set `truncated = len(fetched) > max_rows`, and return `rows = fetched[:max_rows]`.
   - Define `total_count` as **the number of rows returned**, in the DTO docstring
     (`app/providers/dto.py`, docstring only), and make REST and mock agree on it. When
     `truncated` is true it is a lower bound, and every reader must treat it as one.
3. **Fix the scheduled-search path, failing closed.**
   - `execution.truncated` records the real flag.
   - When truncated, do **not** store the `"total"` metric as a measured value. Leave it absent.
     The execution row already says why.
   - When truncated, the threshold sees a lower bound:
     - for `GT`/`GTE`, a lower bound that already breaches the threshold may open or keep an
       alert;
     - a truncated result must **never** resolve an alert;
     - for any operator where a lower bound decides nothing (enumerate the operators that
       exist), there is no verdict: nothing opens and nothing resolves.

     Put this logic where the threshold is applied today (`search_executor.py` and/or
     `app/alerts/search_alerts.py`). Keep `"truncated"` in the alert evidence.
4. **Fix Phase A, failing closed.** In `get_log_source_metrics`, a truncated result raises the
   provider's existing error type. The collector already leaves its watermark on the last whole
   interval when a collection raises. Prove that no bucket rows are written and the watermark
   does not advance.
5. **Audit every other caller** of `get_ariel_search_results`, and of `.truncated` on its DTO,
   including `_run_bounded_aggregate` and the WAF, explanation and MCP providers. In your report,
   list each one: correct already (for example, it compares against its own AQL `LIMIT`), or
   fixed.
