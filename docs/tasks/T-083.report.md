## 5. Cause — **cause 2, a TimescaleDB background worker: proven**

`DROP SCHEMA public CASCADE` takes `AccessExclusiveLock` on every `public` relation; the TimescaleDB
**`Telemetry Reporter [1]` background worker** concurrently reads `public` relations with
`AccessShareLock` and reads Timescale catalog relations. Each side holds one lock and waits for the
other → PostgreSQL detects a deadlock after `deadlock_timeout = 1s`. Whichever session is chosen as
the victim gets the error: when the fixture's drop is the victim, the test errors at setup (the
symptom); when the worker is the victim, the test passes and the worker restarts.

Evidence, all captured:

1. **The error itself** names `DROP SCHEMA public CASCADE` as one side and a process with no query
   text as the other (§4.1, §4.2).
2. **23 deadlocks on the two task databases** in the server log during this task
   (`/tmp/t083/logs/server_full.txt`, dumped with `docker logs … > file 2>&1`, 300 385 lines): 11
   with the fixture's `DROP SCHEMA` as victim, 12 with the other side as victim.
3. **12 of them identify the victim by name**: `LOG: background worker "Telemetry Reporter [1]"
   (PID <victim>) exited with exit code 1` a few milliseconds after the deadlock (PIDs 126914,
   127100, 132436, 134528, 138663, 139532, 140867, 140954, 140999, 141806, 145814, 146669).
4. **3 deadlocks with the fixture as victim name the *partner***: PID `132617`, `135245` and `135499`
   each log `FATAL: terminating background worker "Telemetry Reporter [1]" due to administrator
   command` and `background worker "Telemetry Reporter [1]" (PID …) exited with exit code 1` tagged
   with the partner's own PID — the partner in a `DROP SCHEMA` deadlock is a Telemetry Reporter.
5. **The remaining partner PIDs are never client sessions.** Each of the 11 `DROP SCHEMA`-victim
   deadlocks has a partner PID (125285, 126295, 131948, 132617, 135100, 135245, 135499, 142668,
   142849, 145095, 146105) whose *only* lines in the whole server log are the TimescaleDB worker
   start-up pair `LOG: the "timescaledb" extension is not up-to-date / HINT: …`. A control proves
   that line is worker-only: a plain client session I opened on `qradar_obs_t083` (backend PID
   149165, `SELECT 1`) produced **no** log line at all, while that message appears 558 times in the
   log. Client backends also always print their SQL in the deadlock `DETAIL` (`Process …: DROP
   SCHEMA public CASCADE`), never `<command string not enabled>`.
6. **Live observation**: `recorder.py` recorded `Telemetry Reporter [1]` backends waiting in
   `Lock/relation` on `public.*` and `_timescaledb_*` relations during the fixture's drop (§4.5).
7. The load process on `qradar_obs_t083b` failed 4 of its first 99 passes with the identical
   deadlock, so the fault is not one stray connection in the subject run.

## 6. Causes ruled out

**Cause 1 — lock-table exhaustion ("out of shared memory"): ruled out, measured.**
`/tmp/t083/count_locks.py` rebuilt `qradar_obs_t083` to `head`, then ran `DROP SCHEMA public CASCADE`
inside a transaction, read `pg_locks` and rolled back:

```
relations_total: 225
tables_incl_toast: 65
indexes: 160
sequences: 0
chunk_tables: 0
hypertables: 13
locks_before: 38
locks_held_during_drop: total=1790 backends=3 our_pid=147919
locks_by_mode_during_drop: [('AccessExclusiveLock', 1781), ('AccessShareLock', 4), ('RowExclusiveLock', 4), ('RowShareLock', 1)]
relations_after_rollback: 225 (schema left in place)
lock_table_capacity: 512 locks/txn x 100 connections
```

1 790 locks against a capacity of 512 × 100 = 51 200 shared lock slots (~3.5 %), and
`grep -c 'out of shared memory'` over the whole 300 385-line server log returns **0**. Every captured
error is `DeadlockDetected`, never `LockNotAvailable`/`out of shared memory`. `lock_timeout` and
`statement_timeout` are `0`, so a timeout could not have produced the original (uncaptured) error
either.

**Cause 3 — a leaked connection holding a lock: ruled out.**
* The step-2 alone round ran with **no** other process touching `qradar_obs_t083` (load started 15:18:55,
  after that round finished at 15:15:07) and still failed once.
* In every captured deadlock the other side is not a client backend: a client backend always prints
  its SQL in `DETAIL` (see §4.4 for both sides), while these partners print
  `<command string not enabled>` and are identified as TimescaleDB background workers (§5, points 4–5).
* An idle leaked connection holds no `AccessShareLock`, and the fixture runs no query before the drop
  that could wait on one; the waits are always on relations the drop is about to take
  `AccessExclusiveLock` on, held by a process that is scanning them.
* A 60 s experiment (`probe_lock.py`) that held `AccessExclusiveLock` on every `public` relation on a
  quiet server saw nobody contending for them, i.e. no resident session keeps such locks at rest.

**Not investigated / out of scope but observed:** 13 deadlocks in the same server log belong to
other agents' databases (18579, 1409156, 18566, 11124720, 3311161, 3311169); 8 of them are
`DROP TABLE` vs `INSERT` pairs from concurrent test runs and are a different pattern.

## 7. The fix (step 5)

Only `clean_db` in `backend/tests/integration/test_migrations.py` changed; no test body, assertion,
server setting, compose file or other test file was touched.

```diff
--- a/backend/tests/integration/test_migrations.py
+++ b/backend/tests/integration/test_migrations.py
@@ -44,6 +44,42 @@ def clean_db() -> str:
     """Drop everything (including timescale-managed objects) before each test."""
     sync_url = _sync_url()
     engine = create_engine(sync_url, future=True)
+    with engine.connect() as conn:
+        # The TimescaleDB Telemetry Reporter reads `public` relations while the
+        # drop below takes AccessExclusiveLock on them, and PostgreSQL resolves
+        # the cycle as a deadlock, failing this fixture's setup. Signalled
+        # sessions are cleared first and only then waited for; pg_stat_activity
+        # does not update inside an open transaction, so every step commits
+        # before the next (docs/tasks/T-083.report.md).
+        victims = ",".join(
+            str(pid)
+            for pid in conn.execute(
+                text(
+                    "SELECT pid FROM pg_stat_activity "
+                    "WHERE datname = current_database() AND pid <> pg_backend_pid()"
+                )
+            ).scalars()
+        )
+        conn.commit()
+        if victims:
+            conn.execute(
+                text(
+                    "SELECT pg_terminate_backend(pid) FROM pg_stat_activity "
+                    "WHERE datname = current_database() AND pid <> pg_backend_pid()"
+                )
+            )
+            conn.commit()
+            for _ in range(6):
+                remaining = conn.execute(
+                    text(
+                        "SELECT count(*) FROM pg_stat_activity "
+                        "WHERE pid::text = ANY(string_to_array(:victims, ','))"
+                    ).bindparams(victims=victims)
+                ).scalar()
+                if not remaining:
+                    break
+                conn.execute(text("SELECT pg_sleep(0.05)"))
+                conn.commit()
     with engine.begin() as conn:
         conn.execute(text("DROP SCHEMA public CASCADE"))
         conn.execute(text("CREATE SCHEMA public"))
```

The drop itself is unchanged. Every other session on **this database only** is signalled before it,
and the fixture waits (at most 6 × 50 ms = 300 ms, normally one round) for the signalled PIDs to
really disappear — `pg_terminate_backend` only sends a signal, it does not wait for the process.

Why the commits: `pg_stat_activity` does not refresh inside an open transaction — measured with
`/tmp/t083/probe_snapshot.py`, where a backend killed mid-transaction stayed visible until
`COMMIT`. The first version of this fix polled `pg_stat_activity` inside one transaction, saw the
already-dead sessions forever and burned its full 5 s budget on every test (setups went from ~0.05 s
to 2.2 s each, 70 s per file run); that version was measured with `--durations` and replaced.
