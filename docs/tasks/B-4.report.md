## 2. What I did

- **Models and migration.** Columns, types, CHECKs (`visibility`, plus `schema_version >= 1`, `revision >= 1`), the `(owner_subject, name)` unique, the `updated_at DESC` index and the SET NULL FK follow UR.5.5. ORM defaults (`PRIVATE`, `1`) carry no `server_default`, because `test_migrations.py` forbids leftover server defaults other than on `created_at`/`updated_at`. Round trip and `alembic check` are clean.
- **Layout validation.** Every UR.5.5 bound; strict integers; `extra="forbid"` at both levels; unknown `type` stored as is; unknown `v` gives 422; `upgrade_layout` is the identity for v1 and raises on an unknown version. The server never reads `config` and never logs a layout.
- **RBAC.** Constants added. What each principal can do with dashboards (seeds untouched):
  - `local-dev` (no Authorization header, `admin:*`) and the seeded `admin` role (`admin:*`): everything, including sharing and editing others' SHARED dashboards.
  - `local-token` (any bearer token, `read:*`), seeded `analyst` and `viewer` (`read:*`): list and read only. They get 403 on every write, because `read:*` does not grant `dashboard:write`. **The seeded `analyst` role therefore cannot save a layout until someone grants it `dashboard:write`** (seed changes are outside this task).
  - Under the current auth all dev callers share one owner subject per mode (`local-dev`, `local-token`).
- **API.** `GET`, `POST`, `PUT /default` (declared first), `GET/PUT/PATCH/DELETE /{id}`, `POST /{id}/duplicate`, with the rulings of the spec:
  - Another owner's PRIVATE dashboard answers 404 to read, write, duplicate and default, administrators included.
  - A non-owner on a SHARED one gets 403, and an `admin:*` caller may edit it.
  - Any change of visibility needs `admin:dashboards`; restating the current value is not a change.
  - `PUT` is one `UPDATE ... WHERE id AND revision = :expected ... RETURNING`; a mismatch answers 409 with `detail: {message, current_revision}`. `PATCH` also increments the revision.
  - The list is one count, one page query and one default lookup (a test pins that the statement count does not grow with the row count), and `widget_count` is computed in SQL, so no layout body is loaded.
  - Name conflicts (create, duplicate, PUT, PATCH) and the 21st dashboard answer 409 naming the cause.
  - A per-owner advisory lock serializes inserts so the limit cannot be raced.
- **Audit.** Actions are `create`, `update` (PUT with the same name, or a description-only PATCH), `rename` (a changed name), `share` (any visibility change, both directions), `delete`, `duplicate`, `set_default`. `detail` is `{name, revision, widget_count}`, never the layout. A PATCH that changes name and visibility writes two rows. Clearing the default writes `detail {"cleared": true}` with no `object_id`. A refused write rolls back with the request and leaves no row.
