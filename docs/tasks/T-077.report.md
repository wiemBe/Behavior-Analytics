## 2. What I did
Ran 14 Ariel searches and 1 other GET through `build_provider` (REST provider) with the token and CA overrides in the process environment only. Searches used the provider's `_client` for `POST /ariel/searches` (the provider sanitises 422 bodies, so QRadar's error text is unreadable through `create_ariel_search`); status and results used the provider methods. The process ran from the repo root (not `backend/`) so `.env` supplies provider kind and host; no `.env` content was printed. No MCP, no DB writes. No generator was run (see Q2 and open points). **Headline finding: this QRadar accepts any `GEO::LOOKUP` data name, so no accepted form is proven to work. All lab data is private, loopback or TEST-NET documentation space, so every lookup returned `{}`. Whether GeoIP data exists on the appliance is NOT established by this run.**

## 3. Answers

**Q1. Accepted and rejected forms.** Every form was accepted syntactically; none was rejected by the parser (one rejection happened, caused by my own unreplaced `@` placeholders, not a QRadar function limit: `Parse error: 1:137: token recognition error at: '@'`).
Accepted (HTTP 201, search COMPLETED), all return `"{}"` on this data:
- `GEO::LOOKUP(sourceip, 'country', 'name')`
- `GEO::LOOKUP(sourceip, 'country', 'iso_code')`
- `GEO::LOOKUP(destinationip, 'country', 'iso_code')`
- `GEO::LOOKUP(sourceip, 'country', 'bogus_name')` (an invented data name: accepted, same `{}`)
- `GEO::LOOKUP(sourceip, 'country')` (two arguments: accepted, same `{}`)
- `GEO::LOOKUP(...) IS NOT NULL` in WHERE: accepted; it removed nothing (the value is never NULL here).
- `NOT INCIDR('<cidr>', sourceip)` and on `destinationip`, combined with AND/OR: accepted and effective.
Consequence: QRadar does not validate the data name at parse or run time, so a typo silently yields `{}` for every row. A collector designer cannot rely on rejection to confirm the right name; it must be confirmed with a known public address.
Not tried (budget): destinationip with `'name'`, GROUP BY alias, GROUP BY position (not needed, expression grouping worked), and other names ('iso_3166', 'country_code', 'registered_country'). Not a rejection, just untried.
Events database also exposes columns `sourcegeographiclocation`, `destinationgeographiclocation`, `geographiclocation` (VARCHAR). Grouped over 1 hour they returned only `other`/`other` (92548 events): that is the network-hierarchy location, not GeoIP, and not usable for a country map. There is also a `Remote network` custom property (not probed).

**Q2. Returns.**
- RFC 1918 (10/8, 172.16/12, 192.168/16): the string `{}` (two characters), not NULL, not empty string, not an error.
- Loopback (127/8), as source and as destination: `{}`.
- `0.0.0.0` or missing address: not observed. A search for source or destination outside private, loopback and TEST-NET ranges over 24 hours returned 0 rows, so no 0.0.0.0 and no real public address exists in the lab data. Unknown.
- Public address unknown to GeoIP: TEST-NET-1/2/3 addresses (the generator's synthetic ones, 60 distinct sources over 24 h) also returned `{}`. Same sentinel as private, so private and "unknown public" are indistinguishable by the lookup result; the filter must come from INCIDR.
- Is GeoIP populated? **Unknown.** A bogus data name gives the same `{}`, and no real public address was available. The lab generator (`tools/qradar_lab_loggen.py`, `tools/lloggen.py`) emits only documentation prefixes (192.0.2, 198.51.100, 203.0.113). `qradar_lab_loggen.py` has `--fixed-source-ip`, which could send a real public address, but that is not a documentation or synthetic address, so I did not use it (task rule, and it would put a raw real IP in lab data). No generator burst was sent.
- The sentinel `{}` is a string and must be mapped to "no country" by the collector, never to a country row.

**Q3. Shared GROUP BY with `starttime / 300000`.** Yes, accepted:
`SELECT GEO::LOOKUP(sourceip,'country','iso_code') AS "country", starttime / 300000 AS "k", SUM(eventcount) AS "events" FROM events WHERE starttime >= S AND starttime < E GROUP BY GEO::LOOKUP(sourceip,'country','iso_code'), starttime / 300000 ORDER BY SUM(eventcount) DESC LIMIT 5000 START S STOP E+300000` over one fleet-wide hour: `record_count=4` (data present in 4 of 12 buckets, one country value `{}`), not truncated at LIMIT 5000. (My reader capped fetch at 3 rows, so the `truncated=True` printed there is mine, not QRadar's.) Row count on this lab is not representative: real traffic would give up to (countries x 12) rows per hour, up to ~250 x 12 = 3000, close to a 5000 limit.

**Q4. Cost vs control.** Control (same window, `GROUP BY starttime / 300000` only): COMPLETED, record_count=4, 1.1 s. Geo keyed search: 1.1 s, 4 rows. No QRadar warning field in any response I read (search status body only checked for `error_messages` on failures). My polling granularity is 1 s, so differences below ~1 s are invisible. The only larger geo cost signal: a 24 h search with two geo expressions plus four group keys took 9.3 s (66 rows); the 24 h non-geo grouped searches took 1.1 s, but they had fewer group keys and filters, so this is not a clean comparison. Verdict: no measurable geo penalty at one hour on this lab's volume (~92k events/hour); production volume untested.

**Q5. Source or destination.** From the 24 h window, the only events with a non-private address:
- Palo Alto PA Series (devicetype 206): external address in `sourceip`, destination private. 60 distinct source/destination pairs.
- Cisco Firepower Threat Defense (devicetype 448): external address in `sourceip`, destination private. 60 pairs.
- WAF: no event with a non-private address on either field in 24 h. The lab WAF data offers no evidence for this question.
- "External" here means TEST-NET lab addresses (all 120 pairs), i.e. generator data; the direction convention is the generator's, not proven for real devices. Outbound traffic would have the external party in `destinationip`; none exists in the lab.
Implication: a collector should look up both source and destination and take the non-private one (or run two keyed searches), not assume source.

**Q6. What the run could not show.**
- GeoIP presence, data name correctness and GeoIP data age/version: need one event with a real public address and a check of the three names (`name`, `iso_code`, and a real alternative).
- `{}` is returned for both private and unknown; the private filter must be INCIDR or the collector must also treat `{}` as "no country".
- Skew: the lab is dominated by one private source (about 91.9k of 92.5k events in an hour); real data will be dominated by a few countries plus a long tail; row count scales with countries x buckets.
- Truncation: with ~250 countries x 12 buckets the 5000-row limit is close; collector must treat a truncated result as INSUFFICIENT_DATA (rule 8).
- Production dual-field lookup (source + destination) doubles the searches or needs two result sets per window.
- Duration at production volume and across 24 h of data (9.3 s observed at lab volume for a two-geo, four-key query).
- Both lookup columns must be resolvable on events that have no sourceip (e.g. non-IP DSMs): not observed.

## Follow-up (orchestrator-approved: one real public source IP)

**Bottom line: GeoIP data IS loaded. `GEO::LOOKUP` returns a JSON string, not a bare code, and ignores the third argument.**

### What I sent
- Burst 1: `--types pan_threat --eps 5 --count 400 --duration 90 --fixed-source-ip 8.8.8.8` (LEEF format; the vendor format refuses non-RFC-5737 IPs, and the generator was not changed). 400 events reached log source `pa-fw-01`, but QRadar did not map the payload `src=` to `sourceip`: `sourceip` was the syslog sender (private). So no 8.8.8.8 landed. This is the PAN DSM's LEEF handling, not a geo issue.
- Burst 2: `--types ips waf linux_firewall windows_firewall proxy dns --eps 5 --count 300 --duration 70 --fixed-source-ip 8.8.8.8`. 102 events (summed over the 24 h window) landed with `sourceip` = 8.8.8.8 (generic LEEF `src` is mapped for these profiles; the rest did not show up under that address).
- Both generators ended by themselves before I checked (PIDs 39008 and 47246; I checked with `kill -0` and issued no kill: "stopped"). No generator process is left. Nothing was started by pattern.

### Answers
(a) Yes. `GEO::LOOKUP(sourceip,'country','iso_code')` for 8.8.8.8 returns exactly this string (the same for all three forms):
`{"country":{"confidence":null,"name":"United States","iso_code":"US","geo_id":6252001}}`
The 'iso_code' form, the 'name' form and the 2-argument form all return this same whole JSON string. The third argument is ignored. The collector must extract the country from the JSON (for example a JSON extraction function in AQL, not tested here, or parse the string in Python after grouping by the full string). Grouping by the full string is stable and was accepted. Do not store the string as the key; parse it to `iso_code` and map `{}` to "no country". Earlier "data name not validated" finding is explained: the argument has no effect.

(b) Yes. In one result (24 h, 181 rows, not truncated, LIMIT 5000, ORDER BY SUM(eventcount) DESC, keyed with `starttime / 300000`, `GROUP BY sourceip` added so I could tell the rows apart, and all non-private source addresses): 8.8.8.8 rows carry the US JSON above (102 events) and every TEST-NET row carries `{}` (5331 events). Geo key and `starttime / 300000` share the GROUP BY without trouble. Duration 1.1 s. Note: this search grouped by `sourceip` as well, so it is not byte-for-byte the collector's keyed form; the keyed form without `sourceip` was already verified in the main run.

(c) Not applicable: GeoIP is loaded, so no GET was spent.

### Consequences for the collector design
- Private, loopback and TEST-NET (unknown) all return `{}`; only a parsed JSON with `country.iso_code` counts as a country. `confidence` is null and `geo_id` is a GeoNames id (6252001 = United States).
- `name` and `iso_code` come back together, so one lookup per row suffices; do not select 'name' and 'iso_code' separately.
- GeoIP data age remains unknown (no read-only endpoint was queried).
