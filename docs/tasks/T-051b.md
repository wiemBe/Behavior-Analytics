# Task T-051b — IPS detectors, part 2: persistence (migration `0021`) and the baseline builder

Read `AGENTS.md` at the repository root first and follow it exactly. These rules matter most here:
- rule 3: raw values never persist beyond what the design allows. Baselines are aggregates;
- rule 6: Phase A and WAF tables and enums stay as they are;
- rule 7: the migration is additive and round-trips cleanly; `alembic check` shows no drift **at
  head**;
- rule 8: fail closed. A bucket that is not provably whole never trains a cell;
- rule 9: per-run SQL is constant. Training scales with chunks of subjects, never one query per
  entity;
- §4: never weaken a test.

which comes after this one, adds the engine, the pipeline step and the capability status change.
Design what you build so T-051c can load it in bulk without reshaping it.

## Build

### 1. Migration `0021` (chained after `0020`) and models (`app/models/ips.py`)

Five tables:

| Table | Mirrors | Key points |
|---|---|---|
| `ips_entity_baseline` | `waf_endpoint_baseline` | FK `ips_entity_id` (cascade). `metric_name`, `weekday` 1–7, `hour` 0–23, unique on (entity, metric, weekday, hour). `median`, `mad`, `p05`, `p95`, `sample_count`, `is_reliable`, `completeness`, `observations`, `window_start/end`, `computed_at`, `baseline_version`, `excluded_sample_count`, `exclusion_counts`, `metric_semantics`, **plus `profile_version` and `normalizer_version` (NOT NULL)** |
| `ips_source_baseline` | the same, keyed by source | FK `log_source_id` (cascade). The same cell columns, plus `numerator_sum` and `denominator_sum` for the pooled metrics. One row per (source, metric, weekday, hour), with `profile_version` and `normalizer_version` |
| `ips_detector_state` | `waf_detector_state` | The subject is **either** an entity (`ips_entity_id`) **or** a source (`log_source_id`, with `ips_entity_id` NULL). A `CHECK` says exactly which, by `subject_kind` (`IPS_ENTITY` / `IPS_SOURCE`). Unique on (subject, `detector_type`). The counters and `state` are WAF's. `detector_type` is `String(40)` holding an `IpsAnomalyType` value |
| `ips_anomaly` | `waf_anomaly` | The same subject rule and `CHECK`. The WAF incident columns, including `observed_measurement`. **`fingerprint String(...) NOT NULL`**, fixed at creation and never updated (§D.10; T-052 alerts on it). Indexes as WAF (state lookup, `detected_at`) |
| `ips_anomaly_transition` | `waf_anomaly_transition` | FK `ips_anomaly_id` (cascade) |

- Plus one **evaluation watermark per IPS source**. Store it the way WAF records its evaluation
  watermark, and say in your report which existing table or new column you used and why. If
  reusing an existing watermark table would change a Phase A or WAF table, use a new IPS table
  instead (rule 6).
- `ips_entity_metric` is a hypertable. These new tables are **not** hypertables. Add none to
  `HYPERTABLES` unless a table really is a time series, and say why.
- Add the `IpsAnomalyType` values as the `CHECK` domain where WAF uses one, or follow WAF's choice
  if WAF uses no `CHECK` for `detector_type`.
- Model docstrings in the voice of `app/models/waf.py`, stating what each table holds and what it
  never holds.

### 2. `ips_anomaly_fingerprint` (`app/alerts/fingerprint.py`)

Mirror `waf_anomaly_fingerprint`: stable across runs, derived from the subject (instance, source,
dimension and `value_key` for an entity, or the source for a source detector) and the detector
type. Never from a measured value or a time. A unit test pins the format and its stability.
Nothing calls it yet except the tests. T-051c uses it at incident creation.

### 3. The baseline builder (`app/ips/baseline.py`, new)

`IpsBaselineBuilder`, mirroring `WafBaselineBuilder`:
- **Entity cells** (`entity_events`) per admitted entity, weekday × hour, over a lookback from
  settings.
  - A bucket counts for an entity only if `entity_count(...)` (T-051a) gives an **exact** count:
    a row in an `EXACT` dimension, or a measured zero under the absence rule.
  - An unknown or lower-bound count is **excluded**, and the reason is counted in
    `exclusion_counts`. A lower bound never trains (§D.7, §D.8).
- **Source cells:**
  - `top1_source_share`: pooled `numerator_sum` = Σ `top1_events`, `denominator_sum` =
    Σ `source_events`, over buckets where the source-IP dimension is `EXACT` and its coverage
    met the floor. Plus the per-bucket shares for median, MAD, p05 and p95, as WAF's ratio
    metrics do;
  - `block_ratio`: pooled blocked / action events, over buckets where the action dimension is
    `EXACT`, its coverage met the floor and `unmapped_events == 0`. A bucket with unmapped
    action values is excluded with its reason: its numerator is a lower bound. No cell is built
    when the source has no action mapping;
  - `max_distinct_ports`: per-bucket maximum, over buckets where the fan-out search is `EXACT`
    and destination-port coverage met the floor.
- **Every cell is versioned.** Train only from buckets whose `profile_version` and
  `normalizer_version` equal the source's **current** ones. Write those versions on the cell. A
  version change makes old buckets ineligible, so the cells re-learn. They are not mixed.
- **Exclusions** (counted per reason, as WAF):
  - a bucket in maintenance;
  - a bucket inside an `ips_anomaly` incident span for that subject and detector family;
  - a bucket after `train_through`;
  - a bucket of a different width.
- `is_reliable` and `baseline_min_samples` behave as in WAF.
- **Bulk, bounded:** `rebuild_entities(entities, *, train_through, …)` and
  `rebuild_sources(sources, *, train_through, …)`. Their statement count grows with **chunks**,
  never per entity. A `rebuild_due(..., limit=…)` picks the least recently rebuilt subjects, as
  WAF does.
- **Settings** (`app/core/config.py`, `ips_` prefix, each with a one-line comment in the file's
  voice):
  - lookback days;
  - rebuild batch size;
  - min samples, if IPS needs its own value; otherwise reuse the existing one and say so.
  - Map them onto `IpsThresholds` defaults only where a threshold is a baseline concern.

Not in this task: calling the builder from the pipeline (T-051c does it after the engine).

## Tests

- `tests/integration/test_migration_0021.py`, following `test_migration_0020.py`:
  - upgrade to `0021` and assert the tables, constraints (including the subject `CHECK`s) and the
    cascade;
  - downgrade to `0020` and check the tables are gone and `0020`'s are intact;
  - upgrade, then `alembic check` **at head**.
- `tests/unit/test_ips_baseline.py` (pure parts) and `tests/integration/test_ips_baseline.py`
  (builder against the DB):
  - each exclusion on its own (maintenance, incident span, `train_through`, width, version
    mismatch, lower-bound count, unknown count, unmapped actions for block ratio, coverage below
    the floor);
  - the absence rule's measured zeros **do** train, and its unknowns do not;
  - the pooled sums equal hand-computed values;
  - a profile version bump makes the old buckets ineligible;
  - **statement count** for `rebuild_entities` at two entity counts (for example 10 and 200):
    constant, or growing only with the chunk count. Reuse `recorded_statements` from
    `tests/integration/test_rule_match_collection.py`.
- The fingerprint unit test.
- Break the code on purpose for at least five guards and confirm the tests fail; list them
  (AGENTS.md §4).
- **Ruled in advance:** a migration test whose drift check upgrades to a fixed revision instead of
  `head` (for example the last one, `test_migration_0020.py`) may have **only that final upgrade**
  changed to `"head"` (the T-076 convention). Any other conflicting test: stop and report.
