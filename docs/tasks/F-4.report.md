## 2. What I did

**Cap.** `POST` with `enabled=true`, and a `PATCH` that turns a disabled search on, past `scheduled_searches_max_enabled` return 409 with `the limit is N enabled searches` (the dashboard wording). The count is one `SELECT count(*) ... WHERE enabled`. A disabled search is not counted and can still be created. Turning an already-enabled search back on does not count as a new enable. There is no advisory lock: the task asked for one query.

**Cron floor.** A new or changed `schedule_cron` must fire at least 300 seconds apart. `check_cron_floor` walks the scheduler's `CronTrigger.get_next_fire_time` from `now`. The horizon is 366 days, because a five-field cron repeats within a year, so that window includes every day-of-year at least once. The fire cap is one legal gap per 300 seconds across that horizon: `366 * 24 * 60 * 60 // 300 = 105408`. A denser schedule fails on an earlier gap, so the cap does not hide a short gap inside the window. Gaps are absolute UTC seconds. Wall-clock subtraction on the 2026-11-01 America/New_York fall-back makes `*/5` look negative; UTC keeps it at 300. A bad expression or a cron with no future fire (`0 0 31 2 *`) is 422. The 422 `detail` is a string naming the two fires and the minimum. An unchanged cron, including the same illegal string sent again, is kept verbatim. A timezone-only edit does not recheck.

**422 reasons.** Authoring failures return `{"detail": {"message": "<compatibility string>", "reasons": ["<exact reason>", ...]}}`. `reasons` is `AQLValidationError.reasons` in validator order, then the threshold sentence when it applies. `message` is the string the schema already raised: `unsafe AQL: ` plus the reasons joined by `"; "`, and the threshold sentence. Neither is paraphrased. On create, both are in one response. On update, a writer gets both once the stored row is known; a missing id with an unsafe query is still 422, and a missing id with a valid query is 404. A reader is told about an unsafe query or an unreachable create-threshold before the write check (422, as the schema validators used to). A reader's threshold-only patch, and a reader's too-fast cron, are still 403. Ordinary schema errors (missing `name`, `threshold_value: "high"`) stay FastAPI's list. The shape is in both route docstrings.

**Audit.** A patch whose only field is `enabled` ( `change_note` does not count) writes `search.enable` or `search.disable` with actor and `before`/`after`. Any other patch stays `search.update` with `version_before`/`version_after`.

**Retention.** Daily Celery task `apply_search_result_retention`, beat key `apply-search-result-retention`, schedule `search_result_retention_interval_seconds` (86400). It deletes `search_result_metric` rows with `bucket_start` strictly older than the retention, in batches, committing each batch, and stops at `search_result_retention_max_batches` with `incomplete` set. The delete matches the catch-all/geo pattern: `DELETE ... WHERE (execution_id, bucket_start, metric_key) IN (SELECT ... WHERE bucket_start < :cutoff LIMIT :batch)`. Chunk dropping is not what those tasks do. It stays the optional policy in `timescale.apply_policies`, behind `RETENTION_ENABLED` and `retention_search_result_metric_days` (default off). This task also runs when the table is a plain Postgres table.

Run-now is unchanged: stored query by id. No request AQL is executed.

## 4. Open points

- The cap count is one statement and is not locked. Two concurrent enables can both pass it.
- A short gap that exists only on a 29 February outside the 366-day window is not seen. Four years would catch it and would also walk about four times as many fires of a 5-minute schedule on every save.
- A timezone-only edit does not recheck the stored cron, including a legacy every-minute cron moved to `America/New_York`.
- Saving `*/5` walks 105408 gaps. That is about a second per save. Hourly is much smaller. The check runs only for a caller who may write, and only when the expression is new or changed.
- Retention tests use `Base.metadata.create_all`, not a Timescale hypertable. The batch delete is the same SQL either way. The optional chunk policy was left as it is, off by default.
- A reader who sends an unsafe query is answered before the write check, so that 422 does not also carry the threshold sentence. A writer who sends both gets both reasons in one 422.

### What changed

Inside one UTC offset the wall-clock pattern maps linearly onto real time, so a short gap is one of three things. Consecutive fires on one allowed day come from the hour and minute sets (at most 1,440 values). The gap from the last fire of an allowed day to the first fire of the next is linear only when both days are stable and every day between them shares that offset. A local day whose offset changes, or whose next midnight is not exactly one UTC day later, is not mapped: `CronTrigger.get_next_fire_time` is walked until the next stable fire whose UTC instant matches the map. That window is the unstable day plus the walk out of it, which is wider than a few hours around the transition, because a transition on a day that does not itself fire can make CronTrigger skip the next matching date. If the expression is not on second 0, or the first fire disagrees with the map, the original fire-by-fire walk runs for the whole horizon. Day-of-month and day-of-week still come from the trigger's own fields (Monday is 0, and both must match).

The synchronous check is under the 50 ms budget. Create and update still run it with `asyncio.to_thread` (`ScheduledSearchService._refuse_fast_cron`), so that CPU is not on the event loop. The cost test calls `check_cron_floor` directly and does not include the thread hop. An unchanged cron, including a timezone-only edit, is still not rechecked.

POST `/searches` and PATCH `/searches/{search_id}` still take `body: dict[str, Any]`, so an authoring failure stays the reasons object. Each route sets `openapi_extra` to the `ScheduledSearchCreate` or `ScheduledSearchUpdate` JSON schema, with `$ref`s inlined (a nested `#/$defs/...` would point at the document root) and `additionalProperties` false.

The fourth open point above, that saving `*/5` costs about a second, is closed for the schedules measured here.
