# Task B-2.3 — `GET /anomalies/histogram`: anomaly counts per UTC hour and severity

Read `AGENTS.md` at the repository root first and follow it exactly. Backend only: no frontend
file. The route is `GET` and writes nothing.

## Why

The Home's "Anomalies by severity" chart (`frontend/src/lib/home/severityPerHour.ts`) counts per
UTC hour and severity from `GET /anomalies?since&until&limit=200`. Above 200 anomalies in the range
the list is capped, so the chart can only say "Truncated: first 200 of 345" and every count is a
lower bound. `docs/UI-REDESIGN-PLAN.md` UR.7 lists this task (B-2.3): "Counts by severity per hour
for a range; removes the 200-row cap". A follow-up UI task will switch the chart to it.

## The route

`GET /api/v1/anomalies/histogram?since=&until=&subject_kind=`, on the existing anomalies router
(so `read:anomalies` guards it). **Declare it before `/{anomaly_id}`**, or `histogram` is parsed as
an id; pin that with a test.

- `since` and `until` are **required** (timezone-aware ISO instants; `until > since`). The range is
  at most **7 days** (168 hours; beyond that it is not an hour chart): `422` naming the limit. It
  must also respect `api_max_range_days` (reuse `_validate_range` in
  `backend/app/api/routes/anomalies.py` for that part).
- `subject_kind` is optional, with the meaning it has on `GET /anomalies`: it selects which
  anomaly families are counted, through the repository's existing `_applicable_kinds`.
- **The population is exactly the list's**: an anomaly is counted in the hour that contains its
  `detected_at`, when `since <= detected_at < until`, over the same families `GET /anomalies` would
  return for the same `since`, `until` and `subject_kind` (today Phase A and WAF; IPS joins when
  task T-085 lands). Every state is counted (the list's default, no `active_only`).
- The hours run from `since` floored to the UTC hour through the hour containing `until - 1 µs`,
  and **every hour in that span is present** in the response, in order. Because the count is
  complete (no cap), an hour with no anomaly is a **measured zero** here, unlike the capped list.
- Response (a new schema, e.g. `AnomalyHistogramOut`):
  ```json
  { "since": "...", "until": "...", "bucket_seconds": 3600,
    "families": ["LOG_SOURCE", "WAF_ENDPOINT"],
    "total": 345,
    "hours": [ { "start": "2026-10-14T13:00:00Z",
                 "counts": { "CRITICAL": 1, "HIGH": 4 }, "total": 5 } ] }
  ```
  `counts` has an entry for each severity with a non-zero count (or every severity with zeros:
  choose one, state it in the schema's docstring, and test it). `families` lists the families
  actually counted, so a client knows what the totals cover.
- **One SQL statement per request**, whatever the range and the number of anomalies: a `UNION ALL`
  of one `GROUP BY` per family over `date_trunc('hour', detected_at)` and `severity`, gap-filled in
  Python. Pin it with a statement-count test at two data sizes.

## Tests

- Unit: the gap-filling and hour-span function (mid-hour `since`, `until` on an hour boundary,
  a range of exactly 168 hours, one hour past it).
- Integration (`tests/integration/test_anomaly_histogram.py`, new): Phase A and WAF anomalies mixed
  across hours and severities, totals equal to `GET /anomalies`'s `total` for the same range (assert
  it against the list endpoint); `subject_kind` filtering; the half-open boundaries (`detected_at ==
  until` excluded, `== since` included); an empty range is all measured zeros; the 7-day and
  `api_max_range_days` limits; missing `since`/`until` is `422`; `/anomalies/histogram` is not
  captured by `/{anomaly_id}`; one statement at two data sizes; `read:anomalies` required.
- Break at least five guards on purpose, confirm a test fails each time, restore, list them.
