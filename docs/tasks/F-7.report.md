## 2. What I did

Both routes sit on the router's existing `read:searches` dependency. Neither calls Ariel or writes a row.

`GET /searches/{id}/metric-keys?limit=` (default 200, max 1,000) returns distinct `metric_key`s with `point_count` and `last_bucket_start`. `total` is ordered first when it exists, then last bucket descending. `total` in the payload is the distinct count before the limit. An unknown search is 404 `search not found`.

`GET /searches/{id}/latest-groups?limit=` (default 50, max 500) returns the grouped rows of the latest execution that stored rows, ordered by value descending, with that execution's id, start, status, and `truncated`. `values_are_lower_bounds` is true when the execution is truncated, so the UI can show "≥ n". No execution answers 200 with `empty: "no_execution"`. Executions with no stored rows answer 200 with `empty: "no_rows"`. `total` is the row count before the limit.

`ResultTrend` is the one component on the search page and in the widget.

- `LINE` and `BAR` draw one `metric_key`. The y-axis is "Result rows" and the x-axis is "Time (UTC)". A truncated run is a null gap (`connectNulls: false`), and a missing count is left as a gap.
- `SINGLE_VALUE` shows the latest measured total and its UTC time. A truncated latest run shows "≥ n" and "Threshold: no verdict".
- `TABLE` shows the latest run's rows, highest value first, display-capped. A stored `PIE` or `HEATMAP` uses that table and says so.
- The metric control is a `<select aria-label="Metric">` filled from `metric-keys`.
- States: loading ("Loading result trend…"), never-run (creation time and how to run it), truncated, stale (last success older than twice the schedule interval derived from `last_run_at` and `next_run_at`, with the age), error (`runReadout`, consecutive failures against 3, and what to do), and forbidden (names `read:searches` and that an administrator grants it).

The widget's `range` is null, so `registryRange.test.ts` stayed untouched. `ResultTrend` calls `useEffectiveRange`, and the widget sets `honourRange`, so the dashboard range is sent as `start`/`end` on `/results`. The groups table has no range parameter; the widget says the dashboard range does not filter it.

A widget whose search returns 404 says "This search was deleted." and offers Configure when the dashboard supplies it.

`useInView` is absent from this branch, so the widget is created the same way as the other chart widgets. Nothing extra was added for lazy creation.

The registry source strings use `` `/searches/${id}/results` `` (and the same form for the other search reads). The source-string test requires that template in `api.ts`. The OpenAPI paths are `/searches/{search_id}/...`. They are the same routes.

The OpenAPI 403 parametrization covers mutating methods. A read-only token holds `read:*`, so these GETs are allowed under the existing mount. 401 is the catalogue test; the new unit test pins both paths in that catalogue.

`registry.test.ts` is outside the allowed-file list. The live widget list is an exact equality, so inserting `chart.search_results` required that one line. No other out-of-list product file was edited.
