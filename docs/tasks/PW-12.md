# Task PW-12 — Design: a learning-only history bootstrap for property watches (D-27)

Read `AGENTS.md` at the repository root first and follow it exactly. §2 is binding for every
design choice: read-only against QRadar, AQL only on the REST provider, aggregates only, fail
closed, constant per-run SQL cost. Then read decision **D-27** (and D-28) in `docs/PLANNER.md` §4.

**This is a design task. Write no code and no test, and change no file except the two named
below. Do not contact QRadar.** Where a fact can only be known from the console, write the probe
that would establish it (the AQL or the REST GET, how many requests, what each answer means).
The orchestrator runs those probes as a separate task.

**Why (the user, 2026-10-18 ~17:15).** The user cannot leave the machine on for 24 hours.
Today a watch learns forward only: §G.5 says the "first run seeds the watermark at the latest
closed bucket and replays no history" (`docs/PHASE-G-PROPERTY-WATCH.md` ~L530), and §G.15 says
"No backfill". So:
- the new-value detectors cannot judge anything until `pw_new_value_history_days` of complete
  history exists (default 7, minimum 1, `backend/app/core/config.py:671`);
- the volume detectors need reliable weekly seasonal cells over `pw_baseline_lookback_days` (28).

QRadar already stores the past events. On the lab, PW-10's first probe found the six lab users
on source 212 over the last 30 days. **D-27:** when a watch is enabled, it reads its history from
Ariel once, in bounded searches, **for learning only**. A bootstrapped bucket is never evaluated
and never opens an incident, an F.1 breach or an alert. This respects the rule in
`docs/SEARCH-CADENCE.md` §SC.6 that "an upgrade must not replay history into alerts". The goal:
a new watch detects from day 1, and the lab shows new-value detection in about an hour.

## Deliverable

1. **A new design file, `docs/PHASE-G-HISTORY-BOOTSTRAP.md`**, in the voice and density of
   `docs/PHASE-G-PROPERTY-WATCH.md`. Number its sections §H.0, §H.1 and so on. Each decision must
   cite the code line or design section it rests on. It must answer each item below, and decide
   each one; where you cannot decide, it becomes an open question with your recommendation.
   - **H.0 What the user asked**, and what the bootstrap is not:
     - not an evaluation of the past;
     - not an alert on old events;
     - not fabricated history.
   - **H.1 Per detector:**
     - what history it needs (PW_NEW_VALUE, PW_VALUE_DISAPPEARED, the spike and drop detectors,
       PW_NEW_COMBINATION);
     - what the bootstrap gives it, and what it still cannot know;
     - F.1 threshold rules: do they read bootstrapped buckets, and if not, why not?
   - **H.2 Learning only:**
     - how a bootstrapped bucket is marked, for example its provenance;
     - how evaluation, incidents, F.1 and alerting provably never read it as a pending bucket;
     - how `evaluated_through` and `collected_through` start;
     - the hand-off: zero gap and zero overlap between the last bootstrapped bucket and the first
       live one, including a tick that runs while the bootstrap is half done.
   - **H.3 The window:**
     - how many days, per setting;
     - the bounds: `pw_metric_retention_days` 35, the config validators ~L931–940, Ariel's own
       retention.
     - **How the design knows, read-only, how far back Ariel really holds this scope's events.**
       A totals search that returns 0 for a bucket is silence *or* aged-out data. Telling them
       apart is the central fail-closed question: a bucket that cannot be proved held is not
       complete history. Give the probe.
   - **H.4 The searches:**
     - the AQL shapes, reusing GROUPED, TOTALS and PINNED over wider windows where possible;
     - chunking by rows (values × buckets ≤ `pw_max_rows_per_search`), truncation and its
       split, `START`/`STOP`;
     - how bootstrap searches share the per-tick budget with live collection (live first);
     - a cost table for a 6-value watch and a 200-value watch over 1, 7 and 28 days: searches,
       estimated Ariel time from the measured numbers, ticks to finish;
     - the D-28 5-minute default cadence.
   - **H.5 State:**
     - new columns or a new table (additive migration);
     - progress that resumes after a failure or a restart;
     - what a watch edit (`watch_version`), a disable, a delete, a scope change or an inventory
       re-sync does to a bootstrap in progress;
     - an existing enabled watch at upgrade: does it bootstrap the history before its first
       bucket? Decide.
   - **H.6 Fail closed, in one table**, in the style of §G.12. It must cover:
     - the retention gap;
     - a property that did not parse in old events (coverage below `pw_min_coverage`, so
       PARTIAL, so the history is incomplete);
     - a truncated or failed chunk;
     - today's scope membership applied to the past (a limitation to state);
     - the admission caps hit during the bootstrap;
     - a source that did not exist yet.
   - **H.7 Values:**
     - admission during the bootstrap (`pw_max_new_values_per_bucket`,
       `pw_max_active_values_per_watch`, `pw_min_admission_events`), and which values win when
       the cap binds;
     - `first_seen_at` / `tracked_since` from history;
     - retirement (`pw_value_active_days`) when the bootstrap reads old values;
     - pins.
   - **H.8 Training:**
     - how 2,016 or 8,064 buckets train without breaking AGENTS.md rule 9, which keeps the
       statements per chunk constant (PW-3b, PW-3c);
     - when the seasonal cells become reliable after a 28-day bootstrap.
   - **H.9 API and UI:**

     - what the investigation view and the PW-9 widget say during and after the bootstrap.
     - This follows `docs/PRODUCT-UX-GUIDELINES.md`; read §4, §6 and §8.
   - **H.10 Settings:** names, defaults, bounds and a kill switch (off by default, or on? Decide
     and say why).
   - **H.11 Migration** (additive, round trip).
   - **H.12 The lab demonstration:** a live run of about 1 hour that shows a new value judged

   - **H.13 The build, split into tasks**, each with its size, files, dependencies and tests.

   - **H.14 Open questions for the user:** only the ones that are genuinely theirs, each with a
