# Task T-067 — audit: wall-clock time bombs in the backend tests (report only)

Read `AGENTS.md` at the repository root first. **This is a read-only audit. Change no file**
except your report.

## Why

On 2026-10-13 two integration tests started failing at 09:15 UTC, though nothing in the code had
changed (T-066 and the T-049 follow-up). Each test seeded a timestamp from a fixed constant
(`NOW = datetime(2026, 10, 13, 9, 0, tzinfo=UTC)`). The code under test then compared it with the
**real clock** (`datetime.now(UTC)`, a service built without an injected clock, or the database's
`now()`) against a window or timeout. So once the real time passed `NOW` plus the window, the
outcome flipped. The same pattern can hide anywhere else in the suite, set to go off days or weeks
from now: retention, staleness, maintenance windows, cooldowns, pending timeouts, "last N days",
and so on.

## Method

1. In `backend/tests/`, find every module-level fixed timestamp constant:
   `grep -rn "datetime(20[0-9][0-9]," backend/tests | grep -E "^[^:]+:[0-9]+:[A-Z_]+ *="`, plus any
   others you notice.
2. For each test that uses such a constant **and** calls code that reads the real clock, decide
   whether the outcome depends on the gap between the constant and the real time. Code reads the
   real clock through `datetime.now(`, `utcnow`, `time.time(`, SQL `now()` or `CURRENT_TIMESTAMP`,
   or a service whose `clock` parameter the test does not pass. Read the code under test, under
   `backend/app/`, to see where the real clock is read and what window it compares against.
3. Classify each finding:
   - **BOMB:** the test will fail once the real clock passes a computable date. Give that date.
   - **LATENT:** the test depends on the real clock but has no deadline. For example, it would
     only fail if the clock went backwards.
   - **SAFE:** the code under test receives an injected clock or the constant everywhere.

   Only list BOMB and LATENT findings in detail. Give a count of the SAFE ones.

## Report

Write `docs/tasks/T-067.report.md`. For each BOMB or LATENT finding, give:
- the file, the test name and the line;
- the constant;
- where the code under test reads the real clock (`file:line`);
- the window;
- the date it goes off (for a BOMB);
- a one-line suggested **setup-only** fix (never an assertion change).

End the report with the total count of tests examined. Do not edit any test. Do not commit.
