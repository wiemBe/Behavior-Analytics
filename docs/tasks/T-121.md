## Why

OPS-2 resolved hashed locks for **Python 3.12**, the interpreter of the image and of CI. Every
local gate so far ran on the host venv: Python 3.14 with SQLAlchemy 2.0.51 and mypy 2.3.0. On
the 3.12 lock (SQLAlchemy 2.1.4, mypy 2.3.1), integration passes 1,286/0, but:

1. **TLS posture differs by interpreter.** `ssl.create_default_context()` sets
   `VERIFY_X509_STRICT` and `VERIFY_X509_PARTIAL_CHAIN` only from Python 3.13. So the shipped
   image verifies QRadar without strict RFC 5280, while dev, tests and the lab validations ran
   with it. `tests/unit/test_tls_and_credentials.py::TestSSLContext::test_strict_rfc5280_is_on_by_default`
   and `::test_allow_missing_aki_clears_only_strict` fail on 3.12.
2. **mypy reports three errors** on the lock:
   - `app/repositories/anomaly.py:423`: an unused `type: ignore`;
   - `app/custom_rules/loaders.py:224`: variadic tuple unpacking requires a star target;
   - `app/custom_rules/engine.py:236`: `None` assigned to a variable typed `CustomRuleBreach`.
   CI now runs `mypy app` without `|| true`, so CI is red until they are fixed.
3. **The image installs the package non-editable** (`pip install --no-deps .`). That puts a
   second copy of `app` into site-packages. Any entry point that imports that copy looks for
   `VERSION` (OPS-1, `app/core/version.py`: one level above the `app` package) and for
   `alembic.ini` (the doctor, `Path(__file__).parents[2]`) inside site-packages, and fails.
   The comment's reason, "the image must not depend on a writable source tree", does not hold,
   because an editable install never writes to the tree.
