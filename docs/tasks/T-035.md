## What is wrong today

There are two problems:
- `MetricCollector` runs **one Ariel search per 5-minute bucket**.
- `evaluate_anomalies` calls `AnomalyEngine.evaluate_latest`, which judges only the **newest**
  bucket per source.

If Phase A ran once an hour, 11 of 12 buckets would never be judged. The hysteresis counts
(`anomaly_open_after_intervals` and `anomaly_resolve_after_intervals`) also assume one call per
bucket.

## Build

### 1. Provider: one keyed search for many buckets

Add `get_log_source_metrics_bucketed(window_start, window_end, *, bucket_seconds, max_rows)` to
the provider interface (`app/providers/base.py`), and implement it in the REST provider and the
mock.

**Shape:**
- It returns a DTO with:
  - the per-bucket `LogSourceMetricSample` lists, keyed by bucket start;
  - `truncated`;
  - `rows_returned`;
  - the AQL text.
- It is read-only. Add no write method to the provider (AGENTS.md rule 1).

**REST AQL:**
- It is today's `get_log_source_metrics` query with the following added:
  - `starttime / {bucket_ms} AS "k"` in `SELECT`;
  - `GROUP BY logsourceid, starttime / {bucket_ms}`;
  - `LIMIT {max_rows + 1}`.
- Keep the half-open `WHERE` and `START`/`STOP` exactly as today. T-032 Q1 and Q3 proved this
  form.

**Fold:**
- Put it in a **pure function** in a new module `app/collectors/bucketed_metrics.py`. It maps rows
  to buckets with `bucket_start = k * bucket_ms` (epoch UTC).
- **Any `k` outside the window, or a non-integer `k`, fails the whole search.** Raise the
  provider's existing error type. Never drop the row silently.
- `average_eps`, `last_event_at` and `event_delay_seconds` per bucket must be computed exactly as
  `get_log_source_metrics` computes them today, with that bucket's own end.

**Truncation and validation:**
- More than `max_rows` rows means `truncated = True`. That covers both the AQL `LIMIT` and the
  T-033 one-past-the-cap read.
- The window must be a whole number of buckets, aligned to the epoch. Reject anything else.
- Keep the 168-hour safety bound.

**Mock:** the mock implements the same method from its existing per-interval generator. Its
per-bucket output must be identical to calling its `get_log_source_metrics` once per bucket.

### 2. Collector: one search per tick, split on truncation

In `MetricCollector.collect`, replace the per-interval loop.

**The window:**
- From the first uncollected bucket after the watermark, up to `current_boundary`, exactly as
  today's `_intervals_to_collect` decides.
- Cap it at `cadence_buckets + collection_max_backfill_intervals` buckets. Here
  `cadence_buckets = cadence_seconds // collection_interval_seconds`, with the cadence read
  through `SearchCadenceService.get(SearchFamily.PHASE_A_VOLUME)`.
- The first run (no watermark) is unchanged: only the most recent complete bucket.

**The search:**
- Collect the window with **one** bucketed search, with
  `max_rows = settings.ariel_multi_bucket_max_rows`. This is a new setting, default 5000,
  `ge=1, le=100000`.
- **If it is truncated, keep nothing from it.** Split the window into two halves of whole
  buckets, and search each half, recursively.
- **A single bucket that is still truncated** is a provider error for that bucket. Do this the
  way T-033 made `get_log_source_metrics` raise. Nothing is written for it, and the watermark
  stops before it.
- Cap the searches of one `collect()` call at `settings.search_cadence_max_searches_per_tick`.
  This is a new setting, default 16, `ge=1, le=256`.
  - On reaching the cap, stop.
  - Keep the buckets of every **complete** search, but only the **contiguous** run from the
    start of the window.
  - Leave the watermark at the last contiguous complete bucket.

**Writing:**
- Write each kept bucket through the existing upsert and the **existing zero-fill**. A monitored
  source with no row in a bucket gets its explicit COMPLETE zero row, exactly as today.
- Advance the watermark only past contiguous complete buckets.

**Provenance:** keep every existing provenance key. Add these:
- `search_window_start` and `search_window_end`;
- `search_bucket_count`;
- `bucket_key` (the literal expression);
- `split_depth`.

**Report:** `CollectionReport` gains:
- `searches_sent`;
- `splits`;
- `buckets_collected`, which is the existing `intervals_collected` semantics, kept.

**The equivalence bar (design §SC.5.4).** For any window, the `log_source_metric` rows this path
writes must equal, column for column, what the old per-interval path writes for the same buckets
and the same provider data. That includes the zero-filled rows. Only these may differ:
`query_provenance`, `collected_at`, `collection_duration_ms` and `watermark_at`. Prove it with
a test that runs both paths over the mock for at least 24 buckets, several sources, and at
least one silent monitored source. If the old path has to stay callable for that test, keep it
as a private helper; nothing in production may call it.

### 3. Evaluation watermark: judge every new bucket, in order

**Migration `0014_anomaly_evaluation_watermark.py`** (`down_revision = '0013'`). Table
`anomaly_evaluation_watermark`:
- `log_source_id`: PK, FK to `log_source.id`, `ON DELETE CASCADE`;
- `evaluated_through`: `DateTime(tz)`, NOT NULL;
- `updated_at`: `DateTime(tz)`, NOT NULL.

It is additive, and leaves the Phase A tables as they are (AGENTS.md rule 6). Add the model next
to the other monitoring models.

**`AnomalyEngine.evaluate_pending(log_source)`:**
- It evaluates every `log_source_metric` row with `bucket_start > evaluated_through`, in
  ascending order, each through the existing `evaluate_interval`.
- After each bucket, it advances the watermark to that bucket.
- It is bounded per call by `settings.anomaly_max_buckets_per_evaluation`. This is a new setting,
  default 120, `ge=1, le=10000`. The rest waits for the next run.
- **First run (no watermark row):** evaluate only the latest bucket, exactly as `evaluate_latest`
  does today, and seed the watermark to it. An upgrade must not replay history into alerts.
- A source with `monitoring_enabled = False` keeps today's behavior: a skip.
- `evaluate_latest` stays, unchanged, for any other caller. Production `evaluate_anomalies`
  switches to `evaluate_pending`.
- **Fail closed:** an exception while evaluating one bucket stops that source's loop. Its
  watermark stays before the failed bucket, and the next run retries it. Never skip a bucket
  silently.

## Tests (pin every guard and exit path)

**Fold:**
- keys map to bucket starts;
- a `k` outside the window raises;
- a non-integer `k` raises;
- per-bucket `average_eps`, `last_event_at` and delay equal the per-bucket query's values.

**REST provider** (fake transport):
- the AQL contains the key, `GROUP BY`, `LIMIT n+1`, `WHERE` and `START`/`STOP`;
- `n+1` rows mean truncated;
- `n` rows mean complete;
- a misaligned window is rejected.

**Collector:**
- the equivalence test (§2);
- one search for 12 buckets;
- truncation splits, and the split windows cover the whole window with no overlap;
- a single-bucket truncation writes nothing and holds the watermark;
- the per-tick search cap keeps only the contiguous complete prefix;
- an 8-hour cadence collects 96 buckets in one search when they fit;
- the backfill cap counts beyond the cadence.

**Evaluation:**
- 12 new buckets are judged in order. A spike in bucket 3 of 12 opens per the hysteresis, which
  the old latest-only path would have missed.
- `NO_EVENTS` still fires on zero-filled buckets.
- First run judges only the latest bucket and seeds the watermark.
- The per-run bound is respected.
- An exception holds the watermark before the failed bucket.
- A source with monitoring disabled is skipped.

**Gate:**
- not due means no provider is built and no search is sent;
- due means `record_run` gets the real counts.
