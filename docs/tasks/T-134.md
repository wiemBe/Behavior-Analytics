# Task T-134 — The default search cadence becomes 5 minutes for every family (D-28)

Read `AGENTS.md` at the repository root first and follow it exactly: §2 rule 7 (migrations), §3,
§3a for the one frontend change (screenshots are part of acceptance), and §4 (tests). Then read
`docs/SEARCH-CADENCE.md` (all of it) and decision **D-28** in `docs/PLANNER.md` §4.

**Why (the user, 2026-10-18 ~17:15):** "5 min default everywhere". It replaces D-7's 1 h. The
cadence decides only **when** a family searches QRadar. It never changes the bucket width (5
minutes, `collection_interval_seconds`) or any learning period (§SC.1). The user chose this
knowing that each tick costs about the same whatever its window, so the default Ariel search
count per family rises about 12×.

## Facts from the code (verify each before you rely on it)

- The presets are `SearchCadence` in `backend/app/models/enums.py:111` (300 … 28800). There are
  eight families (`SearchFamily`, `enums.py:100`).
- The seed rows are inserted at 3600 with `updated_by` NULL by migrations `0013` (four families),
  `0018` (IPS), `0020` (CATCHALL_SENDERS), `0022` (GEO) and `0026` (PROPERTY_WATCH). **These
  migrations are on `main`: never edit them.** The head is `0027`.
- `SearchCadenceService.set_cadence` (`backend/app/services/search_cadence.py` ~L100–130) sets
  `updated_by = actor` and writes a `search_cadence.update` audit row. So a row with `updated_by`
  NULL has never been set by an operator.
- The 1 h default is hard-coded in `claim_slot` (the restore of a missing seed row, ~L72) and in
  `_missing_default` (~L181) as `SearchCadence.ONE_HOUR`, and in `backend/app/cli/doctor.py`
  ~L502–510 as `cadences.get(<family>, 3600)` fallbacks.
- A new scheduled search starts with `DEFAULT_SCHEDULE_CRON = "0 * * * *"`
  (`frontend/src/components/searches/authoring.ts:27`).

   `backend/app` for any other place that assumes a 1 h default cadence, and fix or report each
   one.
2. **Migration `0028`** (new file, additive, data only).
   - **Upgrade:** `UPDATE search_cadence SET cadence_seconds = 300, updated_at = now() WHERE
     cadence_seconds = 3600 AND updated_by IS NULL`. For each row it moves, write one `audit_log`
     row: action `search_cadence.update`, actor `system:migration-0028`, object
     `search_cadence`/`<family>`, detail `{"old": 3600, "new": 300, "reason": "D-28 default"}`,
     outcome `SUCCESS`. A row an operator set is never touched, even if it is 3600.
   - **Downgrade:** the exact reverse for rows with `cadence_seconds = 300 AND updated_by IS
     NULL`, audited the same way (`"reason": "downgrade of 0028"`). **Never delete an audit row.**
   - `upgrade → downgrade → upgrade` must run cleanly, and `alembic check` must report no drift.
3. **A fresh install gets 300 for every family:** the seeds insert 3600, then `0028` moves them.
   Prove it with a test that upgrades a fresh DB to head and reads all eight rows.
4. **Per family, check that a 5-minute tick is correct, not just cheaper or dearer.** Read each
   family's dispatch and collection path:

     GEO_COLLECTION;
   - ANOMALY_EXPLANATION: are the searches per open anomaly per tick, or once per anomaly?
   - RULE_MATCH: windows are `rule_match_window_seconds`, default 3600. At a 5-minute cadence, is
     a window that is not yet complete searched again on each tick?
   No family may search a window or bucket it has already collected completely, merely because
   it ticks more often. If one does, **stop and report it** with the code path. Do not redesign
   it.
5. **Frontend:** `DEFAULT_SCHEDULE_CRON` becomes `"*/5 * * * *"`. An existing scheduled search
