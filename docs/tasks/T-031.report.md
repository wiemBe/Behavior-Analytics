## 2. What I did

- **New permissions.** Both constants live beside their read counterparts in `rbac.py`. `read:*`
  expands to `read:*`, not `rule:write`/`coverage:write`, so a read-only principal cannot satisfy
  either.
- **Guard first, 403 before 404.** Both handlers call `_guard(...)` as the first statement, before
  the rule/instance lookup. Tests assert an unknown rule id yields 403 for a `read:*` principal, and
  that no row changes and no audit row is written.
- **Audit.** `PATCH /rules/{id}` and `POST /coverage/mappings` were not audited before; both now
  record an audit row with `actor=principal.subject`, `object_type`, `object_id` and `detail`.
- **Seed.** `admin` and `analyst` hold both permissions; `viewer` holds only `read:*`. The
  existing-role merge is still additive (adds missing permissions, removes none).
- **Guard test.** `_READONLY_MAY_MUTATE` is now an empty set with its `pytest.skip`; the guard test
  proves 403 for a read-only principal on both routes.

## 4. Open points

- **Frontend premise.** The task states `api.ts` calls `PATCH /rules/{id}`; it does not in this
  worktree (only `GET /rules/${id}`). Reported rather than reconciled, since the task says not to
  change frontend code.
- **`test_route_auth_guard.py` comment.** The task said "do not change anything else". I removed the
  two allowlist entries and also rewrote the `# KNOWN GAP ...` comment that existed solely to
  document those two entries; leaving it would have asserted a fix was still pending. The set, its
  skip and every other line are untouched. Flagging the one-line judgment call.
- **Redaction masks UUIDs in audit detail.** `redact()` masks any 24+ char token-shaped string, and
  `_IDENTIFIER_KEYS` exempts only `correlation_id`/`instance_id`. So `detail={"rule_id": <uuid>}`
  would persist as `***redacted***`. I therefore kept the coverage audit detail to
  `technique_id`/`confidence`; the mapping row itself carries `rule_id`. A follow-up could add the
  `*_id` audit keys to `_IDENTIFIER_KEYS`, but `app/security/redaction.py` is outside this task's
  file list so I did not touch it.
- **Handler-level guard ordering.** Body validation runs before the handler, so a forbidden caller
  who sends an invalid body gets 422 rather than 403. This is inherent to the `log_sources.py`
  pattern the task mandated; the router-level `read:*` guard still yields 403 for an unauthenticated
  or unrelated principal.
- **Seed roles are not unit-tested.** There is no existing seed test in `tests/`, and the task named
  only the rules/coverage test modules, so I did not add one; the seed change is a data-only,
  additive edit.
