# Task T-085 — the IPS analyst read API (Phase D §D.11.2, backend)

Read `AGENTS.md` at the repository root first and follow it exactly. Backend only: no frontend
file. Every route is `GET`; nothing writes to QRadar or to the database.

## Why

IPS detection is built (Phase D, migrations `0017`, `0018`, `0021`; alerting T-052), but an analyst
cannot see an IPS anomaly anywhere: `GET /anomalies` unions only Phase A and WAF, the detail route
falls back only to WAF, and every `/ips/*` route is profile administration behind `admin:ips`.
`docs/PHASE-D-IPS-BEHAVIOR.md` §D.11.2 calls for the analyst view "with the WAF analyst API and UI
(design §27.14–§27.15), one subject model". This task builds its API half.

## Build

1. **Subject model.** Add `IPS_ENTITY` and `IPS_SOURCE` to `SubjectKind` (a response enum, never
   persisted). Add an additive `ips_entity` reference to `AnomalyListItem` and `AnomalyDetailOut`:
   `{id, dimension, value_key, display_name}` or null. `log_source_id` stays required (the IPS log
   source). `anomaly_type` accepts `AnomalyType | WafAnomalyType | IpsAnomalyType`. **`AnomalyType`
   itself is not changed** (AGENTS.md rule 6).
2. **Unified list.** `list_unified` gains an IPS branch (`ips_anomaly`, joined to its entity and
   source names inside the branch, as WAF joins its endpoint), and `_applicable_kinds` returns three
   families. The list stays **two statements for any page size** (one count, one page): pin this
   with a statement-count test, as the existing WAF test does. New filter `ips_entity_id` on
   `GET /anomalies` (it excludes the other families, as `waf_endpoint_id` does). Every existing
   filter (`state`, `severity`, `active_only`, the range, `log_source_id`, `instance_id`,
   `evidence_status`) applies to the IPS branch with the same meaning; a filter that cannot apply to
   IPS excludes the IPS branch rather than being ignored (the `_applicable_kinds` rule). Ordering
   and the id tiebreak are unchanged.
3. **Detail.** `GET /anomalies/{id}` falls back Phase A → WAF → IPS. `_ips_detail` mirrors
   `_waf_detail`: `explanation_package` is null (an IPS incident has no evidence package; never
   fabricate one); `detection` comes from a new `ips_detection_detail(details)` whitelist
   projection next to `waf_detection_detail`, exposing only the keys the IPS detectors write that
   an analyst needs (read `app/ips/` to find them; list the whitelist in the report). Transitions
   included.
4. **IPS behavior routes**, on the existing `behavior_router` (so `read:anomalies` guards them like
   the WAF ones), each paginated where it lists, range-bounded by `api_max_range_days`, with a
   **constant number of SQL statements per request** (pin each with a statement-count test at two
   sizes, e.g. 3 and 40 entities):
   - `GET /behavior/ips/sources`: the IPS sources with an enabled profile: profile status, last
     bucket time and completeness, active entity counts per dimension against the ceiling, the
     admission outcome of the last bucket.
   - `GET /behavior/ips/sources/{log_source_id}/entities?dimension=`: the paged entity inventory:
     dimension, `value_key`, `display_name`, first and last seen, retired or active, baseline
     adequacy, current detector state.
   - `GET /behavior/ips/entities/{id}/metrics?since=&until=`: the entity's buckets with their
     completeness; **an unmeasured bucket is null, never 0**.
   - `GET /behavior/ips/entities/{id}/baselines`: the entity's cells with reliability and versions.
   - `GET /behavior/ips/sources/{log_source_id}/metrics?since=&until=` and
     `.../baselines`: the source-level series and cells (`ips_source_bucket`,
     `ips_source_baseline`) that `IPS_SOURCE` detectors judge, with their completeness and
     coverage.
   A log source without an IPS profile answers `404`.
5. **What may leave the database** (AGENTS.md rule 3). Entity `value_key` and `display_name` (by
   §D.4 these are the estate's own ports, destination addresses and signature QIDs) and the bounded
   contributor lists exactly as stored. **A source IP never appears outside a stored, bounded
   contributor list.** If a contributor list is exposed, say which route and field in the report.
6. **Joins the GET-only route test** (`tests/integration/test_phase_a_api.py` or wherever the
   "no route writes" assertion lives): the new routes are covered by it.

## Tests

- Unit: the schema additions, `ips_detection_detail`'s whitelist (an unknown key is dropped), the
  three-family `_applicable_kinds` table (every filter combination that excludes or keeps IPS).
- Integration (`tests/integration/test_ips_analyst_api.py`, new): list with all three families
  mixed and ordered; every filter on the IPS branch; `subject_kind=IPS_ENTITY|IPS_SOURCE`;
  `ips_entity_id`; pagination across a tie; the two-statement list at two page sizes; detail for an
  entity and a source incident (null package, whitelisted detection, transitions); each behavior
  route's happy path, its `404`, its range bound, its null-not-zero bucket, and its statement count
  at two sizes. **Existing Phase A and WAF API tests pass unchanged**: never edit them.
- Break at least six guards on purpose (for example: the IPS branch's `active_only`, the
  `ips_entity_id` exclusion, the null-not-zero bucket, the 404 without a profile, the whitelist,
  the statement count), confirm a test fails each time, restore, list them.
