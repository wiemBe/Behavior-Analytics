## Why

G-2 (merged) added `QRadarRestProvider.get_geo_keyed`, one keyed search per direction:

```
SELECT GEO::LOOKUP(<sourceip|destinationip>, 'country', 'iso_code') AS "geo",
       starttime / <bucket_ms> AS "k", SUM(eventcount) AS "events"
FROM events WHERE starttime >= … AND starttime < …
GROUP BY GEO::LOOKUP(…), starttime / <bucket_ms>
ORDER BY SUM(eventcount) DESC LIMIT <n+1> START … STOP …
```

T-077 proved `GEO::LOOKUP(…, 'country', 'iso_code')` returns a JSON string in a **SELECT**. This
exact shape (the lookup inside `GROUP BY`, with the bucket key and `ORDER BY SUM`) has **never run
on a live QRadar**. T-065 showed an unverified form can sink a feature, and the collector is **on by
default** (`geo_collection_enabled = True`), so it will run on the first deployment. Find out now.

## Method

1. Work from the integration branch's main checkout, `/home/efe/Documents/QRadar-Dash/backend`, with
   `PYTHONPATH=.` and `.venv/bin/python -I`. Assert at the start that

2. Build the provider with the application's factory and the process-environment overrides below
   (as T-074 did; read `docs/tasks/T-074.md` and its report for the pattern).
3. Call `get_geo_keyed` **once per direction** (`SOURCE`, then `DESTINATION`) over **one** window of
   whole buckets, `bucket_seconds = 300`, at most 2 hours long, ending at least 10 minutes in the

   bucket, the default cap of 64). **No database writes.**
4. If a direction is rejected, run **one** alternative for the rejected construct, for example the
   lookup aliased and the `GROUP BY` naming the alias, or `GROUP BY` by position, and report whether
   QRadar accepts it, with its exact AQL. Do not try more than two alternatives in total.
5. Optional, only if the lab has little traffic in the window: send lab traffic with the repository
   generator as T-074 did (read `docs/LAB-SYNTHETIC-TELEMETRY.md`), **at most 5 EPS, at most 6
   minutes**, then search a window covering it. Stop the generator by its PID and confirm it is
   gone.

## Questions

2. After the fold, per direction over the window: the total of country events, `UNRESOLVED`,

   never an IP address.**
3. Did any key fail to parse (count only, never the key)? What does a typical key look like? Quote

4. Does the bucket key `k` fall inside the window for every row (the provider checks it; report
   whether the check passed)?
5. For anything rejected: the accepted alternative and its exact AQL.
