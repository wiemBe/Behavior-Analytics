## The baseline problem: choose and document

Baselines are seasonal cells keyed on (UTC ISO weekday, hour), reliable at
`baseline_min_samples` samples. A live run cannot wait weeks for real cells. You must choose a
strategy that keeps the **real code paths** and **evaluate-before-train**:
- **(A) Same-hour cell.** Send `ips-baseline` for enough of one UTC hour H that H's cells reach the
  sample minimum, let the pipeline train them, then run a change scenario **inside the same hour H
  on a later day**, or within hour H if enough of it remains after training. Show the arithmetic
  for the sample count per cell.
- **(B) Shortened settings in the validation run only**, through process-environment overrides
  (for example `BASELINE_MIN_SAMPLES`, `IPS_BASELINE_LOOKBACK_DAYS`, `IPS_NEW_PORT_HISTORY_DAYS`).
  Document each override and why it does not change what is being validated.
- Never write baseline rows by hand, and never change application code to make a scenario pass.

State which you chose and why before running scenarios.

## Scenarios

For each of `ips-port-sweep`, `ips-new-port`, `ips-source-concentration` and
`ips-signature-burst`, on at least one source (both if time allows):
- send it with the generator, `--format vendor`, **at most 5 EPS**, bounded (`--count`), one
  generator process at a time; stop it by its PID and confirm it is gone;
- run collection and the pipeline over the scenario's buckets;
- check: the **matching detector** goes CANDIDATE → OPEN; **sibling detectors stay `NORMAL`** (or
  `INSUFFICIENT_DATA` with a stated reason, never a false OPEN); after `ips-baseline` traffic
  resumes, the incident goes RECOVERING → RESOLVED;
- with `IPS_ALERTING_ENABLED=true` for **one** scenario only: an alert opens with the IPS
  fingerprint and resolves; a notification is enqueued (the default dispatcher has no notifiers,
  so nothing is sent outside).

`ips-block-shift` needs an ACTION custom property only the user can create on the lab console:
**skip it** and record it as skipped.
