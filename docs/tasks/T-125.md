## What the user asked (2026-10-17)

> "operöttörün herhangi bir log source veya log source type veya log group'u seçip şu custom
> property değerini veya değerlerini takip et diyebilir miyiz bence deriz altyapı hazır"

In English: the operator picks any **log source**, **log source type** or **log source group**,
and says "track this custom property's value, or values". The user believes the infrastructure
is ready.

## The user's answers (2026-10-17, PLANNER D-21) — binding

1. **Outputs: all four.**
   - The value distribution: per-bucket counts per value, as a table, a time-series chart on the
     watch's page and a dashboard widget.
   - **Threshold alerts:** a new F.1 subject kind, so a rule can say "value DENY above 500 per
     bucket, sustained 3 buckets".
   - **New-value detection:** a value never seen before on this watch (the WAF new-endpoint
     idea).
   - **Baseline deviation:** each value against its own baseline: spike, drop, disappearance
     (the Phase A idea).
2. **Values: both.** Values the operator pins are always counted (a measured zero when the
   search can prove it); the most frequent other values are tracked automatically, top-N.
3. **Combination and correlation: wanted** ("korelasyon ve kombinasyon iyi olur").
   - *Combination:* one watch groups by more than one property, for example `Username` ×
     `Action`.
   - *Correlation:* the user did not define it. **Define it precisely** in the design, propose a
     bounded v1, and put the alternatives in the open questions. Candidates to weigh (choose
     with evidence, do not take this list as the answer):
     - a **new combination** of values that were each seen before, but never together (a
       classic behavior signal; it needs no extra Ariel search);
     - **co-movement** of two watches' values in the same buckets (DB-only, but noisy);
     - anything QRadar's own correlation already does better, which then stays out of scope.
4. **Order: design now, build after the operations work** (OPS-5, OPS-6, OPS-9 round 2,
   OPS-10). The task split must say so.

## Questions the design must answer, with evidence from the code

1. **The watch.** Its fields: scope (exactly one of log source, type, group), one or more property
   references (`NORMALIZED` or `CUSTOM_PROPERTY`; say whether normalized fields such as
   `username` belong in v1 and why), pinned values, top-N, cadence, enabled. The maximum number
   of properties in a combination, and the cardinality cap that follows from it.
2. **Scope resolution.**
   - A type becomes a `devicetype` filter; a source an id.
   - A group: does AQL filter by group natively? Do not assume. Cite evidence in the repository,
     or mark it "verify on the lab console" and design the fallback: resolve membership from the
     synced inventory at each run into `logsourceid IN (…)`, under a source cap.
   - What happens when a group or type outgrows the cap, gains or loses members, or its sync is
     stale. Fail closed (rule 8).
3. **Property applicability.** A custom property applies to certain log-source types. A scope
   that mixes types will see events where the property is not parsed. Count that remainder
   separately (never as a value, never as a zero), show the coverage, and say what status a
   watch gets when no source in its scope defines the property.
4. **Collection.**
   - Reuse F.2's scheduled-search machinery (generated AQL stored as a versioned, validated
     query) or a dedicated collector in the IPS keyed style? Choose, and justify against rule 4
     (the browser never sends AQL: the server builds the query from validated parameters, and
     the generated text is visible read-only) and against bucket granularity.
   - How pinned values stay exact (including a measured zero) while top-N is bounded: one search
     or two per run, and the Ariel cost of each choice.
   - The search family and cadence (D-7), watermarks, and the settle delay.
5. **Persistence (rule 3).** Values become aggregate keys, as IPS entities and WAF endpoints
   already are. Values may be personal data (usernames, addresses). State the length cap, the
   retention, who may read them, and whether any value is hashed or truncated. If this is a
   policy choice, it is an open question.
6. **Detection.** For each of the four outputs: the verdict rule, its measurement requirement in
   the vocabulary of `backend/app/anomaly/capabilities.py`, its learning period, and what a
   LOWER_BOUND bucket may prove. New enums; `AnomalyType` is not extended (rule 6). Where the
   anomalies surface (`/anomalies` or not), consistent with WAF, IPS and D-17's answer for F.1
   breaches.
7. **Combination and correlation**, as defined in your answer to user item 3, with its cost and
   its fail-closed rule.
8. **Alerting.** Fingerprints, a shadow-mode setting defaulting to false (the IPS and F.1
   pattern), and how F.1 rules pin a watch value.
9. **Cost.** Ariel searches per watch per cadence; the cap on enabled watches; the source cap;
   the top-N cap; the existing Ariel concurrency budget; per-run SQL constant through bulk
   loaders (rule 9). Give the numbers.
10. **Permissions, audit and API**, matching the existing patterns (who writes a watch, who reads
    its values).
11. **UI.** Where the watch editor and the watch page live (navigation group, routes). The editor:
    the scope picker with search over sources, types and groups; the property search filtered
    by the scope's types, showing which types define each property; pinned values; top-N; the
    preview (D-17 item 4: a real bounded Ariel run of the stored draft). The watch page: the one
    question it answers, the per-value series with the expected band, the unparsed remainder,
    truncation. The widget. Every state of AGENTS.md §3a.
12. **Task split**, in the PLANNER's style, named **PW-1, PW-2, …** (not `G-`, which geo uses):
    narrow backend and UI tasks, each with its agent kind, its dependencies, which can run in
    parallel, and the migration order (head is `0025` today; say "next at build time").
