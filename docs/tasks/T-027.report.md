# T-027 report — what IPS events carry in the lab, for Phase D (goal G2)

Measured on 2026-10-12 against the lab console. **Headline: no IPS or IDS log source delivered a
single event in the last 24 hours** (nor in the last 1,697 hours; see §1). Questions 2 to 6 therefore
cannot be answered from IPS data. Where a question is about Ariel syntax, I measured it on the
QRadar-internal sources that were live (SIM Audit id 64, System Notification id 65, Health Metrics
id 69) as stand-ins, and say so each time. Nothing below is a statement about real IPS payloads
unless marked "from the generator spec" (Q7) or "from a REST read" (Q1, Q5, Q6).

## Method and budget

- Provider built with `build_provider` (REST). Token and CA bundle were supplied by process
  environment on the command line only; the token was never printed. Scripts are in the scratchpad
  `t027/` directory. No repository file other than this report was changed.
- Inventory: `GET` through the provider's `_paginate` (log sources, log source types, regex custom
  properties, AQL property expressions). Four other custom-property list paths returned 0 rows or
  were not probed further; `.../regex_property_expressions` does not exist (404-class "object does
  not exist"). No banned endpoint (`/dependents`, `*_tasks`) was called. No search handle was
  cancelled or deleted.
- Ariel: only `create_ariel_search`, `get_ariel_search_status`, `get_ariel_search_results`, one at a
  time, every search `LAST 24 HOURS` with `LIMIT` 500 or lower. **10 of 10 searches used.**
  Searches 4 and 5 were rejected at create (HTTP-level "invalid"), and I counted them against the
  budget even though no search ran. The provider sanitizes the rejection text, so the reason is
  not visible; it is inferred below.

## 2. Volume shape

**Not measurable for IPS: there are no IPS events in the window.** For the live-form check I ran
the hourly search on SIM Audit and System Notification as stand-ins:

```sql
-- search 9 (accepted, 1.1 s, 4 rows)
SELECT logsourceid, DATEFORMAT(starttime, 'yyyy-MM-dd HH') AS hr, SUM(eventcount) AS ec, COUNT(*) AS c
FROM events WHERE logsourceid IN (64, 65)
GROUP BY logsourceid, DATEFORMAT(starttime, 'yyyy-MM-dd HH') ORDER BY hr LIMIT 500 LAST 24 HOURS
```

- Ariel **accepts** `GROUP BY ..., DATEFORMAT(starttime, 'yyyy-MM-dd HH')` with `SUM(eventcount)` and
  `COUNT(*)` together; one search yields per-source per-hour rows. Cap: 24 hours x 12 sources = 288
  rows, under 500.
- Stand-in data only: the two sources had events in just two hours (10 and 11 UTC), which says the
  console itself had been off before then. Source 65: 9,429 and 3,172 events; source 64: 1,720 and
  360. In every row `COUNT(*)` equals `SUM(eventcount)`: these internal sources do not coalesce.
- **How bursty or coalesced IPS is: not measured.** Whether Snort or McAfee NSP records coalesce
  (records against events) is unknown. T-015 shows `coalesce_events` is a per-source flag in the REST
  row; Phase D must keep `SUM(eventcount)` as the volume and `COUNT(*)` as provenance, as Phase B does.

## 3. Field population

**Not measurable for IPS (no events).** Syntax findings, measured on sources 64, 65, 69 over 24 h:

| Form | Ariel | Notes |
|---|---|---|
| `SUM(CASE WHEN destinationport > 0 THEN eventcount ELSE 0 END)` | **rejected** (searches 4 and 5, at create) | Search 4 had 10 such terms, search 5 had one, so `CASE` is the likely cause, but the sanitized error cannot confirm it. |
| `COUNT(field)` for the 9 fields | accepted (search 6) | Returned `n` equal to the row count for every field on every source: normalized numeric fields are **never NULL**, so `COUNT(field)` and `IS NOT NULL` cannot separate "absent" from "populated". |
| `WHERE destinationport > 0 AND protocolid > 0` with `SUM(eventcount)`, `UNIQUECOUNT` | accepted (search 10, 0 rows) | The zero-versus-populated split has to be a `WHERE` filter, one search per field set, or a `GROUP BY` that exposes the 0 value. |
| `QIDNAME(qid)` in `SELECT` and grouped by `qid` | accepted (search 8) | Returns the event name string. |

```sql
-- search 6 (accepted, 1.1 s, 3 rows)
SELECT logsourceid, SUM(eventcount) AS ev, COUNT(*) AS n, COUNT(destinationport) AS dport,
       COUNT(sourceport) AS sport, COUNT(sourceip) AS sip, COUNT(destinationip) AS dip,
       COUNT(protocolid) AS proto, COUNT(qid) AS q, COUNT(category) AS cat,
       COUNT(severity) AS sev, COUNT(magnitude) AS mag
FROM events WHERE logsourceid IN (64, 65, 69) GROUP BY logsourceid LIMIT 500 LAST 24 HOURS
-- search 10 (accepted, 0.1 s, 0 rows): no row has destinationport > 0 and protocolid > 0
SELECT logsourceid, SUM(eventcount) AS ev, UNIQUECOUNT(destinationport) AS udp
FROM events WHERE logsourceid IN (64, 65, 69) AND destinationport > 0 AND protocolid > 0
GROUP BY logsourceid LIMIT 500 LAST 24 HOURS
```

- Stand-in values: internal sources carry `destinationport = 0` and `protocolid = 255` on every
  row, but `sourceip`/`destinationip` are filled (127.0.0.1 or the console address). So "0" is the
  absent marker for ports, and an IP is filled even when it is meaningless (loopback).
- Custom properties that look relevant (regex properties, `GET .../custom_properties/regex_properties`,
  119 of them, none JSON/LEEF/CEF/NVP): **`IPS_Action`** (id 260, string, created 2026-08-02,
  `use_for_rule_engine: false`; looks lab-made, description empty); `Rule ID` (248), `Rule Name`
  (201), `Policy Name` (161, "NSM Policy"), `Threat Name` (122), `Threat Category` (257), `Threat
  Family` (255), `Threat Severity` (256), `Event ID` (107), `URL` (174). No property is named
  signature id, direction or sensor. Which log source types each regex applies to is **not read**
  (the expression endpoint is not available); so I cannot say whether `IPS_Action` is populated for
  Snort or NSP. Population share of any of these on IPS events: **not measured**.

## 4. Cardinality

**Not measurable for IPS.** The forms were exercised on the stand-ins:

```sql
-- search 7 (accepted, 1.1 s, 3 rows)
SELECT logsourceid, UNIQUECOUNT(destinationport) AS udport, UNIQUECOUNT(sourceip) AS usip,
       UNIQUECOUNT(destinationip) AS udip, UNIQUECOUNT(qid) AS uqid,
       UNIQUECOUNT(protocolid) AS uproto, MAX(destinationport) AS maxdp
FROM events WHERE logsourceid IN (64, 65, 69) GROUP BY logsourceid LIMIT 500 LAST 24 HOURS
-- search 8 (accepted, 1.1 s, 20 rows): top-N over a multi-key group, event name via QIDNAME
SELECT logsourceid, destinationport, sourceip, destinationip, protocolid, QIDNAME(qid) AS qn,
       SUM(eventcount) AS ec
FROM events WHERE logsourceid IN (64, 65, 69)
GROUP BY logsourceid, destinationport, sourceip, destinationip, protocolid, qid
ORDER BY ec DESC LIMIT 20 LAST 24 HOURS
```

- Accepted: `UNIQUECOUNT` on port, IP and qid; `MAX`; a six-key `GROUP BY ... ORDER BY ec DESC LIMIT 20`.
  `UNIQUECOUNT(destinationport)` returned 1 for every stand-in (the single value 0), which confirms
  it counts the absent marker as a value (compare the Phase B note on `UNIQUECOUNT` and NULL): a
  distinct port count must subtract one when port 0 occurs.
- Stand-in numbers (not IPS): distinct source IPs 1 to 5, distinct qids 1 to 17.
- **Where the 500 cap truncated: nowhere** (largest result 20 rows, by `LIMIT 20`). Whether the
  per-source, per-day (port, source IP, destination IP, signature) group counts fit under 500 for a
  real IPS is unknown; a port-scanner source alone can exceed it.

**Not measurable per event.** What exists:

  lab. Its values and its population on real IPS events are unknown.
- The generator's IPS event IDs are `IPS_SIGNATURE_ALERT` (action ALLOW) and `IPS_SIGNATURE_DROP`

## Design implications for Phase D

1. **No live IPS evidence exists.** Every IPS source is 70 days stale and the Phase A IPS source is
   missing. Phase D cannot be validated end to end until a source is created (a manual console
   step) and the generator is extended (§7). Plan for that before any detector acceptance test.
2. A per-source seasonal baseline needs enough distinct, repeated values. Only low-cardinality
   dimensions qualify, and only after the cardinality is measured on a real IPS: destination port,
   and signature/QID, are the candidates; source IP and destination IP are likely too high for a
   per-value baseline (unmeasured here).
3. Source IP and destination IP should follow the WAF endpoint pattern: bounded top-N (Ariel
   `ORDER BY SUM(eventcount) DESC LIMIT n`) plus a remainder bucket, never one baseline per IP.
4. Destination port likely also needs top-N plus remainder (65,535 possible values; a scanner alone
   can fill a 500-row cap). Treat a full 500-row page as truncated.
5. Detectors that look supportable once real data exists: a per-source, per-window event-rate spike
   (already in Phase A), a signature/QID spike (`QIDNAME(qid)` and `GROUP BY qid` work), a
   source-IP concentration share, and a new-destination-port detector (from a bounded top-N plus
   a known-ports set). A block-ratio shift is supportable **only if** a per-event action exists.
6. A block-ratio detector must stay disabled until the action source is identified. In the lab the
   only candidate is the `IPS_Action` custom property (population and values unknown); QRadar's
   normalized fields carry no action. Without it the verdict is `INSUFFICIENT_DATA`, never "no
   blocks".
7. Port-rate spike and new-port detectors depend on `destinationport` being populated. Ports are
   `0`, not NULL, when absent (measured), so a population gate must be a `WHERE destinationport >
   0` share, not `IS NOT NULL` or `COUNT(field)`. Below the coverage threshold the verdict is
   `INSUFFICIENT_DATA`.
8. Treat port `0` and `protocolid` 255 as "absent", never as a destination port and never as a
   distinct value: `UNIQUECOUNT(destinationport)` counts 0, so subtract it. Loopback or console
   IPs are filled on internal events, so an IP-concentration gate should also exclude
   non-routable values or require the source type to be an IPS.
9. Use only Ariel forms measured accepted: `UNIQUECOUNT`, `MAX`, `SUM(eventcount)`, `COUNT(*)`,
   `DATEFORMAT(starttime,...)` grouping, `QIDNAME(qid)`, multi-key `GROUP BY`, `WHERE ... > 0`.
   **Do not use `SUM(CASE WHEN ...)`**: it was rejected by this console (cause unconfirmed). The
   provider hides rejection text, so a rejection must map to `INSUFFICIENT_DATA` and be logged by
   class only.
10. Keep per-run SQL constant: one search per window grouped by `logsourceid` (and top-N searches
    grouped by `logsourceid` plus one entity), never a search per source or per port. One
    `GROUP BY logsourceid, DATEFORMAT(...)` search covers a day of hourly volume for all sources.
11. Persist aggregates only: per-window counts, distinct counts and bounded top-N lists. Raw
    ports, IPs and signature names live inside the fold functions, as in Phase B.
12. Keep `SUM(eventcount)` as volume and `COUNT(*)` as provenance. Coalescing on real IPS sources
    is not measured; a detector that used `COUNT(*)` would under-count a coalesced source.
13. Fail closed on: a stale or disabled source (the lab's 12 IPS sources would all yield
    `INSUFFICIENT_DATA`), an absent or unmapped action or signature field, a population share
    below its threshold, a truncated top-N page, a rejected or timed-out search, and a cell with
    fewer baseline samples than the minimum.
14. Source classification: IPS membership must come from the type table (ids 2 and 25 in the lab
    plus the other 19 IPS/IDS type names), not from names. Eleven McAfee rows are named after
    hosts such as `dns-lab-01`, `proxy-lab-01`, `linux-auth-01` and `linux-fw-01`, and only the
    type says they are IPS.
15. Signature identity: the QID, shown through `QIDNAME(qid)`, is the portable key. A custom
    property such as `Rule ID` or `Threat Name` may not exist for a given DSM and must not be
    required.
