# T-128 report — the beat heartbeat is written at beat start

## Files changed

- `backend/app/workers/celery_app.py` — the `@beat_init.connect` handler now sends
  `beat_heartbeat` as well as `apply_timescale_policies`, through a shared helper that logs a
  warning per failed send (a dead broker no longer stops either send). A comment on the
  `beat-heartbeat` schedule entry records why the start send exists.
- `backend/tests/unit/test_timescale_policy_task.py` — the beat-start test now asserts each task
  is sent exactly once and that a dead broker is survived for both; a new test pins that the
  heartbeat is still sent when the first send raises. Module docstring updated.
- `docs/tasks/T-128.report.md` — this report (new).

## What I did

The old handler `_apply_policies_at_beat_start` sent only `apply_timescale_policies` at beat
start. I renamed it to `_send_startup_tasks_at_beat_start` and factored the per-send logic into
`_send_at_beat_start(name, logger_name)`: each task is sent with `celery_app.send_task(name)`
inside its own `try/except`, so a broker that is down logs a warning and carries on, and a raise
on one send does not skip the other. The handler sends `apply_timescale_policies` (logger
`app.timescale`) then `beat_heartbeat` (logger `app.beat`), each exactly once per beat start. This
closes the window in which a restart (install, upgrade, rollback, reboot) or `upgrade`'s Redis
`FLUSHALL` leaves the heartbeat key missing for up to a minute and `doctor` reports
`FAIL celery_beat … heartbeat is missing` on a healthy stack. `check_celery_beat` is unchanged: a
missing heartbeat is still a FAIL, because a running beat now writes it within seconds.

Tests (in the file that holds the beat-start tests, `tests/unit/test_timescale_policy_task.py`):

- `test_beat_start_sends_each_task_once_and_survives_a_dead_broker`: after a real
  `beat_init.send(sender=None)`, `apply_timescale_policies` and `beat_heartbeat` are each sent
  exactly once. With a broker that raises, both sends are attempted, no exception propagates out
  of the signal, and both warnings ("could not queue apply_timescale_policies" /
  "could not queue beat_heartbeat") are logged.
- `test_beat_start_still_sends_the_heartbeat_when_the_first_send_raises`: the first send raises,
  the second send is still attempted and delivered.

## Open points

- Not run against a real beat/broker: the tests drive the `beat_init` signal with a monkeypatched
  `send_task`, so they prove the handler sends the right names on the right paths but not that a
  real broker accepts them. If the send path were wrong in a way the mock hides, the only symptom
  would be the original doctor FAIL, which the OPS-10 stack run already exercises.
- The two sends are sequential and each is a single non-blocking `send_task`. If a broker is
  unreachable in a way that blocks rather than raises (e.g. a hung TCP connect with no timeout),
  beat start could still be delayed; that is pre-existing behaviour from the policy send and the
  broker's own connection settings govern it, so I did not change it.
- `check_celery_beat` was deliberately left untouched, as the task requires.
