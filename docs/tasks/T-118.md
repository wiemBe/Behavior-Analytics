## Scenario (5-minute buckets; plan in UTC and write the plan in the report before sending)

- **Part 1, shadow mode.** Baseline ≥ 3 buckets at ~1 EPS → spike ≥ 3 buckets at ~8 EPS →
  recovery ≥ 3 buckets at ~1 EPS. Run `evaluate_custom_rules` after each collected bucket.
  Expected: the rule reads `OK` during the baseline; after the second spike bucket a breach row
  is `OPEN` and **no alert exists**; the counters move as §F.4/§F.5 say; after two recovered
  buckets the breach is `RESOLVED`. The stored-rule preview (`GET /custom-rules/{id}/preview`)
  over the same window shows the same breach interval and `fired_count`.
- **Part 2, alerting on.** Same shape. Expected: an alert with the `custom_rule_breach`
  fingerprint opens (one alert, however many breaching buckets: dedup), its evidence carries the
  value, measurement, threshold and bucket bounds, a notification is enqueued per transition,
  and the alert resolves with actor `custom-rule-evaluator` after recovery.
- **One fail-closed check:** skip collecting one bucket during a recovery phase (the row is
  absent), run the evaluator, and show that the gap counts neither toward recovery nor breach
  (`unmeasured_buckets`, counters unchanged), and that the preview draws it as `NOT_MEASURED`.
  Then collect it late and show what the evaluator does (idempotence, §F.5 rule 6).

Record per bucket: `bucket_start`, the stored `event_count`/`average_eps` and completeness, the
evaluator's status and counters, breach state, alert state. A table per part.
