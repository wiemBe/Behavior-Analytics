## 2. What I did

1. **Rename (task step 1).** Replaced every `HTTP_422_UNPROCESSABLE_ENTITY` under `backend/app/` with `HTTP_422_UNPROCESSABLE_CONTENT`, keeping each file's existing `status` import and touching only those calls. `grep -rn HTTP_422_UNPROCESSABLE_ENTITY backend/app` now returns nothing. (Note: `ips.py`, `searches.py` and `waf.py` already used `..._CONTENT` before this task; they were left alone.)

2. **Dependency floor (task step 2).** Findings, from wheel inspection and PyPI metadata (network available):
   - **First Starlette release defining `HTTP_422_UNPROCESSABLE_CONTENT` is `0.48.0`.** I downloaded the `py3-none-any` wheels of `0.44.0 … 0.52.0` and read `starlette/status.py`: absent in `0.47.3`, present from `0.48.0` (`probe_starlette.py`). The 0.48.0 release notes confirm it: *"0.48.0 (September 13, 2025) — Changed: Implement RFC9110 http status names #2939"*.
   - **No FastAPI release guarantees that Starlette.** I read `Requires-Dist` for every FastAPI release from `0.100.0` to `0.143.2` (`fastapi_starlette_pins.txt`). The Starlette pin is `starlette>=0.40.0` (bounded) until `0.133.0`, then `starlette>=0.40.0` (unbounded), and from `0.134.0` onward it is **`starlette>=0.46.0`** — never a lower bound of `0.48.0` or higher (`grep` for `>=0.4[89]`/`>=0.5` over that file finds nothing). So the evidence could not establish a FastAPI release that *guarantees* 0.48.0.
   - **I therefore took the task's fallback: raised the floor to the installed version, `fastapi>=0.139.2`** (`.venv/bin/python -m pip show fastapi` → `0.139.2`; installed Starlette is `1.3.1`). No other dependency was changed.

3. **Tests (task step 3).** Added `backend/tests/unit/test_starlette_status_names.py` in the style of the existing static contract tests (`test_logging_extra_keys.py`, `test_migration_determinism.py`): a parametrized per-file scan of `app/**/*.py` for the deprecated token, a test that the replacement name is actually in use (so the scan cannot pass by the code being deleted), and a scanner self-check. A plain substring test is sufficient because `..._CONTENT` does not contain `..._ENTITY`. Real 422 responses still return 422 — the constant's value is unchanged, so no behavioural test changed.

4. **Break-it (task step 4).** Put one old name back in `geo.py` line 39, ran the new test file: it failed as required (`AssertionError: api/routes/geo.py uses Starlette's deprecated HTTP_422_UNPROCESSABLE_ENTITY on line(s) [39]`) with exit code 1. Restored the line; the file is back to `..._CONTENT` and the working tree contains no old name outside the new test's own text.

## 4. Open points

- **The `fastapi` floor does not by itself guarantee the new name.** FastAPI's Starlette requirement is `starlette>=0.46.0` right up to `0.143.2`, and `0.46.0`/`0.47.x` lack `HTTP_422_UNPROCESSABLE_CONTENT`. A fresh `pip install .` (the Dockerfile installs without a lock file) can build an environment where the floor is satisfied but the constant is still missing, so the routes would fail at import on such a resolve. Closing that needs an explicit `starlette>=0.48` floor, which changes a second dependency and so was out of scope here (`pyproject.toml`, "Change no other dependency"). I flag it for the orchestrator rather than acting on it.
- **One line was reformatted.** `catchall.py`'s first 422 raise is now a wrapped call (see §1). The task said "reformat nothing"; the rename alone pushed that line to 101 columns, which `ruff check` (E501, limit 100) rejects. I judged a minimal wrap of the line I was already changing better than leaving a lint failure, and I am reporting it rather than hiding it.
- The deprecated name survives in `docs/tasks/*.report.md` prose and in `docs/tasks/T-109.md` itself; those are outside the allowed files and were not touched. The new test scans `app/` only, so it is unaffected.
- Starlette's own `status.py` keeps the old name in its deprecation map, so scanning the installed package rather than `app/` would always fail — deliberately not done.
