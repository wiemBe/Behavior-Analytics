# Task T-120 — the enabled-count caps hold under concurrency

Read `AGENTS.md` at the repository root first and follow it exactly.

## Why

Two caps are checked with one unlocked count, so two concurrent requests can both pass:
- custom rules: `custom_rules_max_enabled`, `_enabled_count` in
  `backend/app/api/routes/custom_rules.py` (F-3 report, open point);
- scheduled searches: `scheduled_searches_max_enabled` in `backend/app/api/routes/searches.py`
  (F-4 open point).

For example, at `max_enabled = 1`, two `POST`s with `enabled: true` racing each other can both
commit.

## Build

Serialize the check and the write for each cap inside its transaction. Two options:
- a transaction-scoped advisory lock (`pg_advisory_xact_lock`) on a constant key per cap, taken
  before the count;
- or another approach that is correct on PostgreSQL under READ COMMITTED.

Explain the choice in a short comment in the file's voice. Requirements:
- Every path that can raise the enabled count takes the lock: create with `enabled = true`, and
  a PATCH that enables. Disabling and deleting do not need it.
- The rest of the behaviour stays the same: the 409 sentence, the 422 shape, the audit actions.
- No new query per row (AGENTS.md §2 rule 9 in spirit): one lock and one count per request.

## Tests

**Integration**, on your own DB, for **each** cap:
- two concurrent enabling requests at `max_enabled = 1`, run with two real sessions or
  connections in parallel (for example `asyncio.gather` over two clients or two sessions) so
  that the race is actually exercised;
- exactly one succeeds, and the other gets the cap's 409.

Make the race deterministic enough to fail without the lock: hold the first transaction open
across the count, for example with a test hook or a barrier. Show the test failing with the lock
removed, then restore the lock.
