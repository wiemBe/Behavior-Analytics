# Task T-122 — `COMPOSE_FILE` in `.env`, so a bare `docker compose` in the install directory targets the production stack

Read `AGENTS.md` at the repository root first and follow it exactly. Then read `qradar-dash`:
`write_env`, `load_project_from_env`, the `dc` helper, and the idempotent re-run path. Then read
its tests `backend/tests/unit/test_qradar_dash_installer.py`.

## Why

`./qradar-dash` always calls `docker compose -p "$PROJECT" -f docker-compose.yml -f docker-compose.prod.yml`.
The `.env` it writes sets `COMPOSE_PROJECT_NAME` and `COMPOSE_PROFILES`, but **not
`COMPOSE_FILE`**.

An operator who follows the runbook (`docs/OPERATIONS.md`) and types a bare `docker compose …`
in the install directory therefore gets the right project with the **dev** file only. Examples:
`docker compose run --rm migrate`, `docker compose up -d backend …`, and
`docker compose run --rm --no-deps backend python -m app.cli.users create-admin …`. Those
commands then:
- use other image names, without the GHCR release images;
- publish other ports;
- recreate the containers without the prod overlay.

## Build

1. `write_env` writes `COMPOSE_FILE=docker-compose.yml:docker-compose.prod.yml` next to
   `COMPOSE_PROJECT_NAME`. Add a short comment saying why.
2. **A re-run on an existing install** adds the line when it is missing. It never changes the
   other keys: `ENCRYPTION_KEY` and the rest stay byte-identical, under the same rule the re-run
   already follows.
3. `dc` keeps passing `-f` explicitly. Leave it as it is.

## Tests

In `backend/tests/unit/test_qradar_dash_installer.py` (additions only), or in a new file next to
it:
- a fresh `.env` contains the `COMPOSE_FILE` line;
- a re-run over a `.env` without it adds it, and leaves every other line unchanged (compare the
  bytes of the other lines);
- a re-run over a `.env` that already has it does not duplicate it.

Use the existing harness: no Docker, and stubs where needed. Break the re-run rule once, confirm a
test fails, then restore it.
