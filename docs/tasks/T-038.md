## Build

### 1. `/admin/search-cadence` (new route)

**Navigation:**
- Link it from `/admin`. That page is a Phase 4 scaffold today. Replace the scaffold text only
  as far as needed to link this page.
- Add the route to `AppNav` following its contract (guidelines §8).

**One table, one row per family**, in API order. The columns:
- **Family**: a human name, plus one line of scope:
  - "Phase A volume — event count per log source";
  - "WAF collection — endpoint, status and client breakdowns";
  - "Anomaly explanations — evidence for open anomalies";
  - "Rule matches — events matched per rule".
- **Cadence**: a native `<select>` of the seven presets from `allowed_cadences_seconds`,
  labelled "5 min" … "8 h".
- **Bucket**: `bucket_seconds` as "5 min" / "1 h", or "—" when null. Say in the column header
  what null means: explanations have no buckets.
- **Worst-case detection delay**:
  - Computed as `cadence + bucket + settle` and shown as "up to 1 h 7 min".
  - For `ANOMALY_EXPLANATION`, where `bucket` is null, show "evidence up to …" instead.
  - Make the column header's meaning explicit.
- **Last run** and **Next run**:
  - Times in UTC, with the timezone shown.
  - "Next run" is `next_dispatch_at`.
  - With `last_run` null, the cell says "Not run since upgrade". **Never a zero, never a dash
    that reads as zero.**
- **Searches in last run**: `last_run.searches_sent`.
  - Right-aligned, tabular figures.
  - Null reads "not counted", with a tooltip or footnote saying this family does not count its
    searches yet. Today that is anomaly explanations.

**Changing a cadence:**
- It is a `PUT` per row, with the row showing a pending state.
- On success, the row shows the new value and "changed by `<updated_by>` at `<time UTC>`".
- On **403**, the row says the role cannot change search cadence (permission
  `admin:search_cadence`). The select reverts.
- On any other error, the row says what failed and what the analyst can do. The select reverts.
- Do not pre-judge permissions in the UI. The API's answer is the source of truth; follow the
  comment in `frontend/src/lib/api.ts`.

**Designed states:**
- loading;
- error, for the whole list (say what failed and what to do);
- empty: four rows are seeded, so an empty list is an error state that names the seed problem.

**Rules (§3a):**
- No KPI cards. No new colour, spacing or type literal outside `tokens.css`.
- No inline styles. No new UI framework.

### 2. `/searches/[id]`: schedule presets and truncated runs

**Schedule:**
- Show the schedule as a preset label ("Every 1 h") when `schedule_cron` matches one of the
  §SC.6 preset crons exactly.
- Otherwise show "Custom" and keep the cron visible in `<code>`.
- A control changes it to a preset through `PATCH /searches/{id}` with the preset's cron.
- Saving, success, 403 and error states are designed exactly as in §1.
- An existing custom cron is never rewritten unless the analyst picks a preset.

**Executions table (§SC.8):**
- A truncated run's result count reads "≥ 500", not "500 (trunc)". The "≥" must be announced
  accessibly.
- A truncated run that did not breach shows "no verdict" in the threshold column, with a
  title or footnote explaining that the count is a lower bound. A run within its threshold keeps
  "—".
- The `total` trend (`ResultTrend`) has no point for a truncated run, because the backend no
  longer stores one. It must draw a **gap**, never a zero, and never interpolate across it.
  Verify what `ResultTrend` does today, and fix it if needed.
