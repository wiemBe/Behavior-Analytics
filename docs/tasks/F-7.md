## Build

1. **One component, two mounts (§F.9.2).** Extend the existing `ResultTrend`
   (`frontend/src/components/ResultTrend.tsx`) so that it:
   - renders per the search's `visualization_type`: `LINE` → the series of one `metric_key` as a
     line; `BAR` → the same series as bars; `SINGLE_VALUE` → the latest total with its time;
     `TABLE` → the latest run's top-N rows (`metric_key`, dimensions, value), value-ordered,
     display-capped; a stored `PIE`/`HEATMAP` renders as `TABLE` **with a note saying so**;
   - has a `metric_key` selector (an enumerated picker, never free text);
   - draws a truncated run as a **gap** in the line (never a zero) and "≥ n" / "no verdict" in the
     table, as §F.9.2 says.
   `/searches/[id]` keeps using it; the widget mounts the same component.
2. **The widget `chart.search_results`** in `frontend/src/widgets/registry.ts`: `requires:
   ["read:searches"]`, `sources: ["/searches/{id}/results"]`, config `{ search_id, metric_key }`,
   both chosen from enumerated pickers in the existing Configure drawer (`widgets/Configure.tsx`).
   It honours the dashboard range where the trend endpoint allows it. A widget whose search was
   deleted says so and offers Configure.
3. **Every state of §F.9.2**, designed and tested: `ok`; `empty` (never run, with when it was
   created and how to run it now); TRUNCATED; stale (older than twice the search's own schedule
   interval, with the age); `error` (the failure in words, consecutive failures against
   `search_failure_alert_after`, what to do); `forbidden` (names `read:searches` and who grants
   it); `loading` (the text-only placeholder, guidelines §8). Units on every axis, tabular
   figures, UTC times, no marker on every point, no rainbow series.
4. **Lazy creation (UI-6.7):** the widget's chart goes through the same deferral as every other
   chart widget (the read grid's `useInView` gate, if UI-6.7 has merged by the time you finish;
   otherwise nothing special, and say so).
