## What is wrong today

For each WAF source, `WafEndpointCollector.collect` runs these searches **for every 5-minute
bucket**, under one Ariel permit per bucket:
- `get_waf_observations` (the endpoint groups, plus the totals search);
- one `get_waf_breakdown` per planned breakdown.

That is 3–6 searches per source per bucket, so 36–72 an hour per source.

## Build

### 1. Provider: keyed variants

Add `get_waf_observations_bucketed(...)` and `get_waf_breakdown_bucketed(...)` to the provider
interface, the REST provider and the mock.
- **Arguments:** the same as today's methods, plus `bucket_seconds` and `max_rows`.
- **Return:** per-bucket `WafObservationBatch` / `WafBreakdownBatch` objects keyed by bucket
  start, plus a whole-search `truncated` flag and the AQL.
- **Read-only.**

**REST AQL.** Each is today's query with these changes:
- add `starttime / {bucket_ms} AS "k"` to `SELECT` and to `GROUP BY`;
- `LIMIT max_rows + 1`;
- the same half-open `WHERE` and `START`/`STOP`;
- the same property-allowlist validation before any property reaches query text.

The totals query, today `LIMIT 1`, becomes `GROUP BY starttime / {bucket_ms}`, one row per
bucket.

**Per-bucket top-N moves into the fold** (a pure function, beside the existing WAF folds).
- When the keyed search is **not** truncated, every group of every bucket came back. Each bucket
  then keeps its top `max_groups` (or the breakdown's cap) by request count, with a
  **deterministic** tie-break that you document.
- **The per-bucket `truncated` flag must follow today's rule exactly.** Today a bucket is flagged
  truncated when it returned `>= limit` groups (`len(groups) >= limit`). So a bucket is
  truncated in the fold when it has `>= max_groups` groups.
- Coverage, admission and every other per-bucket fact are then computed from that bucket's batch
  exactly as today.

**Raw values stay inside the fold** (rule 3). Nothing raw leaves except the bounded
top-contributor lists the design already allows.

**A key that is outside the window, or not an integer,** fails the whole search with the
provider's existing error type.

**Mock.** Each bucket of its keyed output must equal its per-bucket output after the fold.

### 2. Collector: one keyed search per kind per tick

**Window.** In `WafEndpointCollector.collect`, the window is the uncollected buckets after the
watermark. Cap it at `cadence_buckets + collection_max_backfill_intervals`, with the cadence
read through `SearchCadenceService.get(SearchFamily.WAF_COLLECTION)`. The first run is
unchanged.

**Searches.**
- Fetch the window with one keyed observation search and one keyed search per planned
  breakdown, under **one** Ariel permit for the whole tick.
- **If any keyed search for the window is truncated:** keep nothing for the window from that
  search kind. Split the window in halves of whole buckets and repeat for both halves, as Phase A
  does.
- **At a single bucket, the base case is today's per-bucket calls**, with today's truncation
  semantics.
- The searches of one `collect()` are capped by `search_cadence_max_searches_per_tick`. On
  reaching the cap, keep only the contiguous run of buckets for which **every** search kind
  completed.
- **A provider failure (not truncation)** stops the tick. The complete contiguous prefix is kept,
  and the watermark stops before the failed bucket. This matches T-035's Phase A behavior. Do
  not split on failure; the design records this as a question for live validation.

**Persisting.** Persist each kept bucket through the existing `_persist_interval`, unchanged in
meaning. The constant-statement guarantees (design §29.5, §29.11) must still hold per bucket.
State the per-tick statement count in the report.

**Provenance and the report.**
- Add the provenance keys from §SC.5.5.
- `WafCollectionReport` gains `searches_sent` (the existing `ariel_searches` may serve) and
  `splits`.
- `collection_metadata` keeps its existing keys.

**The equivalence bar (§SC.5.4).** For any window and the same provider data, the persisted
rows must equal, column for column, what the per-bucket path writes:
- `waf_source_bucket`;
- the endpoint metrics;
- the breakdown measurements;
- endpoint first-seen and admission.

Only provenance, `collected_at` and duration may differ.

Prove it over the mock with a test that has:
- at least 24 buckets;
- several endpoints;
- one bucket over `max_groups`, so it is truncated today;
- one empty bucket;
- every breakdown planned.

The old per-bucket path may stay as a private control helper for that test. Nothing in
production may call it.

### 3. Evaluation

WAF already evaluates through its own `evaluated_through` watermark. **Verify** that, after a
tick that persists 12 buckets, the pipeline evaluates **all 12, in order**, and that training
sees them. Pin this with an integration test through `run_waf_source`. If it does not, fix it
there, in `app/services/waf_pipeline.py`, and report what was wrong.

### 4. The gate, and the beat

In `app/workers/tasks.py::dispatch_waf_collection`:
- Check `waf_collection_enabled` first, unchanged.
- Then claim `SearchFamily.WAF_COLLECTION` in its own committed session.
- **Not due:** return `{"status": "not_due", "family": "WAF_COLLECTION"}` before anything is
  enqueued.
- **Due:** enqueue as today, then call `record_run` with `searches=None`, `buckets=None` and
  `splits=None`. The per-source tasks run asynchronously and are not aggregated. The outcome is:
  - `dispatched` when at least one source was enqueued;
  - `no-sources` when none was eligible.
- `collect_waf_source` is **not** gated; it runs when enqueued.

In `celery_app.py`, `dispatch-waf-collection` ticks every `60.0` s.
