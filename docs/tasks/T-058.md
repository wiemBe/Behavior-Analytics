## What the user asked (2026-10-13)

"No suggestions — but there should be a search in the properties, so I don't have to scroll down or
Ctrl+F." The editor must **not** guess which property is which logical field. It must let the
operator **find** a property in the console's list quickly.

## What exists

`frontend/src/components/fieldmapping/PropertyInput.tsx` is an ARIA combobox whose text is both the
value and the filter. Its limits:
- It shows at most 8 matches (`MAX_SUGGESTIONS`) and says nothing about the rest. The lab console has
  119 properties; most are invisible.
- With a value already set (e.g. `URL`), opening it shows only names containing that value, so
  finding a different property means clearing the field first.
- Matching is a plain substring on the name: `resp code` does not find `WAF_ResponseCode`.

## Build

Rework `PropertyInput` (and only what it needs in `FieldMappingForm.tsx`, `lib/fieldMapping.ts`,
`globals.css`) into a searchable picker. It must stay a correct ARIA combobox (WAI-ARIA APG "editable
combobox with list autocomplete"), keyboard-first.

1. **The whole list is reachable.** No silent cap. The listbox has a bounded height (tokens) and
   scrolls inside itself. Rendering stays fast for 500 items (no virtualisation library; plain
   rendering is fine at this size).
2. **Search.** Case-insensitive; tokens split on spaces, `_`, `-` and camelCase boundaries all must
   match (so `resp code`, `responsecode` and `waf resp` find `WAF_ResponseCode`). Matched characters
   are emphasised with the existing type styles (no new colour).
3. **Separate the query from the value.** Opening the picker on a field that already has a value
   shows the full list with the current value marked as selected and scrolled into view. Typing then
   filters. Choosing commits; Escape restores the previous value. Free text is still allowed (the
   catalog is a suggestion, never a gate, §FM.6): committing a name not in the list is valid, and
   the existing catalog note under the field keeps saying what it says today.
4. **Grouping and counts.** Group the results under two headers: "Applies to this source type" and
   "Other source types" (and "Type unknown" when `applies_to_source_type` is null). Show a live count
   line, e.g. "7 of 119 properties match", announced politely to screen readers. When nothing
   matches: say so and say that the typed name can still be used and will be checked by validation.
5. **Not selectable** names (`name_allowed: false`) stay visible, marked as such, and cannot be
   chosen (as today).
6. **Catalog unavailable** (status `UNAVAILABLE` or null): the input degrades to plain text with the
   existing explanation; no empty listbox.
7. **Normalized options** (`MappingFieldOut.normalized_options`, used by IPS later): if the field
   offers them, they appear first under a "QRadar normalized fields" header and are searchable the
   same way. Do not build anything else for IPS.
8. No new dependency, no inline styles, no new colour/spacing/type literal outside `tokens.css`.

## Tests (Vitest)

Every state and path: open with empty value shows all items grouped with the count; open with a
value shows all and marks the current one; token search (`resp code`, `responsecode`, camelCase);
no-match message; keyboard (Down/Up/Home/End/Enter/Escape restores; Tab commits typed text); mouse
choose; not-selectable item cannot be chosen; unavailable catalog → plain input; 500 items render and
filter; the count is in a live region; existing `FieldMappingForm` and editor tests still pass
unchanged. Break each guard on purpose, see the test fail, restore.
