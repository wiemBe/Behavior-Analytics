### Step 2 — the fix, with every assertion kept

Where the time goes, measured with temporary `performance.now()` marks inside this test
(instrumentation removed afterwards; solo, on this machine):

| phase | before | after |
| --- | --- | --- |
| `render(<Harness suggestions={many(500)} />)` | 1–2ms | 1–2ms |
| `user.click(box())` — opens and renders 500 options | 95–124ms | 69–91ms |
| `expect(names()).toHaveLength(500)` — `queryAllByRole("option")` over 500 nodes | 104–144ms | 81–86ms |
| entering the query | 315–374ms (14 keystrokes) | 12–14ms (one paste) |
| final two assertions | 2–3ms | 1–2ms |
| whole test, per Vitest's reporter | 340–387ms | 151–192ms |

- **Same filtering path — checked in the component, not assumed.** `PropertyInput` sets `query`
  in exactly one place, the input's `onChange` (`PropertyInput.tsx:262-267`). React's `onChange`
  is the DOM `input` event, which `user.paste` fires with `inputType: "insertFromPaste"`
  (user-event `event/behavior/paste.js` calls `input(...)`, the same helper every keystroke
  goes through). `onKeyDown` only moves the active option (arrows/Home/End/Enter/Escape) and
  never filters. A pasted query therefore takes the same
  `onChange → show(false) → setQuery → build()` route a typed one takes, and the string pasted
  is the same `"prop 499 field"`.
- **`delay: null`** removes user-event's per-event `wait()` — one `setTimeout` per keystroke even
  at the default `delay: 0` (`dist/esm/utils/misc/wait.js`, called from `keyboard/index.js` and
  `pointer/index.js`). That timer wait is wall-clock on a loaded machine and buys the test
  nothing.
- **All four assertions are untouched:** `toHaveLength(500)`,
  `toHaveTextContent("500 properties")`, `toEqual(["Prop_499_Field"])`,
  `toHaveTextContent("1 of 500 properties match")`.

**Component observation (reported, not changed, per the task):** `PropertyInput`'s `useMemo`
over `build()` (`PropertyInput.tsx:152-155`) re-runs `matchProperty` over all 500 suggestions on
every query change, and every matched row re-renders — there is no virtualisation and no cap.
The old query's first five keystrokes (`p`, `pr`, `pro`, `prop`, `prop `) still matched all 500
rows, so each test did five full 500-row re-renders plus nine smaller ones, about 23ms of
component work per keystroke. That is avoidable work (a virtualised list or a debounced query
would cut it); changing the component is out of scope here.

**Explicit, commented `15_000` timeout** — the task's third option, used because the cheaper
test alone was still not comfortably clear of the limit:

- with the paste + `delay: null` change in place, a full-suite run measured **3869ms of Vitest's
  5000ms default** (five more full runs on that version: 3042ms, 2091ms, 2030ms, 1761ms, 746ms);
- a deliberate load test (two further full suites running concurrently) still produced
  **`Error: Test timed out in 5000ms.` at 6898ms** on that version.

What remains (~180ms alone) is exactly what the assertions require: open the picker to 500
options, then query all 500 of them. It cannot be made cheaper without changing what the test
proves, so the budget for it is wall-clock only. The `15_000` is on this one test; the global
`testTimeout` is untouched.
