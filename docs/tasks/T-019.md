## The defect (found during T-016)

`Alert.severity` is declared `Mapped[Severity] = mapped_column(String(16))` in
`app/models/alert.py`, so a row **loaded from the database** carries a plain `str`, not a
`Severity`. `NotificationDispatcher._render` in `app/alerts/dispatcher.py` reads
`alert.severity.value`, and a `str` has no `.value`.

So whenever at least one route matches, enqueuing a notification for a DB-loaded alert raises
`AttributeError`. The production paths that do this are:
- Phase A recovery: `AnomalyEngine._resolve` in `app/anomaly/engine.py`. The alert was opened in
  an earlier run and is loaded by `resolve_by_fingerprint`.
- The operator API: `_enqueue_transition` in `app/api/routes/alerts.py`, for acknowledge and
  resolve.
- Possibly the scheduled-search alert paths. Check them.

The lab never showed it because no notification channel was configured. T-016 worked around it
locally, in `WafAnomalyEngine._apply_alert_actions`, with
`result.alert.severity = Severity(result.alert.severity)`.
