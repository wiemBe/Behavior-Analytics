   `Palo Alto PA Series`, `Check Point`, `Cisco Firepower Threat Defense`, `Juniper SRX`;
   kept `Linux iptables Firewall`, `Netgate pfSense`, `Cisco ASA`. Comment added above the rule in
   the module's own voice: *"Multi-role NGFW DSMs are intentionally absent: one DSM carries
   firewall, IPS and threat logs alike, so the site's naming convention must decide."* No other
   rule changed, none added.
2. **Unit matrix**: only the five pinned values changed (`SourceClass.FIREWALL` → `None`), plus
   five new named cases (`fgt-fw-01`→`FIREWALL`, `pa-ips-01`→`IPS`, `cp-fw-01`→`FIREWALL`,
   `fp-fw-01`→`FIREWALL`, `srx-ips-01`→`IPS`). Because the matrix rows now carry the source name,
   the test feeds `NAME_RULES` alongside `TYPE_NAME_RULES` (a type-only rule set cannot decide by
   name); the type-level pin is kept and made explicit per row — a neutral name must be claimed by
   exactly the pinned type rule, a class-token name by no type rule at all. The priority-tie
   assertion (`len(tied_classes) <= 1`) is unchanged. All other expectations are byte-identical;
   the full unit suite reports no other outcome change.
3. **Integration upgrade path**: the test writes the exact pre-release pattern into stored rule 3
   (same id, `built_in` row, `enabled` left as stored), calls `ensure_seed_rules`, and asserts the
   stored pattern equals `TYPE_NAME_RULES[2].pattern`, no longer contains `Palo Alto PA Series`,
   and `enabled is True` (still as stored — the upsert's `set_` does not write `enabled`). The
   following sync classifies the `Palo Alto PA Series` / `pa-ips-01` source as `IPS` on basis
   `NAME_REGEX`, which is only possible because the type rule no longer claims it.
